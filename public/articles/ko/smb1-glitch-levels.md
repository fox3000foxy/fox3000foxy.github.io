## 소개

Super Mario Bros.는 40킬로바이트 ROM이에요. 8개 월드와 32개 레벨, 적과 음악, 파워업, 전부 거기에 들어가요.

하지만 에뮬레이터를 열고 올바른 바이트를 만지작거리면 레벨 36-1을 불러올 수 있어요. 또는 255-1. 또는 모든 것이 Bowser 스프라이트와 nowhere로 가는 파이프로 된 월드에 떨어질 수 있어요.

이 글리치 월드들이 존재하는 것은 단순한 이유예요. SMB1 레벨 저장 시스템은 8비트 최적화의 경이이고, 게임이 건드리지 말아야 할 곳을 읽게 강제하면 매혹적인 결과가 나오거든요.

Retro Game Mechanics Explained가 4개 영상으로 다뤘어요. 그 시대를 가장 많이 판 게임의 6502 코드 속으로 한 번에 합치는 다이빙으로 엮을게요.

## 웜 스타트: 테니스 RAM이 SMB1에서 살아남는 이유

레벨 저장 이야기를 하기 전에 SMB1이 어떻게 시작하는지 이해해야 해요. NES 테니스 카트 교환 글리치가 전적으로 게임의 **웜 스타트와 콜드 스타트 감지 시스템**에 기대기 때문이에요.

### 지켜지는 41바이트

SMB1이 **콜드 스타트**(첫 전원 켜기 또는 전원 껐다 켜기)를 감지하면 RAM 전체를 지워요. **웜 스타트**(리셋 버튼, 전원 끊김 없음)를 감지하면 **41바이트** 메모리 구역을 지켜요.

```asm
; 웜 스타트 때 RAM에 지켜지는 41바이트
; 주소 $075F-$0787
;
; $075F : 시작 바이트 (world - 1)    [1바이트]
; $0760 : 월드 선택 플래그 (B 버튼) [1바이트]
; $0761-$0762 : 쓰지 않음                    [2바이트]
; $0763-$0768 : 타이머 (6자리, 3자리 표시) [6바이트]
; $0769-$076E : Luigi 코인                   [6바이트]
; $076F-$0774 : Mario 코인                   [6바이트]
; $0775-$077A : Luigi 점수                   [6바이트]
; $077B-$0780 : Mario 점수                   [6바이트]
; $0781-$0786 : 최고 점수 (6자리, 1자리 숨김) [6바이트]
; $0787 : 마법 바이트 $A5                 [1바이트]
```

이 41바이트는 기능 하나에 쓰여요. 게임 오버 뒤 **같은 월드에서 계속하기**를 허용하는 것. 6-3에서 죽으면 게임이 월드 6을 시작 바이트에 쓰고, 타이틀 화면에서 A + Start를 누르면 6-1부터 다시 시작해요.

### 웜 스타트 이중 검사

![콜드 스타트 대 웜 스타트: 리셋 감지 도식](/images/smb1-glitch-levels/v1-warm-start.jpg)

SMB1이 부팅할 때 기준 하나가 아니라 **둘**을 확인해요.

```asm
CheckWarmStart:
  ; 1. 마법 바이트 $A5를 $0787에서 확인
  lda $0787
  cmp #$A5
  bne ColdStart        ; $A5가 아니면 콜드 스타트

  ; 2. 최고 점수 6자리 ($0781-$0786) 확인
  ;    각 자리가 0과 9 사이여야 해요
  ldx #0
CheckLoop:
  lda $0781,x
  cmp #$0A
  bcs ColdStart        ; 자리 >= 10이면 콜드 스타트
  inx
  cpx #6
  bne CheckLoop

  ; 두 조건이 통과하면 웜 스타트
  ; RAM을 지우지 않고 시작 월드를 지켜요
  jmp WarmStartBoot
```

![ $A5 바이트와 최고 점수 자리 검사: 웜 스타트의 심장](/images/smb1-glitch-levels/v1-a5-byte.jpg)

왜 이중 검사냐고요? $A5 바이트가 우연히 있을 수 있어서예요 (이 값을 남기는 다른 게임, 또는 RAM 칩 기본 휴지 상태). 최고 점수 자리가 유효한지(0-9) 확인해서 자료 일관성을 보장해요.

### 테니스가 유일하게 통하는 게임인 이유

SMB1을 처음 넣으면 (콜드 스타트) 게임이요.

1. RAM 전체를 지워요 → 최고 점수 = 0, 월드 바이트 = 0
2. $A5를 주소 $0787에 써요

다음에 콘솔을 끄지 않고 테니스로 바꿔요. 테니스는요.

- 시작할 때 RAM을 청소하지 않아요 (그렇게 하는 NES 게임이 적어요)
- 최고 점수 바이트에 쓰지 않아요 → 0으로 남아요 (유효)
- $A5 바이트를 건드리지 않아요 → 그대로 있어요
- 플레이어 발걸음 카운터에 주소 $075F를 써요

```asm
; 테니스 발걸음 증가:
; 코트에서 걸을 때마다 테니스가 $075F 바이트를 증가시켜요.
; 이 바이트는 SMB1의 "world number - 1"로 쓰는 것과 같아요.
;
; 0걸음  → 월드 0 → SMB1 = 월드 1
; 1-7걸음 → 월드 1-7 → 정상 월드
; 8+걸음 → 월드 8+ → 글리치 월드!
;
; 카운터는 음악이 멈출 때만 증가해요
; (음악 중에는 발걸음 소리가 나지 않아요).
```

SMB1을 도로 넣으면요.

1. $A5 바이트가 여전히 있어요 (테니스가 건드리지 않았어요)
2. 최고 점수 자리가 여전히 0이에요 (유효)
3. 월드 바이트가 이제 8 이상이에요 (테니스 발걸음으로 증가)
4. SMB1이 웜 스타트를 감지해요 → 망가진 월드 바이트를 지켜요
5. A + Start 유지 → 월드 9-1, 월드 A-1, 월드 36-1 등.

### Mario를 테니스 전에 부팅해야 하는 이유

미묘한 점: 먼저 SMB1을 부팅한 뒤 테니스, 다음 다시 SMB1 순서여야 해요. 테니스로 바로 시작하면 $A5 바이트가 절대 쓰이지 않아요 (테니스는 $A5를 쓰지 않아요). 웜 스타트 감지가 실패하고 RAM이 지워져요.

## SMB1이 레벨을 40KB에 저장하는 방법

Nintendo R&D4는 겉보기에 단순한 문제를 풀어야 했어요. 가로로 스크롤되는 레벨을 타일과 적, 아이템과 함께 빡빡한 ROM 예산에 나타내기.

해법은 **완전히 독립적인** 두 자료 층 분리예요.

### 타일 배치 (레벨 지도)

각 레벨은 ROM 속 압축 타일 구조를 가리키는 포인터로 정해져요. 압축은 기초적이지만 genial해요. 제어 바이트 하나 다음 자료 1~3바이트.

타일 형식은 **런**(RLE 방식) 시스템을 써요.

```asm
; SMB1 타일 형식 (단순화)
; 각 "명령"은 제어 바이트예요
;
; $00-$7F : 타일 하나 놓고 1열 전진
; $80-$BF : 타일을 N번 반복 (N = 바이트 - $80 + 1)
; $C0-$FF : 특수 명령 (줄 끝, 점프, 팔레트 바꾸기)

예시: 벽돌 3개를 그리려면:
  $82 $01    ; 타일 $01 (벽돌)을 3번 반복
```

각 레벨은 16열짜리 줄 13개(13×16 = 208개 보이는 타일)를 담아요. 하지만 압축 형식 덕분에 훨씬 낮게 내려갈 수 있어요. 예를 들어 하늘과 빈 열은 거의 자리를 차지하지 않아요.

6502 렌더 루프:

```asm
; 타일 압축 해제 - 주 루프
; 입력: $XX의 tile_data 포인터
; 출력: PPU RAM의 레벨 타일맵

DecompressTile:
  lda (tile_ptr),y      ; 제어 바이트 읽기
  iny
  cmp #$80
  bcc SingleTile        ; $00-$7F : 단일 타일
  cmp #$C0
  bcc RunLength         ; $80-$BF : 런렝스
  jmp SpecialCommand    ; $C0-$FF : 특수 명령

SingleTile:
  sta PPU_DATA          ; 타일을 바로 쓰기
  jmp Next

RunLength:
  sec
  sbc #$7E              ; N = control - $7E
  tax
  lda (tile_ptr),y      ; 반복할 타일 읽기
  iny
: sta PPU_DATA
  dex
  bne :-
  jmp Next
```

### 스프라이트 배치 (적과 물건)

나란히 적과 물건(물음표 블록, 파이프, 굼바, 엉금엉금)은 완전히 분리된 구조에 저장돼요. 각 스폰은 2바이트로 정해져요.

```asm
; SMB1 스프라이트 형식
; 바이트 0: X 위치 (열 단위)
; 바이트 1: 스프라이트 종류 + Y 페이지 비트
; Y는 연속 속 인덱스에서 유도돼요

스프라이트 연속 예시:
  $01 $4B    ; 1열에 굼바
  $09 $4B    ; 9열에 굼바
  $10 $61    ; 16열에 물음표 블록 (코인 들어 있어요)
  $15 $54    ; 21열에 초록 엉금엉금
  $FF        ; 연속 끝
```

각 레벨은 서로 다른 스프라이트 페이지 최대 5개(사실상 16열 "화면" 5개)를 참조할 수 있지만, 실제로 대부분 레벨은 2~3개만 써요.

### 포인터 표

설계의 천재성은 포인터 표예요. 각 레벨은 ROM 주소 **쌍**으로 저장돼요.

```c
// 월드맵 내부 구조 (단순화)
struct LevelPointer {
    uint16_t tile_ptr;   // 타일 자료 ROM 주소
    uint16_t sprite_ptr; // 스프라이트 자료 ROM 주소
};

// AreaType별 4개 분리 표:
// 0 = Water, 1 = Overworld, 2 = Underground, 3 = Castle
LevelPointer level_table[4][128];
```

표당 128개 항목. 구역 종류 4개. **512개 가능 조합**이지만, 공식 게임이 쓰는 것은 일부뿐이에요. 나머지는 초기화되지 않은 RAM이거나 포인터로 해석되는 자료예요.

게임이 레벨을 불러올 때 이렇게 해요.

```asm
; 레벨 불러오기
; A = AreaType (0-3), X = LevelID (0-127)

LoadLevel:
  sta AREA_TYPE
  asl                  ; 16비트 표 오프셋으로 *2
  tax
  lda LevelTable_TilePtr, x
  sta TILE_PTR
  lda LevelTable_TilePtr+1, x
  sta TILE_PTR+1       ; 타일 포인터
  lda LevelTable_SpritePtr, x
  sta SPRITE_PTR
  lda LevelTable_SpritePtr+1, x
  sta SPRITE_PTR+1     ; 스프라이트 포인터
  jsr DecompressTiles
```

게임은 포인터를 완전히 신뢰해요. 표에서 주소를 읽고 그 주소에 있는 것을 압축 해제해요. 끝.

### 34개 고유 레벨과 7비트 ID 시스템

![NES RAM 칩 (MB8416A): 카트리지를 바꿔도 자료를 지키는 것이 바로 이거예요](/images/smb1-glitch-levels/v1-ram-chip.jpg)

SMB1에는 32개 레벨이 아니라 **34개 고유 레벨**이 있어요. 많은 레벨이 중복(5-3 = 1-3이지만 총알과 함께)이고 "하드 모드" 깃발로 표시돼요. 진짜 고유 레벨:

- **물** (종류 0): 3개 레벨 (2-2, 7-2, 5-2와 6-2 보너스 구역)
- **오버월드** (종류 1): 22개 레벨 (2개 구름 보너스 방 포함)
- **지하** (종류 2): 3개 레벨 (지하 보너스 방 포함)
- **성** (종류 3): 6개 레벨
- 컷신 방 1개 (지하와 물 레벨 앞)
- 4-2 워프존 1개

각 레벨은 **7비트** ID가 있어요. 하위 5비트는 하위 그룹 번호, 상위 2비트는 구역 종류.

```asm
; 레벨 ID 7비트 인코딩
; 비트 6-5: 종류 (00=Water, 01=Overworld, 10=Underground, 11=Castle)
; 비트 4-0: 하위 그룹 번호
;
; Water ID      : $00-$02  (종류 00, 번호 0-2)
; Overworld ID  : $20-$35  (종류 01, 번호 0-21)
; Underground ID: $40-$42  (종류 10, 번호 0-2)
; Castle ID     : $60-$65  (종류 11, 번호 0-5)
;
; ID $25 = %0100101 → 종류 01 (Overworld), 번호 5 → 1-1
; ID $23 = %0100011 → 종류 01 (Overworld), 번호 3 → 6-2
```

**128개 가능 ID**($00-$7F)에 진짜 레벨이 할당된 것은 34개뿐이에요. 쓰지 않는 ID는 어디든 가리켜요.

### 포인터 표: 두 목록, 두 순서

타일과 스프라이트 포인터는 같은 순서로 저장되지 않아요. 코드는 두 개의 분리 16비트 목록(상위 바이트와 하위 바이트가 두 분리 표)을 써요.

```
스프라이트 포인터 순서:
  인덱스 0-5   : Castle (6개 레벨)
  인덱스 6-27  : Overworld (22개 레벨)
  인덱스 28-30 : Underground (3개 레벨)
  인덱스 31-33 : Water (3개 레벨)

타일 포인터 순서:
  인덱스 0-2   : Water (3개 레벨)
  인덱스 3-24  : Overworld (22개 레벨)
  인덱스 25-27 : Underground (3개 레벨)
  인덱스 28-33 : Castle (6개 레벨)
```

왜 순서가 다를까요? 기술적 이유 없어요. 개발 중에 자료가 그렇게 정리됐을 가능성이 커요. 하지만 매혹적인 결과가 있어요. 레벨 ID가 유효하지 않으면 타일과 스프라이트 포인터가 서로 *다른* 레벨을 불러와서 **프랑켄슈타인 레벨**을 만들어요.

두 목록 사이를 오가려고 게임은 작은 **오프셋 표**(목차처럼)를 써요.

```asm
; 종류별 오프셋 표 (Water, Overworld, Underground, Castle)
; 각 항목 = 해당 목록 시작 인덱스

SpriteOffsetTable:
  .byte $1F, $06, $1C, $00    ; Water=31, Overworld=6, Underground=28, Castle=0

TileOffsetTable:
  .byte $00, $03, $19, $1C    ; Water=0, Overworld=3, Underground=25, Castle=28
```

레벨 6-2(ID $23, Overworld 번호 3)를 불러오려면요.

```asm
; 1. 종류 = 01 (Overworld) → 오프셋 표 인덱스 = 1
; 2. 스프라이트 오프셋 = SpriteOffsetTable[1] = 6
;    최종 인덱스 = 6 + 3 (레벨 번호) = 9 → 10번째 스프라이트 포인터
; 3. 타일 오프셋 = TileOffsetTable[1] = 3
;    최종 인덱스 = 3 + 3 = 6 → 7번째 타일 포인터
; 4. 결과: 타일 포인터 $A619 + 스프라이트 포인터 $9ED0 = 6-2 ✓
```

그럼 $43(존재하지 않는 Underground 번호 3) 같은 유효하지 않은 ID는 어떻게 될까요?

```asm
; ID $43, 종류 = 10 (Underground), 번호 = 3
; 스프라이트 오프셋 = SpriteOffsetTable[2] = $1C = 28
;   인덱스 = 28 + 3 = 31 → 32번째 스프라이트 포인터 = 5-2 물 보너스!
; 타일 오프셋 = TileOffsetTable[2] = $19 = 25
;   인덱스 = 25 + 3 = 28 → 29번째 타일 포인터 = 1-4 (Castle)!
;
; 결과: 1-4 타일에 5-2 물 구역 Blooper가 있는 지하 레벨
; 진짜 프랑켄슈타인.
```

### 월드 인덱스 표: 월드 9가 오버플로우하는 이유

각 월드(1-8)의 첫 레벨 인덱스를 주는 8바이트 ROM 표가 있어요. 바로 뒤에 게임 순서 36개 레벨 ID 표가 있어요.

```asm
; WorldIndexTable (8바이트)
  .byte 0, 5, 10, 15, 20, 25, 28, 33
;   -> 월드 1은 레벨 0에서 시작
;   -> 월드 2는 레벨 5에서 시작
;   -> 월드 8은 레벨 33에서 시작

; LevelIDTable (36바이트)
  .byte $25, $28, $29, $26, $24, ... ; 36개 레벨 ID
```

월드 9를 불러오려고 하면 게임이 존재하지 않는 WorldIndexTable 9번째 바이트를 읽어요. LevelIDTable로 1바이트 오버플로우해서 값 $25를 읽고, $25를 LevelIDTable 인덱스로 쓰고 (37번째 항목). 다시 2바이트 오버플로우해서 SpriteOffsetTable을 읽고 값 6을 읽어요.

```asm
; 월드 9:
;   1. WorldIndexTable[8] (오버플로우) → LevelIDTable의 $25 읽기
;   2. LevelIDTable[37] (오버플로우) → SpriteOffsetTable 2번째 바이트 = 6 읽기
;   3. ID = 6 → 존재하지 않는 Water 레벨 번호 6
;   4. 타일 포인터 = water 포인터 번호 6 = 6-2 타일
;   5. 스프라이트 포인터 = 인덱스 31+6 = 37 > 33 → 유효하지 않은 포인터
;   6. 결과: 글리치된 스프라이트가 있는 물속 6-2
;      → 월드 9-1!
```

월드 G(16)는 오버플로우가 더 멀리 가서 1-2 앞 컷신 레벨인 레벨 ID $01에 떨어져요.

```asm
; 월드 G (16):
;   WorldIndexTable[15] → LevelIDTable의 $01 읽기
;   LevelIDTable[1] = $29 (1-2 컷신)
;   → 월드 G-1 = 1-2 진입 컷신
```

## 글리치 월드가 존재하는 이유

게임에는 "정품" 레벨 32개(8월드 × 4레벨)가 있어요. 하지만 포인터 표가 구역 종류별 128개 항목으로 되어 있어요. 레벨 32 너머 항목에는 ROM 그 주소에 있는 것이 들어 있어요. 가끔 다른 레벨, 가끔 소리 자료, 가끔 RAM, 가끔 아무거나.

![레벨 ID $01 물 (Minus World): 타일 포인터 $AE45, 스프라이트 포인터 $A171](/images/smb1-glitch-levels/minus-world.png)

### 레벨 ID $01 + AreaType 0 = Minus World

가장 유명한 글리치 월드. AreaType 0(물)의 레벨 ID $01이 가리키는 것은요.

- **타일 포인터: $AE45** → 2-2와 7-2 수중 구역
- **스프라이트 포인터: $A171** → 2-2와 7-2 스프라이트

결과: 2-2처럼 보이는 물 레벨이지만, 깃대봉이 없어서 무한히 돌아요. 레벨이 영원히 돌아요.

레벨 36-1이에요 (또는 $-1 월드의 36-1).

![SMB1 웜 스타트 검사: Minus World가 존재하게 하는 것이 바로 이거예요](/images/smb1-glitch-levels/v4-minus-world.jpg)

```asm
; Minus World에 깃대봉이 없는 이유:
; 2-2와 7-2 스프라이트 ($A171)에 순서에 깃대봉이 없어요
; 게임이 스프라이트 $FD (깃대봉)를 찾지만 절대 찾지 못해요 → 무한 루프
;
; 게임이 타이머가 0이 될 때까지 레벨을 무한히 만들어내요
```

### RAM을 가리키는 포인터들

타일 포인터나 스프라이트 포인터가 ROM이 아니라 RAM 주소($00-$7F)를 가리키면, 게임이 계속 바뀌는 RAM을 타일처럼 해석하려고 해요.

```asm
; 예시: 물의 레벨 ID $03
; 타일 포인터: $A46B (3-3 - 유효)
; 스프라이트 포인터: $009D (제로 페이지 RAM을 가리켜요!)
;
; 제로 페이지 RAM에는 게임 레지스터와
; Mario 위치, 카운터 상태가 들어 있어요...
; 게임이 이를 스프라이트 연속으로 압축 해제하고,
; 결과는 레지스터 값인 적들이 있는 레벨이에요.
```

제로 페이지가 바뀌면 (Mario가 움직이고, 타이머가 돌고 등) 레벨 "스프라이트"도 바뀌어요. 그래서 일부 글리치 월드의 적이 깜빡이고 계속 변하는 거예요.

![물의 레벨 ID $03: 스프라이트 포인터 $009D가 RAM을 가리켜요. 못 하는 레벨](/images/smb1-glitch-levels/level-03-water.png)

### 레벨 ID $36: 빈 레벨 (오버월드)

오버월드의 레벨 ID $36:

- **타일 포인터: $AC35** (1-2)
- **스프라이트 포인터: $A0D8** (1-2)

결과: 없음. 게임이 레벨을 불러오지만 RGMechEx 카탈로그에 "레벨 없음"으로 표시돼요. 타일은 유효할지 몰라도 스프라이트가 비었거나 동작하지 않는 레벨을 만드는 곳을 가리켜요.

### 레벨 ID $1D (성): 충돌 챔피언

성의 레벨 ID $1D:

- **타일 포인터: $A210** (4-4)
- **스프라이트 포인터: $7EA0** (RAM!)

RAM 속 스프라이트 포인터 = 정의되지 않은 스프라이트. 게임이 타일 첫 줄에 Spiny 공이나 총알 발사대를 표시하려고 해요. 바로 죽어요.

```asm
; 스프라이트 포인터가 RAM을 가리키면,
; 게임이 계속 바뀌는 바이트를
; "스폰" 지시처럼 압축 해제해요. 결과:
; - 존재하지 않는 물건 나타나기 (정의되지 않은 값)
; - NES 스프라이트가 유효하지 않은 타일을 표시하려고 할 때 PPU 충돌
; - 콘솔 완전 멈춤
```

## 레벨 형식 자세히

레벨 자료의 정확한 형식으로 들어가서 글리치 레벨이 왜 버티는지(또는 아닌지) 이해해요.

### 레벨 헤더: 2바이트, 속성 6개

각 레벨은 6개 속성을 조종하는 2바이트 헤더로 시작해요.

```asm
; 바이트 0: 타이머 + Y 시작 + 수식어
;   비트 7-6: 타이머 (00=그대로, 01=200, 10=300, 11=400)
;   비트 5-3: Mario Y 시작 (111/110 = 자동 걷기)
;   비트 2-0: 레벨 종류 수식어
;              000=기본, 001=파도, 010=벽돌 벽,
;              011=물 바닥, 100=밤, 101=눈,
;              110=눈 밤, 111=회색 밤

; 바이트 1: 플랫폼 + 배경 + 바닥 패턴
;   비트 7-6: 특수 플랫폼 (00=나무, 01=버섯,
;                                 10=총알, 11=구름)
;   비트 5-4: 배경 (00=없음, 01=구름,
;                           10=산, 11=울타리)
;   비트 3-0: 처음 바닥 패턴 (0-15)
```

종류 수식어가 시각 변형을 조종해요. 물 레벨 위 파도, 8-3 벽돌 배경, 4-3 밤 팔레트, 6-2 눈 등.

### 타일 물건: 2바이트, 다음 화면 깃발, 3슬롯 큐

헤더 다음에 **타일 물건** 목록이 와요. 물건마다 2바이트. 바이트 $FD가 목록 끝을 표시해요.

```asm
; 타일 물건 형식 (16비트):
; 바이트 0:
;   비트 7-4: X 위치 (열 0-15)
;   비트 3-0: Y 위치
;     Y=0-11  : 보통 Y 위치
;     Y=12    : 특수 물건 (구멍, 다리, 밧줄, 물음표 블록)
;     Y=13    : 화면 건너뛰기와 특수 물건 2
;     Y=14    : 수식어와 풍경, 바닥 바꾸기
;     Y=15    : 특수 물건 3 (성, 계단, 큰 파이프)

; 바이트 1:
;   비트  7   : 다음 화면 깃발
;   비트 6-4 : 물건 종류 (0-7)
;   비트 3-0 : 너비와 높이 / 하위 종류
```

"다음 화면" 비트가 서면 현재 작업 열이 1 증가해요. 처음 16열 너머에 물건을 둘 수 있어요. 물건은 **순서대로** (왼쪽에서 오른쪽) 나열되어야 해요. 게임이 순서대로 불러오니까요.

```asm
; 불러오기 루틴은 열마다 두 단계를 거쳐요
; 단계 1: 이 열에서 시작하는 새 물건을 찾아서
;            대기열에 넣기
; 단계 2: 대기열의 각 물건을 타일을 그리며 처리하고,
;            이 열에서 끝나는 것들은 빼기
```

큐는 정확히 **3개 슬롯**이에요. 직접 결과: 같은 열에서 시작하는 물건이 3개를 넘을 수 없어요. 큐가 차면 4번째 물건은 무시되고 절대 불러와지지 않아요.

그래서 잘 만든 레벨은 물건을 너무 쌓지 않아요. 1-2 예시: 천장의 1up 블록과 옆 벽돌이 든 열은 3개 한도를 지키려고 두 개 분리 물건으로 나눠요.

### 특수 Y 위치: 12, 13, 14, 15

Y=12면 물건에 Y 위치가 없어요 (종류별로 하드코딩돼요).

```asm
; Y=12: Y 위치 없는 물건
;   종류 0: 구멍 (바닥 지우기)
;   종류 1: 움직이는 플랫폼 밧줄
;   종류 2-4: Y 고정 다리
;   종류 5: 물과 용암이 있는 구멍
;   종류 6-7: 물음표 블록 줄
```

Y=13이면 하위 그룹 둘. 바이트 1의 비트 6이 1이면요.

```asm
; Y=13, 비트6=1: 특수 물건
;   0 = L 파이프 (컷신), 1 = 깃대봉, 2-3 = 다리와 도끼, 망치 (성 끝)
;   4 = 화면 멈춤, 5 = 무작위 적, 6 = 레벨 반복, 7+ = 죽을 수 있어요
```

비트6=0이면 하위 5비트가 **화면 건너뛰기**(다음 화면 깃발을 하나씩 통하지 않고 화면 N으로 바로 점프)를 인코딩해요.

Y=14면요. 종류 바꾸기는 비트6=1, 배경 + 바닥 패턴 바꾸기는 비트6=0으로 같은 원리예요.

### 바닥 패턴: 16개 바닥 무늬

레벨 바닥은 개별 물건으로 만들지 않아요. SMB1은 다음 바뀔 때까지 모든 열에 적용되는 배경 무늬 **바닥 패턴**을 써요.

```asm
; 바닥 패턴 (4비트 = 16가지)
;   0 = 완전 빔
;   1 = 2타일 높이 바닥
;   2 = 1타일 높이 바닥
;   3 = 바닥 + 아래
;   4 = 바닥 + 아래 2
;   5 = 바닥 1/2타일
;   6 = 3/4 바닥
;   ... 15까지 = 완전 채움 (바닥 + 천장)
```

그래서 구멍이 물건인 거예요. 나머지를 위해 패턴을 바꾸지 않고 특정 열에 바닥 패턴을 덮어써요.

### 256바이트 한도와 반복

레벨 타일 자료 전체가 **최대 256바이트**에 들어가요. 6502 Y 레지스터를 인덱스로 쓰고 8비트예요. 게임이 바이트 $FD를 찾지 못하고 자료 끝에 이르면 **처음으로 돌아가서** 256바이트를 무한히 반복해요.

```asm
; Y 인덱스 = 8비트 → 타일 자료 최대 256바이트
; Y 오버플로우 (255 → 0)인데 $FD 없음 → 반복
; 스프라이트도 마찬가지지만 파이프 물건 (3바이트)이
; 불러올 때마다 인덱스 홀짝을 바꿔요.
```

일부 글리치 레벨은 이 반복을 악용해서 "무한히" 이어지는 레벨을 만들어요.

### 스프라이트 시스템: 2바이트 + 파이프 전이

스프라이트는 비슷한 형식을 따르지만 헤더가 없고 몇 가지 핵심 차이가 있어요. 바이트 $FF가 목록 끝을 표시해요.

```asm
; 스프라이트 형식 (2바이트):
; 바이트 0: X 위치 (열)
; 바이트 1:
;   비트 7: 다음 화면 깃발
;   비트 6-0: 스프라이트 종류
;       일부 종류: 굼바, 엉금엉금, Blooper,
;       총알, Lakitu, Spiny, 플랫폼,
;       워프존 명령, 두꺼비와 공주,
;       적 무리 스폰 명령
```

바이트 1 최하위 비트는 **하드 레벨 깃발**이에요. 1이면 스프라이트가 레벨 5-3 이상에만 나타나고. "하드 모드" 레벨이 만들어지는 방법이 바로 이거예요.

Y 위치 15 = **화면 건너뛰기** (타일과 같아요). Y 위치 14 = **파이프 전이** (3바이트):

```asm
; 스프라이트 Y=14: 파이프와 덩굴 전이 (3바이트!)
;   바이트 0: X 위치
;   바이트 1: 비트 6-0 = 목적 레벨 ID 7비트
;   바이트 2: 비트 4-0 = 목적 화면
;            비트 7-5 = 이 전이가 유효한 월드
;
; 왜 월드냐고요? 보너스 방은 월드 사이 재사용돼요.
; 예시: 1-1 보너스 방은 2-1과 7-1도 써요.
; 이 방에 전이가 3개, 월드별 하나씩 있어서 Mario가
; 올바른 곳에 다시 나타나게 해요.
```

스프라이트에는 **큐 시스템이 없어요**. 유일한 한도는 스폰 구역(바로 화면 오른쪽 밖)에 동시에 불러올 수 있는 스프라이트가 4개를 넘을 수 없다는 것. 그 너머는 무시돼요.

## 글리치 월드에 닿는 방법

주된 방법 둘.

### 고전 방법: 벽 뚫기

벽 뚫기(벽 통과)가 정상 레벨 밖으로 나가서 숨은 워프존까지 걷게 해요. RAM 속 월드 카운터를 조작해서 어떤 레벨 ID든 불러올 수 있어요.

기법:

1. 월드 1-2: 숨은 끝 파이프로 가기
2. 오른쪽 벽에 벽 뚫기
3. 빈 곳을 걸어서 워프 구역까지
4. 게임이 값을 월드로 해석해요

하지만 이 방법으로는 글리치 월드의 작은 부분에만 닿을 수 있어요.

### 극단 방법: NES 테니스 카트 교환

자세한 것은 위 "웜 스타트" 섹션을 보세요. 요약: 테니스 발걸음 카운터가 SMB1 시작 월드와 같은 RAM 바이트에 쓰고, 웜 스타트 감지가 이 값을 지켜요.

### 만지작러 구역: 모두 탐험하는 코드

에뮬레이터에서 직접 모든 글리치를 탐험하고 싶으면 레벨 ID에 바로 패치할 수 있어요.

```asm
; FCEUX와 Mesen용 패치:
; RAM 주소 $075F = 현재 레벨 ID
; RAM 주소 $0760 = 구역 종류 (0=Water, 1=Overworld, 2=Underground, 3=Castle)

; 예시: 오버월드로 레벨 57 (0x39) 불러오기
; 에뮬레이터에서 메모리 추적기를 열고 쓰기:
; $075F = 0x39
; $0760 = 0x01
; 다음 워프 파이프에 들어가거나 죽고 다시 시작
; → 게임이 오버월드로 레벨 ID $39를 불러와요
```

RGMechEx가 타일 포인터와 스프라이트 포인터, 레벨 시각 지도가 있는 128개 레벨 × 4종 전체 목록을 [rgmechex.com](https://rgmechex.com/tech/smb1levels/index.html)에 올렸어요.

## 가장 wtf한 레벨들

### 레벨 ID $1F (물): 하나로 15개 글리치 월드

타일 포인터 $A302 (3-4)와 스프라이트 포인터 $02A0 조합이 서로 다른 글리치 월드 15개(D-1, J-1, Y-1, Z-1, 55-1, 73-1...)를 줘요. 설명: 스프라이트 포인터가 할 수 있는 스프라이트에 충분히 가까운 자료 구역을 가리켜서 할 수 있는 결과를 만들지만, 3-4 성 타일과 오버월드 스프라이트 조합이 터무니없는 렌더를 만들어요.

### 레벨 ID $28 (오버월드): 38개 글리치 월드 = 기록

절대 기록. 글리치 월드 항목 38개가 같은 레벨(2-1 타일 + $9F51 스프라이트)을 가리켜요. 왜요? 스프라이트 포인터 $9F51이 많은 ID가 재사용하는 패딩과 소리 자료 구역에 떨어져서예요.

### 레벨 ID $49 (지하): FDS 레벨

타일 포인터 $76AE + 스프라이트 포인터 $1C9D. 타일 포인터가 Famicom Disk System 버전용으로 예약된 ROM 구역을 가리켜요. 결과: 표준 카트리지에는 없는 타일이 있는 레벨. 레벨 52-1과 196-1이 나타나는 레벨이에요.

### 레벨 ID $00-$02: 진짜 보너스 레벨

이 ID들은 게임 정품 하위 레벨이 써요.

- **$00**: 5-2와 6-2 수중 구역 (H-1, 39-1이 써요)
- **$01**: 2-2와 7-2 물 (Minus World, 36-1)
- **$02**: 8-4 하위 레벨 (136-1, 151-1, 215-1이 써요)

보너스로 정상 닿는 레벨과 글리치 월드의 차이는 워프존이 현재 월드를 확인한다는 거예요.

```asm
; 워프존 검사 (단순화)
; 게임이 목표 월드가 1과 8 사이인지 확인해요
CheckWarp:
  lda TARGET_WORLD
  cmp #1
  bcc InvalidWarp       ; < 1 → 거부
  cmp #9
  bcs InvalidWarp       ; > 8 → 거부
  ; 1과 8 사이 유효 월드만
  jmp DoWarp
```

번호가 8보다 크거나 0인 글리치 월드에는 보통 파이프로 닿을 수 없어요. 벽 뚫기나 카트 교환이 필요해요.

## 일부 레벨이 죽는 이유: 점프 표

게임이 타일 물건을 불러올 때 종류를 **점프 표** 인덱스로 써요.

```asm
; 표준 타일 물건 점프 표 (종류 0-11)
JumpTable_TileObjects:
  .word Obj_Special       ; 종류 0: 물음표 블록, 숨김, 깃대봉...
  .word Obj_Platform      ; 종류 1: 특수 플랫폼
  .word Obj_BrickRow      ; 종류 2: 벽돌 줄
  .word Obj_BlockRow      ; 종류 3: 블록 줄
  .word Obj_CoinRow       ; 종류 4: 코인 줄
  .word Obj_BrickCol      ; 종류 5: 벽돌 열
  .word Obj_BlockCol      ; 종류 6: 블록 열
  .word Obj_Pipe          ; 종류 7: 파이프
  .word Obj_8             ; 종류 8
  .word Obj_9             ; 종류 9
  .word Obj_10            ; 종류 10
  .word Obj_11            ; 종류 11
```

![점프 표: 유효하지 않은 물건 종류가 게임을 죽이는 이유](/images/smb1-glitch-levels/v4-jump-table.jpg)

물건 종류가 유효하지 않으면 (12 이상) 게임이 이 표에 없는 포인터로 점프해요. **가능한 결과 4가지**:

1. **유효 포인터** → 물건이 정상 불러와져요
2. **다른 점프 표를 가리키는 포인터** (겹침) → 다른 물건이 나타나요. 예시: 종류 12가 Y=13 표를 가리켜서 L 파이프가 돼요.
3. **실행 파일을 가리키는 포인터** → 무작위 코드 실행 (죽을 가능성)
4. **명시 플레이스홀더 (NOP)** → 물건이 아무것도 안 해요 (일부 스프라이트가 이렇게 움직이지 않고 날아다니는 적을 만들어요)

![글리치 레벨 ID $58: 스프라이트 포인터가 유효하지 않은 주소를 가리켜요. 게임이 죽어요](/images/smb1-glitch-levels/v4-glitch-58-crash.jpg)

![글리치 레벨 ID $50: 망가진 자료가 만든 구름 터널](/images/smb1-glitch-levels/v4-glitch-50.jpg)

글리치 레벨 ID $58 (죽는 터널). 스프라이트 포인터가 매퍼 ROM 없는 NES에 **존재하지 않는** 메모리 영역을 가리켜요. 게임이 같은 Koopa를 프레임마다 5번 위치 (0,0)에 불러오려고 해서 PPU가 포화되고 멈춰요.

```asm
; ID $58이 죽는 이유:
; 스프라이트 포인터 → 유효하지 않은 주소 (표준 NES 공간 밖)
; → 게임이 불확정 바이트를 스프라이트 종류처럼 읽어요
; → 핸들러 없는 Koopa $00 (유효하지 않은 종류)이 재귀 호출에 빠져요
; → 6502 스택 오버플로우 → 멈춤
```

### 파이프 워프 역설

`target_world BETWEEN 1 AND 8` 검사를 기억하세요. 글리치 월드에서 파이프를 찾아도 게임이 목적 월드가 1과 8 사이인지 확인해요. 글리치 월드 번호는 8보다 커요 (36-1, 255-1...). 워프가 실패해요.

Minus World에 끝이 없는 이유도 바로 이거예요. 스프라이트에 깃대봉이 없고, 파이프가 nowhere로 이어져요.

### 한 열에 물건 5개 트릭

한 열 3개 물건 한도를 넘는 엣지 경우가 있어요. 큐가 막히면 (슬롯 참 + 다음 화면 깃발 없는 다음 물건) 게임이 다음 화면 깃발이 있는 물건을 찾을 때까지 현재 열을 루프로 "미리 처리"해요. 각 미리 처리 동안요.

```asm
; 열 미리 처리 동안:
; 1. 대기열 물건들은 남은 너비가
;    열 "가짜 전진"마다 줄어들어요
; 2. 물건 너비가 0이 되면 대기열을 나가요
; 3. 풀린 슬롯을 새 물건이 채울 수 있어요
;    같은 열에 추가돼요

; 결과: 같은 열에 최대 5개 물건을 처리할 수 있어요.
; 기법: 화면 경계를 가로지르는 물건 2개를 두기
; (슬롯 1과 2), 이전 X에 더미 물건 1개 (대기열 막아요),
; 다음 화면 X=0에 물건 3개 (다음 화면 깃발 있는 것 포함).
```

이른바 "queue skip"이라고 하고, 일부 롬해커가 형식이 보통 허용하는 것보다 빽빽한 레벨을 만들려고 써요.

## 버전 사이 차이

### Famicom Disk System

SMB1 FDS 버전은 **메모리 맵이 달라요**. 모든 레벨 포인터가 이동하지만 자료는 같아요. 바뀌는 것: 글리치 월드 인덱스가 완전히 달라요.

```
FDS 월드 36 → 레벨 ID $09 (5-3의 물 버전)
  → 깃대봉이 있어요! 레벨을 마칠 수 있어요.
  → 다음: $27 (정상 7-3) → $44 (4-4 지하)
  → $44을 마칠 수 있어요 → 도끼가 동작해요 → 게임 끝!

그래서 FDS Minus World는 게임 완료로 이어질 수 있는
"보너스 월드"예요. NES 버전과 달라요.
```

제가 제일 좋아하는 FDS 레벨: **ID $5F**, 낮은 터널 속 3-3 후반 지하 버전 (자동 스크롤이라 아쉬워요).

### The Lost Levels (일본 Super Mario Bros. 2)

Lost Levels가 많은 것을 바꿔요.

1. **타일과 스프라이트 순서 같음**: 프랑켄슈타인 레벨 없어요 (유효하지 않은 ID에도 타일과 스프라이트가 같은 레벨을 불러와요)
2. 분리 상위와 하위 표 둘 대신 **단일 16비트 포인터 표 하나**
3. **디스크 파일 4개**: ROM이 FDS용으로 쪼개졌어요.
   - 파일 1: 월드 1-4
   - 파일 2: 월드 5-8
   - 파일 3: 월드 9 + 사운드 엔진
   - 파일 4: 월드 A-D (완전히 다른 포인터 표)
4. **같은 레벨 ID = 4개 가능 레벨**, 불러온 파일에 따라
5. **글리치 테니스 없어요**: 이어하기 옵션(게임 오버 뒤 같은 월드에서 계속)이 웜 스타트를 쓸모없게 하고, 게임이 월드 > 9이면 **바로 리셋**해요
6. **새 물건**: 독버섯, 투명 블록, 투명 블록 불꽃, 거꾸로 파이프, 바람. 하지만 기존 목록 중간에 끼워서 **SMB1 하위 호환 안 돼요**
7. 월드 4 뒤에는 **피라냐 식물이 항상 빨강**, **초록 스프링보드**는 월드 2와 B, 3, C, 7에만

### Super Mario All-Stars (SNES)

같은 6502 루틴 직접 이식 (SNES가 호환 모드로 NES 코드를 실행해요).

- **워프존 수정**: Minus World 없어요 (텍스트 전에 왼쪽 파이프에 들어가면 올바른 월드로 가요)
- **죽음**: 대부분 글리치 레벨이 죽어요 (ID $6A와 9-1 제외)
- **추가 성 물건**: 더 고유하게 렌더돼요
- **하지만**: **4-2 wrong warp**는 여전히 돼요 (패치 안 됐어요!)

### 4-2 wrong warp: 물건 배치 버그

4-2에는 파이프 전이 물건 둘이 있어요. 덩굴 (워프존)과 파이프 (코인 방). 첫 전이 물건(덩굴 것)이 덩굴이 화면에 나타나기 **훨씬 전**에 놓여 있어요. 두 번째(파이프 것)가 레벨에서 **너무 늦게** 놓여 있어요.

```asm
; 4-2 전이 타이밍:
; 전이 물건 1 (덩굴 → 워프존): 덩굴 3화면 전에 놓여 있어요
; 전이 물건 2 (파이프 → 코인 방): 파이프 1화면 뒤에 놓여 있어요
;
; 보통 첫 물건은 Mario가 파이프에 이르기 전에 비활성화돼요.
; 하지만 Mario가 빠르면 (또는 B+오른쪽 블록 지름길을 쓰면)
; 파이프에 닿을 때 덩굴 전이가 여전히 활성 상태예요!
; → 게임이 코인 방 대신 워프존을 불러와요.
;
; 물건이 덩굴 바로 뒤 파이프 앞에 놓였으면 버그가 없었을 거예요.
```

### 반복 레벨

반복(8-4, 7-4)은 어떻게 동작하나요? 레벨에 화면 번호와 하드코딩된 Y 위치가 있는 **체크포인트**가 있어요.

```asm
; 체크포인트: {screen_number, vertical_position}
; Mario가 올바른 높이로 이 체크포인트를 지나면 → 레벨 계속
; 아니면 → 4화면 뒤로 워프 (64블록)
;
; 무한 반복 만들려면: vertical_position = $F0
; (화면 아래) → 검증 불가.
;
; 체크포인트는 단순해요 (깃발 하나). 월드 7만
; 삼중항을 써요 (깃발 3개, 최소 1개 실패해야 해요)
;
; 뒤로 워프는 거칠어요. 타일 자료 오프셋이 하드코딩된 값으로,
; 스프라이트 자료 오프셋이 0으로 돌아가요. 있던 적들이
; 바로 내려가요 → 파이어바가 사라져요.
```

## 형식이 아니라 코드를 바꾸기

이 아키텍처에서 가장 매혹적인 교훈 중 하나는 SMB1 개발자들이 6502 렌더 코드를 절대 건드리지 않고 아주 표현력 있는 레벨 시스템을 만들었다는 거예요. 레벨 사이 모든 변화가 코드가 아니라 **자료**에서 와요 (포인터, 물건, 스프라이트, 바닥 패턴).

256개 글리치 월드가 존재하는 것은 **포인터 표가 종류별 128개 항목으로 되어 있고**, 게임이 읽는 값을 절대 검증하지 않기 때문이에요. 포인터가 RAM에 떨어지면 게임이 Mario 레지스터를 타일처럼 해석해요. 포인터가 소리 자료에 떨어지면 게임이 음악을 레벨 디자인처럼 연주해요. 점프 표가 오버플로우하면 게임이 죽을 때까지 아무거나 실행해요.

## 이 모든 것에서 배울 수 있는 것

1. **타일과 스프라이트 분리**: 두 층 완전 독립. 저장 순서가 달라서 고유 프랑켄슈타인 레벨을 만들어요
2. **RLE 압축 + 물건 시스템**: 레벨은 비트맵이 아니라 놓인 물건 목록이고, 바닥은 바닥 패턴으로
3. **3슬롯 큐**: 하드웨어 (그리고 레벨 디자인)의 엄격 한도
4. **포인터 완전 신뢰**: 게임이 포인터와 점프 표를 믿어서, 할 수 있는 글리치 아니면 죽음이 나와요
5. **최대 256바이트**: 6502 Y 레지스터 한도. 너무 멀리 가면 자료가 반복돼요
6. **웜 스타트와 콜드 스타트**: "이어하기" 시스템이 테니스 카트 교환에서 Mario로 가는 문을 열었어요

가장 아름다운 것은요. 이 모든 것이 40KB에 들어가는 6502 코드예요. 코드가 하드웨어와 직접 대화하고 매 메모리 접근을 완전히 신뢰해요. 포인터가 썩으면 게임이 죽어요. 그리고 죽음을 글리치 월드라고 불러요.

## 기억할 3가지

1. **글리치 월드는 잘못 떨어진 포인터예요**: 게임에 종류별 128개 ID와 4종 구역이 있지만 고유 레벨은 34개뿐이에요. 월드 번호가 망가지면 (테니스나 벽 뚫기로) 게임이 다른 레벨용 포인터를 불러오고, 512개 가능 조합이 예측할 수 없는 결과를 만들어요.

2. **Minus World는 워프 버그와 망가짐의 결합이에요**: 1-2 왼쪽 파이프가 텍스트 전에 켜지면 월드 36 (0x24)을 불러와요. 이 월드는 레벨 ID $01 (2-2 물)을 가리키고, 깃대봉이 없는 레벨이에요. 월드 36용 파이프 전이가 없어서 레벨이 무한히 돌아요. 검사 부재가 아이콘을 만들어요.

3. **테니스에서 Mario로, OoT에서 Paper Mario보다 15년 앞서요**: NES RAM이 콘덴서와 SMB1 웜 스타트와 콜드 스타트 시스템 덕분에 카트리지 교환을 살아남아요. 테니스 발걸음 카운터(발걸음 소리를 내며 RAM 바이트를 증가)는 월드 번호 주소에 딱 떨어져요. 최고 점수 자리가 0으로 남고, $A5 바이트가 온전하고, 게임이 웜 스타트를 감지해야 해요. 테니스에서만 통했던 완벽한 우연 연속이에요.
