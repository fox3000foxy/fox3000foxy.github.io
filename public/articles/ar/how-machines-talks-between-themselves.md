# المشكلة : اختصارات كثيرة، وهرمية قليلة

TCP وUDP وTLS وmTLS وWebSocket وHTTP وHTTPS وgRPC وQUIC ؛ معظم الموارد التي تتكلم عنها تعرضها كقائمة مسطحة من الخيارات القابلة للتبديل، "تُختار حسب حالة الاستخدام". في الواقع ليست على نفس المستوى : بعضها بروتوكولات نقل، وبعضها طبقات أمان تلتف حول النقل، وبعضها الآخر بروتوكولات تطبيقية تستند إلى الأولين. فهم الهرمية يعني فهم لماذا لا "نختار" أبدا بين TCP وTLS : نختار TCP، _ثم_ نقرر إن وضعنا TLS فوقه.

يعيد هذا المقال بناء هذه الهرمية طبقة بطبقة، من النقل الخام حتى المصادقة المتبادلة، مع ذكر ما يضمنه كل مستوى وما لا يضمنه ومتى نكتفي به.

# المستوى 1 : النقل (TCP ضد UDP)

كل شيء يبدأ هنا. TCP وUDP هما البروتوكولان الرئيسيان لطبقة **النقل (Layer 4)** في نموذج OSI. دورهما متطابق : نقل تدفق بيانات بين تطبيقين يعملان على آلتين مختلفتين. لكن طريقتهما في ذلك مختلفة جذريا.

من المهم فهم أن IP (Internet Protocol)، الواقع في طبقة الشبكة (Layer 3)، لا يفعل إلا توجيه الحزم من مضيف إلى آخر. لا يضمن وصولها، ولا ترتيبها، ولا حتى فرادتها. فالموجهات تتخذ ببساطة قرارات توجيه مستقلة لكل حزمة.

وهذا الغياب الدقيق للضمانات هو ما يعوّضه TCP، بينما يختار UDP عمدا ألا يضيف شيئا ليبقى خفيفا للغاية.

## TCP : الموثوقية أولا

TCP (Transmission Control Protocol) بروتوكول **موجه بالاتصال** (_connection-oriented_). قبل تبادل أي بايت من البيانات، يجب على الآلتين إقامة اتصال منطقي.

يُنشأ هذا الاتصال بفضل الـ**Three-Way Handshake** الشهير :

```

Client                           Serveur
SYN ---------------------------->
        <--------------------- SYN + ACK
ACK ----------------------------> 
Connexion établie
```

كل خطوة لها هدف دقيق :

*   SYN : العميل يعلن أنه يريد فتح اتصال ويقدم أول رقم تسلسل (Initial Sequence Number - ISN).

*   SYN-ACK : الخادم يقبل الاتصال، ويقر استلام الـSYN ويقدم بدوره رقم تسلسله الخاص.

*   ACK : العميل يؤكد استلام معلومات الخادم.


من تلك اللحظة، تعرف الآلتان حالة الاتصال ويمكنهما بدء تبادل البيانات.

### **أرقام التسلسل**

لا يرى TCP البيانات كتعاقب حزم، بل كـ**تدفق مستمر من البايتات** (_byte stream_).

كل بايت مرسل يملك رقم تسلسل.

مثال :

```
Message :

Bonjour

B = octet 0
o = octet 1
n = octet 2
...
```

إذا ضاع مقطع يحوي البايتات 1000 إلى 1499 أثناء النقل، يستطيع المستقبل كشف ما ينقص بالضبط.

ويعيد المرسل إرسال ذلك الجزء فقط.

هذه الدقة من أسباب متانة TCP.

### **إشعارات الاستلام (ACK)**

بعد استلام البيانات، يرسل المتلقي **ACK (Acknowledgment)**.

وخلافا لما يُتصور غالبا، لا يعني ACK :

> "لقد استلمت هذه الحزمة"

بل يعني :

> "لقد استلمت كل البايتات حتى الرقم X."

مثلا :

```
Client envoie :

0 → 999

Serveur répond :

ACK = 1000
```

وهذا يعني :

> "كل ما قبل البايت 1000 وصل جيدا."

تسمح هذه الآلية بالإقرار باستلام عدة مقاطع دفعة واحدة (_cumulative acknowledgments_)، مما يقلل عدد حزم التحكم.

### **إعادات الإرسال**

إذا لم يصل ACK أبدا، يفترض TCP أن المقطع ضاع.

فيعيد إرساله تلقائيا.

مهلة إعادة الإرسال (**Retransmission Timeout – RTO**) ليست ثابتة.

يقيس TCP باستمرار زمن الذهاب والإياب (**RTT**) بفضل الـACK المستلمة ويحسب RTO ديناميكيا لتجنب إعادات إرسال غير ضرورية.

تستخدم التنفيذات الحديثة أيضا آليات مثل **Fast Retransmit** : عندما يتلقى المرسل عدة ACK مكررة (عادة ثلاثة)، يستنتج أن مقطعا وسيطا ضاع ويعيده فورا، دون انتظار انتهاء المؤقت.

### **إعادة ترتيب الحزم**

لا يضمن الإنترنت إطلاقا أن تسلك حزمتان الطريق نفسه.

مثال :

```
Paquet 1
Paris
  ↓
Londres
  ↓
New York

Paquet 2
Paris
  ↓
Francfort
  ↓
Chicago
  ↓
New York
```

قد تصل الحزمة الثانية قبل الأولى.

يخزن TCP حينها مؤقتا المقاطع المستلمة **خارج الترتيب** في عازل (_reassembly buffer_)، ثم يعيد تجميعها قبل تسليمها للتطبيق.

وبالنسبة للتطبيق، يبدو كل شيء وكأنه يصل مرتبا تماما.

### التحكم في التدفق

لا يعتمد الاتصال على الشبكة فقط.

فالمستقبل يملك أيضا قدرة ذاكرة محدودة.

وإذا استلم أسرع مما يستطيع معالجة البيانات، تشبع مخازنه المؤقتة في النهاية.

يحل TCP هذه المشكلة بفضل **نافذة منزلقة (Sliding Window)**.

يعلن المستقبل في كل ACK :

```
Window = 32768 octets
```

وهذا يعني :

> "يمكنك إرسال حتى 32 Ko إضافية."

وإذا سقطت هذه النافذة إلى الصفر :

```
Window = 0
```

يعلق المرسل مؤقتا الإرسالات حتى يعلن المستقبل نافذة جديدة متاحة.

تشكل هذه الآلية **التحكم في التدفق (Flow Control)** وتمنع مضيفا سريعا من إغراق مضيف أبطأ.

### التحكم في الازدحام

حتى لو كان المستقبل قادرا على امتصاص البيانات، قد تصبح الشبكة نفسها مشبعة.

تملك الموجهات طوابير انتظار (_queues_) محدودة.

وعندما تفيض، تُحذف الحزم.

يفسر TCP الفقدان كعلامة ازدحام ويكيّف معدل إرساله تلقائيا بفضل **نافذة ازدحام (Congestion Window – cwnd)**.

تضبط الخوارزميات الحديثة (مثل **Reno** و**CUBIC** أو **BBR** حسب أنظمة التشغيل) هذه النافذة لإيجاد توازن بين أقصى معدل واستقرار الشبكة.

كانت الإصدارات الأولى من TCP تستخدم أساسا آليتين :

*   **Slow Start** : زيادة أسية للمعدل حتى كشف ازدحام.

*   **Congestion Avoidance** : نمو أكثر حذرا بعد ذلك، خطي غالبا.


هذا التكيف الدائم من أسباب بقاء TCP فعالا رغم تفاوت جودة الشبكة.

### إغلاق الاتصال

وخلافا لـUDP، يملك اتصال TCP أيضا إغلاقا نظيفا.

يغلق كل طرف تدفقه مستقلا بفضل علم **FIN**.

ويتطلب الإغلاق الكامل عادة أربعة تبادلات :

```
FIN
ACK
FIN
ACK
```

يضمن هذا الإجراء أن كل البيانات العابرة سُلّمت جيدا قبل تدمير الاتصال.

## UDP : أقصى بساطة

يتبنى UDP (User Datagram Protocol) الفلسفة المعاكسة.

إنه **بلا اتصال (connectionless)**.

لا يوجد :

*   أي handshake ؛

*   أي رقم تسلسل ؛

*   أي إشعار استلام ؛

*   أي إعادة إرسال ؛

*   أي تحكم في التدفق ؛

*   أي تحكم في الازدحام.


كل رسالة تُغلَّف ببساطة في **datagramme** مستقل، تُنقل إلى الشبكة، ثم ينساها المرسل.

```
Application → Datagramme UDP → IP → Internet
```

لا يحتفظ البروتوكول بأي حالة بين إرسالين.

وكل datagramme مستقل تماما عن سابقيه.

### سلامة البيانات

رغم أن UDP لا يضمن التسليم ولا الترتيب، فإنه يحمي سلامة البيانات بفضل **checksum**.

عند الاستلام، يُعاد حساب الـchecksum.

*   إذا تطابقت القيمتان، يُقبل الـdatagramme.

*   وإلا، يُرفض فورا.


إذن يكشف UDP البيانات الفاسدة، لكنه لا يحاول أبدا استعادتها.

### لماذا UDP سريع جدا ؟

ترويسة UDP لا تحوي إلا **8 octets**، مقابل **20 octets** كحد أدنى لـTCP (دون احتساب الخيارات مثل timestamps وSACK أو Window Scaling).

وبما أنه لا يُحافَظ على أي اتصال، لا يتعين على نظام التشغيل تتبع حالة كل تبادل، مما يقلل أيضا استهلاك الذاكرة وكost المعالجة.

يستلم التطبيق البيانات فور وصولها تقريبا، دون انتظار إعادات إرسال محتملة.

## عندما يكون فقدان بيانة مفضلا

الفكرة الأساسية بسيطة :

> معلومة قديمة قد تكون أقل قيمة من معلومة ضائعة.

خذ محادثة VoIP.

كل حزمة تحمل حوالي **20 ms** من الصوت.

فإذا ضاعت حزمة، غالبا ما تستغرق إعادة إرسالها أكثر من تلك الـ20 ms.

وعندما تصل أخيرا، تكون المحادثة قد تقدمت فعلا.

تفضل معظم التطبيقات حينها إخفاء الفقدان (استيفاء، صمت، تصحيح خطأ) على انتظار إعادة الإرسال.

وينطبق المنطق نفسه على :

*   ألعاب اللاعبين المتعددين في الوقت الحقيقي ؛

*   بث الفيديو ؛

*   تدفقات القياس عن بعد ؛

*   حساسات IoT ؛

*   بيانات مواقع GPS.


القيمة الحديثة مفيدة دائما تقريبا أكثر من قيمة قديمة موثوقة تماما.

# المستوى 2 : التشفير، TLS

لا يستبدل TLS (Transport Layer Security، خليفة SSL) محل TCP، بل يضاف فوقه. عمليا، يؤسس TLS اتصال TCP عاديا، ثم يتفاوض على جلسة مشفرة داخله : تبادل شهادات، واتفاق على خوارزمية تشفير، واشتقاق مفاتيح جلسة. وكل ما يعبر بعد ذلك مشفر ومصدَّق.

ثلاث ضمانات متميزة، كثيرا ما تُخلط :

*   **السرية** : لا يستطيع أحد غير الطرفين قراءة المحتوى.

*   **السلامة** : أي تغيير للبيانات أثناء العبور يُكتشف.

*   **المصادقة** : لكن في TLS التقليدي، باتجاه واحد : يتحقق العميل من أن الخادم هو فعلا من يدعي أنه هو (عبر شهادته، الموقعة من سلطة موثوقة)، لكن الخادم لا يتحقق من شيء حول هوية العميل. وهذا بالضبط نموذج HTTPS عندما تزور موقعا : المتصفح يصادق الموقع، والموقع لا يصادقك (مصادقة المستخدم تمر عبر آلية منفصلة، cookie جلسة أو token).


قلّص TLS 1.3 (الإصدار الحالي الموصى به) الـhandshake إلى ذهاب وإياب واحد في الحالة الشائعة، مقابل اثنين في TLS 1.2، مما يقلل زمن الاتصال بشكل محسوس.

## المستوى 2 مكرر : mTLS، المصادقة تصبح متبادلة

mTLS (mutual TLS) هو TLS مع قيد إضافي : يطلب الخادم _أيضا_ شهادة من العميل، ويتحقق منها. يثبت الطرفان هويتهما عبر شهادة موقعة من سلطة ثقة مشتركة.

وهي الآلية الطبيعية للتواصل خدمة لخدمة في بنية موزعة : فحيث يكفي HTTPS التقليدي ليتكلم متصفح مع خادم عام، يجيب mTLS عن سؤال مختلف ؛ _كيف تعرف خدمة داخلية أنها تتكلم فعلا مع خدمة داخلية أخرى مرخصة، وليس مع مهاجم هبط على الشبكة ؟_

```
Client                                          Serveur
  │──── ClientHello ─────────────────────────────▶│
  │◀─── ServerHello + certificat serveur ──────────│
  │──── vérifie le certificat serveur ─────────────│
  │──── envoie SON PROPRE certificat client ──────▶│
  │◀─── vérifie le certificat client ───────────────│
  │──── clés de session dérivées, canal chiffré ──▶│
```

مقابل mTLS تشغيلي : يلزم سلطة تصديق (CA) داخلية، وآلية توزيع شهادات لكل خدمة، واستراتيجية تدوير/إبطال. في بيئة آلة واحدة مع خدمات قليلة، يكون أحيانا تعقيدا أكثر من الفائدة، ويصبح mTLS ضروريا منذ اللحظة التي يعبر فيها الترافيك بين الخدمات شبكة لا نتحكم فيها كليا (عدة مضيفين، سحابة متعددة المستأجرين)، أو بمجرد أن نريد سياسة من نوع _zero trust_، حيث لا خدمة جديرة بالثقة ضمنيا لمجرد أنها "داخل" الشبكة.

# المستوى 3 : البروتوكولات التطبيقية فوق TCP+TLS

بمجرد وضع النقل والتشفير، يبقى تحديد _كيفية هيكلة التبادلات_. وهذا دور البروتوكولات التطبيقية.

## HTTP / HTTPS

HTTP بروتوكول طلب-جواب : يفتح العميل اتصالا (أو يعيد استخدام واحد، مع keep-alive)، ويرسل طلبا، وينتظر جوابا، ثم يمكن أن يُغلق الاتصال أو يُعاد استخدامه. HTTPS هو ببساطة HTTP على TLS، فالـS لا يغير شيئا في دلالة البروتوكول، فقط في كون النقل مشفرا.

لنموذج طلب-جواب حد بنيوي : لا يستطيع الخادم أبدا الكلام أولا. لا يستطيع إلا الرد على ما يطلبه العميل. وبالنسبة للـpolling المتكرر (التحقق من "هل من جديد ؟" كل ثانية)، يعمل لكنه يهدر الموارد، فكل طلب يعيد إنشاء عبء بروتوكولي، ليعلن في معظم الوقت أنه لا جديد.

## WebSocket (WS / WSS)

يجيب WebSocket بالضبط عن هذا الحد. يبدأ الاتصال كطلب HTTP تقليدي (مع ترويسة `Upgrade: websocket`)، لكن بمجرد قبول المصافحة، لا يعود الاتصال TCP الكامن قناة طلب-جواب HTTP، بل يصبح قناة ثنائية الاتجاه full-duplex يستطيع فيها العميل والخادم إرسال رسائل في أي وقت، دون إعادة إصدار دورة طلب-جواب مع كل تبادل.

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

WSS هو ببساطة WebSocket على TLS، تماما كما HTTPS هو HTTP على TLS. وهو بروتوكول الاختيار لكل ما يتطلب دفع خادم في الوقت الحقيقي، دردشة وإشعارات وتدفقات تداول وأحداث ألعاب، دون الرغبة في إدارة بروتوكول ثنائي ذاتيا فوق TCP عارٍ.

## gRPC

أقل شهرة خارج عالم الخدمات المصغرة لكنه محوري في التواصل خدمة لخدمة : يستند gRPC إلى HTTP/2 (أي TCP + TLS اختياري)، ويسلسل الرسائل بـProtocol Buffers (ثنائي ومُنمَّط ومضغوط، خلافا لـJSON النصي في معظم واجهات REST)، ويسمح أصلا بالبث ثنائي الاتجاه بفضل تعدد إرسال HTTP/2 (عدة تدفقات منطقية على اتصال TCP واحد، دون head-of-line blocking الذي كانت ستسببه عدة طلبات HTTP/1.1 متسلسلة).

## QUIC / HTTP3

يغير QUIC قواعد اللعبة بالانطلاق من UDP بدلا من TCP في مستوى النقل، مع إعادة تنفيذ فوقه ضمانات الموثوقية التي كان TCP يقدمها أصلا، لكن تدفقا بتدفق بدلا من الشمول، مما يزيل head-of-line blocking في مستوى النقل (حزمة ضائعة في تدفق لم تعد تحجب التدفقات الأخرى لنفس الاتصال). TLS 1.3 مدمج مباشرة في QUIC بدلا من إضافته فوقه، مما يقلل زمن الـhandshake أكثر. وHTTP/3 هو HTTP فوق QUIC.

# نظرة شاملة : أين يقع كل بروتوكول

طبقة بروتوكولات دور نقل TCP وUDP نقل البايتات، موثوقا أو لا نقل (جيل جديد) QUIC بموثوقية UDP + لكل تدفق + TLS مدمج أمان TLS وmTLS تشفير وسلامة ومصادقة (أحادية أو متبادلة) تطبيق HTTP/HTTPS وWS/WSS وgRPC هيكلة التبادلات (طلب-جواب، ثنائي الاتجاه، RPC مُنمَّط)

مثال ملموس لتثبيت الأفكار : بنية خدمات مصغرة مع لوحة ويب وخدمات داخلية يمكنها منطقيا الجمع بين HTTPS (لوحة ← API عامة، مصادقة أحادية الاتجاه كافية جهة المتصفح)، وmTLS (خدمة ← خدمة داخليا، مصادقة متبادلة لازمة)، وWSS (إشعارات وقت حقيقي مدفوعة نحو اللوحة)، ثلاثة بروتوكولات تطبيقية مختلفة، كلها مبنية على نفس الأساس TCP + TLS.

## كيف تختار، عمليا

ثلاثة أسئلة تكفي غالبا للحسم :

1.  **هل أحتاج الموثوقية والترتيب، أم أن حداثة البيانة تسبق تسليمها المضمون ؟** ← TCP إذا نعم، وUDP إذا لا (أو QUIC للجمع بينهما عبر حل وسط مختلف).

2.  **هل يجب أن يستطيع الخادم بدء الرسائل، أم أن العميل هو دائما صاحب الطلب الأول ؟** ← WebSocket/بث gRPC إذا كان الخادم يجب أن يدفع، وHTTP تقليدي إلا ذلك.

3.  **هل يجب أن يثبت الطرفان هويتهما لبعضهما، أم أن واحدا فقط يحتاج التحقق ؟** ← mTLS لخدمة لخدمة في بيئة zero-trust، وTLS بسيط لعميل عام تقليدي.


يزداد التعقيد التشغيلي مع كل طبقة مضافة، فـTCP العاري بلا بنية تحتية تُدار، وTLS يتطلب شهادات، وmTLS يتطلب CA واستراتيجية تدوير، وgRPC يتطلب تعريف مخطط Protobuf مشتركا. والمنعكس الصحيح هو ألا نصعد في التعقيد إلا عندما تُظهر الطبقة الدنيا حدا ملموسا، لا استباقا.
