## Introduction

There's a $1 microcontroller running a Minecraft server.

Not a "flat world with steve blinking". Infinite world generation, biomes, caves, crafting, mining, mobs, hunger, chests. On a chip running at **160 MHz** drawing **0.5 Watt**.

The project is [Bareiron](https://github.com/p2r3/bareiron/), by p2r3.

This isn't "I wrote a server in C". This is "I thought about every single byte and twisted the Minecraft protocol to fit the impossible into 520 KB of SRAM".

## The base problem

The Notchian server is a beast. Gigabytes of RAM, multi-octave Perlin noise, 6 biome parameters (temperature, humidity, continentalness, erosion, weirdness, depth), zlib compression, millions of chunks in memory.

The ESP32-C3 :
- **520 KB SRAM** (400 after boot)
- **160 MHz**
- **0.5 Watt**

The gap between them ? Roughly **20,000x**.

p2r3 didn't optimize the vanilla server. He rebuilt everything from scratch.

## Terrain generation : the smartest move in the project

The core problem : generate infinite terrain with no memory storage and no expensive computation.

Vanilla uses Perlin noise : multiple octaves of stacked noise, biome parameters everywhere. It works, it looks good, it's expensive.

Bareiron uses **bilinear interpolation** on points generated by a **deterministic RNG**.

You know bilinear interpolation ? That thing image software does when you upscale a pixelated icon – the edges get blurry, you get a smooth gradient.

Bareiron applies this to terrain :

```c
height = bilinear_interpolate(
  RNG(chunk_x,     chunk_z),     // top-left corner
  RNG(chunk_x + 1, chunk_z),     // top-right corner
  RNG(chunk_x,     chunk_z + 1), // bottom-left corner
  RNG(chunk_x + 1, chunk_z + 1), // bottom-right corner
  offset_x, offset_z
);
```

The RNG is seeded by the chunk coordinates. Same coordinates always give the same result. It's deterministic. No need to store terrain – you can recompute it on the fly and get the same answer every time.

Adjacent chunks share 2 corners. The interpolation is **continuous across chunk boundaries**. No cracks.

By adjusting how many RNG bits you combine, you control terrain regularity. More bits = more factors combined = smoother terrain (like more coin flips giving a distribution closer to 50/50). Fewer bits = rougher terrain.

Result : infinite terrain, zero memory storage, and a chunk generated in **200 ms** on an ESP32.

### Caves : mirror the surface

Vanilla caves have their own complex generator. Bareiron does this :

```c
cave_y = CAVE_BASE_DEPTH - (surface_height - y);
```

It takes the surface height and mirrors it underground. Looks like the big deepslate cavities you find in the overworld.

Not as varied as vanilla caves. But it cost 1 line of code and zero extra compute.

### Ores : no veins, one operation per column

In vanilla, ores are generated in veins using specialized noise algorithms. Bareiron takes a shortcut : an XOR of column coordinates guarantees exactly one candidate per column, and the type depends on Y level.

```c
candidate = (chunk_x ^ col_x ^ col_z) % 100;
if (candidate < 5 && y < 16) -> diamond
if (candidate < 15 && y < 32) -> gold
// etc.
```

Zero storage, zero Perlin, one math operation.

### The biome system : islands in a grid

Biomes could have been a noise layer on top of the terrain. But that would double the compute requirements. p2r3 took a more radical approach : a **tile map** where each biome is a circular island arranged in a grid.

Each island's type comes from a small repeating pattern calculated from the world seed. Gridded, predictable, and **free**.

Each biome adjusts terrain generation parameters :
- **Plains/Forest** : 4 height factors, flat with occasional features
- **Desert** : max 6 blocks variation, never below sea level
- **Snowy plains** : 2 factors, up to 14 blocks variation, hillier

Surface elements (trees in forests, cacti in deserts, bushes in snow) use the same random numbers from chunk corners. Zero overhead.

## Crafting : when ugly code is smarter

The clean way to implement crafting : define 3x3 matrices for each recipe, use a kernel-fitting algorithm to match against the grid. Clean, maintainable, extensible.

Also memory-hungry.

p2r3 went a different route. The crafting function starts by counting filled slots, noting the first item, and checking if all others are identical.

With this, some recipes match in 4 operations :

```c
if (count == 8 && first == cobblestone && all_identical && center_empty)
    return furnace;
```

For more complex shapes : use the first item's index and check relative positions of others. Shears : 2 iron items positioned diagonally, doesn't matter where in the grid.

Similar recipes share the same matching logic. One shape for all pickaxes, the material determines the output.

The result is code that's way less readable than a clean recipe table. Zero memory overhead, and it runs in a laughably small number of instructions.

## The furnace : a crafting table without the timer

In vanilla, furnaces take time. You need timers, input/output storage, fuel management. Memory and compute for every active furnace.

Bareiron says no. The furnace works like a crafting table : put ingredients in, get result out. Instant.

Less realistic. Way more efficient. On an ESP32, who has time to wait for ore to smelt anyway ?

## Chests : the nastiest memory hack you'll see

When testers demanded chests, p2r3 had a concrete problem : where to store 27 inventory slots without dynamic memory allocation ?

The block change array uses 6-byte entries :
- 2 bytes X
- 1 byte Y
- 2 bytes Z
- 1 byte block ID

And items in Bareiron are : 16 bit ID, 8 bit stack size.

By pure coincidence, each block entry fits **exactly 2 items**.

Each chest takes 15 block change entries : 1 for the chest block itself, 14 for the 27 slots (2 per entry, 3 bytes per slot, 1 byte wasted).

When a player opens a chest, the server **memcpy**s the slot memory into the player's craft buffer. The buffer is recycled because you can't craft with a chest open. A `0x80` flag blocks crafting.

The source code comment :

```c
// Terrible memory hack!!1!
```

Couldn't have said it better myself.

## Hunger for free

Modern Minecraft hunger mechanics are complex. Health, hunger, saturation, timers everywhere.

p2r3 noticed something. When a player moves, their client sends movement packets at roughly 20 per second. When they don't move, they send one.

The server has to process these packets anyway. So p2r3 turned it into a free activity counter.

```c
// Each movement packet received → counter--
// Counter hits 0 → hunger drops by 1
// Eating → counter increases
```

Zero timer, zero allocated memory, zero dedicated compute. Hunger implemented without costing anything.

## Mobs in 8 bytes

Each mob fits in 8 bytes :
- 1 byte type (zombie, chicken, cow, pig, sheep)
- 2 bytes X
- 1 byte Y
- 2 bytes Z
- 1 byte data (health, sheared state, panic timer)

Passives wander in 1 of 8 random directions. Hostiles walk toward the nearest player. No pathfinding, no obstacle avoidance, no A*. Nothing.

At 2 blocks range, a zombie deals 3 hearts per second — deliberately higher than vanilla, to compensate for dumb predictable AI. Armor reduces damage using the pre-1.9 formula.

Mobs spawn when a player crosses a chunk boundary, instead of random ticks. Zero spawn overhead.

## What got cut

All this comes at a cost. Some vanilla features don't exist :

- **No network compression** — zlib is too CPU-heavy. Generating chunks is fast, sending them is the bottleneck.
- **No random ticks** — trees grow with bone meal or not at all.
- **No item entities** — mined blocks go straight to inventory. Visual flying animation, no distance checking.
- **No inventory validation** — server trusts the client. Client says 64 diamonds, you've got 64 diamonds.
- **No server-side lighting** — torches sent after other blocks, client calculates lighting.
- **No gradual fluid flow** — water and lava reach final state instantly.

## The result

Desktop PC with Ryzen 5 3600 : ~0.5 ms per chunk.

ESP32-C3 costing under $1 : ~200 ms per chunk. Playable.

With more than 3 players, lag kicks in — comparable to 2b2t during peak hours, according to the author. But it works.

It's open source, GPLv3, on [GitHub](https://github.com/p2r3/bareiron/).

## The philosophy

Every decision in Bareiron is a conscious tradeoff between features and performance. Nothing is accidental.

Perlin noise → bilinear interpolation : uglier, but 200x faster and zero memory.
Crafting matrices → hardcoded matching : disgusting code, but zero byte overhead.
zlib → nothing : unplayable on bad connections, but playable otherwise.
Inventory validation → trust : zero security, zero compute.

This isn't "making a Minecraft server in C". It's "making a Minecraft server that fits on a $1 microcontroller by making the right sacrifices".

**3 things to remember :**

1. **Bilinear interpolation + deterministic RNG** — Replacing Perlin noise with 4 seeded points is the move that makes everything else possible. Infinite terrain with no storage, generated in 200 ms.
2. **Every feature has a cost** — No compression, no random ticks, no validation. These aren't shortcuts, they're what keeps the whole thing in 520 KB.
3. **The nastiest solutions are sometimes the smartest** — Chests in the block array, hunger tracked by movement packets, instant furnace. The "clean" approach would have been too expensive.
