# 問題：略語が多すぎて階層がなさすぎる

TCP、UDP、TLS、mTLS、WebSocket、HTTP、HTTPS、gRPC、QUIC。これらを語る資料の大半は、平らな互換選択肢リストとして並べて「用途で選べ」って言う。実際は同じ平面にいない。転送プロトコルもあれば、転送を包む安全層もあれば、両者の上に乗るアプリケーションプロトコルもある。階層を理解することが、TCPとTLSの間で「選ぶ」ことは決してない理由の理解だ。TCPを選んで、_それから_TLSを上に乗せるか決めるんだ。

この記事はこの階層を層ごとに再構築する。素の転送から相互認証まで、各水準でこう示す。何を保証するか、何を保証しないか、いつそれで足りるかだ。

# 水準1：転送（TCP対UDP）

全部ここから始まる。TCPとUDPはOSIモデルの**トランスポート層（Layer 4）**の2大プロトコルだ。役割は同じだ。違うマシンで動く2つのアプリ間でデータ流を運ぶことだ。でもやり方は根本的に違う。

大事な理解として、ネットワーク層（Layer 3）のIP（Internet Protocol）はホストからホストへパケットを運ぶだけだ。到着も順序も一意性も保証しない。ルーターは各パケットに独立の経路決定をするだけだ。

この保証欠落をTCPが埋めに来て、UDPはわざと何も足さず極限まで軽く保つ。

## TCP：信頼性が第一

TCP（Transmission Control Protocol）は**コネクション型**（connection-oriented）プロトコルだ。1バイトのデータを交換する前に、2台のマシンが論理コネクションを確立しなきゃいけない。

このコネクションは有名な**スリーウェイハンドシェイク**で作られる。

```

Client                           Serveur
SYN ---------------------------->
        <--------------------- SYN + ACK
ACK ----------------------------> 
Connexion établie
```

各段階に明確な目的がある。

*   SYN：クライアントがコネクションを開きたいと宣言して、最初のシーケンス番号（Initial Sequence Number - ISN）を渡す。
    
*   SYN-ACK：サーバーがコネクションを受けて、SYNを確認して、今度は自分のシーケンス番号を渡す。
    
*   ACK：クライアントがサーバー情報の受信を確認する。
    

ここから2台のマシンはコネクション状態を知って、データ交換を始められる。

### **シーケンス番号**

TCPはデータをパケットの連なりじゃなく**連続バイト流**（byte stream）として見る。

送る各バイトにシーケンス番号がある。

例：

```
Message :

Bonjour

B = octet 0
o = octet 1
n = octet 2
...
```

1000から1499バイト目のセグメントが転送中に失われたら、受信側は正確に何が欠けたか検出できる。

送信側はその部分だけ再送する。

この粒度がTCPの頑丈さの理由の1つだ。

### **確認応答（ACK）**

データ受信後、宛先は**ACK（Acknowledgment）**を送る。

よく想像されるのと違って、ACKの意味はこうじゃない。

> 「このパケットを受け取った」

むしろこうだ。

> 「X番までのバイトは全部受け取った」

たとえばこうだ。

```
Client envoie :

0 → 999

Serveur répond :

ACK = 1000
```

意味はこうだ。

> 「バイト1000より前は全部届いた」

この仕組みで複数セグメントをまとめて確認できる（cumulative acknowledgments）。制御パケット数を減らせる。

### **再送**

ACKが来なければ、TCPはセグメントが失われたとみなす。

自動で再送する。

再送遅延（**Retransmission Timeout、RTO**）は固定じゃない。

TCPは受けたACKで往復時間（**RTT**）を常に測って、無駄な再送を避けるようRTOを動的計算する。

現代実装は**Fast Retransmit**みたいな仕組みも使う。送信側が重複ACKを複数（だいたい3つ）受けたら、中間セグメントが失われたと推測して、タイマー切れを待たず即送り直す。

### **パケットの並べ替え**

インターネットは2つのパケットが同じ道を通ることをまったく保証しない。

例：

```
Paquet 1
Paris
  ↓
Londres
  ↓
New York

Paquet 2
Paris
  ↓
Francfort
  ↓
Chicago
  ↓
New York
```

2つ目のパケットが先に着くことがある。

TCPは**順序外**で受けたセグメントをバッファ（reassembly buffer）に一時置いて、アプリに渡す前に組み立て直す。

アプリからは全部完璧な順序で届いたように見える。

### フロー制御

コネクションはネットワークだけで決まらない。

受信側にも限られたメモリ容量がある。

処理できるより速く受けたらバッファが飽和する。

TCPは**スライディングウィンドウ（Sliding Window）**でこの問題を解く。

受信側は各ACKでこう示す。

```
Window = 32768 octets
```

意味はこうだ。

> 「あと32KBまで送っていいよ」

このウィンドウがゼロになったらこうだ。

```
Window = 0
```

送信側は受信側が新しい利用可能ウィンドウを告げるまで送信を一時止める。

この仕組みが**フロー制御（Flow Control）**で、速いホストが遅いホストを洪水にしない。

### 輻輳制御

受信側がデータを吸収できても、ネットワーク自体が飽和することがある。

ルーターは限られたキュー（queues）を持つ。

溢れたらパケットは捨てられる。

TCPは損失を輻輳の印と読んで、**輻輳ウィンドウ（Congestion Window、cwnd）**で送信量を自動調整する。

現代アルゴリズム（OSによるが**Reno**や**CUBIC**や**BBR**）はこのウィンドウを調整して、最大スループットとネットワーク安定の均衡を探る。

初期のTCPは主に2仕組みを使ってた。

*   **Slow Start**：輻輳検出まで送信量を指数増加させる。
    
*   **Congestion Avoidance**：その後は慎重に、だいたい線形に増やす。
    

この常時適応が、ネットワーク品質が変わってもTCPが高性能な理由の1つだ。

### コネクション終了

UDPと違ってTCPコネクションにはきれいな終了もある。

各端が**FIN**フラグで自分の流を独立に閉じる。

完全な終了にはだいたい4往復要る。

```
FIN
ACK
FIN
ACK
```

この手順で、転送中データが全部届いてからコネクション破棄されることが保証される。

## UDP：最大の単純さ

UDP（User Datagram Protocol）は逆の哲学だ。

**コネクションレス（connectionless）**だ。

存在しないものはこうだ。

*   ハンドシェイクなし。
    
*   シーケンス番号なし。
    
*   確認応答なし。
    
*   再送なし。
    
*   フロー制御なし。
    
*   輻輳制御なし。
    

各メッセージは独立**データグラム**に包まれて、ネットワークに投げられて、送信側は忘れる。

```
Application → Datagramme UDP → IP → Internet
```

プロトコルは2回送信の間に状態を持たない。

各データグラムは前と完全独立だ。

### データ完全性

UDPは配送も順序も保証しないけど、**チェックサム**でデータ完全性は守る。

受信時にチェックサムを再計算する。

*   値が合えばデータグラム受理。
    
*   合わなければ即棄却。
    

つまりUDPは壊れたデータを検出するけど、取り戻そうとは絶対しない。

### なぜUDPは速いのか

UDPヘッダは**8バイト**だけで、TCPは最低**20バイト**だ（タイムスタンプやSACKやWindow Scalingみたいなオプション別）。

コネクションを維持しないので、OSは各交換の状態を追わなくていい。メモリ消費も処理コストも減る。

アプリはデータが着いたらほぼ即受け取る。再送待ちなしだ。

## データを失う方がましなとき

根本発想は単純だ。

> 古い情報は失われた情報より価値が低いことがある。

VoIP通話を取ろう。

各パケットは約**20ms**の声を運ぶ。

パケットが失われたら、再送にはその20msより長くかかることが多い。

ようやく届いた頃には通話は先に進んでる。

だから大半アプリは再送待ちより損失隠し（補間、無音、誤り訂正）を選ぶ。

同じ理屈がこうにも当てはまる。

*   リアルタイムマルチプレイゲーム。
    
*   動画ストリーミング。
    
*   テレメトリ流。
    
*   IoTセンサー。
    
*   GPS位置データ。
    

新しい値は、完全信頼の古い値よりほぼいつも有用だ。

# 水準2：暗号化、TLS

TLS（Transport Layer Security、SSLの後継）はTCPを置き換えない。上に足される。具体的にはTLSは普通のTCPコネクションを確立してから、中に暗号化セッションを交渉する。証明書交換、暗号アルゴリズム合意、セッション鍵導出だ。その後流れるものは全部暗号化されて認証される。

よく混同される3つの別保証だ。

*   **機密性**：両当事者以外は内容を読めない。
    
*   **完全性**：転送中の改変は全部検出される。
    
*   **認証**：でも古典TLSでは片方向だ。クライアントはサーバーが名乗る相手か検証する（信頼できる認証局署名の証明書経由）が、サーバーはクライアント身分を何も検証しない。サイト訪問時のHTTPSモデルがまさにこれだ。ブラウザはサイトを認証する。サイトは君を認証しない（ユーザー認証は別仕組み、セッションクッキーやトークンを通る）。
    

TLS 1.3（現行推奨版）はハンドシェイクを通常1往復に減らした。TLS 1.2の2回からだ。コネクション遅延がかなり減る。

## 水準2bis：mTLS。認証が相互になる

mTLS（mutual TLS）は追加制約付きTLSだ。サーバーもクライアント証明書を要求して検証する。両者が共通の信頼認証局署名の証明書で身分を証明する。

分散アーキテクチャのサービス間通信の自然な仕組みだ。古典HTTPSが公開サーバーと話すブラウザに足りるのに対し、mTLSは違う問いに答える。_内部サービスはどうやって、許可された別の内部サービスと話してると知るのか。ネットワークに入り込んだ攻撃者じゃないと。_

```
Client                                          Serveur
  │──── ClientHello ─────────────────────────────▶│
  │◀─── ServerHello + certificat serveur ──────────│
  │──── vérifie le certificat serveur ─────────────│
  │──── envoie SON PROPRE certificat client ──────▶│
  │◀─── vérifie le certificat client ───────────────│
  │──── clés de session dérivées, canal chiffré ──▶│
```

mTLSの代償は運用だ。内部認証局（CA）が要る。各サービスへの証明書配布仕組みが要る。ローテーションや失効の戦略が要る。サービスが少ない単一マシン環境では複雑さが利益を上回ることもある。mTLSが必要になるのは、サービス間トラフィックが完全管理できない網を通るようになってからだ（複数ホスト、マルチテナントクラウド）。あるいはゼロトラスト型方針が欲しいときだ。網の「内側」にいるだけでサービスが暗黙に信頼に足りることはない、というやつだ。

# 水準3：TCPとTLSの上のアプリケーションプロトコル

転送と暗号化ができたら、残りは交換をどう構造化するかだ。アプリケーションプロトコルの役割だ。

## HTTP / HTTPS

HTTPはリクエストレスポンス型プロトコルだ。クライアントがコネクションを開いて（keep-aliveで再利用して）、リクエストを送って、応答を待つ。コネクションはその後閉じても再利用してもいい。HTTPSはTLS上のHTTPに過ぎない。Sはプロトコル意味を何も変えない。転送が暗号化されるってだけだ。

リクエストレスポンス型モデルには構造的限界がある。サーバーは決して先に話せない。クライアントの求めに答えるだけだ。頻繁ポーリング（毎秒「新着ある」確認）には動くけど資源を無駄にする。新着がないことが大半なのに、各リクエストがプロトコルオーバーヘッドを作り直すからね。

## WebSocket（WS / WSS）

WebSocketはまさにこの限界に答える。コネクションは古典HTTPリクエストとして始まる（`Upgrade: websocket`ヘッダー付き）。でもハンドシェイクが受け入れられたら、下のTCPコネクションはもうHTTPリクエストレスポンス型チャネルじゃない。クライアントもサーバーもいつでもメッセージを送れる双方向全二重チャネルになる。各交換でリクエストレスポンス周期を出し直さなくていい。

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

WSSはTLS上のWebSocketに過ぎない。HTTPSがTLS上のHTTPなのとまったく同じだ。サーバー側プッシュのリアルタイムが必要なもの全部の選択肢プロトコルだ。チャット、通知、取引流、ゲームイベントなど。素のTCP上に自前バイナリプロトコルを管理したくない場合だね。

## gRPC

マイクロサービス界隈外では知名度が低いけどサービス間通信の中心だ。gRPCはHTTP/2の上に乗る（つまりTCPと任意TLS）。メッセージをProtocol Buffersで直列化する（大半REST APIのテキストJSONと違ってバイナリで型付きでコンパクト）。HTTP/2の多重化のおかげで生来の双方向ストリーミングができる（単一TCPコネクション上の複数論理流。HTTP/1.1逐次リクエスト複数みたいなhead-of-line blockingなし）。

## QUIC / HTTP3

QUICは転送水準でUDPから出直して流れを変える。それでいてTCP本来の信頼保証を上に再実装する。でも全体じゃなく流ごとにだ。これで転送水準のhead-of-line blockingを消す（1つの流のパケット損失が同じコネクションの他流を止めない）。TLS 1.3は上に足すんじゃなくQUICに直接統合されてて、ハンドシェイク遅延をさらに減らす。HTTP/3はQUIC上のHTTPだ。

# 全体図：各プロトコルの位置

層 プロトコル 役割 転送 TCP、UDP バイトを運ぶ、信頼ありかなしか 転送（新世代） QUIC UDPと流ごと信頼とTLS統合 安全 TLS、mTLS 暗号化、完全性、認証（片方向か相互） 応用 HTTP/HTTPS、WS/WSS、gRPC 交換の構造化（リクレス、双方向、型付きRPC）

具体例で固めよう。ウェブダッシュボードと内部サービスのあるマイクロサービスアーキテクチャなら、HTTPS（ダッシュボードと公開API間。ブラウザ側は片方向認証で十分）、mTLS（内部のサービス間。相互認証が必要）、WSS（ダッシュボードへのリアルタイム通知プッシュ）と組み合わせるのが合理的だ。違う応用プロトコル3つで、土台は全部同じTCPとTLSだ。

## 実際どう選ぶか

3つの問いがあればだいたい決まる。

1.  **信頼と順序が要るか。データ鮮度が保証配送より勝つか。** → 前者ならTCP、後者ならUDP（両方欲しければQUICで違う妥協）。
    
2.  **サーバーがメッセージを始められなきゃいけないか。クライアントがいつも先に求めるか。** → サーバーが押すならWebSocketやgRPCストリーミング、そうじゃないなら古典HTTP。
    
3.  **両者が互いに身分を証明し合わなきゃいけないか。片方検証でいいか。** → ゼロトラスト環境のサービス間ならmTLS、古典公開クライアントなら単純TLS。
    

足す層ごとに運用複雑さは上がる。素のTCPは管理土台ゼロ、TLSは証明書が要る、mTLSはCAとローテーション戦略が要る、gRPCは共有Protobufスキーマ定義が要る。正しい反射は、下の層が具体的な限界を見せたときだけ複雑さを上げることで、先回りじゃない。
