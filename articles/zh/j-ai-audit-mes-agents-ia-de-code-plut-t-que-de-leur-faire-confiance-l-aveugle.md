## 先有症状，再有诊断

每版交易平台技术报告都逼我把架构重走一遍：服务、智能体、数据管线。写第 4 版时仓库体积终于刺眼了，之前看它一点点变大都没停下来想过：仓库最初几千行，不到 10ko，现在干到 100Mo。平台功能几乎没多。我只是靠 Claude Chat 这类智能体实现和修代码，从没精确框过要它干什么、在多大范围干。

写报告逼我从"在往前走"模式切回"到底发生了什么"模式。我对仓库历史做了两次审计。两次指向同一个病因，理由完全不同。

## 审计一：说谎的上下文窗口

第一次审计是把几个月里一个 AI 智能体逐个服务做的修改重走一遍，检查在当时和仓库别处对不对得上。

反复出现的模式：智能体在局部修问题，就在它眼前的那个文件或模块里，没看到仓库别处等价的东西，或者记不住。结果：同一个接口在两个服务里被略微不同地重定义一次，重命名改一半因为第二处在 prompt 时在上下文窗口外面，命名规范这个模块遵守下个模块丢。一处看都小事，攒几十个 session，就是让下一个接手的工具跟丢思路的冗余和 code smell。自我强化的圈：仓库越大越碎，智能体越难一次装进脑子，修得越局部越零散，仓库越大。

问题不是智能体"撒谎"编造，它在给到的上下文上答得正确。问题是我大多时候从没在上游定义问题的范围。我说"修这个 typo、这个行为、这个函数"，没问这个 bug 在智能体看不见的地方有没有等价物。

## 审计二：啰嗦变成代码

第二次审计更机械：对全部历史跑 `git log --numstat`，按提交聚合新增行数和新增字符数，看分布。

新增行数最多的 30 个提交，占仓库总体积的比例高得不成比例。系统性地，这些提交在新增字符数上也是最大的。本来可预期，但这些提交的每行字符数也更啰嗦：跟函数名重复的解释性注释更多，错误处理块复制粘贴而不是抽出来，docstring 把同一件事换三种说法讲三遍。

这是跟 LLM 聊天时熟知的行为的直接后果：不显式要求简洁，它默认多说，解释，注释，换说法。聊天里这只费输出 token。写代码时，同样的习惯变成留在仓库里的行，一个提交一个提交攒，只要代码能跑就没人真重读。

## 两次审计并排放，得到什么

第一份报告：跨服务一致性死于上下文窗口太小装不下整个仓库，导致局部修改、冗余、规范分叉。

第二份：`git log --numstat` 显示没框过啰嗦的 LLM 默认有多话，导致新增行和新增字符不成比例地多，代码没有好好抽取复用。

合起来指向冗余和体积：仓库大到未来的智能体装不进脑子，这又加重第一次审计发现的第一个问题。

写报告时最让我不安的就是最后一行：两个问题相连，互相喂饭。生成的代码越啰嗦，仓库涨越快，涨越快智能体越装不进上下文，越装不进修得越局部越冗余，越冗余体积越大。负反馈环，全因用智能体没加框。

## 为什么不是某个具体工具的一次性 bug

诊断里没有任何东西绑定特定模型或产品。任何聊天型智能体都这样：在 T 时刻它只能操作你给它看到的东西，默认生成最完整、最 justified 的回答。这正是聊天助手该有的行为，也正是往生产仓库写东西时要避免的。缺的是工具和仓库之间的框：要看的文件范围、期望输出格式、行数或啰嗦预算、写新东西之前先引用已存在的东西的义务。

## 之后我改了什么

直觉反应是把写出来的东西大刀砍掉。我个人选择反着来。审计另有他用：扫代码找 code smell，用来精确定位真问题在哪。跨服务不一致、冗余、思路丢了的地方，而不是瞎猜。写出来的体积基本原样保留：啰嗦不啰嗦，用对地方就有用。杠杆是知道该看哪里去修对不上的地方，而不是拦着智能体写。

## 下一步

把仓库切成更小、边界更清的单元。再加生产执行的 guardrail 和文档。随之而来的问题是架构问题：拆开后服务、组件、文档怎么分析、互评、干净地协调决策，而不退回同一个单体。
