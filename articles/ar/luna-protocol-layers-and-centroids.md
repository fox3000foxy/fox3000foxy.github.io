# Luna Protocol : تجميع الأدمغة، والتصنيف العاطفي، والتوجيه ممتع/تافه

في [المقالين](/articles/fr/luna-protocol-discord-bot) [السابقين](/articles/fr/luna-protocol-official-models)، قدمت Luna Protocol كبوت Discord وحيد مع نظام سلوكي معقد ونموذج مضبوط. لكن البنية تطورت كثيرا منذ ذلك الحين. ما كان monolithe : عملية Node.js واحدة تدير في آن واحد بوت Discord والسلوك واستدعاءات LLM، تحول إلى **أربع طبقات مستقلة**، لكل واحدة مسؤوليتها ولغتها ودورة حياتها الخاصة.

جلب هذا الفصل فوائد غير متوقعة : تجميع "الأدمغة" بين عدة منصات، ونظام تصنيف عاطفي يضبط ديناميكيا معاملات LLM، وتوجيه ذكي للرسائل بين نموذجين حسب الأهمية المدركة للمحادثة.

لم يحدث التطور دفعة واحدة : بل اتبع مسارا عضويا. فصلت أولا مجلد `server/` عن مستودع البوت، منشئا **Krystal** من جهة وتاركا **Jade** كمحول Discord. ثم أنشأت **Pixieglow** (محول Matrix) مستعيدا `llm-core` وناقل الأحداث من Jade. ثم جاء **Sapphire** لإدخال تصنيف GENERIC/SEMANTIC مع DistilBERT. لم تكن النتائج مقنعة، فانتقلت إلى centroids الـembeddings، الأكثر قابلية للتشكيل لإثراء الأمثلة والأدق ؛ وصار التصنيف FUTILE/INTERESSANT. أضفت أخيرا centroids للـ**valence** والـ**arousal** لتنظيم حرارة LLM وrepeat penalty. وفي النهاية، أزحت كل الكود الزائد بين Jade وPixieglow بإنشاء **Emerald**، الدماغ المجمَّع، محوّلا Jade وPixieglow إلى مجرد عميلين يقودهما socket.

بالتوازي، حافظت على موقع ويب يروي تقدم المشروع : [protocol-luna.github.io](https://protocol-luna.github.io/).

يروي هذا المقال كيف ولماذا قطّعت هذه الطبقات، وماذا يفعل كل خدمة بالضبط، وكيف حوّلت مفاهيم مثل **centroids** (متجهات متوسطة للـembeddings) و**متغيرات الشعور** (المستوحاة من شاتبوت PARRY في السبعينيات) بوت Discord بسيطا إلى نظام متعدد المنصات متسق بشكل مدهش.

## المشكلة مع الـmonolithe

في البداية، كان Luna Protocol في عملية Node.js واحدة. كان الكود يدير :

- الاتصال بـDiscord (عبر مكتبة Eris)
- تقييم المحفزات (إشارات وكلمات مفتاحية ومتابعة...)
- محاكاة السلوكيات الإنسانية (أخطاء مطبعية وتردد ونوم...)
- استدعاءات HTTP لخادم LLM المحلي (llama.cpp)
- إدارة الجلسات ومكافحة السبام
- خط TTS

كان كل شيء في نفس العملية، يتواصل عبر نواقل أحداث مُنمَّطة (`TypedBus`). كان يعمل، لكن بحدود :

- **مستحيل إضافة عميل Matrix** دون تكرار كل كود السلوك
- **LLM والبوت في نفس المستودع** : مجلد `server/` موجود فعلا، لكن مستحيل تطوير أحدهما دون لمس الآخر
- **معالجة غير مميزة** : كل رسالة عولجت بنفس الطريقة، سواء كانت "lol" أو سؤالا وجوديا
- **فقدان عاطفي** : البوت لم "يشعر" بشيء

حلّ التقطيع إلى طبقات كل هذه المشاكل.

## الطبقات الأربع

البنية الحالية لـLuna Protocol منظمة كقمع من أربعة مستويات :

```
Matrix / Discord
      |
      v
  [ADAPTATEURS]      Pixieglow (Matrix) / Jade (Discord)
      |
      v
  [BRAIN]            Emerald (WebSocket, port 3126)
      |
      v
  [CLASSIFIEUR]      Sapphire (HTTP, port 3123)
      |
      v
  [INFERENCE]        Krystal (llama.cpp, ports 3124 / 3125)
```

يمكن إعادة تشغيل كل طبقة أو تحديثها أو استبدالها مستقلة.

### الطبقة 1 : المحولات (Pixieglow وJade)

وهي أبسط الطبقات. عملها الوحيد هو ترجمة أحداث منصة مراسلة إلى بروتوكول معياري نحو Emerald :

- **Jade** هو محول Discord. يستخدم مكتبة Eris للاتصال بـDiscord وتمرير الرسائل إلى Emerald عبر WebSocket. يدير أيضا خط TTS (تركيب صوتي عبر Piper، وتحويل إلى OGG، ورفع على Discord).
- **Pixieglow** هو محول Matrix. يستخدم Client-Server HTTP API الخاص بـMatrix مباشرة (دون SDK)، مع sync بالاستطلاع الطويل. لا TTS لديه.

يتشارك المحولان نفس بروتوكول WebSocket المعرّف في `emerald-client.ts` :

```typescript
type ClientId = "jade" | "pixieglow";

// أحداث (محول ← Emerald)
type InEvent = MessageEvent | ReadyEvent | BotMessageEvent | PresenceEvent;

// أوامر (Emerald ← محول)
type OutCommand = RespondCommand | TypingCommand | SetPresenceCommand
                | SpontaneousCommand | ForgotCommand;
```

يثبت وجود محولين بنفس الواجهة التجميع : **نفس "الدماغ" (Emerald) يخدم بلا تمييز بوت Discord وبوت Matrix**، بسلوكيات متطابقة. البروتوكول تصريحي : لا يقول Emerald للمحول *كيف* يرسل رسالة، بل يقول *ماذا* يرسل (النص مع مهلة، وربما خطة دفعة، وتفاعل، إلخ). ينفذ كل محول التنفيذ الملموس حسب منصته.

إنها قوة هذه البنية : لإضافة دعم Telegram أو Signal أو غيرهما، يكفي كتابة محول ينفذ بروتوكول WebSocket.

### الطبقة 2 : الدماغ (Emerald)

Emerald هو خدمة القرار المركزية. يستمع على المنفذ 3126 عبر WebSocket ويدير :

- **تقييم المحفزات** : إشارة ورسالة خاصة واسم وكلمة مفتاحية ومتابعة وعشوائي
- **المحاكاة السلوكية** : مهلات تركيز وأخطاء مطبعية وتردد ونسيان ودفعة وتعب موضوعي
- **دورات النوم** : أوضاع sleep / slow / short
- **إدارة الجلسات** : تهدئة وحدود جلسة ومكافحة سبام
- **التوجيه نحو Sapphire** : إرسال الرسائل، واستلام الردود المبثوثة

Emerald هو الخدمة المركزية التي أتاحت التجميع، وهي التي استفادت أكثر من الفصل. قبل ذلك، كان كل سلوك (خطأ مطبعي ودفعة وتردد) متشابكا مع كود Discord. الآن، هي في وحدات مخصصة في `behavior/` :

```
emerald/src/behavior/
  burst.ts         -- تخطيط الرسائل في دفعات
  mannerisms.ts    -- مهلات وتردد وتفاعلات ونسيان
  sleep.ts         -- تقييم جداول النوم
  typo.ts          -- محاكاة الأخطاء المطبعية (AZERTY/QWERTY)
```

لا يعرف الدماغ على أي منصة يعمل. يستلم `MessageEvent` مع `clientId` ("jade" أو "pixieglow")، ويتخذ قرارا، ويعيد أمرا. ويتكفل المحول بالباقي.

### الطبقة 3 : المصنف العاطفي (Sapphire)

Sapphire هو الخدمة الأكثر إثارة تقنيا. إنه **وسيط LLM** مكتوب بـPython مع FastAPI، ويلعب أربعة أدوار حاسمة :

1. **مصنف ثنائي FUTILE / INTERESSANT** عبر centroids الـembeddings
2. **مُحرِز عاطفي** (valence / arousal) عبر centroids
3. **موجّه backends** نحو Krystal (نموذج صغير ضد نموذج كبير)
4. **حاقن few-shot** ومدير جلسات

#### الـcentroids : قلب التصنيف

الـ**centroid** مفهوم بسيط : إنه متوسط مجموعة من متجهات الـembeddings. عمليا، جمعت مئات الأمثلة من الرسائل، ومررتها في نموذج embedding (`BAAI/bge-small-en-v1.5`، 384 بعدا)، وحسبت متوسط المتجهات الناتجة.

هناك **centroidان للتصنيف** :

- `futile_centroid` : ~683 رسالة تافهة ("lol" و"ok" و"hello") عبر k-means (k=10 وseed=42)
- `interessant_centroid` : ~678 رسالة جوهرية (تقنية وشخصية وفلسفية) عبر k-means (k=10 وseed=42)

عندما تصل رسالة :

```python
def classify(text, embedder, futile_centroids, interessant_centroids):
    emb = embedder.query_embed(text)                     # متجه 384-D
    sim_f = max(cos(emb, c) for c in futile_centroids)     # الأقصى على 10
    sim_i = max(cos(emb, c) for c in interessant_centroids) # الأقصى على 10
    diff = sim_i - sim_f
    label = "INTERESSANT" if diff > 0 else "FUTILE"
    return label, abs(diff), sim_f, sim_i
```

نتيجة كل فئة هي **أقصى تشابه جيبي** بين centroids العشرة. وهذا يلتقط الأنواع الفرعية في كل فئة : تحية ووداع يقعان كلاهما قرب واحد من centroids التافهة العشرة حتى لو كانا بعيدين في فضاء الـembedding. فقط k-means عند الإقلاع وجداءات نقطية عند التشغيل : دون تدريب، ودون GPU.

#### لماذا نموذجان ؟

تقرر نتيجة هذا التصنيف أي backend للـLLM يُستدعَى :

| التسمية | Backend الخاص بـKrystal | النموذج | المنفذ |
|-------|----------------|--------|------|
| `FUTILE` | `generic` | Luna-Protocol-1.5B (941 Mo وQ4_K_M) | 3124 |
| `INTERESSANT` | `semantic` | Hermes-3-3B أو 8B (حسب الإعداد) | 3125 |

الحدس بسيط : "lol" أو "nm just chillin u" لا تستحق استدعاء نموذج من 8 مليارات معامل. النموذج الصغير المضبوط Luna 1.5B، المدرَّب على 200 000 عينة Discord، يكفي إلى حد كبير للتبادلات الخفيفة. بينما سؤال عن الحياة أو اعتراف أو نقاش تقني يُوجَّه نحو النموذج الكبير الذي يستطيع إنتاج رد أغنى.

يقلل هذا التوجيه الاقتصادي الحمل على خادم LLM كثيرا : حوالي 70% من الرسائل تُصنَّف FUTILE وتُعالَج بالنموذج الصغير، محرِّرة النموذج الكبير للمحادثات التي تستحق فعلا.

#### المحور العاطفي : valence وarousal

لكن هذا ليس كل شيء. يستخدم Sapphire **نفس آلية centroids** على محور مستقل لتقييم عاطفة الرسالة :

هناك **أربعة centroids عاطفية** :

| القطب | أمثلة |
|------|----------|
| `positive` | "hell yeah" و"love that" و"this is great" |
| `negative` | "shut up" و"i hate this" و"this sucks" |
| `high_arousal` | "WHAT THE HELL" و"omg omg omg" و"AAAAA" |
| `low_arousal` | "just chilling" و"meh" و"i guess" |

يُحسب الرصيد كفرق تشابه على كل محور :

```python
valence = sim(emb, positive) - sim(emb, negative)     # [-1, +1]
arousal = sim(emb, high_arousal) - sim(emb, low_arousal)  # [-1, +1]
```

تقيس **Valence** إن كانت الرسالة إيجابية أو سلبية. وتقيس **Arousal** شدتها العاطفية. معا، تشكلان نموذج circumplex للوجدان (Russell، 1980)، نفس النموذج النفسي الذي ألهم شاتبوت **PARRY** في 1972.

#### متغيرات الشعور : كيف تتحكم العواطف في LLM

هنا يصبح إلهام PARRY ملموسا. PARRY (أنشأه Kenneth Colby في 1972) كان الشات بوت PARRY مصمما لمحاكاة مريض مصاب بالبارانويا. كان يملك متغيرات داخلية (خوف وغضب وارتياب) تعدّل ردوده. فمثلا PARRY "الخائف" كان يرد بطريقة أكثر عدوانية.

يفعل Sapphire الشيء نفسه، لكن بمتغيرات مستمرة وطريقة أكثر أناقة : تُضبط معاملات أخذ عينات LLM في الوقت الحقيقي حسب الحالة العاطفية للمحادثة.

##### الحرارة تتبع arousal

```python
temperature = clamp(0.7 + arousal * 0.3, 0.4, 1.0)
```

| Arousal | الحرارة | الأثر |
|---------|-------------|-------|
| -1.0 (هادئ) | 0.40 | إبداعية منخفضة، وردود متوقعة |
| 0.0 (محايد) | 0.70 | إبداعية افتراضية |
| +1.0 (متحمس) | 1.00 | أقصى عشوائية، وردود مفاجئة |

عندما يكون شخص متحمسا أو غاضبا (arousal مرتفع)، ترتفع الحرارة. ينتج النموذج ردودا أكثر تنوعا وإبداعية، وأحيانا أكثر فوضوية، كإنسان "يتحمس". وعندما تكون المحادثة هادئة، تنخفض الحرارة، والردود أكثر رزانة.

##### repeat penalty يتبع valence

```python
repeat_penalty = clamp(1.15 - valence * 0.1, 1.0, 1.3)
```

| Valence | Repeat Penalty | الأثر |
|---------|---------------|-------|
| -1.0 (سلبي) | 1.25 | عقوبة قوية، تتجنب التكرارات |
| 0.0 (محايد) | 1.15 | القيمة الافتراضية |
| +1.0 (إيجابي) | 1.05 | عقوبة ضعيفة، تسمح بالتكرارات |

كلما كانت المحادثة أكثر سلبية، دُفع النموذج أكثر لتجنب تكرار نفسه، كشخص يبحث عن كلماته في جدال متوتر. وكلما كانت أكثر إيجابية، استطاع النموذج السماح بتأكيدات زائدة، كمحادثة مسترخية.

##### الحالة العاطفية التراكمية

لا تحمل هذه الدرجات الرسالة الفورية فقط. يحافظ `EmotionState` على **متوسط متحرك أسّي** للـvalence والـarousal لكل جلسة :

```python
class EmotionState:
    def __init__(self, decay=0.85, deadzone=0.06):
        self.decay = decay
        self.deadzone = deadzone

    def update(self, key, valence_delta, arousal_delta):
        if abs(valence_delta) < self.deadzone:
            valence_delta = 0.0
        if abs(arousal_delta) < self.deadzone:
            arousal_delta = 0.0
        s = self._state.setdefault(key, {"valence": 0.0, "arousal": 0.0})
        s["valence"] = s["valence"] * self.decay + valence_delta * (1 - self.decay)
        s["arousal"] = s["arousal"] * self.decay + arousal_delta * (1 - self.decay)
        return s
```

يعني `decay` عند 0.85 أن 85% من الحالة السابقة تُحفَظ مع كل رسالة، و15% من الإشارة الجديدة تُدمَج. وهذا يعطي **ذاكرة عاطفية** تملّس التغيرات العنيفة : رسالة سلبية واحدة لا تجعل البوت "حزينا"، لكن سلسلة رسائل سلبية تحرف مزاجه تدريجيا.

عمليا : إذا بدأ شخص محادثة بطريقة متحمسة جدا (`arousal=+0.8`)، تبقى الحرارة مرتفعة لعدة تبادلات، حتى لو كانت الرسائل التالية أهدأ. تستغرق العاطفة وقتا لتهدأ، كإنسان يبقى "ساخنا" بعد جدال.

### الطبقة 4 : الاستدلال (Krystal)

Krystal هي الطبقة الدنيا : غلاف حول `llama.cpp` يعرض API متوافقة مع OpenAI (`/v1/chat/completions`). يعمل في نسختي PM2 :

- `krystal-small` : نموذج Luna 1.5B المضبوط، على المنفذ 3124، مع تقارب CPU 0
- `krystal-large` : نموذج Hermes 3B، على المنفذ 3125، مع تقارب CPU 0,1

النسختان عمليتا `llama-server` مُجمَّعتين مسبقا، تُطلقان مع `taskset` لتثبيت CPU.

تطور ضبط نموذج Luna هو أيضا منذ المقال الثاني : صار مدرَّبا على **200 000 عينة** (مقابل 50 000 سابقا)، دائما انطلاقا من Qwen2.5-1.5B-Instruct عبر QLoRA. عينات الـ200k مجموعة فرعية من طقم Discord-Dialogues، مُرشَّحة للاحتفاظ بالمحادثات الأكثر طبيعية وتنوعا. الهدف : توسيع السجل الأسلوبي للنموذج دون فقدان المرونة التي تجعل التمهيد few-shot فعالا جدا.

## المخطط الكامل : رسالة في transit

إليكم ما يحدث عمليا عندما يرسل شخص "أنا حزين فعلا اليوم" على Discord :

1. يستلم **Jade** الرسالة عبر Discord Gateway API. يحوّلها إلى `MessageEvent` ويرسلها إلى Emerald عبر WebSocket.
2. يقيّم **Emerald** المحفز (إشارة ؟ اسم ؟ كلمة مفتاحية ؟). إنها إشارة مباشرة. يحسب مهلة تركيز، ويتحقق من التهدئة والجلسة والتعب الموضوعي. يقرر الرد ويرسل الرسالة إلى Sapphire عبر HTTP.
3. يضمّن **Sapphire** الرسالة مع `bge-small-en-v1.5`.
    - التصنيف : الرسالة أقرب إلى centroid الـ`interessant` من centroid الـ`futile` (diff = +0.31) ← **INTERESSANT**
    - العاطفة : valence سلبية (-0.42)، وarousal معتدل (0.35)
    - التوجيه : اتجاه `KRYSTAL_SEMANTIC_URL` (منفذ 3125، نموذج كبير)
    - معاملات أخذ العينات : الحرارة = 0.80 (arousal مرتفع)، وrepeat_penalty = 1.19 (valence سلبية)
    - تُحدَّث الحالة العاطفية للجلسة بهذه القيم
4. يولّد **Krystal** (النسخة الكبيرة) الرد بالمعاملات المضبوطة عاطفيا ويعيده إلى Sapphire.
5. يبث **Sapphire** الرد نحو Emerald مع البيانات الوصفية (التسمية والـvalence والـarousal وإحصاءات التصحيح).
6. يقرر **Emerald** إضافة تردد ("oh...")، ويخطط دفعة (جزأين)، ويختار تفاعلا. يرسل `RespondCommand` إلى Jade.
7. ينفذ **Jade** : ينتظر المهلة الأولية، ويرسل الجزء الأول مع التردد، وينتظر 1.5s، ويرسل الجزء الثاني. يعرض مؤشر الكتابة طوال التوليد.

كل ذلك في أقل من 3 ثوانٍ للمستخدم.

## الـcentroids : لماذا أفضل من مصنف عصبي

يستحق اختيار centroids الـembeddings بدلا من مصنف تقليدي (مثل DistilBERT الذي كنت أستخدمه قبل ذلك) تفسيرا.

يتعلم المصنف العصبي حد قرار بين الفئات، عادة تحويلا غير خطي يسقط المدخلات نحو احتمالات. إنه دقيق، لكن :

- يتطلب بيانات تدريب موسومة
- حساس لتغير التوزيع (data drift)
- صعب التفسير
- يجب إعادة تدريبه لإضافة فئة جديدة

أما الـcentroid، فهو **متجه متوسط** لـembeddings أمثلة. يتم التصنيف بالتشابه الجيبي مع هذا المتجه المتوسط. المزايا :

- **لا تدريب مطلوب** : نحسب فقط متوسط embeddings أمثلة مختارة يدويا
- **سهل التفسير** : يمكن النظر لأي أمثلة أقرب للـcentroid لفهم "ما تعلمه الـcentroid"
- **إضافة فئة** : نضيف فقط centroid جديدا، دون إعادة تدريب
- **متين** : الـcentroid متوسط، لذا القيم الشاذة قليلة الأثر

القوة الحقيقية للـcentroids أنها تحوّل مشكلة تصنيف إلى مشكلة **قياس مسافة مكانية**. يمكن تصور الفئات كمناطق في فضاء من 384 بعدا (أو في 2D/3D بعد اختزال الأبعاد PCA/t-SNE).

### تصور ثلاثي الأبعاد للـcentroids

عمليا، إليكم كيف تبدو centroids التصنيف في فضاء الـembedding. كل نقطة رسالة مثال، مسقطة ثلاثية الأبعاد بـPCA (الأبعاد الأصلية الـ384 تُختزَل إلى 3 للتصور). النقاط الزرقاء رسائل تافهة، والنقاط الصفراء رسائل ممتعة. **علامات المعين الـ20** هي centroids الـk-means (10 لكل فئة، seed=42). مرر الفأرة فوق نقطة لرؤية نص المثال الأصلي.

مثالا الاختبار معروضان بالأحمر : "lol" (مصنف تافه) و"i feel sad today" (مصنف ممتع). حتى بعد الاختزال من 384 إلى 3 أبعاد (14,7% من التباين المفسَّر)، العنقودان منفصلان بوضوح. يظهر التعليق في الأعلى الأعداد الدقيقة والمنطقة الغامضة.

يتجول centroid رسالة المدخلات في هذا الفضاء حسب محتواها. يقتصر تصنيف FUTILE/INTERESSANT ببساطة على قياس أي centroid أقرب بالتشابه الجيبي. ويمكننا هكذا تمثيل كل رسالة كنقطة في فضاء متعدد الأبعاد، كل بعد يقابل خاصية دلالية.

## ما الذي يغيره عمليا

لا يرى المستخدمون الطبقات والـcentroids وضبط الحرارة. لكنهم يشعرون بالآثار :

- **ردود أسرع** للرسائل البسيطة (النموذج الصغير أسرع بمرتين ويدير 70% من الترافيك)
- **نبرة متكيفة** : إذا كنت غاضبا، "يشعر" البوت بالغضب ويكيّف أسلوبه
- **اتساق عبر المنصات** : بوت Matrix وبوت Discord يتشاركان نفس الدماغ ونفس الحالة العاطفية
- **نبرة أصيلة محفوظة** : الضبط + few-shot + التوجيه الذكي يتجنب الردود المؤسساتية

عزز الانتقال إلى 200k عينة تدريب للنموذج الصغير هذه الآثار أكثر : يلتقط النموذج تنوع محادثات Discord أفضل دون فقدان القابلية للتشكيل التي يتيحها التمهيد few-shot.

## الخلاصة

لم يكن تقسيم Luna Protocol إلى أربع طبقات مجرد تمرين بنية. بل كان جوابا على حدود ملموسة : استحالة دعم Matrix، وغياب الوعي العاطفي، وغياب ترتيب ذكي للرسائل.

اليوم، النظام أكثر متانة (انهيار LLM لا يقتل البوت)، وأكثر قابلية للتوسع (محول Telegram أو WhatsApp سيتبع نفس بروتوكول WebSocket)، وأكثر "حياة" : يكيّف البوت سلوكه ونبرته، وحتى معاملات LLM، مع الحالة العاطفية المدركة للمحادثة.

centroids الـembeddings هي العنصر الأساسي الذي يجعل كل هذا ممكنا دون تعقيد مفرط : لا شبكة عصبية مُدرَّبة، ولا خط بيانات موسومة، فقط متوسطات متجهات وتشابهات جيبية. إنها تقنية بسيطة، وفعالة بشكل لا يصدق، ومُقلَّل من شأنها بشكل رهيب.
