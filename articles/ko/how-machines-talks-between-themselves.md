# 문제: 약어는 많고 위계는 부족해요

TCP, UDP, TLS, mTLS, WebSocket, HTTP, HTTPS, gRPC, QUIC. 이들을 다루는 대부분의 자료는 "쓰임에 따라 고르라"며 평평하고 바꿔 쓸 수 있는 선택지 목록으로 보여줘요. 실제로는 같은 층에 있지 않아요. 어떤 것은 전송 프로토콜이고, 어떤 것은 전송을 감싸는 보안 층이고, 또 어떤 것은 앞의 둘 위에 얹는 애플리케이션 프로토콜이에요. 위계를 이해하는 것이 TCP와 TLS 사이에서 "고르지" 않는 이유를 이해하는 거예요. TCP를 고른 뒤 위에 TLS를 올릴지 정해요.

이 글은 그 위계를 층마다 다시 쌓아요. 날것 전송에서 상호 인증까지요. 각 수준마다 보장하는 것과 보장하지 않는 것, 그리고 언제 그 수준으로 충분한지 함께요.

# 수준 1: 전송 (TCP 대 UDP)

모든 것이 여기서 시작해요. TCP와 UDP는 OSI 모델의 **전송 (4계층)** 프로토콜 두 가지예요. 역할은 같아요. 서로 다른 기기에서 돌아가는 두 애플리케이션 사이에 자료 흐름을 나르는 거예요. 그런데 해내는 방식이 근본적으로 달라요.

네트워크 계층(3계층)의 IP(Internet Protocol)는 패킷을 한 호스트에서 다른 호스트로 나를 뿐임을 이해하는 것이 중요해요. 도착도 순서도 유일함도 보장하지 않아요. 라우터는 각 패킷마다 독립적인 라우팅 결정을 내릴 뿐이에요.

보장 부재를 메우는 것이 바로 TCP이고, UDP는 극도로 가볍게 남으려고 일부러 아무것도 더하지 않아요.

## TCP: 믿을 수 있음이 먼저

TCP(Transmission Control Protocol)는 **연결 지향**(_connection-oriented_) 프로토콜이에요. 자료 1바이트를 주고받기 전에 두 기기가 논리적 연결을 맺어야 해요.

이 연결은 유명한 **Three-Way Handshake**로 만들어져요.

```

Client                           Serveur
SYN ---------------------------->
        <--------------------- SYN + ACK
ACK ---------------------------->
Connexion établie
```

각 단계에는 정확한 목표가 있어요.

*   SYN: 클라이언트가 연결을 열고 싶다고 알리고 첫 순서 번호(Initial Sequence Number - ISN)를 줘요.

*   SYN-ACK: 서버가 연결을 받아들이고 SYN을 확인하며 차례로 자신의 순서 번호를 줘요.

*   ACK: 클라이언트가 서버 정보 수신을 확인해요.


이 순간부터 두 기기는 연결 상태를 알고 자료를 주고받기 시작할 수 있어요.

### **순서 번호**

TCP는 자료를 패킷 연속이 아니라 **끊기지 않는 바이트 흐름**(_byte stream_)으로 봐요.

보내는 각 바이트에 순서 번호가 있어요.

예시:

```
메시지:

Bonjour

B = 바이트 0
o = 바이트 1
n = 바이트 2
...
```

1000번에서 1499번 바이트가 든 세그먼트가 전송 중에 사라지면 수신자가 정확히 무엇이 없는지 감지할 수 있어요.

송신자는 그 부분만 다시 보내요.

이 세밀함이 TCP 강건함의 이유 중 하나예요.

### **수신 확인 (ACK)**

자료를 받은 뒤 수신자가 **ACK (Acknowledgment)**를 보내요.

흔히 생각하는 것과 달리 ACK의 뜻은 이것이 아니에요.

> "이 패킷을 받았어요"

오히려 뜻은요.

> "X번까지의 바이트를 모두 받았어요."

예를 들어요.

```
클라이언트가 보내요:

0 → 999

서버가 답해요:

ACK = 1000
```

뜻은요.

> "1000번 바이트 앞의 모든 것이 잘 도착했어요."

이 구조로 여러 세그먼트를 한 번에 확인(_cumulative acknowledgments_)해서 제어 패킷 수를 줄여요.

### **재전송**

ACK이 절대 오지 않으면 TCP는 세그먼트가 사라졌다고 봐요.

자동으로 다시 보내요.

재전송 대기 시간(**Retransmission Timeout – RTO**)은 고정되지 않아요.

받은 ACK로 TCP는 왕복 시간(**RTT**)을 계속 재고, 쓸데없는 재전송을 피하려고 RTO를 동적으로 계산해요.

현대 구현은 **Fast Retransmit** 같은 구조도 써요. 송신자가 중복 ACK를 여러 번(보통 셋) 받으면 중간 세그먼트 하나가 사라졌다고 보고, 타이머 만료를 기다리지 않고 바로 다시 보내요.

### **패킷 재정렬**

두 패킷이 같은 길을 따른다고 인터넷은 전혀 보장하지 않아요.

예시:

```
패킷 1
Paris
  ↓
Londres
  ↓
New York

패킷 2
Paris
  ↓
Francfort
  ↓
Chicago
  ↓
New York
```

두 번째 패킷이 첫 번째보다 먼저 도착할 수 있어요.

그러면 TCP가 순서 밖에 도착한 세그먼트들을 버퍼(_reassembly buffer_)에 잠시 저장했다가 애플리케이션에 건네기 전에 다시 조립해요.

애플리케이션 보기에는 모든 것이 완벽한 순서로 도착하는 것처럼 보여요.

### 흐름 제어

연결은 네트워크에만 달려 있지 않아요.

수신자도 메모리 용량이 제한되어 있어요.

처리할 수 있는 것보다 빨리 받으면 버퍼가 결국 포화돼요.

TCP는 **슬라이딩 윈도 (Sliding Window)**로 이 문제를 풀어요.

수신자는 각 ACK에 이렇게 알려줘요.

```
Window = 32768 octets
```

뜻은요.

> "32KB까지 더 보내도 돼요."

이 창이 0이 되면요.

```
Window = 0
```

송신자는 수신자가 새 가용 창을 알릴 때까지 전송을 잠시 멈춰요.

이 구조가 **흐름 제어 (Flow Control)**이고, 빠른 호스트가 느린 호스트를 넘치게 하는 것을 막아요.

### 혼잡 제어

수신자가 자료를 받아낼 수 있어도 네트워크 자체가 포화될 수 있어요.

라우터에는 제한된 대기열(_queues_)이 있어요.

넘치면 패킷이 버려져요.

TCP는 손실을 혼잡 신호로 보고 **혼잡 윈도 (Congestion Window – cwnd)**로 속도를 자동으로 맞춰요.

현대 알고리즘(운영체제에 따라 **Reno**, **CUBIC**, **BBR**)이 최대 속도와 네트워크 안정 사이 균형을 찾으려고 이 창을 조정해요.

초기 TCP 버전은 주로 두 가지 구조를 썼어요.

*   **Slow Start**: 혼잡을 감지할 때까지 속도를 지수적으로 올려요.

*   **Congestion Avoidance**: 그 뒤에는 더 조심스럽게, 보통 선형으로 키워요.


이 영속 적응이 네트워크 품질 변화에도 TCP가 성능을 유지하는 이유 중 하나예요.

### 연결 닫기

UDP와 달리 TCP 연결에는 깔끔한 닫기도 있어요.

각 끝이 **FIN** 깃발로 자기 흐름을 독립적으로 닫아요.

완전한 닫기에는 보통 네 번 교환이 필요해요.

```
FIN
ACK
FIN
ACK
```

이 절차는 연결을 없애기 전에 전송 중 자료가 모두 잘 배달됐음을 보장해요.

## UDP: 최대한 단순

UDP(User Datagram Protocol)는 반대 철학을 써요.

**비연결형 (connectionless)**이에요.

존재하지 않아요.

*   핸드셰이크 없음;

*   순서 번호 없음;

*   수신 확인 없음;

*   재전송 없음;

*   흐름 제어 없음;

*   혼잡 제어 없음.


각 메시지는 독립 **데이터그램**에 그냥 캡슐화되어 네트워크로 보내지고, 송신자는 잊어버려요.

```
Application → Datagramme UDP → IP → Internet
```

프로토콜은 두 번 보내기 사이에 상태를 유지하지 않아요.

각 데이터그램은 앞선 것들과 완전히 독립적이에요.

### 자료 무결성

UDP는 배달도 순서도 보장하지 않지만, **체크섬**으로 자료 무결성은 지켜요.

수신하면 체크섬을 다시 계산해요.

*   값이 맞으면 데이터그램을 받아들여요.

*   아니면 바로 버려요.


그래서 UDP는 망가진 자료를 감지하지만, 되찾으려고 절대 시도하지 않아요.

### UDP가 왜 이렇게 빠른가요?

UDP 헤더는 **8바이트**뿐이고, TCP는 최소 **20바이트**예요 (타임스탬프, SACK, 윈도 스케일링 같은 옵션 제외).

유지되는 연결이 없으니 운영체제가 각 교환 상태를 따라갈 필요가 없어서 메모리 소비와 처리 비용도 줄어요.

애플리케이션은 혹시 모를 재전송을 기다리지 않고 도착하자마자 거의 바로 자료를 받아요.

## 자료를 잃는 것이 나을 때

기본 생각은 단순해요.

> 오래된 정보는 사라진 정보보다 가치가 떨어질 수 있어요.

VoIP 통화를 가져와요.

각 패킷은 약 **20ms** 음성을 나르요.

패킷 하나가 사라지면 다시 보내는 데 이 20ms보다 오래 걸리는 경우가 많아요.

겨우 도착했을 때는 대화가 이미 앞으로 나아가 있어요.

대부분 애플리케이션은 재전송을 기다리기보다 손실 가리기(보간, 무음, 오류 정정)를 택해요.

같은 논리가 적용돼요.

*   실시간 멀티플레이어 게임;

*   비디오 스트리밍;

*   텔레메트리 흐름;

*   IoT 센서;

*   GPS 위치 자료.


최근 값은 완벽히 믿을 만한 오래된 값보다 거의 항상 유용해요.

# 수준 2: 암호화, TLS

TLS(Transport Layer Security, SSL의 후계자)는 TCP를 대신하지 않고 위에 얹어요. 구체적으로 TLS는 정상 TCP 연결을 맺은 뒤 안에 암호화된 세션을 협상해요. 인증서 교환, 암호화 알고리즘 합의, 세션 키 유도. 그 뒤에 지나가는 모든 것은 암호화되고 인증돼요.

흔히 섞이는 세 가지 서로 다른 보장:

*   **기밀성**: 두 당사자 말고는 누구도 내용을 읽을 수 없어요.

*   **무결성**: 전송 중 자료 변경은 모두 감지돼요.

*   **인증**: 하지만 고전 TLS에서는 단방향이에요. 클라이언트는 서버가 말하는 그 사람인지 확인해요 (신뢰할 수 있는 기관이 서명한 인증서 경유). 서버는 클라이언트 신원에 대해 아무것도 확인하지 않아요. 사이트에 들어갈 때 HTTPS 모델이 정확히 그거예요. 브라우저는 사이트를 인증하고, 사이트는 여러분을 인증하지 않아요 (사용자 인증은 별도 구조, 세션 쿠키와 토큰으로 지나가요).


TLS 1.3(현재 권장 버전)은 흔한 경우 핸드셰이크를 한 번 왕복으로 줄였어요. TLS 1.2의 두 번과 달라서 연결 지연을 눈에 띄게 줄여요.

## 수준 2bis: mTLS. 인증이 상호가 돼요

mTLS(mTLS)는 제약 하나가 더 붙은 TLS예요. 서버도 클라이언트 인증서를 요구하고 확인해요. 양쪽이 공통으로 신뢰하는 기관이 서명한 인증서로 신원을 증명해요.

분산 아키텍처에서 서비스 대 서비스 통신의 자연스러운 구조예요. 고전 HTTPS가 브라우저와 공개 서버 대화에 충분하다면, mTLS는 다른 질문에 답해요. 내부 서비스는 어떻게 상대가 허용된 다른 내부 서비스인지, 네트워크에 들어온 공격자가 아닌지 알 수 있을까요?

```
Client                                          Serveur
  │──── ClientHello ─────────────────────────────▶│
  │◀─── ServerHello + certificat serveur ──────────│
  │──── vérifie le certificat serveur ─────────────│
  │──── envoie SON PROPRE certificat client ──────▶│
  │◀─── vérifie le certificat client ───────────────│
  │──── clés de session dérivées, canal chiffré ──▶│
```

mTLS의 대가는 운영이에요. 내부 인증 기관(CA)과 각 서비스에 인증서를 나눠주는 구조, 교체와 폐기 전략이 필요해요. 서비스가 적은 단일 기기 환경에서는 이득보다 복잡함이 클 때가 있어요. 서비스 사이 트래픽이 완전히 통제하지 못하는 네트워크를 지날 때(여러 호스트, 멀티테넌트 클라우드)부터, 또는 네트워크 "안"에 있다는 이유만으로 어떤 서비스도 암묵적으로 믿지 않는 제로 트러스트 정책을 원할 때부터 mTLS가 필요해져요.

# 수준 3: TCP와 TLS 위의 애플리케이션 프로토콜

전송과 암호화가 자리 잡으면 남은 것은 교환을 어떻게 구조화할지 정하는 거예요. 애플리케이션 프로토콜의 역할이에요.

## HTTP와 HTTPS

HTTP는 요청-응답 프로토콜이에요. 클라이언트가 연결을 열고 (킵얼라이브로 재사용해요), 요청을 보내고, 응답을 기다려요. 연결은 그 뒤에 닫히거나 재사용될 수 있어요. HTTPS는 TLS 위의 HTTP일 뿐이에요. S는 프로토콜 의미를 바꾸지 않고, 전송이 암호화된다는 것만 바꿔요.

요청-응답 모델에는 구조적 한계가 있어요. 서버는 먼저 말할 수 없어요. 클라이언트가 묻는 것에만 답할 수 있어요. 잦은 폴링("새 것 있어요?"를 1초마다 확인)에 동작하지만 자원을 낭비해요. 매 요청이 프로토콜 오버헤드를 새로 만들고, 대부분은 알릴 새 것이 없어요.

## WebSocket (WS와 WSS)

WebSocket은 바로 이 한계에 답해요. 연결은 고전 HTTP 요청으로 시작해요 (`Upgrade: websocket` 헤더와 함께). 하지만 핸드셰이크가 받아들여지면 밑바탕 TCP 연결은 더 이상 HTTP 요청-응답 채널이 아니에요. 클라이언트와 서버가 언제든 메시지를 보낼 수 있는 전이중 양방향 채널이 돼요. 매 교환마다 요청-응답 사이클을 다시 내지 않아도요.

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

WSS는 TLS 위의 WebSocket일 뿐이고, HTTPS가 TLS 위의 HTTP인 것과 똑같아요. 서버 푸시가 실시간으로 필요한 모든 것의 선택 프로토콜이에요. 채팅, 알림, 트레이딩 흐름, 게임 이벤트. 날것 TCP 위에 바이너리 프로토콜을 직접 다루고 싶지 않을 때요.

## gRPC

마이크로서비스 세상 밖에서는 덜 알려졌지만 서비스 대 서비스 통신의 중심이에요. gRPC는 HTTP/2에 기대고(그래서 TCP와 선택적 TLS), 메시지를 Protocol Buffers(이진, 타입 있음, 간결. 대부분 REST API의 텍스트 JSON과 달라요)로 직렬화하고, HTTP/2 멀티플렉싱 덕분에 양방향 스트리밍을 네이티브로 허용해요 (하나의 TCP 연결에 여러 논리 흐름, 여러 순차 HTTP/1.1 요청이 가질 head-of-line 블로킹 없이).

## QUIC와 HTTP3

QUIC는 전송 수준에서 TCP가 아니라 UDP에서 다시 시작하면서 판을 바꿔요. TCP가 네이티브로 주던 믿을 만함 보장을 위에 다시 구현해요. 하지만 전체가 아니라 흐름별로요. 그래서 전송 수준 head-of-line 블로킹이 사라져요 (한 흐름의 손실 패킷이 같은 연결의 다른 흐름을 더 이상 막지 않아요). TLS 1.3은 위에 얹지 않고 QUIC 안에 직접 통합돼서 핸드셰이크 지연을 더 줄여요. HTTP/3은 QUIC 위의 HTTP예요.

# 전체 보기: 각 프로토콜의 자리

| 층 | 프로토콜 | 역할 |
|---|---|---|
| 전송 | TCP, UDP | 바이트 나르기, 믿을 만하거나 아니거나 |
| 전송 (새 세대) | QUIC | UDP + 흐름별 믿을 만함 + 통합 TLS |
| 보안 | TLS, mTLS | 암호화, 무결성, 인증 (단방향 또는 상호) |
| 애플리케이션 | HTTP/HTTPS, WS/WSS, gRPC | 교환 구조화 (요청-응답, 양방향, 타입 RPC) |

생각을 굳히는 구체 예시예요. 웹 대시보드와 내부 서비스가 있는 마이크로서비스 아키텍처는 HTTPS(대시보드와 공개 API 사이, 브라우저 쪽 단방향 인증이면 충분), mTLS(내부에서 서비스와 서비스 사이, 상호 인증 필요), WSS(대시보드로 미는 실시간 알림) 조합이 합리적일 수 있어요. 서로 다른 애플리케이션 프로토콜 셋이지만 모두 같은 TCP와 TLS 토대 위에 지어져요.

## 실제로 고르기

보통 세 가지 질문이면 정해져요.

1.  **믿을 만함과 순서가 필요한가요, 아니면 보장된 배달보다 자료 신선함이 우선인가요?** → 예라면 TCP, 아니면 UDP (또는 다른 절충으로 둘 다 원하면 QUIC).

2.  **서버가 메시지를 먼저 보낼 수 있어야 하나요, 아니면 클라이언트가 항상 먼저 요청하나요?** → 서버가 밀어야 하면 WebSocket과 gRPC 스트리밍, 아니면 고전 HTTP.

3.  **양쪽이 서로 신원을 증명해야 하나요, 아니면 한쪽만 확인되면 되나요?** → 제로 트러스트 환경의 서비스 대 서비스에는 mTLS, 고전 공개 클라이언트에는 단순 TLS.


추가되는 층마다 운영 복잡함이 커져요. 날것 TCP에는 관리할 인프라가 없고, TLS에는 인증서가 필요하고, mTLS에는 CA와 교체 전략이 필요하고, gRPC에는 공유 Protobuf 스키마 정의가 필요해요. 밑 층이 구체적 한계를 보일 때만 복잡함을 올리는 것이 좋은 반사 행동이지, 미리 올리는 것이 아니에요.
