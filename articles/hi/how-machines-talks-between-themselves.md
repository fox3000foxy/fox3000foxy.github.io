# समस्या : बहुत सारे संक्षिप्त, पदानुक्रम कम

TCP, UDP, TLS, mTLS, WebSocket, HTTP, HTTPS, gRPC, QUIC; ज्यादातर संसाधन जो इनकी बात करते हैं उन्हें विनिमेय विकल्पों की सपाट सूची के रूप में पेश करते हैं, "उपयोग मामले के अनुसार चुनने को"। वास्तव में वे एक ही तल पर नहीं हैं : कुछ परिवहन प्रोटोकॉल हैं, दूसरे सुरक्षा परतें हैं जो परिवहन के चारों ओर लिपटती हैं, और अन्य applicative प्रोटोकॉल हैं जो पहले दोनों पर निर्भर हैं। पदानुक्रम समझना यह समझना है कि हम TCP और TLS के बीच कभी "चुनते" नहीं: हम TCP चुनते हैं, _फिर_ तय करते हैं कि ऊपर TLS रखना है या नहीं।

यह लेख इस पदानुक्रम को परत दर परत फिर से बनाता है, कच्चे परिवहन से पारस्परिक प्रमाणीकरण तक, हर स्तर के लिए : वह क्या गारंटी देता है, वह क्या गारंटी नहीं देता, और कब उसी से संतोष करना है।

# स्तर 1 : परिवहन (TCP बनाम UDP)

सब यहाँ शुरू होता है। TCP और UDP OSI मॉडल की **परिवहन (Layer 4)** परत के दो मुख्य प्रोटोकॉल हैं। उनकी भूमिका समान है : अलग मशीनों पर चल रहे दो application के बीच डेटा प्रवाह पहुँचाना। फिर भी, वहाँ पहुँचने का उनका तरीका मौलिक रूप से अलग है।

यह समझना महत्वपूर्ण है कि IP (Internet Protocol), नेटवर्क परत (Layer 3) पर स्थित, सिर्फ एक host से दूसरे तक पैकेट पहुँचाता है। वह न उनकी पहुँच गारंटी देता है, न उनका क्रम, न उनकी अद्वितीयता भी। router हर पैकेट के लिए स्वतंत्र routing निर्णय लेते हैं।

ठीक गारंटियों की यही अनुपस्थिति है जिसकी भरपाई TCP करता है, जबकि UDP जानबूझकर अत्यंत हल्का रहने के लिए कुछ नहीं जोड़ना चुनता है।

## TCP : विश्वसनीयता पहले

TCP (Transmission Control Protocol) एक **कनेक्शन उन्मुख** (_connection-oriented_) प्रोटोकॉल है। डेटा का एक भी octet आदान प्रदान करने से पहले, दोनों मशीनों को तार्किक कनेक्शन स्थापित करना होगा।

यह कनेक्शन प्रसिद्ध **Three-Way Handshake** से बनता है :

```

Client                           Serveur
SYN ---------------------------->
        <--------------------- SYN + ACK
ACK ---------------------------->
Connexion établie
```

हर चरण का सटीक उद्देश्य है :

*   SYN : client घोषणा करता है कि वह कनेक्शन खोलना चाहता है और पहला अनुक्रम संख्या (Initial Sequence Number - ISN) देता है।

*   SYN-ACK : serveur कनेक्शन स्वीकार करता है, SYN की प्राप्ति स्वीकार करता है और अपनी ओर से अपना अनुक्रम संख्या देता है।

*   ACK : client serveur की जानकारी की प्राप्ति पुष्टि करता है।


इस क्षण से, दोनों मशीनें कनेक्शन स्थिति जानती हैं और डेटा आदान प्रदान शुरू कर सकती हैं।

### **अनुक्रम संख्याएँ**

TCP डेटा को पैकेटों के क्रम के रूप में नहीं देखता, बल्कि **octet की सतत धारा** (_byte stream_) के रूप में देखता है।

भेजे गए हर octet की अनुक्रम संख्या होती है।

उदाहरण :

```
संदेश :

Bonjour

B = octet 0
o = octet 1
n = octet 2
...
```

अगर परिवहन के दौरान octet 1000 से 1499 वाला खंड खो जाता है, तो प्राप्तकर्ता बिल्कुल पहचान सकता है कि क्या छूटा है।

प्रेषक सिर्फ वही हिस्सा फिर से भेजता है।

यह दानेदारी TCP की मजबूती के कारणों में से एक है।

### **प्राप्ति स्वीकृतियाँ (ACK)**

डेटा प्राप्ति के बाद, गंतव्य **ACK (Acknowledgment)** भेजता है।

अक्सर कल्पना के विपरीत, ACK का मतलब नहीं है :

> "मुझे यह पैकेट मिला"

उसका मतलब बल्कि है :

> "मुझे संख्या X तक सभी octet मिले।"

उदाहरण के लिए :

```
Client भेजता है :

0 → 999

Serveur जवाब देता है :

ACK = 1000
```

इसका मतलब है :

> "octet 1000 से पहले सब कुछ अच्छी तरह पहुँचा।"

यह तंत्र एक साथ कई खंडों की प्राप्ति स्वीकार करने देता है (_cumulative acknowledgments_), इस तरह नियंत्रण पैकेट संख्या घटाता है।

### **पुनः प्रसारण**

अगर ACK कभी नहीं आता, तो TCP मानता है कि खंड खो गया है।

वह उसे अपने आप फिर से भेजता है।

पुनः प्रसारण विलंब (**Retransmission Timeout – RTO**) स्थिर नहीं है।

TCP प्राप्त ACK से round trip समय (**RTT**) लगातार मापता है और अनावश्यक पुनः प्रसारण से बचने के लिए RTO गतिशील गणना करता है।

आधुनिक कार्यान्वयन **Fast Retransmit** जैसे तंत्र भी इस्तेमाल करते हैं : जब प्रेषक कई दोहराए ACK पाता है (आमतौर पर तीन), तो वह निष्कर्ष निकालता है कि बीच का खंड खो गया है और उसे timer समाप्ति प्रतीक्षा किए बिना तुरंत फिर से भेजता है।

### **पैकेट पुनर्व्यवस्था**

Internet बिल्कुल गारंटी नहीं देता कि दो पैकेट एक ही रास्ते चलेंगे।

उदाहरण :

```
Paquet 1
Paris
  ↓
Londres
  ↓
New York

Paquet 2
Paris
  ↓
Francfort
  ↓
Chicago
  ↓
New York
```

दूसरा पैकेट पहले से पहले पहुँच सकता है।

TCP तब प्राप्त खंडों को अस्थायी रूप से **क्रम से बाहर** बफर (_reassembly buffer_) में संग्रहित करता है, फिर application को देने से पहले उन्हें फिर से जोड़ता है।

application के लिए, सब कुछ पूरी तरह क्रम में आता लगता है।

### प्रवाह नियंत्रण

कनेक्शन सिर्फ नेटवर्क पर निर्भर नहीं करता।

प्राप्तकर्ता की स्मृति क्षमता भी सीमित होती है।

अगर वह जितना प्रोसेस कर सकता है उससे तेज प्राप्त करता है, तो उसके buffer आखिर संतृप्त हो जाते हैं।

TCP इस समस्या को **चल विंडो (Sliding Window)** से सुलझाता है।

प्राप्तकर्ता हर ACK में बताता है :

```
Window = 32768 octets
```

इसका मतलब है :

> "तुम मुझे 32 Ko अतिरिक्त तक भेज सकते हो।"

अगर यह विंडो शून्य पर गिरती है :

```
Window = 0
```

प्रेषक अस्थायी रूप से प्रसारण निलंबित करता है जब तक प्राप्तकर्ता नई उपलब्ध विंडो घोषित न करे।

यह तंत्र **प्रवाह नियंत्रण (Flow Control)** बनाता है और रोकता है कि तेज host धीमे host को डुबो दे।

### भीड़ नियंत्रण

भले ही प्राप्तकर्ता डेटा अवशोषित करने में सक्षम हो, नेटवर्क खुद संतृप्त हो सकता है।

router के पास सीमित कतारें (_queues_) होती हैं।

जब वे छलकती हैं, पैकेट हटाए जाते हैं।

TCP हानियों को भीड़ संकेत मानता है और **भीड़ विंडो (Congestion Window – cwnd)** से अपनी दर अपने आप अनुकूलित करता है।

आधुनिक एल्गोरिदम (जैसे **Reno**, **CUBIC** या **BBR**, operating system अनुसार) अधिकतम दर और नेटवर्क स्थिरता के बीच संतुलन खोजने के लिए इस विंडो समायोजित करते हैं।

TCP के पहले संस्करण मुख्यतः दो तंत्र इस्तेमाल करते थे :

*   **Slow Start** : भीड़ पहचानने तक दर की घातांकीय वृद्धि।

*   **Congestion Avoidance** : फिर ज्यादा सतर्क वृद्धि, आमतौर पर रैखिक।


यह स्थायी अनुकूलन कारणों में से एक है जिनसे TCP नेटवर्क गुणवत्ता भिन्नता के बावजूद प्रदर्शनकारी रहता है।

### कनेक्शन बंद करना

UDP के विपरीत, TCP कनेक्शन की साफ बंदी भी होती है।

हर छोर **FIN** ध्वज से अपना प्रवाह स्वतंत्र बंद करता है।

पूरी बंदी के लिए आमतौर पर चार आदान प्रदान चाहिए :

```
FIN
ACK
FIN
ACK
```

यह प्रक्रिया गारंटी देती है कि पारगमन में सारा डेटा कनेक्शन नष्ट करने से पहले अच्छी तरह पहुँचाया गया है।

## UDP : अधिकतम सरलता

UDP (User Datagram Protocol) उल्टी दर्शन अपनाता है।

यह **कनेक्शन रहित (connectionless)** है।

मौजूद नहीं है :

*   कोई handshake ;

*   कोई अनुक्रम संख्या ;

*   कोई प्राप्ति स्वीकृति ;

*   कोई पुनः प्रसारण ;

*   कोई प्रवाह नियंत्रण ;

*   कोई भीड़ नियंत्रण।


हर संदेश बस स्वतंत्र **datagram** में लपेटा जाता है, नेटवर्क को प्रेषित किया जाता है, फिर प्रेषक भूल जाता है।

```
Application → Datagramme UDP → IP → Internet
```

प्रोटोकॉल दो भेजने के बीच कोई स्थिति नहीं रखता।

हर datagram पिछले से पूरी तरह स्वतंत्र है।

### डेटा अखंडता

हालाँकि UDP न वितरण न क्रम गारंटी देता है, वह **checksum** से डेटा अखंडता फिर भी सुरक्षित करता है।

प्राप्ति पर, checksum फिर से गणना किया जाता है।

*   अगर मान मेल खाते हैं, तो datagram स्वीकार किया जाता है।

*   वरना, वह तुरंत अस्वीकृत होता है।


UDP इसलिए भ्रष्ट डेटा पहचानता है, लेकिन उन्हें कभी पुनः प्राप्त करने की कोशिश नहीं करता।

### UDP इतना तेज क्यों है ?

UDP हेडर में सिर्फ **8 octet** होते हैं, TCP के लिए न्यूनतम **20 octet** के मुकाबले (timestamp, SACK या Window Scaling जैसे विकल्प गिने बिना)।

कोई कनेक्शन बनाए न रखने से, operating system को हर आदान प्रदान की स्थिति नहीं देखनी पड़ती, जो स्मृति खपत और प्रोसेसिंग लागत भी घटाता है।

application डेटा लगभग पहुँचते ही पाता है, संभावित पुनः प्रसारण प्रतीक्षा किए बिना।

## जब डेटा खोना बेहतर हो

मूलभूत विचार सरल है :

> पुरानी जानकारी खोई जानकारी से कम मूल्यवान हो सकती है।

VoIP बातचीत लो।

हर पैकेट लगभग **20 ms** आवाज ले जाता है।

अगर कोई पैकेट खो जाता है, तो उसे फिर से भेजने में अक्सर इन 20 ms से ज्यादा समय लगेगा।

जब वह आखिर पहुँचेगा, बातचीत पहले ही आगे बढ़ चुकी होगी।

ज्यादातर application तब हानि छिपाना पसंद करते हैं (अंतर्वेशन, मौन, त्रुटि सुधार) बजाय पुनः प्रसारण प्रतीक्षा के।

वही तर्क लागू होता है :

*   वास्तविक समय मल्टीप्लेयर गेम ;

*   वीडियो streaming ;

*   telemetry प्रवाह ;

*   IoT सेंसर ;

*   GPS स्थिति डेटा।


हाल मान लगभग हमेशा पूरी तरह विश्वसनीय पुराने मान से ज्यादा उपयोगी होता है।

# स्तर 2 : एन्क्रिप्शन, TLS

TLS (Transport Layer Security, SSL का उत्तराधिकारी) TCP को बदलता नहीं, वह उसके ऊपर जुड़ता है। ठोस रूप में, TLS सामान्य TCP कनेक्शन स्थापित करता है, फिर अंदर एन्क्रिप्टेड सत्र बातचीत करता है : प्रमाणपत्र आदान प्रदान, एन्क्रिप्शन एल्गोरिदम पर सहमति, सत्र कुंजी व्युत्पत्ति। फिर जो कुछ गुजरता है वह एन्क्रिप्ट और प्रमाणित होता है।

तीन अलग गारंटियाँ, अक्सर भ्रमित :

*   **गोपनीयता** : दोनों पक्षों के अलावा कोई और सामग्री नहीं पढ़ सकता।

*   **अखंडता** : पारगमन में डेटा का कोई बदलाव पहचाना जाता है।

*   **प्रमाणीकरण** : लेकिन क्लासिक TLS में, एकतरफा : client जाँचता है कि serveur वही है जो वह होने का दावा करता है (उसके प्रमाणपत्र से, विश्वास प्राधिकारी द्वारा हस्ताक्षरित), लेकिन serveur client की पहचान पर कुछ नहीं जाँचता। ठीक HTTPS मॉडल है जब तुम कोई साइट देखते हो : ब्राउजर साइट प्रमाणित करता है, साइट तुम्हें प्रमाणित नहीं करती (उपयोगकर्ता प्रमाणीकरण अलग तंत्र से गुजरता है, सत्र cookie, token)।


TLS 1.3 (वर्तमान अनुशंसित संस्करण) ने handshake को सामान्य मामले में एक ही round trip घटाया है, TLS 1.2 के दो के मुकाबले, जो कनेक्शन विलंबता संवेदनशील घटाता है।

## स्तर 2bis : mTLS, प्रमाणीकरण पारस्परिक होता है

mTLS (mutual TLS) अतिरिक्त बाधा वाला TLS है : serveur _भी_ client से प्रमाणपत्र माँगता है, और उसे जाँचता है। दोनों पक्ष सामान्य विश्वास प्राधिकारी द्वारा हस्ताक्षरित प्रमाणपत्र से अपनी पहचान साबित करते हैं।

यह वितरित आर्किटेक्चर में service से service संचार का प्राकृतिक तंत्र है : जहाँ क्लासिक HTTPS ब्राउजर को सार्वजनिक serveur से बात करने के लिए काफी है, mTLS अलग प्रश्न का उत्तर देता है; _आंतरिक service कैसे जानती है कि वह सच में दूसरी अधिकृत आंतरिक service से बात कर रही है, न कि हमलावर से जो नेटवर्क पर उतर आया है ?_

```
Client                                          Serveur
  │──── ClientHello ─────────────────────────────▶│
  │◀─── ServerHello + certificat serveur ──────────│
  │──── vérifie le certificat serveur ─────────────│
  │──── envoie SON PROPRE certificat client ──────▶│
  │◀─── vérifie le certificat client ───────────────│
  │──── clés de session dérivées, canal chiffré ──▶│
```

mTLS की भरपाई परिचालनात्मक है : आंतरिक प्रमाणन प्राधिकारी (CA) चाहिए, हर service को प्रमाणपत्र वितरण तंत्र, और घूर्णन/निरसन रणनीति। कम service वाले एकल मशीन वातावरण में, यह कभी कभी लाभ से ज्यादा जटिलता है, mTLS उस क्षण से जरूरी होता है जब अंतर service ट्रैफिक ऐसे नेटवर्क से गुजरता है जिसे हम पूरी तरह नियंत्रित नहीं करते (कई host, multi-tenant cloud), या जैसे ही _zero trust_ तरह की नीति चाहिए, जहाँ कोई service सिर्फ इसलिए निहित विश्वसनीय नहीं है क्योंकि वह नेटवर्क के "अंदर" है।

# स्तर 3 : TCP+TLS के ऊपर applicative प्रोटोकॉल

एक बार परिवहन और एन्क्रिप्शन जगह पर, _आदान प्रदान कैसे संरचित करें_ परिभाषित करना बाकी है। यह applicative प्रोटोकॉल की भूमिका है।

## HTTP / HTTPS

HTTP अनुरोध उत्तर प्रोटोकॉल है : client कनेक्शन खोलता है (या keep-alive से फिर से इस्तेमाल करता है), अनुरोध भेजता है, उत्तर प्रतीक्षा करता है, कनेक्शन फिर बंद हो सकता है या फिर से इस्तेमाल हो सकता है। HTTPS, बस TLS पर HTTP है, S प्रोटोकॉल अर्थ नहीं बदलता, सिर्फ यह कि परिवहन एन्क्रिप्ट है।

अनुरोध उत्तर मॉडल की संरचनात्मक सीमा है : serveur कभी पहले नहीं बोल सकता। वह सिर्फ वही जवाब दे सकता है जो client माँगता है। बार बार polling के लिए ("क्या कुछ नया है ?" हर सेकंड जाँचना), यह चलता है लेकिन संसाधन बर्बाद करता है, हर अनुरोध प्रोटोकॉल overhead फिर से बनाता है, ज्यादातर समय घोषित करने को कुछ नया नहीं होता।

## WebSocket (WS / WSS)

WebSocket ठीक इस सीमा का उत्तर देता है। कनेक्शन क्लासिक HTTP अनुरोध की तरह शुरू होता है (`Upgrade: websocket` हेडर के साथ), लेकिन एक बार handshake स्वीकार होने पर, अंतर्निहित TCP कनेक्शन HTTP अनुरोध उत्तर चैनल नहीं रहता, वह द्विदिश full-duplex चैनल बन जाता है जहाँ client और serveur किसी भी समय संदेश भेज सकते हैं, बिना हर आदान प्रदान पर अनुरोध उत्तर चक्र फिर से जारी किए।

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

WSS बस TLS पर WebSocket है, बिल्कुल जैसे HTTPS TLS पर HTTP है। यह हर चीज के लिए पसंदीदा प्रोटोकॉल है जिसे वास्तविक समय serveur push चाहिए, चैट, सूचनाएँ, trading प्रवाह, गेम घटनाएँ, बिना नंगे TCP पर खुद बाइनरी प्रोटोकॉल प्रबंधित करना चाहे।

## gRPC

microservices दुनिया के बाहर कम ज्ञात लेकिन service से service संचार में केंद्रीय : gRPC HTTP/2 पर निर्भर है (इसलिए TCP + वैकल्पिक TLS), संदेश Protocol Buffers में क्रमबद्ध करता है (बाइनरी, typed, संक्षिप्त, ज्यादातर REST API के पाठ JSON के विपरीत), और HTTP/2 multiplexing से स्वाभाविक द्विदिश streaming देता है (एक ही TCP कनेक्शन पर कई तार्किक प्रवाह, बिना head-of-line blocking जो कई क्रमिक HTTP/1.1 अनुरोधों में होता)।

## QUIC / HTTP3

QUIC परिवहन स्तर पर TCP के बजाय UDP से फिर से शुरू करके खेल बदलता है, फिर ऊपर विश्वसनीयता गारंटियाँ फिर से लागू करता है जो TCP स्वाभाविक देता था, लेकिन वैश्विक के बजाय प्रवाह दर प्रवाह, जो परिवहन स्तर पर head-of-line blocking खत्म करता है (एक प्रवाह पर खोया पैकेट उसी कनेक्शन के अन्य प्रवाहों को नहीं रोकता)। TLS 1.3 ऊपर जोड़े जाने के बजाय सीधे QUIC में एकीकृत है, जो handshake विलंबता और घटाता है। HTTP/3 QUIC पर HTTP है।

# अवलोकन : हर प्रोटोकॉल कहाँ स्थित है

परत प्रोटोकॉल भूमिका परिवहन TCP, UDP octet पहुँचाना, विश्वसनीय या नहीं परिवहन (नई पीढ़ी) QUIC UDP + प्रवाह दर विश्वसनीयता + एकीकृत TLS सुरक्षा TLS, mTLS एन्क्रिप्शन, अखंडता, प्रमाणीकरण (एकल या पारस्परिक) Application HTTP/HTTPS, WS/WSS, gRPC आदान प्रदान संरचित करना (अनुरोध उत्तर, द्विदिश, typed RPC)

ठोस उदाहरण विचार स्थिर करने के लिए : web dashboard और आंतरिक service वाली microservices आर्किटेक्चर युक्तिसंगत HTTPS (dashboard ↔ सार्वजनिक API, ब्राउजर तरफ एकतरफा प्रमाणीकरण काफी), mTLS (service ↔ service आंतरिक, पारस्परिक प्रमाणीकरण जरूरी), और WSS (dashboard की ओर धकेली वास्तविक समय सूचनाएँ) जोड़ सकती है, तीन अलग applicative प्रोटोकॉल, सभी उसी TCP + TLS आधार पर बने।

## व्यवहार में कैसे चुनें

आमतौर पर निर्णय के लिए तीन प्रश्न काफी हैं :

1.  **क्या मुझे विश्वसनीयता और क्रम चाहिए, या डेटा ताजगी गारंटीकृत वितरण पर प्रधान है ?** → हाँ होने पर TCP, नहीं होने पर UDP (या अलग समझौते से दोनों एक साथ पाने के लिए QUIC)।

2.  **क्या serveur को संदेश शुरू करने में सक्षम होना चाहिए, या client हमेशा पहली माँग करता है ?** → serveur को धकेलना हो तो WebSocket/gRPC streaming, वरना क्लासिक HTTP।

3.  **क्या दोनों पक्षों को एक दूसरे को अपनी पहचान साबित करनी चाहिए, या सिर्फ एक को सत्यापित होना है ?** → zero-trust वातावरण में service से service के लिए mTLS, क्लासिक सार्वजनिक client के लिए साधारण TLS।


जोड़ी हर परत पर परिचालन जटिलता बढ़ती है, नंगे TCP का प्रबंधित करने को कोई बुनियादी ढाँचा नहीं, TLS प्रमाणपत्र माँगता है, mTLS CA और घूर्णन रणनीति माँगता है, gRPC साझा Protobuf schema परिभाषा माँगता है। सही प्रवृत्ति तभी जटिलता बढ़ाना है जब नीचे की परत ठोस सीमा दिखाए, पूर्वानुमान से नहीं।
