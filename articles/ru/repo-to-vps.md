## GitHub даёт бесплатный VPS на 6ч. Я нашёл, как сделать его постоянным.

GitHub Actions даёт бесплатные машины Linux.

Типа настоящие серверы Ubuntu. 2 ядра, 7 ГБ RAM, 14 ГБ диска. Бесплатно. На 6ч за запуск.

Единственная "проблема" : в конце запуска всё стирается. Машина одноразовая. Ставишь пакеты, кодишь, настраиваешь... и пуф, в конце всё исчезает. Будто ничего не делал.

Если бы не.

Если бы не использовать **git как жёсткий диск**.

И тут вдруг у тебя бесплатный VPS с персистентным диском, переживающим запуски. Переподключаешься, всё ещё на месте. Продолжаешь, где остановился.

Это совершенно сломано. Дай объясню.

---

## Контекст : раннеры GitHub Actions

Когда запускаешь воркфлоу GitHub Actions, GitHub выдаёт тебе VM.

Это сделано, чтобы билдить код, гонять тесты, деплоить. Воркфлоу крутится, делает работу, а машина уничтожается.

Но ничто не мешает делать с этой VM что-то ещё. Типа открыть на ней шелл SSH и использовать как сервер.

Ограничение в том, что эти машины **stateless** и **временные** :
- Временная : 6ч макс за запуск (`timeout-minutes: 360`, потолок GitHub)
- Stateless : в конце всё стирается

Так что чтобы сделать из этого usable VPS, надо решить две проблемы :
1. **Как подключиться туда в реальном времени?**
2. **Как сохранить диск между двумя запусками?**

Здесь становится грязным хаком.

---

## Проблема 1 : живой SSH с tmate

**tmate** это форк tmux, создающий расшариваемую SSH-сессию.

Запускаешь на машине, он генерирует две ссылки :
- SSH URL (`ssh xxx@nyc1.tmate.io`)
- веб-URL (терминал в браузере)

Подключаешься по одной из ссылок, и бум, ты в шелле на машине. В реальном времени.

Воркфлоу, стало быть, запускает tmate :

```bash
tmate -S /tmp/tmate.sock new-session -d "bash --rcfile $HOME/.bashrc -i"
tmate -S /tmp/tmate.sock set-option -g remain-on-exit on

# забираем ссылки подключения
tmate_ssh=$(tmate -S /tmp/tmate.sock display -p '#{tmate_ssh}')
tmate_web=$(tmate -S /tmp/tmate.sock display -p '#{tmate_web}')
```

А эти ссылки пишутся прямо в README репозитория скриптом Python. Открываешь свой репозиторий, видишь ссылку подключения, кликаешь. Вот ты в своём VPS.

Первая проблема решена. Но вторая по-настоящему дикая.

## Проблема 2 : git как жёсткий диск

Вот идея, меняющая всё.

Машина стирается при каждом запуске. Так что храним **файловую систему в выделенной ветке git** под названием `filesystem`.

На старте скрипт восстанавливает состояние из этой ветки :

```bash
filesystem_branch="filesystem"

# забираем ветку filesystem с remote
git fetch origin "$filesystem_branch":refs/remotes/origin/$filesystem_branch

# восстанавливаем workspace из этой ветки
git checkout -B filesystem-workspace "refs/remotes/origin/$filesystem_branch"
git reset --hard "refs/remotes/origin/$filesystem_branch"
```

Ветка `filesystem` И ЕСТЬ твой жёсткий диск. Твои файлы, установки, конфиги -- всё внутри.

Видишь идею? Машина одноразовая, а диск живёт в git. Перезапускаешь воркфлоу, диск восстанавливается, продолжаешь ровно, где был.

Это как VPS, впадающий в гибернацию. Только гибернация это git-репозиторий.

### Первый запуск : создать пустой диск

При самом первом запуске ветки `filesystem` ещё нет. Надо создать. И это не пустяк :

```bash
ensure_filesystem_branch() {
  if ! git ls-remote --exit-code origin "refs/heads/$filesystem_branch" >/dev/null 2>&1; then
    git checkout --orphan filesystem-workspace
    git rm -rf --cached .
    git clean -fdx -e .git -e .github -e .github/scripts -e .github/workflows
    git commit --allow-empty -m "init filesystem (empty)"
    push_filesystem
  fi
}
```

`git checkout --orphan` это ключ. Сиротская ветка это ветка **безо всякой истории** -- будто стартуешь с пустого репозитория.

Почему сиротская? Потому что НЕ хочешь, чтобы твой персистентный диск тащил всю историю исходного кода. Диск остаётся изолированным, со своей жизнью. Начинает девственным.

А `git ls-remote --exit-code` в начале это просто чистая проверка : "существует ли ветка уже на remote?". Если да, ничего не трогаем. Если нет, создаём. Идемпотентно, как любим.

### Селективный git clean : защитить кэши

Эта строка заслуживает остановиться на ней :

```bash
git clean -fdx -e .apt-cache -e .cache -e host.conf -e tmate.sock
```

`git clean -fdx` сносит ВСЁ, не отслеживаемое git. Обычно это жестоко -- вычищает workspace начисто.

Но `-e` (exclude) защищают отдельные файлы :
- `.apt-cache` → кэш пакетов APT (вернёмся, это умно)
- `.cache` → общий кэш
- `host.conf` → SSH-адрес сессии
- `tmate.sock` → сокет текущей tmate-сессии

Если бы вычищал и эти файлы, сломал бы активную сессию или потерял кэш. Так что щадим их при сбросе.

Глупая деталь на первый взгляд, но без неё всё ломается.

## Автосейв : inotify, наблюдающий за всем

Ладно, а как файлы попадают в ветку `filesystem`?

Ответ : вотчер, наблюдающий ВСЕ изменения файлов и автоматически коммитящий/пушащий.

Волшебный инструмент это **inotifywait** (из пакета `inotify-tools`). Он наблюдает файловую систему на уровне ядра и срабатывает, как только файл меняется.

```bash
autosave() {
  while inotifywait -qq -r -e modify,create,delete,move \
    --exclude '(^|/)(\.git|\.apt-cache|\.cache|host\.conf|tmate\.sock|\.gitignore|\.txt\.swp)(/|$)' .; do
    echo "[autosave] change detected"
    commit_and_push
    sleep 1   # debounce, если много изменений разом
  done
}

autosave &
```

Разберём флаги inotify, потому что каждый считается :
- `-r` → рекурсивно, наблюдает все подпапки
- `-e modify,create,delete,move` → реагирует на эти 4 типа событий
- `--exclude '...'` → regex для игнора отдельных файлов

`--exclude` критичен. Смотри, что он игнорирует :
- `.git` → очевидно, иначе каждый коммит триггерил бы автосейв, триггерящий коммит... бесконечный цикл. Катастрофа.
- `.apt-cache` и `.cache` → кэши, меняющиеся всё время, которые не хочется спамить в git
- `host.conf` и `tmate.sock` → файлы сессии, шевелящиеся без остановки
- `.gitignore`, `.txt.swp` → временные файлы (`.swp` это файлы редактирования vim)

Без этого exclude получил бы автосейв, срабатывающий по кругу на собственных изменениях. `.git` в списке это ТА строка, не дающая выстрелить себе в ногу.

Меняешь файл? inotify детектит мгновенно, это коммитится, пушится. Меньше чем за секунду твоё изменение в ветке `filesystem`.

Ставишь пакет, пишешь код, трогаешь конфиг -- всё сохраняется в реальном времени, автоматически, без твоих действий.

Буквально система автосохранения целого диска. Сломано.

### Debounce : не спамить git

`sleep 1` после каждого сейва это **debounce**.

Когда сохраняешь файл в редакторе, часто это генерирует несколько событий файловой системы очередью (создание temp-файла, rename, удаление старого...). Без debounce триггерил бы 3-4 коммита на одно сохранение.

`sleep 1` говорит : "подожди секунду после сейва, пока очередь успокоится, прежде чем слушать снова". Это группирует близкие изменения в один коммит. Умно.

### А ещё периодический сейв сверху

На случай если inotify пропустит событие, есть ещё сейв каждые 5 секунд :

```bash
periodic_save() {
  while true; do
    sync_from_remote   # забирает возможные удалённые изменения
    sleep 5
    commit_and_push
  done
}

periodic_save &
```

И ремень, И подтяжки. Главное не потерять состояние диска.

## Умная деталь : один коммит

Если коммитить при каждом изменении файла, накопишь тысячи коммитов. За час сессии история git взрывается. Репозиторий становится огромным. Отвратительно.

Решение элегантно : **аммендим существующий коммит** вместо создания нового.

```bash
commit_and_push() {
  (
    flock -n 200 || return   # лок, чтобы два сейва не крутились одновременно

    git add -A
    git reset -- .github/workflows/ .github/scripts/   # не трогаем скрипты

    if ! git diff --cached --quiet; then
      if git rev-parse --verify HEAD >/dev/null 2>&1; then
        git commit --amend --no-edit    # AMEND : затирает предыдущий коммит
      else
        git commit -m "autosave $(date -u +%Y%m%dT%H%M%SZ)"
      fi
      git push --force origin "filesystem-workspace:filesystem"
    fi
  ) 200>/tmp/tmate_autosave.lock
}
```

`git commit --amend` значит : "замени последний коммит этим".

Так ветка `filesystem` ВСЕГДА на одном коммите. Сколько бы раз ни сохранялся. Это просто снапшот текущего состояния, форспушенный снова и снова.

`flock` это замок : раз есть два цикла сейва (inotify + периодический), надо не дать им запускать git одновременно и мешать друг другу. Один процесс git зараз.

Чисто.

## Sync_from_remote : управление несколькими сессиями

Держи, случай, о котором сначала не думаешь : а если запустить ДВА рана одновременно? Или если сессия меняет ветку `filesystem`, пока крутится другая?

Скрипт разруливает это через `sync_from_remote` перед каждым коммитом :

```bash
sync_from_remote() {
  git fetch origin "filesystem":refs/remotes/origin/filesystem
  git merge --ff-only "refs/remotes/origin/filesystem"
}
```

`--ff-only` (только fast-forward) важен : значит "мерджи ТОЛЬКО если можно чисто продвинуться вперёд, без создания merge-коммита".

Если обе ветки разошлись (типа две сессии меняли разные файлы), fast-forward молча падает (`2>/dev/null || true`), и сохраняем локальное состояние. Это не идеальная merge-система, но избегает порчи в простом случае, когда крутится одна сессия.

Честно, не надо запускать 3 сессии параллельно на одном репо. Но код всё равно старается не взрываться, если так вышло. Это защита.

## APT-кэш : быстрая установка

Есть деталь в воркфлоу, выглядящая никак, но хорошо продуманная :

```yaml
- name: Cache & install APT packages (tmate + watcher)
  uses: awalsh128/cache-apt-pkgs-action@v1.6.0
  with:
    packages: tmate inotify-tools
```

tmate и inotify-tools ставятся через экшен, **кэширующий пакеты APT**.

При первом запуске это скачивает и ставит. При следующих запусках восстанавливается из кэша GitHub Actions -- быстрее, не надо перекачивать.

А помнишь `git clean -fdx -e .apt-cache` раньше? Это связано. Папка `.apt-cache` защищена от чистки как раз чтобы пакеты, ставленные во время сессии, могли минимально персистить.

Всё сходится. Я продумал полный жизненный цикл.

## Скрипты, спрятанные в /tmp

Ещё одна коварная, но умная деталь. В самом начале скрипта :

```bash
RUNNER_SCRIPTS_DIR="/tmp/runner-scripts"
rm -rf "$RUNNER_SCRIPTS_DIR"
mkdir -p "$RUNNER_SCRIPTS_DIR"
cp -r .github/scripts "$RUNNER_SCRIPTS_DIR/"
```

Скрипты (`update_readme.py` и т.д.) копируются в `/tmp` ДО касания ветки `filesystem`.

Почему? Потому что когда делаешь `git reset --hard` на ветку `filesystem` (пустую в начале или содержащую твой диск), файлы `.github/scripts` исходного репозитория исчезают из workspace.

Но скрипту они ещё нужны во время сессии (чтобы обновлять README при каждом перезапуске tmate). Так что он прячет их в `/tmp`, вне досягаемости git :

```bash
python3 "$RUNNER_SCRIPTS_DIR/scripts/update_readme.py" --ssh "$tmate_ssh" ...
```

Если об этом не подумать, полчаса недоумеваешь, почему скрипт исчез. Я подумал.

## Кастомный шелл

Маленькое удобство : сессия даёт настроенный шелл, а не голый bash.

`prestart.sh` копирует кастомный `.bashrc` :

```bash
if ! grep -q "Custom prompt and aliases for remote sessions" "$HOME/.bashrc"; then
  cp .github/scripts/remote_bashrc "$HOME/.bashrc"
fi
sudo cp "$HOME/.bashrc" /root/.bashrc
```

А этот `.bashrc` содержит цветной промпт, алиасы (`ll`, `lla`, `rm -i`) и главное override `exit` :

```bash
exit() {
    killall -9 -u "$(whoami)" tmate 2>/dev/null || true
    builtin exit "$@"
}

# Ctrl+D делает то же, что exit
bind -x '"\C-d": "exit"'
```

Когда набираешь `exit` (или Ctrl+D), это чисто убивает процессы tmate перед закрытием. Это избегает висячих зомби-сессий tmate.

Есть ещё функция `tmate-detach`, если хочешь отключиться, НЕ убивая сессию (чтобы переподключиться позже). Деталь удобства, но показывает уровень заботы.

## Tmate, перезапускающийся сам

Маленькое удобство : если набираешь `exit` в шелле, нормально tmate-сессия умирает, и ты отключён навсегда.

Только здесь tmate в цикле `while true` :

```bash
while true; do
  tmate -S /tmp/tmate.sock new-session -d "bash --rcfile $HOME/.bashrc -i"
  while tmate -S /tmp/tmate.sock display -p '#{tmate_ssh}' >/dev/null 2>&1; do
    sleep 2
  done
  echo "tmate session ended; restarting..."
done
```

Ты делаешь `exit`? Сессия сама перезапускается. Переподключаешься по той же ссылке.

Это тупо, но делает сессию usable.

## Переподключение одной командой

Как переподключаешься после дисконнекта, не роясь в логах запуска каждый раз?

SSH-адрес tmate пишется в файл `host.conf`, коммитящийся в ветку `filesystem` :

```bash
printf '%s' "${tmate_ssh#ssh }" > host.conf
```

А раз этот файл в git, его можно забрать через API GitHub одной командой :

```bash
ssh "$(gh api -H 'Accept: application/vnd.github.v3.raw' \
  "/repos/USER/REPO/contents/host.conf?ref=filesystem" | tr -d '\r\n')"
```

Запускаешь это, оно забирает текущий SSH-адрес из репозитория и подключает. Даже если адрес сменился между сессиями.

## Полный флоу

Резюмируем :

1. Триггеришь воркфлоу (push или ручная кнопка)
2. GitHub выдаёт тебе VM Ubuntu
3. Скрипт восстанавливает диск из ветки "filesystem"
4. inotify начинает наблюдать все изменения
5. periodic_save коммитит каждые 5s как бэкап
6. tmate стартует → генерирует SSH/веб-ссылки
7. Ссылки пишутся в README + host.conf
8. Подключаешься по ssh или веб-терминалу
9. Делаешь что хочешь -- каждое изменение файла = автосейв
10. Через 6ч GitHub убивает VM
11. Твой диск цел в ветке "filesystem"
12. Перезапускаешь воркфлоу → назад к шагу 3, всё ещё на месте

Бесплатный VPS с персистентным диском. Только с git и GitHub Actions.

## Ладно, честно : лимиты

Это хак, а не настоящий VPS. Так что :

- **6ч макс за запуск.** Надо регулярно перезапускать воркфлоу. Аптайм ограничен каждым запуском.
- **Только для dev и исследования.** Не будешь хостить на этом свой сайт. Это для исследования, dev, отладки, теста одноразового, но восстанавливаемого окружения Linux.
- **GitHub видит всё.** Это их машины. Ничего чувствительного не клади.
- **Держи репозиторий приватным.** Ты выставляешь шелл SSH. Публичный репозиторий = кто угодно потенциально может подключиться. Плохая идея.
- **Это на грани условий использования.** GitHub Actions сделан для CI/CD, а не для бесплатного VPS. Так что использовать умеренно, для легитимного, без злоупотреблений.

### Настоящая ахиллесова пята : git ненавидит большие файлы

Git сделан для текста, а не для файловой системы.

Персистентный диск живёт в ветке git. Так что всё сохраняемое идёт через git. А git :
- плохо управляет большими бинарными файлами (Docker-образ на 2 ГБ в git? забудь)
- имеет лимит 100 МБ на файл на GitHub (жёсткий лимит, дальше не пушится)
- рекомендует оставаться под ~5 ГБ на репозиторий

Так что если делаешь `npm install` проекта с 500 МБ `node_modules` или билдишь проект, генерирующий тяжёлые бинарники, push в `filesystem` будет либо смертельно тормозить, либо вообще падать.

`git commit --amend` помогает (один коммит, без раздувающейся истории), но не меняет того, что файл на 200 МБ никогда не пройдёт.

Короче : **отлично работает для кода, конфигов, мелких файлов. Не работает для хранения больших данных или бинарных артефактов.** Это надо держать в голове про то, что делаешь в сессии.

### Это не полный снапшот системы

Другой важный нюанс : ветка `filesystem` сохраняет **workspace** (папку репозитория), а не всю систему.

Если делаешь `apt install htop`, бинарник ложится в `/usr/bin/htop`, ВНЕ workspace. Стало быть, сохранён НЕ будет. При следующем запуске надо переустанавливать.

Поэтому есть APT-кэш и `prestart.sh` : чтобы переготавливать системное окружение при каждом старте, раз персистит только workspace.

Если хочешь, чтобы установки переживали, надо класть их в workspace (типа ставить в локальную папку вместо системной). Это гимнастика для встраивания.

## Паттерн за всем этим

Если отступить, repo-to-vps и email-бот (моя другая статья) опираются на одну идею :

> **Git не только менеджер версий. Это персистентное хранилище, бесплатное, версионированное, доступное через API.**

Как только есть stateless-система (GitHub Actions, Worker, serverless-функция), и хочешь сохранить состояние между двумя запусками, git может служить "диском".

- Email-бот хранит `lastId` в git-теге.
- repo-to-vps хранит целый filesystem в ветке git.

Тот же паттерн, два масштаба. Одно значение с одной стороны, диск с другой.

А `git commit --amend` + force-push это общая техника : **держишь один коммит, представляющий текущее состояние, затираемый при каждом апдейте.**

Это не для того сделано. Но работает. И бесплатно.

---

**3 пункта запомнить :**

1. **Ветка git = персистентный жёсткий диск** -- Храни свой filesystem в выделенной ветке, восстанавливай на старте, и получаешь состояние, переживающее одноразовые машины.

2. **inotify + git = автосейв реального времени** -- `inotifywait` наблюдает изменения на уровне kernel и мгновенно пушит в git. С `git commit --amend`, чтобы держать один чистый коммит.

3. **tmate превращает раннер в VPS** -- Живой SSH на машину GitHub Actions, с авторестартом и переподключением одной командой через API GitHub.

Git как жёсткий диск, второй эпизод. Думаю, я в итоге всё буду хранить в ветках git
