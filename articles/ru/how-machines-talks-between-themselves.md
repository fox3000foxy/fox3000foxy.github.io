# Проблема : слишком много аббревиатур, мало иерархии

TCP, UDP, TLS, mTLS, WebSocket, HTTP, HTTPS, gRPC, QUIC; большинство ресурсов про них подают их как плоский список взаимозаменяемых опций, "выбирать по юзкейсу". В реальности они не на одном уровне : одни транспортные протоколы, другие слои безопасности, оборачивающиеся вокруг транспорта, третьи прикладные протоколы, опирающиеся на первые два. Понять иерархию значит понять, почему никогда не "выбирают" между TCP и TLS : выбирают TCP, _потом_ решают, класть ли сверху TLS.

Эта статья перестраивает эту иерархию слой за слоем, от сырого транспорта до взаимной аутентификации, с для каждого уровня : что он гарантирует, чего не гарантирует и когда им довольствоваться.

# Уровень 1 : транспорт (TCP против UDP)

Всё начинается здесь. TCP и UDP два главных протокола уровня **Transport (Layer 4)** модели OSI. Их роль одинакова : переносить поток данных между двумя приложениями, выполняющимися на разных машинах. Однако способ достичь этого радикально разный.

Важно понимать, что IP (Internet Protocol) на сетевом уровне (Layer 3) лишь маршрутизирует пакеты от хоста к хосту. Он не гарантирует ни их прибытия, ни порядка, ни даже уникальности. Роутеры просто принимают независимые решения о маршрутизации для каждого пакета.

Именно это отсутствие гарантий TCP и приходит компенсировать, а UDP осознанно выбирает ничего не добавлять, чтобы оставаться экстремально лёгким.

## TCP : надёжность прежде всего

TCP (Transmission Control Protocol) это протокол **ориентированный на соединение** (_connection-oriented_). Прежде чем обменять хоть байт данных, обе машины должны установить логическое соединение.

Это соединение создаётся знаменитым **трёхсторонним хендшейком** :

```

Клиент                          Сервер
SYN ---------------------------->
        <--------------------- SYN + ACK
ACK ---------------------------->
Соединение установлено
```

Каждый шаг имеет точную цель :

*   SYN : клиент объявляет, что хочет открыть соединение, и даёт первый порядковый номер (Initial Sequence Number - ISN).

*   SYN-ACK : сервер принимает соединение, подтверждает получение SYN и в свою очередь даёт собственный порядковый номер.

*   ACK : клиент подтверждает получение информации сервера.


С этого момента обе машины знают состояние соединения и могут начинать обмен данными.

### **Порядковые номера**

TCP видит данные не как очередь пакетов, а как **непрерывный поток байтов** (_byte stream_).

У каждого отправленного байта есть порядковый номер.

Пример :

```
Сообщение :

Bonjour

B = байт 0
o = байт 1
n = байт 2
...
```

Если сегмент, содержащий байты 1000-1499, потерян при транспортировке, получатель может детектировать ровно, чего не хватает.

Отправитель переотправляет только эту порцию.

Эта гранулярность одна из причин робастности TCP.

### **Подтверждения (ACK)**

После приёма данных получатель отправляет **ACK (Acknowledgment)**.

Вопреки тому, что часто воображают, ACK не значит :

> "Я получил этот пакет"

Он скорее значит :

> "Я получил все байты вплоть до номера X."

Например :

```
Клиент отправляет :

0 → 999

Сервер отвечает :

ACK = 1000
```

Это значит :

> "Всё до байта 1000 дошло нормально."

Этот механизм позволяет подтверждать несколько сегментов сразу (_cumulative acknowledgments_), снижая число контрольных пакетов.

### **Переотправки**

Если ACK так и не приходит, TCP предполагает, что сегмент потерян.

Он автоматически его переотправляет.

Задержка переотправки (**Retransmission Timeout – RTO**) не фиксирована.

TCP постоянно измеряет время туда-обратно (**RTT**) по полученным ACK и динамически вычисляет RTO, чтобы избегать бесполезных переотправок.

Современные реализации используют также механизмы вроде **Fast Retransmit** : когда отправитель получает несколько дублированных ACK (обычно три), он выводит, что промежуточный сегмент потерян, и шлёт его сразу, не дожидаясь истечения таймера.

### **Переупорядочивание пакетов**

Интернет совершенно не гарантирует, что два пакета пойдут одним путём.

Пример :

```
Пакет 1
Париж
  ↓
Лондон
  ↓
Нью-Йорк

Пакет 2
Париж
  ↓
Франкфурт
  ↓
Чикаго
  ↓
Нью-Йорк
```

Второй пакет может прийти раньше первого.

TCP тогда временно хранит полученные **вне порядка** сегменты в буфере (_reassembly buffer_), затем пересобирает их, прежде чем отдать приложению.

Для приложения всё выглядит приходящим идеально по порядку.

### Контроль потока

Соединение зависит не только от сети.

У получателя тоже ограниченная память.

Если он получает быстрее, чем может обрабатывать данные, его буферы в итоге насыщаются.

TCP решает эту проблему через **скользящее окно (Sliding Window)**.

Получатель указывает в каждом ACK :

```
Window = 32768 байтов
```

Это значит :

> "Можешь слать мне до 32 КБ дополнительно."

Если это окно падает до нуля :

```
Window = 0
```

Отправитель временно приостанавливает передачи, пока получатель не объявит новое доступное окно.

Этот механизм составляет **контроль потока (Flow Control)** и не даёт быстрому хосту затопить более медленный.

### Контроль перегрузки

Даже если получатель способен поглощать данные, сама сеть может стать насыщенной.

У роутеров ограниченные очереди (_queues_).

Когда они переполняются, пакеты отбрасываются.

TCP интерпретирует потери как признак перегрузки и автоматически адаптирует свою скорость через **окно перегрузки (Congestion Window – cwnd)**.

Современные алгоритмы (вроде **Reno**, **CUBIC** или **BBR**, в зависимости от ОС) подстраивают это окно, чтобы найти баланс между максимальной пропускной способностью и стабильностью сети.

Первые версии TCP использовали в основном два механизма :

*   **Slow Start** : экспоненциальный рост скорости до детекта перегрузки.

*   **Congestion Avoidance** : затем более осторожный, обычно линейный рост.


Эта постоянная адаптация одна из причин, почему TCP остаётся производительным несмотря на вариации качества сети.

### Закрытие соединения

В отличие от UDP, TCP-соединение имеет и чистое закрытие.

Каждый конец независимо закрывает свой поток флагом **FIN**.

Полное закрытие обычно требует четырёх обменов :

```
FIN
ACK
FIN
ACK
```

Эта процедура гарантирует, что все данные в пути были доставлены до разрушения соединения.

## UDP : максимальная простота

UDP (User Datagram Protocol) исповедует обратную философию.

Он **без соединения (connectionless)**.

Нет :

*   никакого хендшейка ;

*   никаких порядковых номеров ;

*   никаких подтверждений ;

*   никаких переотправок ;

*   никакого контроля потока ;

*   никакого контроля перегрузки.


Каждое сообщение просто инкапсулируется в независимую **дейтаграмму**, передаётся сети, затем забывается отправителем.

```
Приложение → Дейтаграмма UDP → IP → Интернет
```

Протокол не хранит состояния между двумя отправками.

Каждая дейтаграмма полностью независима от предыдущих.

### Целостность данных

Хотя UDP не гарантирует ни доставку, ни порядок, он всё же защищает целостность данных через **контрольную сумму**.

При приёме контрольная сумма пересчитывается.

*   Если значения совпадают, дейтаграмма принимается.

*   Иначе она сразу отбрасывается.


UDP, таким образом, детектирует повреждённые данные, но никогда не пытается их восстанавливать.

### Почему UDP такой быстрый?

Заголовок UDP содержит всего **8 байтов** против минимум **20 байтов** у TCP (не считая опций вроде timestamps, SACK или Window Scaling).

Раз соединение не держится, ОС не надо отслеживать состояние каждого обмена, что снижает потребление памяти и стоимость обработки.

Приложение получает данные почти сразу по прибытии, не дожидаясь возможных переотправок.

## Когда потеря данных предпочтительна

Фундаментальная идея проста :

> Une information ancienne peut avoir moins de valeur qu'une information perdue.

Возьмём разговор VoIP.

Каждый пакет несёт около **20 мс** голоса.

Если пакет потерян, его переотправка часто заняла бы больше этих 20 мс.

Когда бы он наконец пришёл, разговор уже ушёл бы вперёд.

Большинство приложений предпочитают маскировать потерю (интерполяция, тишина, коррекция ошибок), а не ждать переотправки.

То же рассуждение применимо :

*   многопользовательским играм реального времени ;

*   видеосримингу ;

*   потокам телеметрии ;

*   IoT-датчикам ;

*   данным GPS-позиции.


Свежее значение почти всегда полезнее старого, но идеально надёжного.

# Уровень 2 : шифрование, TLS

TLS (Transport Layer Security, преемник SSL) не заменяет TCP, он добавляется сверху. Конкретно TLS устанавливает нормальное TCP-соединение, затем договаривается о шифрованной сессии внутри : обмен сертификатами, согласование алгоритма шифрования, вывод сессионных ключей. Всё, что идёт дальше, шифруется и аутентифицируется.

Три отдельные гарантии, часто смешиваемые :

*   **Конфиденциальность** : никто, кроме двух сторон, не может читать содержимое.

*   **Целостность** : любое изменение данных в пути детектируется.

*   **Аутентификация** : но в классическом TLS односторонняя : клиент проверяет, что сервер именно тот, за кого себя выдаёт (через свой сертификат, подписанный доверенным центром), а сервер ничего не проверяет про идентичность клиента. Это ровно модель HTTPS, когда ты заходишь на сайт : браузер аутентифицирует сайт, сайт тебя не аутентифицирует (аутентификация пользователя идёт через отдельный механизм, сессионный cookie, token).


TLS 1.3 (текущая рекомендуемая версия) ужала хендшейк до одного round-trip в обычном случае против двух у TLS 1.2, что заметно снижает задержку соединения.

## Уровень 2bis : mTLS -- аутентификация становится взаимной

mTLS (mutual TLS) это TLS с дополнительным ограничением : сервер требует _тоже_ сертификат клиента и проверяет его. Обе стороны доказывают идентичность через сертификат, подписанный общим доверенным центром.

Это естественный механизм для коммуникации сервис-сервис в распределённой архитектуре : там, где классического HTTPS достаточно, чтобы браузер говорил с публичным сервером, mTLS отвечает на другой вопрос; _как внутренний сервис знает, что говорит именно с другим разрешённым внутренним сервисом, а не с атакующим, оказавшимся в сети?_

```
Клиент                                         Сервер
  │──── ClientHello ─────────────────────────────▶│
  │◀─── ServerHello + сертификат сервера ──────────│
  │──── проверяет сертификат сервера ─────────────│
  │──── отправляет СВОЙ сертификат клиента ──────▶│
  │◀─── проверяет сертификат клиента ───────────────│
  │──── сессионные ключи выведены, канал шифрован ──▶│
```

Расплата за mTLS операционная : нужен внутренний центр сертификации (CA), механизм раздачи сертификатов каждому сервису и стратегия ротации/отзыва. В моно-машинном окружении с малым числом сервисов это порой больше сложности, чем выгоды -- mTLS становится нужен с момента, когда межсервисный трафик идёт через сеть, контролируемую не полностью (несколько хостов, мультитенантный cloud), или как только хочешь политику типа _zero trust_, где ни один сервис не достоин доверия имплицитно просто потому, что он "внутри" сети.

# Уровень 3 : прикладные протоколы поверх TCP+TLS

Когда транспорт и шифрование на месте, остаётся определить _как структурировать обмены_. Это роль прикладных протоколов.

## HTTP / HTTPS

HTTP это протокол запрос-ответ : клиент открывает соединение (или переиспользует его с keep-alive), шлёт запрос, ждёт ответ, соединение может затем закрыться или переиспользоваться. HTTPS это просто HTTP поверх TLS -- S ничего не меняет в семантике протокола, только в том, что транспорт шифрован.

У модели запрос-ответ структурный лимит : сервер никогда не может заговорить первым. Он может лишь отвечать на то, что просит клиент. Для частого polling ("есть новое?" каждую секунду) это работает, но тратит ресурсы -- каждый запрос пересоздаёт протокольный оверхед ради, чаще всего, отсутствия чего-то нового для объявления.

## WebSocket (WS / WSS)

WebSocket отвечает ровно на этот лимит. Соединение стартует как классический HTTP-запрос (с заголовком `Upgrade: websocket`), но как только хендшейк принят, нижележащее TCP-соединение больше не канал запрос-ответ HTTP -- оно становится двунаправленным full-duplex каналом, где клиент и сервер могут слать сообщения в любой момент, без нужды перевыпускать цикл запрос-ответ при каждом обмене.

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

WSS это просто WebSocket поверх TLS, ровно как HTTPS это HTTP поверх TLS. Это протокол выбора для всего, где нужен серверный push в реальном времени -- чат, уведомления, потоки трейдинга, игровые события -- без желания самому рулить бинарным протоколом поверх голого TCP.

## gRPC

Менее известен вне мира микросервисов, но централен в коммуникации сервис-сервис : gRPC опирается на HTTP/2 (то есть TCP + опциональный TLS), сериализует сообщения в Protocol Buffers (бинарный, типизированный, компактный -- в отличие от текстового JSON большинства REST API) и нативно позволяет двунаправленный стриминг благодаря мультиплексированию HTTP/2 (несколько логических потоков на одном TCP-соединении без head-of-line blocking, какой был бы у нескольких последовательных запросов HTTP/1.1).

## QUIC / HTTP3

QUIC меняет правила, стартуя с UDP вместо TCP на транспортном уровне, перереализуя сверху гарантии надёжности, что TCP давал нативно, -- но поток за потоком, а не глобально, что убирает head-of-line blocking на транспортном уровне (потерянный пакет на одном потоке больше не блокирует другие потоки того же соединения). TLS 1.3 встроен прямо в QUIC, а не добавлен сверху, что ещё снижает задержку хендшейка. HTTP/3 это HTTP поверх QUIC.

# Обзор : где находится каждый протокол

Слой Протоколы Роль Транспорт TCP, UDP Гонять байты, надёжно или нет Транспорт (новое поколение) QUIC UDP + надёжность по потокам + встроенный TLS Безопасность TLS, mTLS Шифрование, целостность, аутентификация (одно- или взаимная) Прикладной HTTP/HTTPS, WS/WSS, gRPC Структурировать обмены (запрос-ответ, двунаправленный, типизированный RPC)

Конкретный пример, чтобы зафиксировать идеи : архитектура микросервисов с веб-дашбордом и внутренними сервисами могла бы разумно комбинировать HTTPS (дашборд ↔ публичный API, односторонней аутентификации достаточно со стороны браузера), mTLS (сервис ↔ сервис внутри, нужна взаимная аутентификация) и WSS (пуш уведомлений реального времени в дашборд) -- три разных прикладных протокола, все построенные на том же фундаменте TCP + TLS.

## Как выбирать на практике

Трёх вопросов обычно достаточно, чтобы решить :

1.  **Нужны ли мне надёжность и порядок, или свежесть данных важнее гарантированной доставки?** → TCP если да, UDP если нет (или QUIC, чтобы иметь оба сразу через другой компромисс).

2.  **Должен ли сервер уметь инициировать сообщения, или клиент всегда делает первый запрос?** → WebSocket/gRPC streaming если сервер должен пушить, классический HTTP иначе.

3.  **Должны ли обе стороны взаимно доказывать идентичность, или проверяться нужно только одной?** → mTLS для сервис-сервис в окружении zero-trust, простой TLS для классического публичного клиента.


Операционная сложность растёт с каждым добавленным слоем, голый TCP не имеет инфраструктуры для управления, TLS требует сертификатов, mTLS требует CA и стратегии ротации, gRPC требует общего определения схемы Protobuf. Правильный рефлекс подниматься в сложности, только когда нижний слой показывает конкретный лимит, а не впрок.
