How to Get Any Cape on Minecraft Bedrock

On Java, there are plenty of twisted ways to end up with a cape you shouldn't have (see the article on cape-mod). On Bedrock, the game is different, auth is different, but there's still a way -- you just need a third-party launcher and a game version old enough to ignore the validation everyone takes for granted.

Here's how to do it, and then we'll look at what's probably going on under the hood.

What you need

  • A Microsoft account that already owns Minecraft Bedrock (yours works just fine)
  • The official Minecraft launcher installed
  • BedrockLauncher, an open-source third-party launcher that lets you install and launch any historical Bedrock version
  • .NET 8.0 Desktop Runtime
  • Developer mode enabled on Windows

Step 1 -- Install Bedrock at least once with the official launcher

Before anything else, open the official Minecraft launcher, go to the Minecraft: Bedrock Edition tab, and click Install. Bedrock must have been installed and launched at least once through the official channel before you touch BedrockLauncher.

Step 2 -- Download BedrockLauncher

Head to the project's GitHub releases page. Grab the zip of the latest listed version in the Assets.

Step 3 -- Extract the archive

Once the zip is downloaded, extract it into your Downloads folder (or anywhere, as long as you can find the folder afterward).

Step 4 -- Run the executable

Go into the extracted folder and launch BedrockLauncher.exe.

Step 5 -- Install the .NET Desktop Runtime and enable developer mode

On first launch, Windows will very likely ask you for the .NET 8.0 Desktop Runtime -- install it. You also need to enable developer mode in Settings > System > For Developers, because BedrockLauncher installs the game as a loose package (raw files, not a real signed Store package), and Windows refuses that kind of install without this mode.

Step 6 -- Create a new installation

Relaunch BedrockLauncher, sign in with your Microsoft account, go to the Installations tab, then click New installation.

Step 7 -- Pick an old version

Give the installation a name, then in the version list, pick an old version -- typically a 1.16.x or older. Click Create.

Step 8 -- Launch the installation

Click Play. Extracting the files can take up to ten minutes depending on the machine -- the launcher will look frozen ("Not Responding"), that's normal, just let it run.

Step 9 -- Pick the cape

Once the game is running, sign in with your account, create a new character, and go to the skin editor, Capes tab. There you'll find the full list of every cape that exists in Minecraft -- including the ones you never had (promo event capes, past festivals, Mob Vote, etc). Pick the one you want.

Don't touch the rest of the skin's appearance at this point, just the cape.

Step 10 -- Reinstall the official version

Go back to the official launcher, Installation tab, and click Uninstall on the main Bedrock installation, then reinstall it (or hit Check for Updates). Relaunch Minecraft Bedrock from the official launcher this time.

And there it is -- your cape is there, on the official version, on your real profile.

What probably happens

I didn't dig into Bedrock's closed source (unlike Java, which is decompilable), so what follows is a likely explanation, not absolute certainty. But the observed behavior fits the following hypothesis pretty well.

The cape picker was never an access control

On Bedrock, the cape selection screen most likely shows the full list of capes that exist in the game, not just the ones your account owns. On recent clients, an application filter (client-side or via a network call to an Xbox/Microsoft entitlement service) grays out or hides the capes you don't own.

The key point is that this filter was probably added after the fact, on a recent enough game version. A version like 1.16.x predates that filter, or uses a different (possibly nonexistent) verification mechanism: everything in the list becomes selectable, entitlement or not.

Where is the cape actually stored?

This is the part that explains why it survives reinstallation. The skin/cape choice on Bedrock is not just a throwaway local file -- it's most likely synced to the Xbox Live profile tied to your Microsoft account (the same system that manages your skin on other Bedrock platforms -- mobile, console, etc.). When you pick a cape in the old client, it very likely sends that choice to the profile service, exactly like an up-to-date client would with a legitimate cape -- because from the client's point of view, there is no difference between a cape that is "yours" and one that is "picked". The profile service, for its part, trusts the client on this: it records the selection without revalidating whether the entitlement actually exists behind it, at least not at write time.

Result: when you relaunch the up-to-date official game, it fetches your current skin/cape from the profile service -- and the service faithfully returns what was recorded, non-legitimate cape included. The entitlement check, if there is one, probably happens only at selection time in the UI (hence the filter on recent clients), and lets display of what's already recorded on the profile pass through.

The parallel with Java

It's the same family of logic flaw as the cape-mod one on Java: a service trusting data without re-verifying its origin at every step. On Java, it's a valid RSA signature but replayed onto the wrong profile. On Bedrock, it's most likely a cape selection accepted by an old client that never had the right filter, then propagated without revalidation into the account's persistent state. In both cases, the problem isn't the entry point (the Java mod, the old Bedrock client) -- it's that the layer that should revalidate the entitlement downstream doesn't, or only does it once, in the wrong place.

Why it still works

Two possible explanations, not incompatible with each other:

  1. Mojang probably doesn't consider it a priority. It takes a third-party launcher, a multi-step manipulation, and the result is purely cosmetic -- no gameplay advantage, no one else's data compromised.
  2. Fixing it properly would mean revalidating entitlements on every profile read, not just at selection -- which means an extra network call on every skin display, for a problem that only concerns cosmetics.

Conclusion

This tutorial fits in ten screenshots, but it illustrates a principle you find everywhere in software security: as soon as a historical system (an old client version, a legacy API, a never-updated service) can still write into shared state, the present day's access control only protects what goes through the present. Everything that can still talk to the old API bypasses the newer filter -- the filter works on recent versions, but it was never applied to the version that came before it.

  2. The selection is then synced to your Xbox Live profile like any legitimate cape -- the profile service trusts the client.
  3. The entitlement check, if there is one, happens at selection time in the recent UI -- not when reading what's already recorded on the account.

Comment obtenir n'importe quelle cape sur Minecraft Bedrock

Sur Java, il existe plein de moyens tordus de se retrouver avec une cape qu'on ne devrait pas avoir (voir l'article sur cape-mod). Sur Bedrock, le jeu est différent, l'auth est différente, mais il existe quand même un moyen -- il te suffit d'un launcher tiers et d'une version du jeu suffisamment vieille pour ignorer la validation qu'on croit acquise.

Voici comment faire, et ensuite on regarde ce qui se passe probablement sous le capot.

Ce qu'il te faut

  • Un compte Microsoft qui possède déjà Minecraft Bedrock (le tien fait très bien l'affaire)
  • Le launcher Minecraft officiel installé
  • BedrockLauncher, un launcher tiers open source qui permet d'installer et de lancer n'importe quelle version historique de Bedrock
  • .NET 8.0 Desktop Runtime
  • Le mode développeur activé sur Windows

Étape 1 -- Installer Bedrock au moins une fois avec le launcher officiel

Avant de faire quoi que ce soit d'autre, ouvre le launcher Minecraft officiel, va sur l'onglet Minecraft: Bedrock Edition, et clique sur Install. Il faut que Bedrock ait été installé et lancé au moins une fois par la voie officielle avant de toucher à BedrockLauncher.

Étape 2 -- Télécharger BedrockLauncher

Direction la page des releases GitHub du projet. Prends le zip de la dernière version listée dans les Assets.

Étape 3 -- Extraire l'archive

Une fois le zip téléchargé, extrais-le dans ton dossier Downloads (ou n'importe où, tant que tu retrouves le dossier après).

Étape 4 -- Lancer l'exécutable

Va dans le dossier extrait et lance BedrockLauncher.exe.

Étape 5 -- Installer .NET Desktop Runtime et activer le mode développeur

Au premier lancement, Windows va très probablement te réclamer le .NET 8.0 Desktop Runtime -- installe-le. Il faut aussi activer le mode développeur dans Paramètres > Système > Pour les développeurs, parce que BedrockLauncher installe le jeu comme un paquet loose (des fichiers bruts, pas un vrai paquet signé du Store), et Windows refuse ce genre d'installation sans ce mode.

Étape 6 -- Créer une nouvelle installation

Relance BedrockLauncher, connecte-toi avec ton compte Microsoft, va dans l'onglet Installations, puis clique sur New installation.

Étape 7 -- Choisir une vieille version

Donne un nom à l'installation, puis dans la liste des versions, choisis une vieille version -- typiquement une version 1.16.x ou plus ancienne. Clique sur Create.

Étape 8 -- Lancer l'installation

Clique sur Play. L'extraction des fichiers peut prendre jusqu'à dix minutes selon la machine -- le launcher va sembler figé (« Not Responding »), c'est normal, laisse-le tourner.

Étape 9 -- Choisir la cape

Une fois le jeu lancé, connecte-toi avec ton compte, crée un nouveau personnage et va dans l'éditeur de skin, onglet Capes. Là, tu vas retrouver la liste complète de toutes les capes qui existent dans Minecraft -- y compris celles que tu n'as jamais eues (capes d'events promo, de festivals passés, de Mob Vote, etc). Choisis celle que tu veux.

Ne touche pas au reste de l'apparence du skin à ce stade, laisse juste la cape.

Étape 10 -- Réinstaller la version officielle

Retourne dans le launcher officiel, onglet Installation, et clique sur Uninstall sur l'installation Bedrock principale, puis réinstalle-la (ou fais Check for Updates). Relance Minecraft Bedrock depuis le launcher officiel cette fois.

Et voilà -- ta cape est là, sur la version officielle, sur ton vrai profil.

Ce qu'il se passe probablement

Je n'ai pas mis les mains dans le code source fermé de Bedrock (contrairement à Java qui est décompilable), donc ce qui suit est une explication probable, pas une certitude absolue. Mais le comportement observé colle assez bien à l'hypothèse suivante.

Le sélecteur de capes n'a jamais été un contrôle d'accès

Sur Bedrock, l'écran de sélection de capes affiche vraisemblablement la liste complète des capes qui existent dans le jeu, pas seulement celles que ton compte possède. Sur les clients récents, un filtre applicatif (côté client ou via un appel réseau vers un service d'entitlements Xbox/Microsoft) grise ou masque les capes que tu ne possèdes pas.

Le point clé, c'est que ce filtre a probablement été ajouté après coup, sur une version du jeu suffisamment récente. Une version comme 1.16.x est antérieure à ce filtre, ou utilise un mécanisme de vérification différent (voire absent) : tout ce qui est dans la liste devient sélectionnable, entitlement ou pas.

La cape est stockée où, exactement ?

C'est la partie qui explique pourquoi ça survit à la réinstallation. Le choix de skin/cape sur Bedrock n'est pas juste un fichier local jetable -- il est probablement synchronisé sur le profil Xbox Live associé à ton compte Microsoft (le même système qui gère ton skin sur les autres plateformes Bedrock -- mobile, console, etc.). Quand tu sélectionnes une cape dans le vieux client, celui-ci envoie très probablement cette sélection au service de profil, exactement comme le ferait un client à jour avec une cape légitime -- parce que du point de vue du client, il n'y a aucune différence entre une cape « à toi » et une cape « choisie ». Le service de profil, lui, fait confiance au client sur ce point : il enregistre la sélection sans revalider si l'entitlement existe réellement derrière, du moins pas au moment de l'écriture.

Résultat : quand tu relances le jeu officiel à jour, il va chercher ton skin/cape actuel sur le service de profil -- et le service renvoie fidèlement ce qui a été enregistré, cape non-légitime comprise. Le check d'entitlement, s'il existe, se fait probablement uniquement au moment de la sélection dans l'UI (d'où le filtre sur les clients récents), et laisse passer l'affichage de ce qui est déjà enregistré sur le profil.

Le parallèle avec Java

C'est la même famille de faille logique que celle du cape-mod sur Java : un service fait confiance à une donnée sans revérifier son origine à chaque étape. Sur Java, c'est une signature RSA valide mais replayée sur le mauvais profil. Sur Bedrock, c'est vraisemblablement une sélection de cape acceptée par un vieux client qui n'a jamais eu le bon filtre, puis propagée sans re-vérification vers l'état persistant du compte. Dans les deux cas, le problème n'est pas le point d'entrée (le mod Java, le vieux client Bedrock) -- c'est que la couche qui devrait revalider l'entitlement en aval ne le fait pas, ou ne le fait qu'une fois, au mauvais endroit.

Pourquoi ça marche encore

Deux explications possibles, pas incompatibles entre elles :

  1. Mojang ne considère probablement pas ça comme prioritaire. Il faut un launcher tiers, une manipulation en plusieurs étapes, et le résultat est purement cosmétique -- aucun avantage de gameplay, aucune donnée d'autrui compromise.
  2. Patcher ça correctement demanderait de revalider les entitlements à chaque lecture du profil, pas seulement à la sélection -- ce qui veut dire un appel réseau supplémentaire à chaque affichage de skin, pour un problème qui ne concerne que l'esthétique.

Conclusion

Ce tuto tient en dix captures d'écran, mais il illustre un principe qu'on retrouve partout en sécurité logicielle : dès qu'un système historique (une vieille version de client, une API legacy, un service jamais mis à jour) peut encore écrire dans un état partagé, le contrôle d'accès du présent ne protège que ce qui passe par le présent. Tout ce qui peut encore parler à l'ancienne API contourne le filtre plus récent -- le filtre fonctionne sur les versions récentes, mais il n'a jamais été appliqué à la version qui l'a précédé.

3 points clés

  1. Le sélecteur de capes d'une vieille version de Bedrock affiche probablement la liste complète des capes du jeu, sans filtre d'entitlement.
  2. La sélection est ensuite synchronisée sur ton profil Xbox Live comme n'importe quelle cape légitime -- le service de profil fait confiance au client.
  3. Le check d'entitlement, s'il existe, se fait à la sélection dans l'UI récente -- pas à la lecture de ce qui est déjà enregistré sur le compte.

Minecraft Bedrock 任意披风获取法

Java 版有一堆歪门邪道搞到本不该有的披风（见 cape-mod 那篇）。Bedrock 不一样，认证不一样，但路还是有，你只需要第三方启动器加足够老的游戏版本，老到无视你以为天经地义的校验。

下面先讲怎么做，再看底下可能发生了什么。

你需要

  • 拥有 Minecraft Bedrock 的微软账号（你自己的就行）
  • 装好官方 Minecraft 启动器
  • BedrockLauncher，开源第三方启动器，能装能跑 Bedrock 任意历史版本
  • .NET 8.0 Desktop Runtime
  • Windows 开开发者模式

第 1 步，先用官方启动器装一次 Bedrock

碰 BedrockLauncher 之前，打开官方 Minecraft 启动器，进 Minecraft: Bedrock Edition 标签，点 Install。Bedrock 必须先被官方路子装过跑过一次。

第 2 步，下 BedrockLauncher

去项目 GitHub releases 页。拿 Assets 里最新版的 zip。

第 3 步，解压

zip 下好解到 Downloads 文件夹（随便哪，解完找得到就行）。

第 4 步，跑可执行文件

进解压的文件夹，跑 BedrockLauncher.exe。

第 5 步，装 .NET Desktop Runtime，开开发者模式

第一次启动，Windows 大概率跟你要 .NET 8.0 Desktop Runtime，装上。还要在设置 > 系统 > 开发者选项里开开发者模式，因为 BedrockLauncher 把游戏装成松散包（一堆裸文件，不是商店签名的正经包），不开这模式 Windows 拒绝装。

第 6 步，建新安装

重开 BedrockLauncher，微软账号登录，进安装标签，点 New installation。

第 7 步，选老版本

起个名，版本列表里选个老版本，一般 1.16.x 或更老。点 Create。

第 8 步，启动安装

点 Play。解压文件看机器要 up to 十分钟，启动器看着像卡死（"Not Responding"），正常，让它跑。

第 9 步，选披风

游戏起来了，账号登录，建新角色进皮肤编辑器，Capes 标签。这时你会看到游戏里全部披风列表，包括你从来没拥有过的（活动限定、往届节日、Mob Vote 等）。选你想要的。

这时皮肤别处别动，只动披风。

第 10 步，装回官方版本

回官方启动器，安装标签，主 Bedrock 安装点 Uninstall，再装回来（或 Check for Updates）。这次从官方启动器启动 Minecraft Bedrock。

完事了，披风在官方版本、你的真 profile 上了。

底下可能发生了什么

Bedrock 闭源我没法下手翻（Java 能反编译它不能），下面是可能的解释，不是板上钉钉。但观察到的行为和这个假设对得很好。

披风选择器从来不是访问控制

Bedrock 的披风选择界面大概率显示游戏里存在的全部披风，不是你账号拥有的。新客户端有个应用层过滤（客户端本地或调 Xbox/微软 entitlement 服务走网络），把没拥有的灰掉或隐藏。

关键这过滤大概率是后加上的，足够新的版本才有。1.16.x 这种老版本早于过滤，或用另一套验证（甚至没有）：列表里有的都能选，有没有 entitlement 都行。

披风到底存哪了？

这解释了为什么重装还在。Bedrock 的皮肤/披风选择不只是本地文件一扔，大概率同步到微软账号绑的 Xbox Live profile（管 Bedrock 全平台皮肤的同一套系统，手机、主机等）。老客户端里选披风，大概率像正版披风一样把选择发给 profile 服务，对客户端来说"你的"和"选的"没区别。profile 服务信客户端写的：记下选择，当时不回头验 entitlement 到底有没有，至少写的时候不验。

结果：重开新版官方游戏，它去 profile 服务取你当前皮肤/披风，服务原样返回记下的，非正版披风也一样。entitlement 检查如果有，也只在新版 UI 选的时候做一次（所以新版有过滤），显示已存 profile 时放行。

和 Java 的对照

和 Java cape-mod 同一族逻辑漏洞：服务信了数据，不在每步重验来源。Java 是 RSA 签名有效但重放到错的 profile。Bedrock 大概率是老客户端没过滤的披风选择，被一路同步到账号持久状态，下游不重验 entitlement。入口不同（Java 的 mod，老版 Bedrock 客户端），病一样：该重验 entitlement 的下游没验，或只验了一次还验错了地方。

为什么现在还管用

两种可能，不互斥：

  1. Mojang 大概率觉得不值得修。 要第三方启动器，加多步操作，结果纯 cosmetic，无玩法优势，不碰别人数据。
  2. 修好要每次读 profile 都重验 entitlement，不只选的时候验一次，等于每次显示皮肤多一次网络调用，就为个外观问题。

结语

教程十张截图，但讲的是软件安全里反复出现的原理：只要还有历史系统（老客户端、legacy API、没升级的服务）能写共享状态，今天的访问控制只管得住走今天路的人。还能讲老 API 的话，全绕过新过滤，新版上过滤好好的，老版本出生时根本没有它。

  2. 选择像正版披风一样同步到你的 Xbox Live profile，profile 服务信客户端。
  3. entitlement 检查如果有，只在新版 UI 选的时候做，不在读已存账号时做。

Minecraft Bedrockで好きなケープを付ける方法

Java版には、本来持てないはずのケープを手に入れるひねくれた方法がいくらでもある（cape-modの記事参照）。Bedrockではゲームが違い、認証も違う。それでも方法はある。サードパーティランチャーと、当然と思われてる検証を無視できるくらい古いゲームバージョンがあればいい。

やり方を示してから、裏側でたぶん何が起きてるか見ていく。

用意するもの

  • Bedrock版Minecraftを所有するMicrosoftアカウント（自分のもので十分）
  • 公式Minecraftランチャーのインストール済み
  • BedrockLauncher。あらゆる歴史的Bedrock版をインストールして起動できるオープンソースのサードパーティランチャー
  • .NET 8.0 Desktop Runtime
  • Windowsで開発者モード有効化

ステップ1：公式ランチャーでBedrockを最低1回インストールする

他に何するより先に、公式Minecraftランチャーを開いてMinecraft: Bedrock Editionタブに行ってインストールを押す。BedrockLauncherに触る前に、Bedrockが公式ルートで最低1回インストールされて起動されたことが必要だ。

ステップ2：BedrockLauncherをダウンロードする

プロジェクトのGitHubリリースページへ行く。Assetsに載ってる最新版のzipを取る。

ステップ3：アーカイブを展開する

zipをダウンロードしたら、Downloadsフォルダ（どこでもいいけど後で見つけられるところ）に展開する。

ステップ4：実行ファイルを実行する

展開したフォルダに入ってBedrockLauncher.exeを起動する。

ステップ5：.NET Desktop Runtimeを入れて開発者モードを有効化する

初回起動でWindowsがほぼ確実に**.NET 8.0 Desktop Runtimeを要求してくる。インストールすること。あと設定 > システム > 開発者向けで開発者モード**も有効化する。BedrockLauncherはゲームをlooseパッケージ（Storeの正式署名パッケージじゃない生ファイル群）としてインストールするので、このモードなしではWindowsがそういうインストールを拒否するからだ。

ステップ6：新しいインストールを作る

BedrockLauncherを再起動してMicrosoftアカウントでサインインし、Installationsタブに行ってNew installationを押す。

ステップ7：古いバージョンを選ぶ

インストールに名前を付けて、バージョン一覧から古いバージョンを選ぶ。だいたい1.16.x以前だ。Createを押す。

ステップ8：インストールを開始する

Playを押す。ファイル展開にマシンによっては10分くらいかかることがある。ランチャーが固まったように見える（「応答なし」）のは正常だ。回したままにしておく。

ステップ9：ケープを選ぶ

ゲームが起動したらアカウントでサインインして、新しいキャラクターを作ってスキン編集画面のケープタブに行く。そこにはMinecraftに存在するケープの完全一覧が出てくる。持ったことのないものも含めてだ（プロモイベントケープ、過去フェス、Mob投票など）。好きなのを選ぶ。

この段階ではスキンの見た目の他部分は触らないこと。ケープだけにしておく。

ステップ10：公式バージョンを入れ直す

公式ランチャーに戻ってインストールタブでメインのBedrockインストールをアンインストールしてから入れ直す（または更新チェック）。今度は公式ランチャーからMinecraft Bedrockを起動し直す。

以上だ。公式バージョンの本物プロフィールにケープが付いてる。

裏側でたぶん起きてること

私はBedrockのクローズドソースには手を突っ込んでない（Javaと違ってデコンパイルできない）。だから以下は推定の説明で、絶対の確実性はない。でも観察された挙動はこの仮説にかなり合う。

ケープ選択画面はアクセス制御じゃなかった

Bedrockではケープ選択画面はたぶん、自分のアカウントが持ってるケープだけじゃなくゲームに存在するケープの完全一覧を表示してる。最近のクライアントでは、アプリ側フィルタ（クライアント側か、XboxやMicrosoftのentitlementサービスへのネットワーク呼び出し経由）で持ってないケープをグレーアウトか非表示にしてる。

ポイントは、このフィルタはたぶん後から足されたってことだ。十分最近のバージョンに追加されたものだ。1.16.xみたいなバージョンはこのフィルタより前か、違う（あるいは存在しない）検証機構を使ってる。一覧にあるものは全部選択可能になる。entitlementの有無に関わらずだ。

ケープは結局どこに保存されるのか

これが再インストール後も残る理由を説明する部分だ。Bedrockのスキンやケープ選択は使い捨てのローカルファイルじゃない。Microsoftアカウントに紐付いたXbox Liveプロフィールに同期されてる可能性が高い（他のBedrockプラットフォーム、モバイルやコンソールなどでスキンを管理するのと同じ仕組み）。古いクライアントでケープを選ぶと、その選択はたぶんプロフィールサービスに送信される。正規ケープを持つ最新クライアントがやるのとまったく同じようにだ。クライアント視点では「自分のケープ」と「選んだケープ」に違いはないからね。プロフィールサービス側はこの点でクライアントを信頼してる。選択を記録して、裏に本当にentitlementがあるか再検証しない。少なくとも書き込み時にはね。

結果、最新の公式ゲームを起動し直すと、プロフィールサービスから現在のスキンやケープを取りに行く。サービスは記録されたものを忠実に返す。正規じゃないケープ込みでだ。entitlementチェックがあるとしても、たぶん選択時のUIでだけ行われて（だから最近クライアントにフィルタがある）。プロフィールにすでに記録されたものの表示は通してしまう。

Java版との共通点

Java版のcape-modと同じ系統の論理欠陥だ。サービスがデータを信頼して、各段階で出所を再検証しないパターンだ。Java版では有効なRSA署名だけど間違ったプロフィールにリプレイされたものだ。Bedrock版ではたぶん、正しいフィルタを持たなかった古いクライアントに受け入れられたケープ選択が、アカウントの永続状態へ再検証なしに伝播したものだ。どちらも問題は入口（Java版mod、Bedrock版古クライアント）じゃない。下流でentitlementを再検証すべき層がしないか、間違った場所で1回だけするかってことだ。

なぜ今も動くのか

2つの説明が考えられる。互いに矛盾しない。

  1. Mojangはたぶんこれを優先事項と思ってない。 サードパーティランチャーが必要で、手順が多段階で、結果は見た目だけだ。ゲームプレイ有利も他人のデータ侵害もない。
  2. ちゃんと直すにはプロフィール読み取りのたびにentitlementを再検証する必要がある。 選択時だけじゃなくだ。つまりスキン表示のたびに追加のネットワーク呼び出しってことで、見た目だけの問題にしては重い。

結論

このチュートリアルはスクショ10枚だけど、ソフトウェアセキュリティのあちこちに出る原則を例示してる。歴史的システム（古いクライアントバージョン、レガシーAPI、更新されないサービス）が共有状態にまだ書き込める限り、今のアクセス制御は今を通るものしか守らない。古いAPIにまだ話せるものは全部、新しめのフィルタを迂回する。フィルタは最近バージョンでは効いてるけど、その前のバージョンには適用されたことがなかったんだ。

Minecraft Bedrock에서 모든 망토를 얻는 방법

Java에서는 가져서는 안 될 망토를 손에 넣는 이상한 방법이 잔뜩 있어요 (cape-mod 글을 보세요). Bedrock에서는 게임도 다르고 인증도 다르지만, 그래도 방법이 하나 있어요. 서드파티 런처 하나와 당연하게 여겨지던 검증을 무시할 만큼 충분히 오래된 게임 버전만 있으면 돼요.

방법은 이렇고, 이어서 내부에서 아마 무슨 일이 일어나는지 살펴봐요.

필요한 것

  • Minecraft Bedrock을 이미 보유한 Microsoft 계정 (여러분 계정이면 충분해요)
  • 공식 Minecraft 런처 설치
  • 어떤 Bedrock 역사 버전이든 설치하고 실행할 수 있게 해주는 오픈 소스 서드파티 런처 BedrockLauncher
  • .NET 8.0 Desktop Runtime
  • Windows에서 개발자 모드 활성화

1단계: 공식 런처로 Bedrock을 최소 한 번 설치하기

다른 것을 하기 전에 공식 Minecraft 런처를 열고 Minecraft: Bedrock Edition 탭으로 가서 Install을 눌러요. BedrockLauncher를 만지기 전에 공식 경로로 Bedrock을 최소 한 번 설치하고 실행해야 해요.

2단계: BedrockLauncher 다운로드하기

프로젝트의 GitHub 릴리스 페이지로 가요. Assets에 있는 최신 버전 zip을 가져와요.

3단계: 압축 풀기

zip을 다운로드했으면 Downloads 폴더(나중에 찾을 수 있는 곳이면 어디든)에 풀어요.

4단계: 실행 파일 실행하기

푼 폴더로 가서 BedrockLauncher.exe를 실행해요.

5단계: .NET Desktop Runtime 설치와 개발자 모드 활성화

첫 실행 때 Windows가 .NET 8.0 Desktop Runtime을 요구할 가능성이 커요. 설치해요. 개발자 모드도 설정 > 시스템 > 개발자용에서 켜야 해요. BedrockLauncher가 게임을 루즈 패키지(날것 파일, Store의 진짜 서명 패키지가 아님)로 설치하는데, 이 모드 없이는 Windows가 그런 설치를 거부하거든요.

6단계: 새 설치 만들기

BedrockLauncher를 다시 실행하고 Microsoft 계정으로 로그인한 뒤 Installations 탭으로 가서 New installation을 눌러요.

7단계: 오래된 버전 고르기

설치에 이름을 짓고 버전 목록에서 오래된 버전, 보통 1.16.x나 그 이전 버전을 골라요. Create를 눌러요.

8단계: 설치 실행하기

Play를 눌러요. 기기에 따라 파일 추출에 최대 10분까지 걸릴 수 있어요. 런처가 멈춘 것처럼 보여요("Not Responding"). 정상이니 그냥 두세요.

9단계: 망토 고르기

게임이 실행되면 계정으로 로그인하고 새 캐릭터를 만든 뒤 스킨 편집기의 망토 탭으로 가요. 거기에서 Minecraft에 존재하는 모든 망토의 전체 목록을 보게 돼요. 한 번도 가져본 적 없는 것들까지요 (프로모 이벤트 망토, 지난 축제 망토, Mob Vote 망토 등). 원하는 것을 고르세요.

이 단계에서는 스킨 외형의 나머지를 건드리지 마세요. 망토만 두세요.

10단계: 공식 버전 다시 설치하기

공식 런처로 돌아가 설치 탭에서 주 Bedrock 설치의 Uninstall을 누른 뒤 다시 설치해요 (또는 업데이트 확인). 이번에는 공식 런처에서 Minecraft Bedrock을 다시 실행해요.

됐어요. 공식 버전에서, 진짜 프로필에 망토가 있어요.

아마 내부에서 일어나는 일

Bedrock의 닫힌 소스 코드를 뜯어보지는 않았어요 (역컴파일되는 Java와는 달라요). 그래서 다음 설명은 그럴듯한 설명이지 절대적인 확신은 아니에요. 하지만 관찰된 동작은 다음 가설과 꽤 잘 맞아요.

망토 선택기는 애초에 접근 제어가 아니었어요

Bedrock에서 망토 선택 화면은 아마 여러분 계정이 가진 망토만이 아니라 게임에 존재하는 모든 망토의 전체 목록을 보여줘요. 최신 클라이언트에서는 애플리케이션 필터(클라이언트 측이나 Xbox와 Microsoft entitlement 서비스로의 네트워크 호출)가 가지지 않은 망토를 회색으로 비활성화하거나 숨겨요.

핵심은, 그 필터가 아마 나중에 충분히 최신 게임 버전에 추가됐다는 거예요. 1.16.x 같은 버전은 그 필터 이전이거나, 다른(혹은 없는) 검증 방식을 써요. 목록에 있는 모든 것이 entitlement 여부와 무관하게 선택 가능해져요.

망토는 정확히 어디에 저장될까요?

재설치 후에도 남는 이유를 설명하는 부분이에요. Bedrock의 스킨과 망토 선택은 그냥 버릴 수 있는 로컬 파일이 아니에요. 아마 Microsoft 계정에 연결된 Xbox Live 프로필에 동기화돼요 (다른 Bedrock 플랫폼인 모바일, 콘솔 등에서 스킨을 관리하는 것과 같은 시스템이에요). 오래된 클라이언트에서 망토를 고르면 아마 이 선택을 프로필 서비스로 보내요. 정품 망토를 가진 최신 클라이언트가 하는 것과 똑같이요. 클라이언트 관점에서는 "내 것"인 망토와 "고른" 망토 사이에 아무 차이가 없으니까요. 프로필 서비스는 이 지점에서 클라이언트를 신뢰해요. 뒤에 진짜 entitlement가 있는지 다시 검증하지 않고 기록해요. 적어도 쓰는 시점에는요.

결과: 최신 공식 게임을 다시 실행하면 프로필 서비스에서 현재 스킨과 망토를 가져와요. 그리고 서비스는 기록된 것을 충실히 돌려줘요. 정품이 아닌 망토까지요. entitlement 검사가 있다면 아마 UI에서 선택하는 시점(그래서 최신 클라이언트에 필터가 있음)에만 일어나고, 프로필에 이미 기록된 것을 표시할 때는 통과시켜요.

Java와의 유사점

Java의 cape-mod와 같은 논리적 결함 계열이에요. 서비스가 출처를 매 단계 다시 확인하지 않고 데이터를 신뢰해요. Java에서는 유효하지만 잘못된 프로필에 재생된 RSA 서명이에요. Bedrock에서는 아마 적절한 필터를 가져본 적 없는 오래된 클라이언트가 수락한 망토 선택이 계정의 지속 상태로 다시 검증 없이 전파된 거예요. 두 경우 모두 문제는 진입점(Java 모드, 오래된 Bedrock 클라이언트)이 아니에요. 하류에서 entitlement를 다시 검증해야 할 층이 하지 않거나, 한 번만 잘못된 지점에서 하기 때문이에요.

아직도 통하는 이유

가능한 설명 두 가지인데, 서로 모순되지 않아요.

  1. Mojang은 아마 이것을 우선순위로 보지 않아요. 서드파티 런처가 필요하고 여러 단계 조작이 필요하며, 결과는 순전히 외형이에요. 게임플레이 이점도 없고 타인의 데이터 침해도 없어요.
  2. 제대로 패치하려면 프로필을 읽을 때마다 entitlement를 다시 검증해야 해요. 선택할 때만이 아니라요. 외형 문제 하나 때문에 스킨을 표시할 때마다 네트워크 호출을 하나 더 한다는 뜻이에요.

  • Zaten Minecraft Bedrocka sahip bir Microsoft hesabı (seninki gayet iyi iş görür)

Muhtemelen neler oluyor

Pelerin seçici hiç erişim kontrolü olmadı

Kilit nokta şu ki bu filtre muhtemelen sonradan eklendi, yeterince güncel bir oyun sürümünde. 1.16.x gibi bir sürüm bu filtreden öncedir ya da farklı bir doğrulama mekanizması kullanır (hatta yok): listedeki her şey yetki olsun olmasın seçilebilir olur.

Yeniden kurulmadan sağ çıkmayı açıklayan kısım bu. Sonuç: güncel resmi oyunu yeniden çalıştırdığında mevcut görünümünü/pelerinini profil servisinden çeker ve servis kaydedileni sadakatle döndürür, meşru olmayan pelerin dahil. Javadaki cape-mod ile aynı mantıksal açık ailesi: bir servis her adımda kaynağını yeniden doğrulamadan bir veriye güvenir. Javada geçerli ama yanlış profilde tekrar oynatılan bir RSA imzasıdır. Bedrockta büyük olasılıkla doğru filtreye hiç sahip olmamış eski bir istemci tarafından kabul edilen bir pelerin seçimi, sonra hesabın kalıcı durumuna yeniden doğrulama olmadan yayılır. İki durumda da sorun giriş noktası değildir (Java modu, eski Bedrock istemcisi): yetkilendirmeyi aşağıda yeniden doğrulaması gereken katmanın bunu yapmaması, ya da yanlış yerde bir kez yapmasıdır.

  1. Mojang bunu muhtemelen öncelikli görmüyor. Üçüncü parti bir başlatıcı, çok adımlı bir manipülasyon gerekir ve sonuç tamamen kozmetiktir: oyun avantajı yok, başkasının verisi ele geçirilmiş değil.
  2. Bunu düzgün yamalamak yetkilendirmeleri profilin her okunuşunda yeniden doğrulamayı gerektirirdi, yalnızca seçimde değil: bu da yalnızca estetikle ilgili bir sorun için her görünüm gösteriminde ek bir ağ çağrısı demektir.

Come ottenere qualsiasi mantello su Minecraft Bedrock

Su Java, esistono un sacco di modi strani per ritrovarti con un mantello che non dovresti avere (vedi l'articolo su cape-mod). Su Bedrock, il gioco è diverso, l'auth è diversa, ma esiste comunque un modo: ti basta un launcher di terzi e una versione del gioco abbastanza vecchia da ignorare la validazione che si crede acquisita.

Ecco come fare, e poi guardiamo cosa succede probabilmente sotto il cofano.

Cosa ti serve

  • Un account Microsoft che possiede già Minecraft Bedrock (il tuo va benissimo)
  • Il launcher Minecraft ufficiale installato
  • BedrockLauncher, un launcher di terzi open source che permette di installare e lanciare qualsiasi versione storica di Bedrock
  • .NET 8.0 Desktop Runtime
  • La modalità sviluppatore attivata su Windows

Passo 1: installa Bedrock almeno una volta col launcher ufficiale

Prima di fare qualsiasi altra cosa, apri il launcher Minecraft ufficiale, vai sulla scheda Minecraft: Bedrock Edition, e clicca su Install. Bedrock deve essere stato installato e lanciato almeno una volta per via ufficiale prima di toccare BedrockLauncher.

Passo 2: scarica BedrockLauncher

Vai sulla pagina delle release GitHub del progetto. Prendi lo zip dell'ultima versione elencata negli Assets.

Passo 3: estrai l'archivio

Una volta scaricato lo zip, estrailo nella tua cartella Downloads (o ovunque, basta che ritrovi la cartella dopo).

Passo 4: lancia l'eseguibile

Vai nella cartella estratta e lancia BedrockLauncher.exe.

Passo 5: installa .NET Desktop Runtime e attiva la modalità sviluppatore

Al primo lancio, Windows molto probabilmente ti chiederà il .NET 8.0 Desktop Runtime: installalo. Bisogna anche attivare la modalità sviluppatore in Impostazioni > Sistema > Per gli sviluppatori, perché BedrockLauncher installa il gioco come pacchetto loose (file grezzi, non un vero pacchetto firmato dallo Store), e Windows rifiuta questo tipo di installazione senza questa modalità.

Passo 6: crea una nuova installazione

Rilancia BedrockLauncher, accedi col tuo account Microsoft, vai nella scheda Installations, poi clicca su New installation.

Passo 7: scegli una vecchia versione

Dai un nome all'installazione, poi nella lista delle versioni, scegli una versione vecchia: tipicamente una 1.16.x o più antica. Clicca su Create.

Passo 8: lancia l'installazione

Clicca su Play. L'estrazione dei file può prendere fino a dieci minuti secondo la macchina: il launcher sembrerà bloccato ("Not Responding"), è normale, lascialo girare.

Passo 9: scegli il mantello

Una volta lanciato il gioco, accedi col tuo account, crea un nuovo personaggio e vai nell'editor di skin, scheda Capes. Lì, ritroverai la lista completa di tutti i mantelli che esistono in Minecraft: compresi quelli che non hai mai avuto (mantelli di eventi promo, di festival passati, di Mob Vote, ecc). Scegli quello che vuoi.

Non toccare il resto dell'aspetto della skin a questo punto, lascia solo il mantello.

Passo 10: reinstalla la versione ufficiale

Torna nel launcher ufficiale, scheda Installation, e clicca su Uninstall sull'installazione Bedrock principale, poi reinstallala (o fai Check for Updates). Rilancia Minecraft Bedrock stavolta dal launcher ufficiale.

E voilà: il tuo mantello è lì, sulla versione ufficiale, sul tuo vero profilo.

Cosa succede probabilmente

Non ho messo le mani nel codice sorgente chiuso di Bedrock (a differenza di Java che è decompilabile), quindi ciò che segue è una spiegazione probabile, non una certezza assoluta. Ma il comportamento osservato si adatta abbastanza bene all'ipotesi seguente.

Il selettore di mantelli non è mai stato un controllo di accesso

Su Bedrock, la schermata di selezione mantelli mostra verosimilmente la lista completa dei mantelli che esistono nel gioco, non solo quelli che il tuo account possiede. Sui client recenti, un filtro applicativo (lato client o via una chiamata rete verso un servizio di entitlement Xbox/Microsoft) rende grigi o nasconde i mantelli che non possiedi.

Il punto chiave, è che questo filtro è stato probabilmente aggiunto dopo, su una versione del gioco abbastanza recente. Una versione come 1.16.x è anteriore a questo filtro, o usa un meccanismo di verifica diverso (se non assente): tutto ciò che è nella lista diventa selezionabile, entitlement o no.

Il mantello è salvato dove, esattamente?

È la parte che spiega perché sopravvive alla reinstallazione. La scelta di skin/mantello su Bedrock non è solo un file locale usa e getta: è probabilmente sincronizzata sul profilo Xbox Live associato al tuo account Microsoft (lo stesso sistema che gestisce la tua skin sulle altre piattaforme Bedrock: mobile, console, ecc.). Quando selezioni un mantello nel vecchio client, questo invia molto probabilmente questa selezione al servizio di profilo, esattamente come farebbe un client aggiornato con un mantello legittimo: perché dal punto di vista del client, non c'è alcuna differenza tra un mantello "tuo" e un mantello "scelto". Il servizio di profilo, lui, si fida del client su questo punto: registra la selezione senza rivalidare se l'entitlement esiste davvero dietro, almeno non al momento della scrittura.

Risultato: quando rilanci il gioco ufficiale aggiornato, va a cercare la tua skin/mantello attuale sul servizio di profilo: e il servizio restituisce fedelmente ciò che è stato registrato, mantello non legittimo compreso. Il check di entitlement, se esiste, si fa probabilmente solo al momento della selezione nella UI (da cui il filtro sui client recenti), e lascia passare la visualizzazione di ciò che è già registrato sul profilo.

Il parallelo con Java

È la stessa famiglia di falla logica di quella del cape-mod su Java: un servizio si fida di un dato senza riverificarne l'origine a ogni passo. Su Java, è una firma RSA valida ma rigiocata sul profilo sbagliato. Su Bedrock, è verosimilmente una selezione di mantello accettata da un vecchio client che non ha mai avuto il filtro giusto, poi propagata senza riverifica verso lo stato persistente dell'account. In entrambi i casi, il problema non è il punto di ingresso (il mod Java, il vecchio client Bedrock): è che lo strato che dovrebbe rivalidare l'entitlement a valle non lo fa, o lo fa una volta sola, nel posto sbagliato.

Perché funziona ancora

Due spiegazioni possibili, non incompatibili tra loro:

  1. Mojang probabilmente non lo considera prioritario. Serve un launcher di terzi, una manipolazione in più passi, e il risultato è puramente cosmetico: nessun vantaggio di gameplay, nessun dato altrui compromesso.
  2. Patcharlo correttamente richiederebbe di rivalidare gli entitlement a ogni lettura del profilo, non solo alla selezione: il che vuol dire una chiamata rete in più a ogni visualizzazione di skin, per un problema che riguarda solo l'estetica.

Conclusione

Questo tutorial sta in dieci screenshot, ma illustra un principio che si ritrova ovunque in sicurezza software: appena un sistema storico (una vecchia versione di client, una API legacy, un servizio mai aggiornato) può ancora scrivere in uno stato condiviso, il controllo di accesso del presente protegge solo ciò che passa dal presente. Tutto ciò che può ancora parlare alla vecchia API aggira il filtro più recente: il filtro funziona sulle versioni recenti, ma non è mai stato applicato alla versione che l'ha preceduto.

Sobald das Zip heruntergeladen ist, extrahiere es in deinen Downloads-Ordner (oder irgendwohin, solange du den Ordner danach wiederfindest).

Schritt 4, die Executable starten

Geh in den extrahierten Ordner und starte BedrockLauncher.exe.

Schritt 5, .NET Desktop Runtime installieren und Entwicklermodus aktivieren

Beim ersten Start wird Windows sehr wahrscheinlich das .NET 8.0 Desktop Runtime verlangen, installiere es. Du musst auch den Entwicklermodus in Einstellungen > System > Für Entwickler aktivieren, weil BedrockLauncher das Spiel als loses Paket installiert (rohe Dateien, kein echtes signiertes Store-Paket), und Windows verweigert diese Art Installation ohne diesen Modus.

Sobald das Spiel gestartet ist, melde dich mit deinem Konto an, erstelle einen neuen Charakter und geh in den Skin-Editor, Tab Capes. Dort findest du die komplette Liste aller Capes, die es in Minecraft gibt, einschließlich derer, die du nie hattest (Promo-Event-Capes, vergangene Festivals, Mob Vote usw.). Wähle die, die du willst.

Fass den Rest des Skin-Aussehens in diesem Stadium nicht an, lass nur die Cape.

Geh zurück in den offiziellen Launcher, Tab Installation, und klicke auf Uninstall bei der Haupt-Bedrock-Installation, installiere sie dann neu (oder mach Check for Updates). Starte Minecraft Bedrock diesmal aus dem offiziellen Launcher.

Und da ist sie, deine Cape, auf der offiziellen Version, auf deinem echten Profil.

Was wahrscheinlich passiert

Ich habe meine Hände nicht in den geschlossenen Bedrock-Quellcode gesteckt (im Gegensatz zu Java, das dekompilierbar ist), also ist das Folgende eine wahrscheinliche Erklärung, keine absolute Gewissheit. Aber das beobachtete Verhalten passt ziemlich gut zur folgenden Hypothese.

Der Cape-Selektor war nie eine Zugriffskontrolle

Auf Bedrock zeigt der Cape-Auswahlbildschirm wahrscheinlich die komplette Liste der Capes, die es im Spiel gibt, nicht nur die, die dein Konto besitzt. Auf aktuellen Clients graut oder versteckt ein Anwendungsfilter (clientseitig oder über einen Netzwerkaufruf an einen Xbox/Microsoft-Entitlement-Service) die Capes aus, die du nicht besitzt.

Der springende Punkt ist, dass dieser Filter wahrscheinlich nachträglich hinzugefügt wurde, auf einer hinreichend aktuellen Spielversion. Eine Version wie 1.16.x ist älter als dieser Filter oder nutzt einen anderen (oder fehlenden) Verifizierungsmechanismus: Alles in der Liste wird auswählbar, Entitlement oder nicht.

Wo genau ist die Cape gespeichert?

Das ist der Teil, der erklärt, warum es die Neuinstallation überlebt. Die Skin/Cape-Wahl auf Bedrock ist nicht nur eine wegwerfbare lokale Datei, sie wird wahrscheinlich auf das Xbox-Live-Profil synchronisiert, das mit deinem Microsoft-Konto verknüpft ist (dasselbe System, das deinen Skin auf den anderen Bedrock-Plattformen verwaltet, Mobile, Konsole usw.). Wenn du in dem alten Client eine Cape auswählst, schickt dieser die Auswahl sehr wahrscheinlich an den Profildienst, exakt wie es ein aktueller Client mit einer legitimen Cape täte, weil es aus Clientsicht keinen Unterschied zwischen einer Cape "von dir" und einer "gewählten" Cape gibt. Der Profildienst vertraut dabei dem Client: Er speichert die Auswahl, ohne erneut zu validieren, ob das Entitlement wirklich dahintersteht, zumindest nicht zum Schreibzeitpunkt.

Ergebnis: Wenn du das aktuelle offizielle Spiel neu startest, holt es deinen aktuellen Skin/Cape vom Profildienst, und der Dienst gibt treu zurück, was gespeichert wurde, nicht-legitime Cape eingeschlossen. Der Entitlement-Check, falls es ihn gibt, passiert wahrscheinlich nur zum Zeitpunkt der Auswahl in der UI (daher der Filter auf aktuellen Clients) und lässt die Anzeige dessen durch, was schon auf dem Profil gespeichert ist.

Die Parallele zu Java

Es ist dieselbe Familie logischer Lücke wie beim cape-mod auf Java: Ein Service vertraut Daten, ohne ihren Ursprung bei jedem Schritt erneut zu prüfen. Auf Java ist es eine gültige, aber auf das falsche Profil replayte RSA-Signatur. Auf Bedrock ist es wahrscheinlich eine Cape-Auswahl, die von einem alten Client akzeptiert wurde, der nie den richtigen Filter hatte, und dann ohne Re-Verifizierung in den persistenten Kontostand propagiert wurde. In beiden Fällen ist das Problem nicht der Eintrittspunkt (der Java-Mod, der alte Bedrock-Client), sondern dass die Schicht, die das Entitlement nachgelagert erneut validieren sollte, es nicht tut, oder nur einmal, an der falschen Stelle.

Warum es immer noch funktioniert

Zwei mögliche Erklärungen, die sich nicht ausschließen:

  1. Mojang betrachtet das wahrscheinlich nicht als prioritär. Es braucht einen Drittanbieter-Launcher, eine mehrstufige Manipulation, und das Ergebnis ist rein kosmetisch, kein Gameplay-Vorteil, keine kompromittierten Daten anderer.
  2. Es korrekt zu patchen würde erfordern, die Entitlements bei jedem Lesen des Profils erneut zu validieren, nicht nur bei der Auswahl, was einen zusätzlichen Netzwerkaufruf bei jeder Skin-Anzeige bedeuten würde, für ein Problem, das nur die Ästhetik betrifft.

Fazit

Dieses Tutorial passt in zehn Screenshots, aber es illustriert ein Prinzip, das man überall in der Softwaresicherheit wiederfindet: Sobald ein historisches System (eine alte Client-Version, eine Legacy-API, ein nie aktualisierter Service) noch in einen geteilten Zustand schreiben kann, schützt die Zugriffskontrolle der Gegenwart nur das, was durch die Gegenwart geht. Alles, was noch mit der alten API reden kann, umgeht den neueren Filter, der Filter funktioniert auf aktuellen Versionen, wurde aber nie auf die Version angewendet, die ihm vorausging.

Как получить любой плащ в Minecraft Bedrock

На Java есть куча кривых способов оказаться с плащом, которого быть не должно (см. статью про cape-mod). На Bedrock игра другая, авторизация другая, но способ всё равно есть -- тебе достаточно стороннего лаунчера и версии игры достаточно старой, чтобы игнорировать валидацию, которую считают само собой разумеющейся.

Вот как это сделать, а потом посмотрим, что, вероятно, происходит под капотом.

Что тебе нужно

  • Аккаунт Microsoft, уже владеющий Minecraft Bedrock (твой отлично подойдёт)
  • Установленный официальный лаунчер Minecraft
  • BedrockLauncher, сторонний опенсорсный лаунчер, позволяющий ставить и запускать любую историческую версию Bedrock
  • .NET 8.0 Desktop Runtime
  • Включённый режим разработчика в Windows

Шаг 1 -- Установить Bedrock хотя бы раз через официальный лаунчер

Прежде чем делать что-то ещё, открой официальный лаунчер Minecraft, зайди на вкладку Minecraft: Bedrock Edition и нажми Install. Нужно, чтобы Bedrock был установлен и запущен хотя бы раз официальным путём, прежде чем трогать BedrockLauncher.

Шаг 2 -- Скачать BedrockLauncher

Иди на страницу релизов GitHub проекта. Бери zip последней версии в списке Assets.

Шаг 3 -- Распаковать архив

Когда zip скачался, распакуй его в папку Downloads (или куда угодно, лишь бы потом найти папку).

Шаг 4 -- Запустить исполняемый файл

Зайди в распакованную папку и запусти BedrockLauncher.exe.

Шаг 5 -- Установить .NET Desktop Runtime и включить режим разработчика

При первом запуске Windows, скорее всего, потребует .NET 8.0 Desktop Runtime -- установи его. Нужно ещё включить режим разработчика в Параметры > Система > Для разработчиков, потому что BedrockLauncher ставит игру как свободный пакет (сырые файлы, а не настоящий подписанный пакет Store), а Windows отказывает в такой установке без этого режима.

И вот -- твой плащ здесь, на официальной версии, на твоём настоящем профиле.

Что, вероятно, происходит

Я не лазил в закрытый исходник Bedrock (в отличие от Java, которая декомпилируется), так что дальше идёт вероятное объяснение, а не абсолютная уверенность. Но наблюдаемое поведение довольно хорошо ложится на следующую гипотезу.

Селектор плащей никогда не был контролем доступа

На Bedrock экран выбора плащей, видимо, показывает полный список плащей, что есть в игре, а не только те, которыми владеет твой аккаунт. На свежих клиентах прикладной фильтр (на клиенте или через сетевой вызов к сервису разрешений Xbox/Microsoft) сереет или скрывает плащи, которых у тебя нет.

Ключевой момент : этот фильтр, вероятно, добавили задним числом на достаточно свежей версии игры. Версия вроде 1.16.x старше этого фильтра или использует другой (а то и отсутствующий) механизм проверки : всё, что в списке, становится выбираемым, есть разрешение или нет.

Где именно хранится плащ?

Это часть, объясняющая, почему переживает переустановку. Выбор скина/плаща на Bedrock это не просто выбрасываемый локальный файл -- он, вероятно, синхронизируется с профилем Xbox Live, привязанным к твоему аккаунту Microsoft (та же система, что управляет твоим скином на других платформах Bedrock -- мобильные, консоли и т.д). Когда ты выбираешь плащ в старом клиенте, он, скорее всего, отправляет этот выбор в сервис профиля ровно так же, как это сделал бы свежий клиент с легитимным плащом -- потому что с точки зрения клиента нет никакой разницы между плащом «твоим» и плащом «выбранным». Сервис профиля доверяет клиенту в этом вопросе : он записывает выбор, не перепроверяя, есть ли реально разрешение позади, по крайней мере не в момент записи.

Итог : когда ты перезапускаешь свежий официальный клиент, он забирает твой текущий скин/плащ с сервиса профиля -- и сервис честно возвращает записанное, включая нелегитимный плащ. Проверка разрешения, если она есть, делается, вероятно, только в момент выбора в UI (отсюда фильтр на свежих клиентах), а отображение уже записанного в профиле пропускает.

Параллель с Java

Это то же семейство логической уязвимости, что у cape-mod на Java : сервис доверяет данным, не перепроверяя их происхождение на каждом шаге. На Java это валидная, но переигранная на чужом профиле подпись RSA. На Bedrock это, видимо, выбор плаща, принятый старым клиентом, у которого никогда не было правильного фильтра, а затем распространённый без перепроверки в сохраняемое состояние аккаунта. В обоих случаях проблема не точка входа (мод Java, старый клиент Bedrock) -- а то, что слой, который должен бы перепроверить разрешение ниже по течению, этого не делает или делает один раз не в том месте.

Почему это до сих пор работает

Два возможных объяснения, не исключающих друг друга :

  1. Mojang, вероятно, не считает это приоритетом. Нужен сторонний лаунчер, манипуляция в несколько шагов, а результат чисто косметический -- никакого геймплейного преимущества, никаких скомпрометированных чужих данных.
  2. Правильно запатчить это потребовало бы перепроверять разрешения при каждом чтении профиля, а не только при выборе -- а это значит лишний сетевой вызов при каждом отображении скина ради проблемы, касающейся только эстетики.

Заключение

Этот туториал укладывается в десять скриншотов, но он иллюстрирует принцип, встречающийся везде в безопасности ПО : как только историческая система (старая версия клиента, legacy API, никогда не обновлённый сервис) ещё может писать в общее состояние, контроль доступа настоящего защищает только то, что идёт через настоящее. Всё, что ещё может говорить со старым API, обходит более новый фильтр -- фильтр работает на свежих версиях, но никогда не применялся к версии, что была до него.

Cómo conseguir cualquier capa en Minecraft Bedrock

En Java hay un montón de formas retorcidas de acabar con una capa que no deberías tener (ver el artículo sobre cape-mod). En Bedrock el juego es distinto, la autenticación es distinta, pero aun así hay una forma: solo necesitas un launcher de terceros y una versión del juego lo bastante vieja como para ignorar la validación que creías adquirida.

Así se hace, y luego vemos qué pasa probablemente bajo el capó.

Qué necesitas

  • Una cuenta Microsoft que ya tenga Minecraft Bedrock (la tuya sirve perfectamente)
  • El launcher oficial de Minecraft instalado
  • BedrockLauncher, un launcher de terceros open source que permite instalar y lanzar cualquier versión histórica de Bedrock
  • .NET 8.0 Desktop Runtime
  • El modo desarrollador activado en Windows

Paso 1: instalar Bedrock al menos una vez con el launcher oficial

Antes de hacer nada más, abre el launcher oficial de Minecraft, ve a la pestaña Minecraft: Bedrock Edition, y haz clic en Install. Bedrock tiene que haberse instalado y lanzado al menos una vez por la vía oficial antes de tocar BedrockLauncher.

Paso 2: descargar BedrockLauncher

Ve a la página de releases de GitHub del proyecto. Coge el zip de la última versión listada en los Assets.

Paso 3: extraer el archivo

Una vez descargado el zip, extráelo en tu carpeta Downloads (o donde sea, mientras encuentres la carpeta después).

Paso 4: lanzar el ejecutable

Ve a la carpeta extraída y lanza BedrockLauncher.exe.

Paso 5: instalar .NET Desktop Runtime y activar el modo desarrollador

En el primer lanzamiento, Windows muy probablemente te pida el .NET 8.0 Desktop Runtime: instálalo. También hay que activar el modo desarrollador en Configuración > Sistema > Para desarrolladores, porque BedrockLauncher instala el juego como un paquete loose (archivos en bruto, no un paquete firmado de verdad de la Store), y Windows rechaza ese tipo de instalación sin ese modo.

Paso 6: crear una nueva instalación

Vuelve a lanzar BedrockLauncher, inicia sesión con tu cuenta Microsoft, ve a la pestaña Installations, y haz clic en New installation.

Paso 7: elegir una versión vieja

Dale un nombre a la instalación, y en la lista de versiones elige una versión vieja: típicamente una versión 1.16.x o anterior. Haz clic en Create.

Paso 8: lanzar la instalación

Haz clic en Play. La extracción de archivos puede tardar hasta diez minutos según la máquina: el launcher parecerá congelado ("Not Responding"), es normal, déjalo correr.

Paso 9: elegir la capa

Una vez lanzado el juego, inicia sesión con tu cuenta, crea un personaje nuevo y ve al editor de skins, pestaña Capes. Ahí encontrarás la lista completa de todas las capas que existen en Minecraft, incluidas las que nunca tuviste (capas de eventos promo, de festivales pasados, de Mob Vote, etc). Elige la que quieras.

No toques el resto de la apariencia del skin en este punto, deja solo la capa.

Paso 10: reinstalar la versión oficial

Vuelve al launcher oficial, pestaña Installation, y haz clic en Uninstall en la instalación principal de Bedrock, luego reinstálala (o haz Check for Updates). Vuelve a lanzar Minecraft Bedrock desde el launcher oficial esta vez.

Y listo: tu capa está ahí, en la versión oficial, en tu perfil de verdad.

Qué pasa probablemente

No metí las manos en el código fuente cerrado de Bedrock (al contrario que Java, que es descompilable), así que lo que sigue es una explicación probable, no una certeza absoluta. Pero el comportamiento observado encaja bastante bien con la hipótesis siguiente.

El selector de capas nunca fue un control de acceso

En Bedrock, la pantalla de selección de capas muestra verosímilmente la lista completa de las capas que existen en el juego, no solo las que posee tu cuenta. En los clientes recientes, un filtro aplicativo (en el cliente o vía una llamada de red a un servicio de entitlements de Xbox/Microsoft) atenúa u oculta las capas que no posees.

El punto clave es que ese filtro probablemente se añadió a posteriori, en una versión del juego lo bastante reciente. Una versión como la 1.16.x es anterior a ese filtro, o usa un mecanismo de verificación distinto (o inexistente): todo lo que está en la lista se vuelve seleccionable, haya entitlement o no.

Dónde se guarda la capa, exactamente

Esta es la parte que explica por qué sobrevive a la reinstalación. La elección de skin/capa en Bedrock no es solo un archivo local desechable: probablemente se sincroniza en el perfil de Xbox Live asociado a tu cuenta Microsoft (el mismo sistema que gestiona tu skin en las demás plataformas Bedrock: móvil, consola, etc.). Cuando seleccionas una capa en el cliente viejo, este muy probablemente envía esa selección al servicio de perfil, exactamente como lo haría un cliente actualizado con una capa legítima, porque desde el punto de vista del cliente no hay ninguna diferencia entre una capa "tuya" y una capa "elegida". El servicio de perfil, por su parte, confía en el cliente en ese punto: registra la selección sin revalidar si el entitlement existe de verdad detrás, al menos no en el momento de escribir.

Resultado: cuando vuelves a lanzar el juego oficial actualizado, este va a buscar tu skin/capa actual en el servicio de perfil, y el servicio devuelve fielmente lo registrado, capa no legítima incluida. El check de entitlement, si existe, se hace probablemente solo en el momento de la selección en la UI (de ahí el filtro en los clientes recientes), y deja pasar la visualización de lo ya registrado en el perfil.

El paralelismo con Java

Es la misma familia de fallo lógico que la del cape-mod en Java: un servicio confía en un dato sin revalidar su origen en cada etapa. En Java, es una firma RSA válida pero repetida en el perfil equivocado. En Bedrock, es verosímilmente una selección de capa aceptada por un cliente viejo que nunca tuvo el filtro correcto, y luego propagada sin revalidación hacia el estado persistente de la cuenta. En ambos casos, el problema no es el punto de entrada (el mod Java, el cliente viejo de Bedrock): es que la capa que debería revalidar el entitlement más abajo no lo hace, o lo hace una sola vez, en el sitio equivocado.

Por qué sigue funcionando

Dos explicaciones posibles, no incompatibles entre sí:

  1. Mojang probablemente no lo considera prioritario. Hace falta un launcher de terceros, una manipulación en varios pasos, y el resultado es puramente cosmético: ninguna ventaja de gameplay, ningún dato ajeno comprometido.
  2. Parchearlo bien exigiría revalidar los entitlements en cada lectura del perfil, no solo en la selección: lo que significa una llamada de red adicional en cada visualización de skin, para un problema que solo afecta a la estética.

Conclusión

Este tutorial cabe en diez capturas de pantalla, pero ilustra un principio que se repite en todas partes en seguridad de software: en cuanto un sistema histórico (una versión vieja de cliente, una API legacy, un servicio jamás actualizado) aún puede escribir en un estado compartido, el control de acceso del presente solo protege lo que pasa por el presente. Todo lo que aún pueda hablar con la API antigua sortea el filtro más reciente: el filtro funciona en las versiones recientes, pero nunca se aplicó a la versión que lo precedió.

Minecraft Bedrock पर कोई भी केप कैसे पाएँ

Java पर बहुत सारे टेढ़े तरीके हैं किसी ऐसी केप के साथ खत्म होने के जो तुम्हें नहीं मिलनी चाहिए थी (cape-mod पर लेख देखें)। Bedrock पर खेल अलग है, प्रमाणीकरण अलग है, लेकिन फिर भी एक तरीका है, तुम्हें बस एक तृतीय पक्ष लॉन्चर और खेल का पर्याप्त पुराना संस्करण चाहिए ताकि उस सत्यापन को नजरअंदाज किया जा सके जिसे हम पक्का मानते हैं।

यह कैसे करना है, और फिर देखते हैं कि हुड के नीचे संभवतः क्या होता है।

तुम्हें क्या चाहिए

  • एक Microsoft खाता जिसके पास पहले से Minecraft Bedrock हो (तुम्हारा अपना बहुत अच्छा चलेगा)
  • आधिकारिक Minecraft लॉन्चर स्थापित
  • BedrockLauncher, एक ओपन सोर्स तृतीय पक्ष लॉन्चर जो Bedrock के किसी भी ऐतिहासिक संस्करण को स्थापित और चलाने देता है
  • .NET 8.0 Desktop Runtime
  • Windows पर डेवलपर मोड सक्षम

चरण 1, आधिकारिक लॉन्चर से कम से कम एक बार Bedrock स्थापित करना

कुछ और करने से पहले, आधिकारिक Minecraft लॉन्चर खोलो, Minecraft: Bedrock Edition टैब पर जाओ, और Install पर क्लिक करो। BedrockLauncher को छूने से पहले Bedrock आधिकारिक रास्ते से कम से कम एक बार स्थापित और चलाया गया होना चाहिए।

चरण 2, BedrockLauncher डाउनलोड करना

प्रोजेक्ट के GitHub releases पेज पर जाओ। Assets में सूचीबद्ध नवीनतम संस्करण का zip लो।

चरण 3, आर्काइव निकालना

zip डाउनलोड हो जाने पर, इसे अपने Downloads फोल्डर में निकालो (या कहीं भी, जब तक तुम्हें बाद में फोल्डर मिल जाए)।

चरण 4, निष्पादन योग्य चलाना

निकाले गए फोल्डर में जाओ और BedrockLauncher.exe चलाओ।

चरण 5, .NET Desktop Runtime स्थापित करना और डेवलपर मोड सक्षम करना

पहले लॉन्च पर, Windows बहुत संभवतः तुमसे .NET 8.0 Desktop Runtime माँगेगा, इसे स्थापित करो। सेटिंग्स > सिस्टम > डेवलपर्स के लिए में डेवलपर मोड भी सक्षम करना होगा, क्योंकि BedrockLauncher खेल को loose पैकेज के रूप में स्थापित करता है (कच्ची फाइलें, Store का असली हस्ताक्षरित पैकेज नहीं), और Windows इस तरह की स्थापना इस मोड के बिना मना कर देता है।

चरण 6, नया इंस्टॉलेशन बनाना

BedrockLauncher फिर से चलाओ, अपने Microsoft खाते से जुड़ो, Installations टैब पर जाओ, फिर New installation पर क्लिक करो।

चरण 7, पुराना संस्करण चुनना

इंस्टॉलेशन को नाम दो, फिर संस्करण सूची में पुराना संस्करण चुनो, आमतौर पर 1.16.x या पुराना संस्करण। Create पर क्लिक करो।

चरण 8, इंस्टॉलेशन चलाना

Play पर क्लिक करो। मशीन के अनुसार फाइल निकालने में दस मिनट तक लग सकते हैं, लॉन्चर जमा हुआ लगेगा ("Not Responding"), यह सामान्य है, इसे चलने दो।

चरण 9, केप चुनना

खेल शुरू हो जाने पर, अपने खाते से जुड़ो, नया पात्र बनाओ और स्किन एडिटर में जाओ, Capes टैब। वहाँ, तुम्हें Minecraft में मौजूद सभी केप की पूरी सूची मिलेगी, वे भी जो तुम्हें कभी नहीं मिलीं (प्रोमो इवेंट केप, पिछले त्योहारों की, Mob Vote की, आदि)। वह चुनो जो तुम चाहते हो।

इस स्तर पर स्किन दिखावट के बाकी हिस्से को मत छुओ, बस केप रहने दो।

चरण 10, आधिकारिक संस्करण फिर से स्थापित करना

आधिकारिक लॉन्चर में वापस जाओ, Installation टैब, और मुख्य Bedrock इंस्टॉलेशन पर Uninstall क्लिक करो, फिर इसे फिर से स्थापित करो (या Check for Updates करो)। इस बार आधिकारिक लॉन्चर से Minecraft Bedrock फिर से चलाओ।

और हो गया, तुम्हारी केप वहाँ है, आधिकारिक संस्करण पर, तुम्हारे असली प्रोफाइल पर।

संभवतः क्या होता है

मैंने बंद स्रोत Bedrock कोड में हाथ नहीं डाले (Java के विपरीत जो डीकंपाइल हो सकता है), इसलिए आगे जो है वह संभावित व्याख्या है, पूर्ण निश्चितता नहीं। लेकिन देखा गया व्यवहार आगे की परिकल्पना से काफी मेल खाता है।

केप चयनकर्ता कभी एक्सेस नियंत्रण नहीं था

Bedrock पर, केप चयन स्क्रीन संभवतः खेल में मौजूद सभी केप की पूरी सूची दिखाती है, सिर्फ वे नहीं जो तुम्हारा खाता रखता है। हाल के क्लाइंट पर, एक एप्लिकेटिव फ़िल्टर (क्लाइंट तरफ या Xbox/Microsoft एंटाइटेलमेंट सेवा की ओर नेटवर्क कॉल के माध्यम से) उन केप को धूसर करता है या छिपाता है जो तुम्हारे पास नहीं हैं।

मुख्य बिंदु यह है कि यह फ़िल्टर संभवतः बाद में जोड़ा गया था, खेल के पर्याप्त हाल के संस्करण पर। 1.16.x जैसा संस्करण इस फ़िल्टर से पहले का है, या अलग सत्यापन तंत्र (या अनुपस्थित भी) इस्तेमाल करता है : सूची में जो कुछ है वह चयन योग्य हो जाता है, एंटाइटेलमेंट हो या न हो।

केप ठीक कहाँ संग्रहित है ?

यही वह हिस्सा है जो समझाता है कि यह फिर से स्थापना से क्यों बचता है। Bedrock पर स्किन/केप चुनाव सिर्फ फेंकने योग्य स्थानीय फाइल नहीं है, यह संभवतः तुम्हारे Microsoft खाते से जुड़े Xbox Live प्रोफाइल पर समकालिक होता है (वही प्रणाली जो अन्य Bedrock प्लेटफार्मों, मोबाइल, कंसोल, आदि पर तुम्हारी स्किन प्रबंधित करती है)। जब तुम पुराने क्लाइंट में केप चुनते हो, तो वह बहुत संभवतः यह चुनाव प्रोफाइल सेवा को भेजता है, बिल्कुल वैसे जैसे वैध केप वाला अद्यतित क्लाइंट करता, क्योंकि क्लाइंट की दृष्टि से "तुम्हारी" केप और "चुनी हुई" केप में कोई अंतर नहीं है। प्रोफाइल सेवा, अपनी ओर से, इस बिंदु पर क्लाइंट पर भरोसा करती है : वह बिना पुनः सत्यापित किए चुनाव दर्ज करती है कि पीछे एंटाइटेलमेंट सच में मौजूद है या नहीं, कम से कम लिखने के समय नहीं।

परिणाम : जब तुम अद्यतित आधिकारिक खेल फिर से चलाते हो, तो वह प्रोफाइल सेवा से तुम्हारी वर्तमान स्किन/केप लेने जाता है, और सेवा वफादारी से वही लौटाती है जो दर्ज किया गया था, अवैध केप सहित। एंटाइटेलमेंट जाँच, अगर मौजूद है, संभवतः सिर्फ हाल UI में चयन के समय होती है (इसीलिए हाल क्लाइंट पर फ़िल्टर), और प्रोफाइल पर पहले से दर्ज चीज के प्रदर्शन को जाने देती है।

Java के साथ समानता

यह Java पर cape-mod वाली तार्किक खामी का वही परिवार है : एक सेवा हर चरण में उसकी उत्पत्ति पुनः सत्यापित किए बिना डेटा पर भरोसा करती है। Java पर, यह वैध RSA हस्ताक्षर है लेकिन गलत प्रोफाइल पर फिर से चलाया गया। Bedrock पर, यह संभवतः पुराने क्लाइंट द्वारा स्वीकार किया गया केप चुनाव है जिसमें कभी सही फ़िल्टर नहीं था, फिर खाते की स्थायी स्थिति की ओर बिना पुनः सत्यापन प्रचारित। दोनों मामलों में, समस्या प्रवेश बिंदु नहीं है (Java mod, पुराना Bedrock क्लाइंट), यह है कि जिस परत को downstream एंटाइटेलमेंट पुनः सत्यापित करना चाहिए वह नहीं करती, या सिर्फ एक बार करती है, गलत जगह।

यह अभी भी क्यों काम करता है

दो संभावित व्याख्याएँ, आपस में असंगत नहीं :

  1. Mojang शायद इसे प्राथमिकता नहीं मानता। तृतीय पक्ष लॉन्चर चाहिए, कई चरणों की हेरफेर, और परिणाम विशुद्ध सौंदर्य है, कोई गेमप्ले फायदा नहीं, किसी और का कोई डेटा समझौता नहीं।
  2. इसे सही से पैच करने के लिए प्रोफाइल के हर पढ़ने पर एंटाइटेलमेंट पुनः सत्यापित करना होगा, सिर्फ चयन पर नहीं, जिसका मतलब हर स्किन प्रदर्शन पर अतिरिक्त नेटवर्क कॉल होगा, ऐसी समस्या के लिए जो सिर्फ सौंदर्य से जुड़ी है।

निष्कर्ष

यह ट्यूटोरियल दस स्क्रीनशॉट में सिमटता है, लेकिन यह एक सिद्धांत दर्शाता है जो सॉफ्टवेयर सुरक्षा में हर जगह मिलता है : जैसे ही कोई ऐतिहासिक प्रणाली (क्लाइंट का पुराना संस्करण, legacy API, कभी अद्यतन न हुई सेवा) साझा स्थिति में लिख सकती है, वर्तमान का एक्सेस नियंत्रण सिर्फ उसी की रक्षा करता है जो वर्तमान से गुजरता है। जो कुछ भी पुराने API से बात कर सकता है वह हाल फ़िल्टर को दरकिनार करता है, फ़िल्टर हाल संस्करणों पर काम करता है, लेकिन यह कभी उस संस्करण पर लागू नहीं हुआ था जो उससे पहले था।

كيف تحصل على أي cape في Minecraft Bedrock

في Java، توجد طرق ملتوية كثيرة لتنتهي مع cape ما كان يجب الحصول عليها (انظر المقال عن cape-mod). في Bedrock، اللعبة مختلفة والمصادقة مختلفة، لكن توجد طريقة على أي حال، يكفيك لانشر طرف ثالث ونسخة لعبة قديمة بما يكفي لتتجاهل التحقق الذي يُظن مُسلَّما به.

إليكم كيف تفعل، ثم ننظر ماذا يحدث غالبا تحت الغطاء.

ما الذي تحتاجه

  • حساب Microsoft يملك فعلا Minecraft Bedrock (حسابك يفي بالغرض تماما)
  • لانشر Minecraft الرسمي مثبت
  • BedrockLauncher، لانشر طرف ثالث مفتوح المصدر يسمح بتثبيت وتشغيل أي نسخة تاريخية من Bedrock
  • .NET 8.0 Desktop Runtime
  • وضع المطور مفعّل على Windows

الخطوة 1، تثبيت Bedrock مرة واحدة على الأقل مع اللانشر الرسمي

قبل فعل أي شيء آخر، افتح لانشر Minecraft الرسمي، واذهب إلى تبويب Minecraft: Bedrock Edition، وانقر Install. يجب أن تكون Bedrock قد ثُبّتت وشُغّلت مرة واحدة على الأقل بالطريق الرسمي قبل لمس BedrockLauncher.

الخطوة 2، تنزيل BedrockLauncher

إلى صفحة إصدارات GitHub للمشروع. خذ zip أحدث نسخة مذكورة في Assets.

الخطوة 3، استخراج الأرشيف

بعد تنزيل zip، استخرجه في مجلد Downloads (أو أي مكان، ما دمت تجد المجلد بعده).

الخطوة 4، تشغيل الملف التنفيذي

اذهب إلى المجلد المستخرج وشغّل BedrockLauncher.exe.

الخطوة 5، تثبيت .NET Desktop Runtime وتفعيل وضع المطور

عند أول تشغيل، سيطالبك Windows على الأرجح بـ**.NET 8.0 Desktop Runtime**، ثبّته. يجب أيضا تفعيل وضع المطور في الإعدادات > النظام > للمطورين، لأن BedrockLauncher يثبت اللعبة كحزمة مفكوكة (ملفات خام، لا حزمة موقعة حقيقية من المتجر)، ويرفض Windows هذا النوع من التثبيت دون هذا الوضع.

الخطوة 6، إنشاء تثبيت جديد

أعد تشغيل BedrockLauncher، واتصل بحساب Microsoft، واذهب إلى تبويب Installations، ثم انقر New installation.

الخطوة 7، اختيار نسخة قديمة

سَمِّ التثبيت، ثم في قائمة النسخ، اختر نسخة قديمة، عادة نسخة 1.16.x أو أقدم. انقر Create.

الخطوة 8، تشغيل التثبيت

انقر Play. قد يستغرق استخراج الملفات حتى عشر دقائق حسب الآلة، سيبدو اللانشر متجمدا («Not Responding»)، وهذا طبيعي، دعه يعمل.

الخطوة 9، اختيار cape

بمجرد تشغيل اللعبة، اتصل بحسابك، وأنشئ شخصية جديدة واذهب إلى محرر skin، تبويب Capes. هناك ستجد القائمة الكاملة لكل capes الموجودة في Minecraft، بما فيها التي لم تحصل عليها أبدا (capes أحداث ترويجية ومهرجانات ماضية وMob Vote، إلخ). اختر ما تريد.

لا تلمس بقية مظهر skin في هذه المرحلة، اترك فقط cape.

الخطوة 10، إعادة تثبيت النسخة الرسمية

وهكذا، cape موجودة، على النسخة الرسمية، على ملفك الحقيقي.

ماذا يحدث غالبا

لم أضع يدي في الكود المصدري المغلق لـBedrock (خلافا لـJava القابلة لفك الترجمة)، فما يلي تفسير محتمل، لا يقين مطلق. لكن السلوك المرصود يطابق جيدا الفرضية التالية.

منتقي capes لم يكن أبدا ضبط وصول

في Bedrock، يعرض شاشة اختيار capes غالبا القائمة الكاملة للـcapes الموجودة في اللعبة، لا فقط التي يملكها حسابك. في العملاء الحديثين، مرشح تطبيقي (جهة العميل أو عبر استدعاء شبكة نحو خدمة استحقاقات Xbox/Microsoft) يخفي capes التي لا تملكها أو يرمّدها.

النقطة الأساسية أن هذا المرشح أُضيف غالبا لاحقا، على نسخة لعبة حديثة بما يكفي. نسخة مثل 1.16.x سابقة لهذا المرشح، أو تستخدم آلية تحقق مختلفة (أو غائبة) : كل ما في القائمة يصبح قابلا للاختيار، باستحقاق أو دونه.

أين تُخزَّن cape بالضبط ؟

هذا هو الجزء الذي يفسر بقاءها بعد إعادة التثبيت. اختيار skin/cape في Bedrock ليس مجرد ملف محلي قابل للرمي، بل غالبا مُزامَن على ملف Xbox Live المرتبط بحساب Microsoft (نفس النظام الذي يدير skin على منصات Bedrock الأخرى، هاتف ووحدات تحكم، إلخ). عندما تختار cape في العميل القديم، يرسل غالبا هذا الاختيار لخدمة الملف، تماما كما يفعل عميل محدث مع cape شرعية، لأنه من وجهة نظر العميل، لا فرق بين cape "لك" وcape "مختارة". وخدمة الملف تثق بالعميل في هذه النقطة : تسجل الاختيار دون إعادة التحقق إن كان الاستحقاق موجودا فعلا خلفه، على الأقل ليس لحظة الكتابة.

النتيجة : عندما تعيد تشغيل اللعبة الرسمية المحدثة، تبحث عن skin/cape الحالي على خدمة الملف، وتعيد الخدمة بأمانة ما سُجّل، بما فيه cape غير الشرعية. فحص الاستحقاق، إن وُجد، يحدث غالبا فقط لحظة الاختيار في الواجهة (ومن هنا المرشح على العملاء الحديثين)، ويمرّر عرض ما هو مسجل فعلا على الملف.

الموازاة مع Java

إنها نفس عائلة الثغرة المنطقية مثل cape-mod في Java : خدمة تثق ببيانة دون إعادة التحقق من مصدرها في كل خطوة. في Java، توقيع RSA صالح لكن مُعاد تشغيله على الملف الخطأ. في Bedrock، غالبا اختيار cape قبله عميل قديم لم يملك المرشح الصحيح أبدا، ثم نُشر دون إعادة تحقق نحو الحالة الدائمة للحساب. في الحالتين، المشكلة ليست نقطة الدخول (mod الـJava، والعميل القديم لـBedrock)، بل أن الطبقة التي يجب أن تعيد التحقق من الاستحقاق لاحقا لا تفعل، أو تفعله مرة واحدة، في المكان الخطأ.

لماذا ما زال يعمل

تفسيران ممكنان، غير متعارضين :

  1. لا تعتبره Mojang أولوية غالبا. يلزم لانشر طرف ثالث، وتلاعب بعدة خطوات، والنتيجة تجميلية خالصة، لا ميزة لعب، ولا بيانات آخرين مُخترَقة.
  2. تصحيحه صحيحا يتطلب إعادة التحقق من الاستحقاقات مع كل قراءة للملف، لا فقط عند الاختيار، وهذا يعني استدعاء شبكة إضافيا مع كل عرض skin، لمشكلة لا تخص إلا الشكل.

Cách lấy bất kỳ cape nào trên Minecraft Bedrock

Trên Java, có đầy cách lắt léo để có một chiếc cape lẽ ra bạn không được có (xem bài về cape-mod). Trên Bedrock, game khác, xác thực khác, nhưng vẫn có cách -- bạn chỉ cần một launcher bên thứ ba và một phiên bản game đủ cũ để bỏ qua bước kiểm tra mà ai cũng tưởng là đương nhiên.

Đây là cách làm, rồi sau đó ta xem chuyện gì có thể đang diễn ra bên dưới.

Những gì bạn cần

  • Một tài khoản Microsoft đã sở hữu Minecraft Bedrock (tài khoản của bạn là đủ tốt)
  • Launcher Minecraft chính thức đã cài
  • BedrockLauncher, một launcher bên thứ ba open source cho phép cài và chạy bất kỳ phiên bản Bedrock lịch sử nào
  • .NET 8.0 Desktop Runtime
  • Chế độ nhà phát triển bật trên Windows

Bước 1 -- Cài Bedrock ít nhất một lần bằng launcher chính thức

Trước khi làm gì khác, mở launcher Minecraft chính thức, vào tab Minecraft: Bedrock Edition, và bấm Install. Bedrock phải được cài và chạy ít nhất một lần qua đường chính thức trước khi đụng tới BedrockLauncher.

Bước 2 -- Tải BedrockLauncher

Tới trang releases GitHub của dự án. Lấy file zip của phiên bản mới nhất liệt kê trong Assets.

Bước 3 -- Giải nén

Khi zip đã tải xong, giải nén vào thư mục Downloads của bạn (hoặc bất cứ đâu, miễn bạn tìm lại được thư mục sau đó).

Bước 4 -- Chạy file thực thi

Vào thư mục đã giải nén và chạy BedrockLauncher.exe.

Bước 5 -- Cài .NET Desktop Runtime và bật chế độ nhà phát triển

Lần chạy đầu tiên, Windows rất có thể sẽ đòi .NET 8.0 Desktop Runtime -- hãy cài nó. Bạn cũng cần bật chế độ nhà phát triển trong Cài đặt > Hệ thống > Dành cho nhà phát triển, vì BedrockLauncher cài game dưới dạng gói loose (tệp thô, không phải gói có chữ ký Store thật), và Windows từ chối kiểu cài đặt đó nếu thiếu chế độ này.

Bước 6 -- Tạo bản cài mới

Chạy lại BedrockLauncher, đăng nhập bằng tài khoản Microsoft, vào tab Installations, rồi bấm New installation.

Bước 7 -- Chọn một phiên bản cũ

Đặt tên cho bản cài, rồi trong danh sách phiên bản, chọn một phiên bản cũ -- thường là 1.16.x hoặc cũ hơn. Bấm Create.

Bước 8 -- Chạy bản cài

Bấm Play. Giải nén tệp có thể mất tới mười phút tùy máy -- launcher sẽ trông như bị treo (« Not Responding »), đó là bình thường, cứ để nó chạy.

Bước 9 -- Chọn cape

Khi game đã chạy, đăng nhập bằng tài khoản của bạn, tạo nhân vật mới và vào trình chỉnh skin, tab Capes. Ở đó, bạn sẽ thấy danh sách đầy đủ mọi cape tồn tại trong Minecraft -- kể cả những cái bạn chưa từng có (cape sự kiện promo, lễ hội cũ, Mob Vote, v.v.). Chọn cái bạn muốn.

Đừng đụng vào phần còn lại của ngoại hình skin ở bước này, chỉ để cape thôi.

Bước 10 -- Cài lại phiên bản chính thức

Quay lại launcher chính thức, tab Installation, và bấm Uninstall trên bản cài Bedrock chính, rồi cài lại (hoặc bấm Check for Updates). Lần này chạy Minecraft Bedrock từ launcher chính thức.

Và xong -- cape của bạn ở đó, trên phiên bản chính thức, trên hồ sơ thật của bạn.

Chuyện có thể đang diễn ra

Tôi chưa thọc tay vào mã nguồn đóng của Bedrock (không như Java có thể dịch ngược), nên những gì sau đây là lời giải thích có thể, không phải chắc chắn tuyệt đối. Nhưng hành vi quan sát được khớp khá tốt với giả thuyết sau.

Bộ chọn cape chưa bao giờ là kiểm soát truy cập

Trên Bedrock, màn hình chọn cape rất có thể hiển thị danh sách đầy đủ các cape tồn tại trong game, không chỉ những cái tài khoản của bạn sở hữu. Trên client mới, một bộ lọc ứng dụng (phía client hoặc qua gọi mạng tới dịch vụ entitlements Xbox/Microsoft) làm mờ hoặc ẩn các cape bạn không sở hữu.

Điểm mấu chốt là bộ lọc này có thể được thêm sau này, trên một phiên bản game đủ mới. Một phiên bản như 1.16.x ra đời trước bộ lọc đó, hoặc dùng cơ chế kiểm tra khác (thậm chí không có) : mọi thứ trong danh sách đều thành có thể chọn, có entitlement hay không.

Cape được lưu ở đâu, chính xác?

Đây là phần giải thích vì sao nó sống sót sau khi cài lại. Lựa chọn skin/cape trên Bedrock không chỉ là tệp cục bộ dùng một lần rồi vứt -- nó có thể được đồng bộ lên hồ sơ Xbox Live gắn với tài khoản Microsoft của bạn (cùng hệ thống quản lý skin của bạn trên các nền tảng Bedrock khác -- di động, console, v.v.). Khi bạn chọn một cape trong client cũ, nó rất có thể gửi lựa chọn đó tới dịch vụ hồ sơ, y hệt như client cập nhật làm với một cape hợp lệ -- vì từ góc nhìn client, không có khác biệt nào giữa cape « của bạn » và cape « được chọn ». Dịch vụ hồ sơ thì tin client ở điểm này : nó ghi lại lựa chọn mà không kiểm tra lại entitlement thực sự đằng sau có tồn tại hay không, ít nhất không phải lúc ghi.

Kết quả : khi bạn chạy lại game chính thức cập nhật, nó đi lấy skin/cape hiện tại trên dịch vụ hồ sơ -- và dịch vụ trả về trung thành những gì đã ghi, kể cả cape không hợp lệ. Bước kiểm tra entitlement, nếu tồn tại, có thể chỉ diễn ra lúc chọn trong UI (vì vậy có bộ lọc trên client mới), và bỏ qua bước hiển thị những gì đã ghi trên hồ sơ.

Song song với Java

Đây là cùng họ lỗ hổng logic với cape-mod trên Java : một dịch vụ tin vào một dữ liệu mà không kiểm tra lại nguồn gốc ở mỗi bước. Trên Java, đó là chữ ký RSA hợp lệ nhưng replay sang hồ sơ sai. Trên Bedrock, đó có thể là một lựa chọn cape được client cũ chấp nhận trong khi nó chưa từng có bộ lọc đúng, rồi lan truyền không kiểm tra lại về trạng thái bền vững của tài khoản. Trong cả hai trường hợp, vấn đề không phải điểm vào (mod Java, client Bedrock cũ) -- mà là lớp lẽ ra phải kiểm tra lại entitlement ở phía sau đã không làm, hoặc chỉ làm một lần, sai chỗ.

Vì sao nó vẫn hoạt động

Hai lời giải thích có thể, không loại trừ nhau :

  1. Mojang có thể không coi đây là ưu tiên. Cần launcher bên thứ ba, thao tác nhiều bước, và kết quả thuần túy thẩm mỹ -- không lợi thế gameplay, không dữ liệu của người khác bị xâm phạm.
  2. Vá đúng cách sẽ đòi kiểm tra lại entitlements mỗi lần đọc hồ sơ, không chỉ lúc chọn -- nghĩa là thêm một gọi mạng mỗi lần hiển thị skin, cho một vấn đề chỉ liên quan tới thẩm mỹ.

Kết luận

Hướng dẫn này gói trong mười ảnh chụp màn hình, nhưng nó minh họa một nguyên tắc gặp ở khắp nơi trong bảo mật phần mềm : hễ một hệ thống lịch sử (phiên bản client cũ, API legacy, dịch vụ chưa từng cập nhật) còn có thể ghi vào một trạng thái chung, kiểm soát truy cập của hiện tại chỉ bảo vệ những gì đi qua hiện tại. Mọi thứ còn nói được với API cũ đều lách qua bộ lọc mới hơn -- bộ lọc hoạt động trên phiên bản mới, nhưng chưa từng được áp lên phiên bản đi trước nó.

วิธีรับผ้าคลุมใดๆ ใน Minecraft Bedrock

ใน Java มีวิธีวกวนมากมายที่จะได้ผ้าคลุมที่คุณไม่ควรมี (ดูบทความ cape-mod) ใน Bedrock เกมต่างออกไป การยืนยันตัวตนต่างออกไป แต่ก็ยังมีวิธี -- ไม่ต้องใช้ม็อด ไม่ต้องแตะแพ็กเก็ตเครือข่ายใดๆ แค่ลันเชอร์บุคคลที่สามกับเวอร์ชันเก่าพอของเกมที่ยังไม่มีการตรวจสอบอย่างที่คิด

นี่คือวิธีการทำ แล้วเราค่อยดูว่ามีอะไรเกิดขึ้นใต้ฝากระโปรง

สิ่งที่คุณต้องมี

  • บัญชี Microsoft ที่มี Minecraft Bedrock อยู่แล้ว (บัญชีของคุณใช้ได้เลย)
  • ติดตั้งลันเชอร์ Minecraft ทางการแล้ว
  • BedrockLauncher ลันเชอร์บุคคลที่สามแบบโอเพนซอร์สที่ให้คุณติดตั้งและรันเวอร์ชันประวัติศาสตร์ใดๆ ของ Bedrock
  • .NET 8.0 Desktop Runtime
  • เปิดโหมดนักพัฒนาบน Windows แล้ว

ขั้นตอนที่ 1 -- ติดตั้ง Bedrock อย่างน้อยหนึ่งครั้งด้วยลันเชอร์ทางการ

ก่อนจะทำอะไรอีก เปิดลันเชอร์ Minecraft ทางการ ไปที่แท็บ Minecraft: Bedrock Edition แล้วคลิก Install ต้องมีการติดตั้งและรัน Bedrock อย่างน้อยหนึ่งครั้งผ่านช่องทางทางการก่อนที่จะแตะ BedrockLauncher

ขั้นตอนที่ 2 -- ดาวน์โหลด BedrockLauncher

ไปที่หน้า Releases บน GitHub ของโปรเจกต์ เอาซิปของเวอร์ชันล่าสุดที่อยู่ใน Assets

ขั้นตอนที่ 3 -- แตกไฟล์เก็บ

หลังจากดาวน์โหลดซิปแล้ว แตกไฟล์ไปยังโฟลเดอร์ Downloads (หรือที่ไหนก็ได้ ขอแค่คุณหาโฟลเดอร์เจอทีหลัง)

ขั้นตอนที่ 4 -- รันไฟล์สั่งการ

เข้าไปในโฟลเดอร์ที่แตกไฟล์แล้ว รัน BedrockLauncher.exe

ขั้นตอนที่ 5 -- ติดตั้ง .NET Desktop Runtime และเปิดโหมดนักพัฒนา

ตอนรันครั้งแรก Windows จะขอ .NET 8.0 Desktop Runtime อย่างแน่นอน -- ติดตั้งเลย คุณต้องเปิด โหมดนักพัฒนา ใน การตั้งค่า > ระบบ > สำหรับนักพัฒนา ด้วย เพราะ BedrockLauncher ติดตั้งเกมเป็นแพ็กเกจหลวม (ไฟล์ดิบ ไม่ใช่แพ็กเกจ Store จริงที่เซ็นชื่อ) และ Windows ปฏิเสธการติดตั้งแบบนี้หากไม่มีโหมดนั้น

ขั้นตอนที่ 6 -- สร้างการติดตั้งใหม่

เปิด BedrockLauncher อีกครั้ง เข้าสู่ระบบด้วยบัญชี Microsoft ของคุณ ไปที่แท็บ Installations แล้วคลิก New installation

ขั้นตอนที่ 7 -- เลือกเวอร์ชันเก่าๆ

ตั้งชื่อให้การติดตั้ง แล้วในรายการเวอร์ชัน เลือกเวอร์ชัน เก่า -- ปกติ 1.16.x หรือก่อนหน้านั้น คลิก Create

ขั้นตอนที่ 8 -- เปิดการติดตั้ง

คลิก Play การแตกไฟล์อาจใช้เวลาถึงสิบนาทีขึ้นอยู่กับเครื่อง -- ลันเชอร์จะดูค้าง ("ไม่ตอบสนอง") นี่ปกติ ปล่อยให้มันทำงาน

ขั้นตอนที่ 9 -- เลือกผ้าคลุม

เมื่อเกมเริ่ม เข้าสู่ระบบด้วยบัญชีของคุณ สร้างตัวละครใหม่ แล้วไปที่ตัวแก้ไขสกิน แท็บ ผ้าคลุม ที่นั่นคุณจะเจอรายการทั้งหมดของผ้าคลุมทุกชิ้นที่มีในเกม -- รวมถึงของที่คุณไม่เคยมี (ผ้าคลุมอีเวนต์โปรโมชัน เทศกาลที่ผ่านมา Mob Vote ฯลฯ) เลือกอันที่คุณต้องการ

อย่าแตะส่วนที่เหลือของรูปลักษณ์สกินในขั้นตอนนี้ ให้เหลือแค่ผ้าคลุม

ขั้นตอนที่ 10 -- ติดตั้งเวอร์ชันทางการใหม่

กลับไปที่ลันเชอร์ทางการ แท็บ การติดตั้ง แล้วคลิก ถอนการติดตั้ง บนการติดตั้ง Bedrock หลัก จากนั้นติดตั้งใหม่ (หรือกด ตรวจสอบอัปเดต) รัน Minecraft Bedrock ครั้งนี้จากลันเชอร์ทางการ

แค่นี้แหละ -- ผ้าคลุมของคุณอยู่ที่นั่นแล้ว บนเวอร์ชันทางการ บนโปรไฟล์จริงของคุณ

สิ่งที่น่าจะเกิดขึ้น

ผมไม่ได้ขุดลงไปในโค้ดต้นฉบับแบบปิดของ Bedrock (ไม่เหมือน Java ที่ถอดรหัสย้อนกลับได้) ดังนั้นต่อไปนี้เป็นคำอธิบาย ที่น่าจะเป็นไปได้ ไม่ใช่ความแน่นอนสมบูรณ์ แต่พฤติกรรมที่สังเกตได้เข้ากับสมมติฐานต่อไปนี้ได้ดีทีเดียว

ตัวเลือกผ้าคลุมไม่เคยเป็นการควบคุมการเข้าถึง

ใน Bedrock หน้าจอเลือกผ้าคลุมน่าจะแสดง รายการทั้งหมดของผ้าคลุมทุกชิ้นที่มีในเกม ไม่ใช่แค่ที่บัญชีของคุณมี ในไคลเอนต์ใหม่ๆ ฟิลเตอร์แอปพลิเคชัน (ฝั่งไคลเอนต์หรือผ่านการเรียกเครือข่ายไปยังบริการเอนไตเติลเมนต์ Xbox/Microsoft) จะทำให้ผ้าคลุมที่คุณไม่มีเป็นสีเทาหรือซ่อนไว้

จุดสำคัญคือฟิลเตอร์นี้น่าจะถูกเพิ่มเข้ามา ภายหลัง ในเวอร์ชันเกมที่ใหม่พอสมควร เวอร์ชันอย่าง 1.16.x อยู่ก่อนฟิลเตอร์นี้ หรือใช้กลไกการตรวจสอบที่แตกต่าง (หรือไม่มีเลย): ทุกอย่างในรายการสามารถเลือกได้ ไม่ว่าจะมีเอนไตเติลเมนต์หรือไม่

ผ้าคลุมถูกเก็บไว้ที่ไหนกันแน่?

นี่คือส่วนที่อธิบายว่าทำไมมันถึงรอดจากการติดตั้งใหม่ การเลือกสกิน/ผ้าคลุมใน Bedrock ไม่ใช่แค่ไฟล์ท้องถิ่นที่ใช้แล้วทิ้ง -- มันน่าจะซิงค์กับโปรไฟล์ Xbox Live ที่เชื่อมกับบัญชี Microsoft ของคุณ (ระบบเดียวกับที่จัดการสกินของคุณบนแพลตฟอร์ม Bedrock อื่นๆ -- มือถือ คอนโซล ฯลฯ) เมื่อคุณเลือกผ้าคลุมในไคลเอนต์เก่า มันน่าจะส่งการเลือกนั้นไปยังบริการโปรไฟล์ อย่างเดียวกับที่ไคลเอนต์ล่าสุดจะทำกับผ้าคลุมที่ถูกต้อง -- เพราะจากมุมมองของไคลเอนต์ ไม่มีความแตกต่างระหว่างผ้าคลุม "ที่คุณมี" กับผ้าคลุม "ที่เลือก" บริการโปรไฟล์ในส่วนของมัน เชื่อใจไคลเอนต์ในจุดนี้: มันบันทึกการเลือกโดยไม่ตรวจสอบซ้ำว่ามีเอนไตเติลเมนต์อยู่จริงเบื้องหลังหรือไม่ อย่างน้อยก็ไม่ใช่ในขณะที่เขียน

ผลลัพธ์: เมื่อคุณรันเกมทางการล่าสุดอีกครั้ง มันจะดึงสกิน/ผ้าคลุมปัจจุบันของคุณจากบริการโปรไฟล์ -- และบริการก็คืนสิ่งที่ถูกบันทึกไว้อย่างซื่อตรง รวมถึงผ้าคลุมที่ไม่ถูกต้องด้วย การตรวจสอบเอนไตเติลเมนต์ถ้ามี ก็น่าจะเกิดตอน เลือก ใน UI ใหม่ (จึงมีฟิลเตอร์ในไคลเอนต์ล่าสุด) ไม่ใช่ตอน แสดงผล ของสิ่งที่ถูกบันทึกไว้ในโปรไฟล์แล้ว

ความคล้ายคลึงกับ Java

มันคือตระกูลข้อบกพร่องทางตรรกะเดียวกันกับ cape-mod ใน Java: บริการเชื่อใจข้อมูลโดยไม่ตรวจสอบที่มาของมันซ้ำในทุกขั้นตอน ใน Java มันคือลายเซ็น RSA ที่ถูกต้องที่ถูกเล่นซ้ำบนโปรไฟล์ที่ผิด ใน Bedrock มันน่าจะเป็นการเลือกผ้าคลุมที่ถูกยอมรับโดยไคลเอนต์เก่าที่ไม่เคยมีฟิลเตอร์ที่ถูกต้อง แล้วถูกเผยแพร่โดยไม่ตรวจสอบซ้ำไปยังสถานะถาวรของบัญชี ในทั้งสองกรณี ปัญหาไม่ได้อยู่ที่จุดเข้า (ม็อด Java, ไคลเอนต์ Bedrock เก่า) -- แต่อยู่ที่ว่าชั้นที่ควรจะตรวจสอบเอนไตเติลเมนต์ซ้ำในขั้นตอนถัดไปไม่ได้ทำ หรือทำแค่ครั้งเดียว ในที่ที่ผิด

ทำไมมันยังทำงานได้

คำอธิบายที่เป็นไปได้สองข้อ ไม่ได้แยกจากกัน:

  1. Mojang คงไม่ถือว่านี่เป็นเรื่องสำคัญ มันต้องใช้ลันเชอร์บุคคลที่สาม กระบวนการหลายขั้นตอน และผลลัพธ์เป็นเรื่องความสวยงามล้วนๆ -- ไม่มีความได้เปรียบในการเล่น ไม่มีข้อมูลของผู้อื่นถูกบุกรุก
  2. การแพตช์สิ่งนี้ให้ถูกต้องจะต้องตรวจสอบเอนไตเติลเมนต์ซ้ำทุกครั้งที่อ่านโปรไฟล์ ไม่ใช่แค่ตอนเลือก -- ซึ่งหมายถึงการเรียกเครือข่ายเพิ่มทุกครั้งที่แสดงสกิน สำหรับปัญหาที่เกี่ยวกับความสวยงามเท่านั้น

บทสรุป

คู่มือนี้ใช้แค่สิบภาพหน้าจอ แต่มันแสดงให้เห็นหลักการที่พบได้ทุกที่ในความปลอดภัยซอฟต์แวร์: ทันทีที่ระบบเก่า (เวอร์ชันไคลเอนต์เก่า, API เก่า, บริการที่ไม่เคยอัปเดต) ยังสามารถเขียนลงในสถานะที่ใช้ร่วมกันได้ การควบคุมการเข้าถึงในปัจจุบันจะปกป้องเฉพาะสิ่งที่ผ่านปัจจุบันเท่านั้น อะไรก็ตามที่ยังพูดกับ API เก่าได้จะข้ามฟิลเตอร์ที่ใหม่กว่า -- ไม่ใช่เพราะฟิลเตอร์พัง แต่เพราะมันไม่เคยถูกใช้กับเวอร์ชันก่อนหน้ามัน
