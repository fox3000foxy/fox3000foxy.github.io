Cape Mod: how to steal Jeb_'s cape with an RSA signature injection

What if I told you a valid RSA signature -- but for the wrong account -- is enough to make your friends believe you're wearing Mojang's official cape? Welcome to cape-mod, a Fabric exploit showing how Minecraft trusts a signature while skipping the check that the profile it belongs to is actually yours.

Context: how Minecraft handles skins and capes

In Java Edition, there's a rarely asked question: who is responsible for displaying a player's skin and cape -- the client or the server?

The nuanced answer:

Component Who sends it? Who downloads it?
Skin texture The server sends the signed URL The client downloads from textures.minecraft.net
Cape texture The server sends the signed URL The client downloads from textures.minecraft.net
textures property The server sends the GameProfile from Mojang auth The client verifies the RSA signature

The key point: everything sits in a property called textures on the GameProfile. That property holds:

  • A base64 JSON payload with the texture URLs
  • An RSA signature made with Mojang's private key

The RSA signature wall

Each textures property looks like this when decoded:

{
  "timestamp": 1783666316269,
  "profileId": "d90b68bc81724329a047f1186dcd4336",
  "profileName": "akronman1",
  "signatureRequired": true,
  "textures": {
    "SKIN": {
      "url": "http://textures.minecraft.net/texture/3e6defcb7de5a0e05c75525c6cd46e4b9b416b92e0cf4baa1e0a9e212a887f3f7"
    },

      "url": "http://textures.minecraft.net/texture/70efffaf86fe5bc089608d3cb297d3e276b9eb7a8f9f2fe6659c23a2d8b18edf"

The client verifies the RSA signature against the public key baked into the jar (yggdrasil_session_pubkey.der):

// Property.java (authlib)
public boolean isSignatureValid(PublicKey publicKey) {
    Signature sig = Signature.getInstance("SHA1withRSA");
    sig.initVerify(publicKey);
    sig.update(this.value.getBytes());
    return sig.verify(Base64.decodeBase64(this.signature));
}

For remote players (outside local play), the client only accepts skins marked secure -- i.e. with a valid signature:

// SkinManager.createLookup() -- simplified
PlayerSkin optional = ...
    .filter(ps -> !isRemote || ps.secure())  // ← remote players must be secure
    .orElse(defaultSkin);

That check blocks spoofing in theory. But validation stops there, and that's exactly where the attack starts.

The flaw: signature replay

The client checks that the RSA signature is valid. It systematically skips checking that the profileId inside the JSON matches the player's actual UUID.

In other words: a textures property taken from an existing Mojang account (say a Mojang employee's) can be replayed onto any other player. The signature stays valid -- it was genuinely produced by Mojang -- it just comes from a different account.

That field's signature was produced by Mojang. It's RSA-2048 SHA-1. It's absolutely valid, even if you replay it onto another UUID -- because Jeb_'s signature stays Jeb_'s signature, and the client skips checking who it was meant for.

The code: how the mod works

The cape-mod mod is tiny -- 65 lines of Java. Here's the core:

@Mixin(Player.class)
public class ServerPlayerMixin {
    private static final String TEXTURES_VALUE =
        "ewogICJ0aW1lc3RhbXAiIDogMTc4MzY2NjMxNjI2OSwKICAicHJvZmlsZUlkIiA6ICJkOTBi...";
    
    private static final String TEXTURES_SIGNATURE =
        "oxoAfZRLVNSfXYFMNbDKZ9XxrTHmz/k2yxzOxksXY3f6aDhY3gCyFCCtDreEWI7fpG9...";

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;", 
            at = @At("RETURN"), cancellable = true)
    private void injectCape(CallbackInfoReturnable<GameProfile> cir) {
        Player self = (Player) (Object) this;
        if (!(self instanceof ServerPlayer serverPlayer)) return;
        MinecraftServer server = ((ServerPlayerAccessor) serverPlayer).getServer();
        if (!(server instanceof IntegratedServer)) return;

        GameProfile host = server.getSingleplayerProfile();
        GameProfile original = cir.getReturnValue();
        if (host == null || !host.name().equals(original.name())) return;

        // Replace the textures property with Jeb_'s
        ImmutableMultimap.Builder<String, Property> b = ImmutableMultimap.builder();
        for (Property p : original.properties().values()) {
            if (!p.name().equals("textures")) {
                b.put(p.name(), p);
            }
        }
        b.put("textures", new Property("textures", TEXTURES_VALUE, TEXTURES_SIGNATURE));
        cir.setReturnValue(new GameProfile(original.id(), original.name(), 
                                           new PropertyMap(b.build())));
    }
}

Steps:

  1. Mixin on Player.getGameProfile() -- the point where the player's profile is returned
  2. Check it's a local server (Integrated Server)
  3. Check it's the host (LAN world)
  4. Replace the textures property with Jeb_'s (hardcoded)
  5. Return a new GameProfile with the injected textures

The GameProfile is therefore forged: it's an artificially built profile that doesn't match the real player. The textures properties are replayed from Jeb_ -- the RSA signature is authentic but applied to the wrong profile. The network packet, on the other hand, is legitimate: the server normally sends the ClientboundPlayerInfoUpdatePacket with that modified profile. It's the profile that's forged; the packet stays legitimate.

When the host's friends join over LAN, they receive the ClientboundPlayerInfoUpdatePacket with the modified profile. The client:

  1. Decodes the base64 payload
  2. Verifies the RSA signature → ✅ valid (it's really Jeb_'s)
  3. Marks the skin as secure=true (since the signature is valid)
  4. Passes the !isRemote || ps.secure() filter → ✅ passes
  5. Downloads and displays Jeb_'s cape

Why it's a flaw (and why it isn't one)

It's ironic: the exploit works precisely because the signature is valid. This isn't a crypto bypass -- it's worse: a logic flaw in the trust model.

Check Result
RSA signature validity ✅ Valid (signed by Mojang for Jeb_)
Does the profileId in the payload match the host's UUID? ❌ No (Jeb_'s UUID ≠ host's UUID)
Does the client check the match? ❌ No. Only the RSA signature is verified.

Minecraft trusts the signature rather than the identity of whoever carries it. As long as the signature comes from Mojang, the client accepts it. It's like showing a fake passport signed by the government -- the seal is legitimate, even though the passport doesn't belong to you.

Security implications

Scope limited to LAN

The mod only works on an integrated server (LAN). The attacker must:

  • Have a Fabric mod installed
  • Be the host of a LAN world
  • Their friends connect without mods (vanilla)

But the possibilities widen

In theory, with the same technique, you could:

  • Reinject other signed data: heads, illegal enchantments, malicious chat components
  • Combine with a LAN tunnel (NGROK, playit.gg, Radmin VPN) to affect players over the internet
  • Extend to other profile properties that rely on signatures

Why Mojang probably won't patch

This isn't a "vulnerability" in the strict sense -- the signature is valid. Patching it would require Mojang to change the whole authentication model, which is complex. For now, it's an edge case: LAN players are assumed to trust each other.

The philosophical trap

Cape Mod is an excellent proof of concept of a broader truth: you must always check who signed data and for which subject before trusting it.

It's a basic crypto lesson. RSA signs a message; the recipient's identity stays outside the signature. If I hand you a valid Mojang RSA signature, all you know is that Mojang signed something, with no reliable indication of the recipient from the message alone.

That's exactly what happened with SSL/TLS certificates in the 2000s when CAs signed certificates without properly verifying the domain -- the signature was valid, but it applied to the wrong domain.

Conclusion

Cape Mod is something other than a hack in the classic sense -- it's an elegant exploitation of a missing logic check in Minecraft. It shows that:

  1. A valid signature doesn't guarantee the identity of whoever carries it
  2. On LAN, trust is weaker than you'd think
  3. Minecraft's textures properties are essentially injected content -- you must check they match the player carrying them

If you join a LAN world on an "unknown" server (or rather, one whose host runs a suspicious mod), you already have a security problem way before the cape. But it's revealing: Minecraft assumes everyone on a LAN trusts each other. That's true... until the first host abuses that trust.

关键全在 GameProfile 的 textures 属性里。包含：

  • base64 JSON payload，带材质 URL
  • Mojang 私钥做的 RSA 签名

RSA 签名这堵墙

每个 textures 属性解码出来长这样：

客户端拿 jar 里嵌的公钥（yggdrasil_session_pubkey.der）验 RSA 签名：

// Property.java (authlib)
public boolean isSignatureValid(PublicKey publicKey) {
    Signature sig = Signature.getInstance("SHA1withRSA");
    sig.initVerify(publicKey);
    sig.update(this.value.getBytes());
    return sig.verify(Base64.decodeBase64(this.signature));
}

对远程玩家（非本地游戏），客户端只接受标为 secure 的皮肤，也就是签名有效的：

// SkinManager.createLookup() -- 简化
PlayerSkin skin = optional
    .filter(ps -> !isRemote || ps.secure())  // ← 远程玩家必须 secure
    .orElse(defaultSkin);

这道检查理论上堵死了伪造。但验证到这里就停了，攻击恰恰从这里开始。

漏洞：签名重放

客户端验证 RSA 签名有效。但它从来不验证 JSON 里的 profileId 是不是这个玩家的真实 UUID。

换句话说：从一个真实存在的 Mojang 账号（比如 Mojang 员工号）扒下来的 textures 属性，可以重放到任何别的玩家身上。签名依然有效，它确实是 Mojang 签的，只是签的不是这个号。

怎么搞到真签名？

Jeb_（UUID 853c80ef-3c37-49fd-aa49-938b674adae6）有 Mojang Studios 披风。从 Mojang session 服务器拿：

curl -s "https://sessionserver.mojang.com/session/minecraft/profile/853c80ef-3c37-49fd-aa49-938b674adae6?unsigned=false"

返回：

{
  "id": "853c80ef-3c37-49fd-aa49-938b674adae6",

这个 value 的 signature 是 Mojang 亲手签的。RSA-2048 SHA-1。绝对有效，哪怕你把它重放到别的 UUID 上，因为 Jeb_ 的签名永远是 Jeb_ 的签名，而客户端压根不查它本来发给谁。

代码：mod 怎么工作的

cape-mod 很小，65 行 Java。核心在这里：

@Mixin(Player.class)
public class ServerPlayerMixin {
    private static final String TEXTURES_VALUE =
        "ewogICJ0aW1lc3RhbXAiIDogMTc4MzY2NjMxNjI2OSwKICAicHJvZmlsZUlkIiA6ICJkOTBi...";

    private static final String TEXTURES_SIGNATURE =
        "oxoAfZRLVNSfXYFMNbDKZ9XxrTHmz/k2yxzOxksXY3f6aDhY3gCyFCCtDreEWI7fpG9...";

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;",
            at = @At("RETURN"), cancellable = true)
    private void injectCape(CallbackInfoReturnable<GameProfile> cir) {
        Player self = (Player) (Object) this;
        if (!(self instanceof ServerPlayer serverPlayer)) return;
        MinecraftServer server = ((ServerPlayerAccessor) serverPlayer).getServer();
        if (!(server instanceof IntegratedServer)) return;

        GameProfile host = server.getSingleplayerProfile();
        GameProfile original = cir.getReturnValue();
        if (host == null || !host.name().equals(original.name())) return;

        // 把 textures 属性换成 Jeb_ 的
        ImmutableMultimap.Builder<String, Property> b = ImmutableMultimap.builder();
        for (Property p : original.properties().values()) {
            if (!p.name().equals("textures")) {
                b.put(p.name(), p);
            }
        }
        b.put("textures", new Property("textures", TEXTURES_VALUE, TEXTURES_SIGNATURE));
        cir.setReturnValue(new GameProfile(original.id(), original.name(),
                                           new PropertyMap(b.build())));
    }
}

步骤：

  1. Mixin 到 Player.getGameProfile()，玩家 profile 返回的地方
  2. 确认是本地服务器（Integrated Server）
  3. 确认是房主（LAN 世界）
  4. 把 textures 属性换成硬编码的 Jeb_ 那份
  5. 返回新的 GameProfile

所以 GameProfile 是伪造的：人工拼出来的 profile，对应不上真玩家。textures 属性是从 Jeb_ 那重放来的，RSA 签名真 authentic，但贴错了 profile。网络包本身合法：服务器正常发 ClientboundPlayerInfoUpdatePacket，带的 profile 被改过。是 profile 伪造，包合法。

朋友通过 LAN 进来，收到带改后 profile 的 ClientboundPlayerInfoUpdatePacket，客户端：

  1. 解 base64 payload
  2. 验 RSA 签名 → ✅ 有效（本来就是 Jeb_ 的）
  3. 标成 secure=true（签名有效嘛）
  4. 过 !isRemote || ps.secure() 过滤 → ✅ 通过
  5. 下载显示 Jeb_ 的披风

为什么说这是漏洞（又为什么不算）

讽刺的是：exploit 能成立，恰恰因为签名有效。这不是密码学 bypass，比那更糟：是信任模型的逻辑漏洞。

检查项 结果
RSA 签名有效性 ✅ 有效（Mojang 给 Jeb_ 签的）
payload 里 profileId 和房主 UUID 对得上吗？ ❌ 对不上（Jeb_ 的 UUID ≠ 房主 UUID）
客户端验对应关系吗？ ❌ 不验。只验 RSA 签名。

Minecraft 信任的是签名，不是签名属于谁。只要签名出自 Mojang，客户端就收。这就像拿着政府盖真章的假护照，章是真的，护照不是你的。

安全影响

范围限于 LAN

mod 只在内置服务器（LAN）上工作。攻击者要：

  • 装 Fabric mod
  • 当 LAN 世界房主
  • 朋友用 vanilla 客户端进来

但思路能放大

理论上同一手法可以：

  • 重放别的签名数据：heads、非法附魔、恶意聊天组件
  • 配 LAN 穿透（NGROK、playit.gg、Radmin VPN）打到公网玩家
  • 扩展到 profile 的别的签名属性

Mojang 大概率不会修

这严格说不算"漏洞"，签名有效。要修得动整个认证模型，成本巨大。目前算边界情况：LAN 玩家默认互相信任。

哲学陷阱

Cape Mod 是个极好的 proof of concept，讲了一个更大的道理：信任签名数据之前，永远要验谁签的、签给谁。

这是密码学基本课。RSA 签的是消息；收件人身份不在签名里。我给你一个 Mojang 的有效 RSA 签名，你只知道 Mojang 签过什么东西，光看消息看不出签给谁。

2000 年代 SSL/TLS 证书干过一模一样的事，CA 不好好验证域名就签发，签名有效，发错了域名。

结语

Cape Mod 不是传统意义的 hack，是对 Minecraft 缺了一块逻辑校验的优雅利用。说明了：

  1. 有效签名不保证持有人身份，这个坑坑过无数系统
  2. LAN 里信任比你以为的弱
  3. Minecraft 的 textures 属性本质上是注入内容，得验它和穿的人对不对得上

如果你进了陌生人的 LAN 世界（或者说，房主装了可疑 mod），披风之前你早就有更大的安全问题。但它很说明问题：Minecraft 默认 LAN 里人人互信。没错……直到第一个滥用信任的房主出现。

ケープMod：Jeb_のケープをRSA署名インジェクションで盗む方法

有効なRSA署名1つで、でも間違ったアカウントのもので、友達にMojang公式ケープを着てると思わせられると言ったらどうする。cape-modへようこそ。署名は信頼するのに、そのプロフィールが本当に自分のものか検証し忘れるMinecraftの仕組みを突くエクスプロイトだ。

背景：Minecraftがスキンとケープをどう扱うか

Java版にはめったに問われない疑問がある。プレイヤーのスキンとケープを表示する責任はクライアントとサーバーのどっちにあるのか。

欠陥：署名リプレイ

クライアントはRSA署名が有効か検証する。JSON内のprofileIdがプレイヤーの本当UUIDと一致するかを体系的に見落とす。

つまり、既存Mojangアカウント（Mojang社員とか）から取ったtexturesプロパティを他の任意プレイヤーにリプレイできる。署名は有効なままだ。本当にMojangが作ったものだから。ただ別のアカウントのものってだけだ。

なぜ欠陥で、なぜ欠陥じゃないのか

皮肉なのは、エクスプロイトがまさに署名が有効だから動くことだ。暗号突破とは別の話だ。もっと悪い。信頼モデルの論理欠陥だ。

チェック 結果
RSA署名の有効性 有効（Jeb_向けにMojang署名）
ペイロード内profileIdはホストUUIDと一致するか 不一致（Jeb_のUUIDはホストのUUIDじゃない）
クライアントは一致を検証するか いいえ。RSA署名だけ検証される。

Minecraftは身分を着る人じゃなく署名を信頼してる。Mojang由来の署名ならクライアントは受け入れる。政府発行の印鑑付き偽パスポートを見せるようなものだ。印鑑は正規だけど、パスポートは持ち主のものじゃない。

セキュリティへの示唆

範囲はLANに限定

modは統合サーバー（LAN）でのみ動く。攻撃者はこうでなきゃいけない。

  • Fabric modを入れてる
  • LANワールドのホストだ
  • 友達はmodなしバニラで参加する

でも可能性は広がる

理論上同じ手口でこうもできる。

  • 他の署名付きデータを再注入する。head、不正エンチャント、悪性チャット部品
  • LANトンネル（NGROK、playit.gg、Radmin VPN）と組み合わせてネット上のプレイヤーに影響させる
  • 署名に依存するプロフィールの他プロパティに拡張する

Mojangがたぶん直さない理由

厳密な意味の「脆弱性」とは別の話だ。署名は有効だからね。直すにはMojangが認証モデル全体を変えなきゃいけなくて複雑だ。今のところ際どいケースだ。LANプレイヤーは互いを信頼する前提だからね。

哲学的な罠

Cape Modは優れた概念実証だ。もっと広い真実を示す。署名したデータと誰宛かを常に検証してから信頼しなきゃいけないってことだ。

基礎暗号の教訓だ。RSAはメッセージに署名する。受取人の身分は署名の外にある。Mojangの有効RSA署名を渡されても分かるのは、Mojangが何かに署名したことだけで、メッセージだけから受取人を確実には示さない。

2000年代にCAがドメインをちゃんと検証せず証明書に署名したSSLやTLS証明書で起きたのとまったく同じだ。署名は有効だったけど、間違ったドメインに適用されてた。

結論

Cape Modは古典的な意味のハックとは別のものだ。Minecraftの論理検証欠落を突く優雅なエクスプロイトだ。示すのはこうだ。

  1. 有効な署名は着る人の身分を保証しない
  2. LANでは信頼は思うより弱い

Cape Mod: RSA 서명 주입으로 Jeb_의 망토 훔치기

유효한 RSA 서명 하나, 다만 잘못된 계정 앞으로 된 것으로 친구들에게 Mojang 공식 망토를 입은 것처럼 믿게 할 수 있다면 어떨까요? cape-mod에 오신 것을 환영해요. 서명은 믿으면서 그 서명이 속한 프로필이 정말 여러분 것인지 확인하는 것을 빠뜨리는 Minecraft를 보여주는 Fabric 익스플로잇이에요.

배경: Minecraft가 스킨과 망토를 다루는 방법

Java Edition에는 잘 묻지 않는 질문이 있어요. 플레이어의 스킨과 망토를 표시할 책임은 클라이언트와 서버 중 누구에게 있을까요?

답은 미묘해요.

구성 요소 누가 보내나요? 누가 다운로드하나요?
스킨 텍스처 서버가 서명된 URL을 보내요 클라이언트가 textures.minecraft.net에서 다운로드해요
망토 텍스처 서버가 서명된 URL을 보내요 클라이언트가 textures.minecraft.net에서 다운로드해요
textures 속성 서버가 Mojang 인증의 GameProfile을 보내요 클라이언트가 RSA 서명을 검증해요

핵심은 모든 것이 GameProfile의 textures라는 속성에 담긴다는 거예요. 이 속성에 들어있는 것은요.

  • 텍스처 URL이 담긴 base64 JSON 페이로드
  • Mojang 개인 키로 만든 RSA 서명

RSA 서명의 벽

각 textures 속성을 디코딩하면 이렇게 생겼어요.

클라이언트는 jar에 내장된 공개 키(yggdrasil_session_pubkey.der)로 RSA 서명을 검증해요.

// Property.java (authlib)
public boolean isSignatureValid(PublicKey publicKey) {
    Signature sig = Signature.getInstance("SHA1withRSA");
    sig.initVerify(publicKey);
    sig.update(this.value.getBytes());
    return sig.verify(Base64.decodeBase64(this.signature));
}

원격 플레이어(로컬 게임 바깥)의 경우 클라이언트는 secure로 표시된 스킨, 즉 서명이 유효한 것만 받아들여요.

// SkinManager.createLookup() -- 단순화
PlayerSkin skin = optional
    .filter(ps -> !isRemote || ps.secure())  // ← 원격 플레이어는 안전해야 해요
    .orElse(defaultSkin);

이 검사는 이론상 스푸핑을 막아요. 하지만 검증은 거기서 멈추고, 바로 그 지점에서 공격이 시작돼요.

결함: 서명 재생

클라이언트는 RSA 서명이 유효한지 검증해요. JSON 안에 든 profileId가 플레이어의 실제 UUID와 일치하는지는 체계적으로 확인하지 않아요.

다시 말하면, 기존 Mojang 계정(예를 들어 Mojang 직원 계정)에서 가져온 textures 속성을 다른 어떤 플레이어에게든 재생할 수 있어요. 서명은 여전히 유효해요. 실제로 Mojang이 만든 것이니까요. 그저 다른 계정에서 온 것뿐이에요.

진짜 서명을 어떻게 꺼낼까요?

Jeb_(UUID 853c80ef-3c37-49fd-aa49-938b674adae6)은 Mojang Studios 망토를 가지고 있어요. Mojang 세션 서버에서요.

curl -s "https://sessionserver.mojang.com/session/minecraft/profile/853c80ef-3c37-49fd-aa49-938b674adae6?unsigned=false"

응답:

{
  "id": "853c80ef-3c37-49fd-aa49-938b674adae6",
  "name": "jeb_",
  "properties": [
    {
      "name": "textures",
      "value": "ewogICJ0aW1lc3RhbXAiIDogMTc4MzYxOTcyNjAxMSwKICAicHJvZmlsZUlkIiA6ICI4NTNjODBl...",

이 value 필드의 signature는 Mojang이 만든 거예요. RSA-2048 SHA-1이에요. 다른 UUID에 재생해도 절대적으로 유효해요. Jeb_의 서명은 여전히 Jeb_의 서명이고, 클라이언트는 그것이 누구를 위한 것이었는지 확인하지 않으니까요.

코드: 모드가 동작하는 방법

cape-mod 모드는 아주 작아요. Java 65줄이에요. 핵심은 이렇습니다.

@Mixin(Player.class)
public class ServerPlayerMixin {
    private static final String TEXTURES_VALUE =
        "ewogICJ0aW1lc3RhbXAiIDogMTc4MzY2NjMxNjI2OSwKICAicHJvZmlsZUlkIiA6ICJkOTBi...";

    private static final String TEXTURES_SIGNATURE =
        "oxoAfZRLVNSfXYFMNbDKZ9XxrTHmz/k2yxzOxksXY3f6aDhY3gCyFCCtDreEWI7fpG9...";

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;",
            at = @At("RETURN"), cancellable = true)
    private void injectCape(CallbackInfoReturnable<GameProfile> cir) {
        Player self = (Player) (Object) this;
        if (!(self instanceof ServerPlayer serverPlayer)) return;
        MinecraftServer server = ((ServerPlayerAccessor) serverPlayer).getServer();
        if (!(server instanceof IntegratedServer)) return;

        GameProfile host = server.getSingleplayerProfile();
        GameProfile original = cir.getReturnValue();
        if (host == null || !host.name().equals(original.name())) return;

        // textures 속성을 Jeb_의 것으로 바꿔요
        ImmutableMultimap.Builder<String, Property> b = ImmutableMultimap.builder();
        for (Property p : original.properties().values()) {
            if (!p.name().equals("textures")) {
                b.put(p.name(), p);
            }
        }
        b.put("textures", new Property("textures", TEXTURES_VALUE, TEXTURES_SIGNATURE));
        cir.setReturnValue(new GameProfile(original.id(), original.name(),
                                           new PropertyMap(b.build())));
    }
}

단계:

  1. Player.getGameProfile()에 Mixin. 플레이어 프로필이 반환되는 지점이에요
  2. 로컬 서버(Integrated Server)인지 확인
  3. 호스트(LAN 월드)인지 확인
  4. textures 속성을 하드코딩된 Jeb_의 것으로 교체
  5. 주입된 텍스처가 담긴 새 GameProfile 반환

그래서 GameProfile은 위조된 거예요. 진짜 플레이어와 일치하지 않는 인위적으로 만든 프로필이에요. textures 속성은 Jeb_에게서 재생된 거예요. RSA 서명은 진짜지만 잘못된 프로필에 적용됐어요. 네트워크 패킷 자체는 정당해요. 서버는 수정된 프로필이 담긴 ClientboundPlayerInfoUpdatePacket을 정상적으로 보내요. 위조된 것은 프로필이고, 패킷은 정당하게 남아 있어요.

호스트의 친구들이 LAN으로 들어오면 수정된 프로필이 담긴 ClientboundPlayerInfoUpdatePacket을 받아요. 클라이언트는요.

  1. base64 페이로드를 디코딩
  2. RSA 서명 검증 → ✅ 유효 (실제로 Jeb_의 것이에요)
  3. 서명이 유효하니 스킨을 secure=true로 표시
  4. !isRemote || ps.secure() 필터 통과 → ✅ 통과
  5. Jeb_의 망토를 다운로드하고 표시

게임 속 결과: 스킨 위의 망토

게임에서 보이는 모습은 이렇습니다. 먼저 호스트에 표시된 Jeb_ 망토를 정면에서 본 모습이에요.

공식 Mojang Studios 망토의 빨강과 흰색 무늬가 선명히 보여요. 렌더링은 자신의 망토를 입은 진짜 Jeb_와 똑같아요. 클라이언트는 textures.minecraft.net에서 정확히 같은 텍스처를 다운로드하거든요.

그리고 실제 플레이 장면의 몰입 시점이에요.

망토가 플레이어 뒤에서 펄럭이고 움직임에 따라 흔들려요. 공식 망토가 있는 진짜 스킨과 완벽히 구분할 수 없어요.

다른 각도, 용암과 지형이 있는 월드에서요.

그리고 실제 고전 Minecraft 게임플레이를 가까이서 본 마지막 장면, 망토가 실제로 보이는 모습이에요.

호스트가 모드를 쓴다는 것을 모르고 LAN에 들어온 사람에게는, 망토가 진짜 Mojang 망토와 시각적으로 똑같아요. 바로 그 점이 핵심이에요. 서명이 유효해서 클라이언트가 정품으로 처리해요.

왜 결함인지 (그리고 왜 결함이 아닌지)

아이러니하게도 이 익스플로잇은 서명이 유효하기 바로 그 이유로 동작해요. 암호 우회와는 다른 이야기예요. 더 나빠요. 신뢰 모델의 논리적 결함이에요.

검사 결과
RSA 서명 유효성 ✅ 유효 (Jeb_를 위해 Mojang이 서명)
페이로드의 profileId가 호스트 UUID와 일치하나요? ❌ 아니요 (Jeb_의 UUID ≠ 호스트의 UUID)
클라이언트가 일치를 검증하나요? ❌ 아니요. RSA 서명만 검증해요.

Minecraft는 서명을 든 사람의 신원보다 서명을 믿어요. 서명이 Mojang에서 온 한 받아들여요. 정부가 서명한 위조 여권을 보여주는 것과 같아요. 도장은 진짜지만, 여권이 여러분 것은 아니에요.

보안 함의

LAN으로 제한된 범위

모드는 통합 서버(LAN)에서만 동작해요. 공격자는 다음을 갖춰야 해요.

  • 설치된 Fabric 모드
  • LAN 월드의 호스트 자리
  • 친구들은 모드 없이(vanilla) 접속

하지만 가능성은 넓어져요

이론적으로 같은 기법으로 다음을 할 수 있어요.

  • 서명된 다른 데이터 재주입: 머리, 불법 인챈트, 악의적 채팅 컴포넌트
  • LAN 터널(NGROK, playit.gg, Radmin VPN)과 결합해서 인터넷의 플레이어에게 영향
  • 서명에 의존하는 프로필의 다른 속성으로 확장

Mojang이 아마 패치하지 않을 이유

엄밀한 의미의 "취약점"과는 다른 이야기예요. 서명은 유효해요. 패치하려면 Mojang이 인증 모델 전체를 바꿔야 해서 복잡해요. 지금은 경계 사례예요. LAN 플레이어는 서로 신뢰한다고 가정하니까요.

철학적 함정

Cape Mod는 더 넓은 진실에 대한 훌륭한 개념 증명이에요. 데이터를 신뢰하기 전에 누가 서명했고 누구를 위해 서명했는지 항상 확인해야 해요.

기본 암호학 교훈이에요. RSA는 메시지에 서명해요. 수신자의 신원은 서명 밖에 있어요. Mojang의 유효한 RSA 서명을 드리면, 여러분이 아는 것은 Mojang이 무언가에 서명했다는 것뿐이고, 메시지 하나만으로는 수신자에 대한 믿을 만한 표시가 없어요.

2000년대에 CA가 도메인을 제대로 확인하지 않고 인증서에 서명했을 때 SSL과 TLS 인증서에 정확히 일어났던 일이에요. 서명은 유효했지만 잘못된 도메인에 적용됐어요.

결론

Cape Mod는 고전적 의미의 핵과는 다른 것이에요. Minecraft의 논리적 검증 부재를 우아하게 파고든 거예요. 보여주는 것은요.

  1. 유효한 서명이 서명을 든 사람의 신원을 보장하지 않아요
  2. LAN에서는 신뢰가 생각보다 약해요
  3. Minecraft의 textures 속성은 본질적으로 주입된 콘텐츠예요. 그것을 든 플레이어와 일치하는지 확인해야 해요

"알 수 없는" 월드(정확히는 호스트가 수상한 모드를 가진)의 LAN 월드에 들어가면, 망토 이전에 이미 보안 문제가 있어요. 하지만 시사하는 바가 있어요. Minecraft는 LAN의 모든 사람이 서로 신뢰한다고 가정해요. 그 가정은 맞아요. 신뢰를 남용하는 첫 호스트가 나오기 전까지는요.

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;",

Il contesto: come Minecraft gestisce skin e mantelli

In Java Edition, c'è una domanda raramente posta: chi è responsabile di mostrare la skin e il mantello di un giocatore: il client o il server?

La risposta è sfumata:

Componente Chi lo invia? Chi lo scarica?
Texture di skin Il server invia l'URL firmata Il client scarica da textures.minecraft.net
Texture di mantello Il server invia l'URL firmata Il client scarica da textures.minecraft.net
Proprietà textures Il server invia il GameProfile dall'auth Mojang Il client verifica la firma RSA

Il punto chiave: tutto è contenuto in una proprietà chiamata textures del GameProfile. Questa proprietà contiene:

  • Un payload JSON in base64 con gli URL delle texture
  • Una firma RSA fatta con la chiave privata di Mojang

La falla: signature replay

Il client verifica che la firma RSA sia valida. Omette sistematicamente di verificare che il profileId contenuto nel JSON corrisponda all'UUID reale del giocatore.

In altre parole: una proprietà textures presa da un account Mojang esistente (per esempio quello di un impiegato Mojang) può essere rigiocata su qualsiasi altro giocatore. La firma resta valida: è stata davvero prodotta da Mojang: viene solo da un altro account.

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;",
            at = @At("RETURN"), cancellable = true)
    private void injectCape(CallbackInfoReturnable<GameProfile> cir) {
        Player self = (Player) (Object) this;
        if (!(self instanceof ServerPlayer serverPlayer)) return;
        MinecraftServer server = ((ServerPlayerAccessor) serverPlayer).getServer();

Passi:

  1. Mixin su Player.getGameProfile(): il punto dove il profilo del giocatore è restituito
  2. Verifica che sia un server locale (Integrated Server)
  3. Verifica che sia l'host (mondo LAN)
  4. Sostituisce la proprietà textures con quella di Jeb_ (hardcodata)
  5. Restituisce un nuovo GameProfile con le texture iniettate

Il GameProfile è quindi forgiato: è un profilo costruito artificialmente, che non corrisponde al vero giocatore. Le proprietà textures sono rigiocate da Jeb_: la firma RSA è autentica ma applicata al profilo sbagliato. Il pacchetto rete, lui, è legittimo: il server invia normalmente il ClientboundPlayerInfoUpdatePacket con questo profilo modificato. È il profilo che è forgiato; il pacchetto resta legittimo.

Quando gli amici dell'host si uniscono via LAN, ricevono il ClientboundPlayerInfoUpdatePacket col profilo modificato. Il client:

  1. Decodifica il payload base64
  2. Verifica la firma RSA: valida (è davvero quella di Jeb_)
  3. Segna la skin come secure=true (perché la firma è valida)
  4. Passa il filtro !isRemote || ps.secure(): passa
  5. Scarica e mostra il mantello di Jeb_

Perché è una falla (e perché non lo è)

È ironico: l'exploit funziona proprio perché la firma è valida. Si tratta d'altro che un bypass crittografico: è peggio: una falla logica nel modello di fiducia.

Check Risultato
Validità della firma RSA Valida (firmata da Mojang per Jeb_)
Il profileId nel payload corrisponde all'UUID dell'host? No (UUID di Jeb_ diverso da UUID dell'host)
Il client verifica la corrispondenza? No. Solo la firma RSA è verificata.

Minecraft si fida della firma invece che dell'identità di chi la porta. Finché la firma viene da Mojang, il client l'accetta. È come mostrare un passaporto falso firmato dal governo: il sigillo è legittimo, anche se il passaporto non ti appartiene.

Le implicazioni di sicurezza

Portata limitata alla LAN

Il mod funziona solo su un server integrato (LAN). L'attaccante deve:

  • Avere un mod Fabric installato
  • Essere l'host di un mondo LAN
  • I suoi amici si connettono senza mod (vanilla)

Ma le possibilità si allargano

In teoria, con la stessa tecnica, si potrebbe:

  • Re-iniettare altri dati firmati: teste, incantesimi illegali, componenti di chat malevoli
  • Combinare con un tunnel LAN (NGROK, playit.gg, Radmin VPN) per colpire giocatori su internet
  • Estendere ad altre proprietà del profilo che dipendono da firme

Perché Mojang probabilmente non patcherà

Si tratta d'altro che una "vulnerabilità" in senso stretto: la firma è valida. Patcharla richiederebbe a Mojang di modificare il modello di autenticazione completo, il che è complesso. Per ora, è un caso limite: i giocatori LAN sono supposti fidarsi.

La trappola filosofica

Cape Mod è un ottimo proof of concept di una verità più ampia: devi sempre verificare chi ha firmato un dato e per quale soggetto prima di fidarti.

È una lezione di crittografia di base. RSA firma un messaggio; l'identità del destinatario resta fuori dalla firma. Se ti do una firma RSA valida di Mojang, sai solo che Mojang ha firmato qualcosa, senza indicazione affidabile sul destinatario dal solo messaggio.

È esattamente ciò che è successo coi certificati SSL/TLS negli anni 2000 quando le CA firmavano certificati senza verificare correttamente il dominio: la firma era valida, ma si applicava al dominio sbagliato.

Conclusione

Cape Mod è d'altro che un hack in senso classico: è uno sfruttamento elegante di una mancanza di validazione logica in Minecraft. Mostra che:

  1. Una firma valida non garantisce l'identità di chi la porta
  2. In LAN, la fiducia è più debole di quanto si creda

Der Kontext: wie Minecraft Skins und Capes handhabt

In der Java Edition gibt es eine selten gestellte Frage: Wer ist verantwortlich, den Skin und die Cape eines Spielers anzuzeigen, der Client oder der Server ?

Die Antwort ist nuanciert:

Komponente Wer schickt sie? Wer lädt sie herunter?
Skin-Textur Der Server schickt die signierte URL Der Client lädt von textures.minecraft.net herunter
Cape-Textur Der Server schickt die signierte URL Der Client lädt von textures.minecraft.net herunter

Der springende Punkt: Alles steckt in einer Eigenschaft namens textures des GameProfile. Diese Eigenschaft enthält:

  • Einen base64-codierten JSON-Payload mit den Textur-URLs
  • Eine RSA-Signatur mit Mojangs privatem Schlüssel gemacht

Die Lücke: Signature Replay

Der Client prüft, dass die RSA-Signatur gültig ist. Er vergisst systematisch zu prüfen, dass die im JSON enthaltene profileId der echten UUID des Spielers entspricht.

Anders gesagt: Eine textures-Eigenschaft von einem existierenden Mojang-Konto (zum Beispiel dem eines Mojang-Mitarbeiters) kann auf jeden anderen Spieler replayt werden. Die Signatur bleibt gültig, sie wurde wirklich von Mojang produziert, sie kommt nur von einem anderen Konto.

Der cape-mod-Mod ist winzig, 65 Zeilen Java. Hier das Herz:

        "ewogICJ0aW1lc3RhbXAiIDogMTc4MzY2NjMxNjI2OSwKICAicHJvZmlsZUlkIiA6ICJkOTBi...";
    
    private static final String TEXTURES_SIGNATURE =
        "oxoAfZRLVNSfXYFMNbDKZ9XxrTHmz/k2yxzOxksXY3f6aDhY3gCyFCCtDreEWI7fpG9...";

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;", 
            at = @At("RETURN"), cancellable = true)
    private void injectCape(CallbackInfoReturnable<GameProfile> cir) {
        Player self = (Player) (Object) this;
        if (!(self instanceof ServerPlayer serverPlayer)) return;
        MinecraftServer server = ((ServerPlayerAccessor) serverPlayer).getServer();
        if (!(server instanceof IntegratedServer)) return;

        GameProfile host = server.getSingleplayerProfile();
        GameProfile original = cir.getReturnValue();
        if (host == null || !host.name().equals(original.name())) return;

            if (!p.name().equals("textures")) {
                b.put(p.name(), p);
            }

                                           new PropertyMap(b.build())));

Schritte:

  1. Mixin auf Player.getGameProfile(), den Punkt, an dem das Spielerprofil zurückgegeben wird
  2. Prüft, dass es ein lokaler Server ist (Integrated Server)
  3. Prüft, dass es der Host ist (LAN-Welt)
  4. Ersetzt die textures-Eigenschaft durch die von Jeb_ (hardcodiert)
  5. Gibt ein neues GameProfile mit den injizierten Texturen zurück

Das GameProfile ist also gefälscht: Es ist ein künstlich gebautes Profil, das nicht zum echten Spieler passt. Die textures-Eigenschaften sind von Jeb_ replayt, die RSA-Signatur ist authentisch, aber auf das falsche Profil angewendet. Das Netzwerkpaket dagegen ist legitim: Der Server schickt normal das ClientboundPlayerInfoUpdatePacket mit diesem modifizierten Profil. Das Profil ist gefälscht; das Paket bleibt legitim.

  1. Dekodiert den base64-Payload

Warum das eine Lücke ist (und warum keine)

Es ist ironisch: Der Exploit funktioniert genau weil die Signatur gültig ist. Es geht um etwas anderes als einen kryptografischen Bypass, es ist schlimmer: Eine Logiklücke im Vertrauensmodell.

Check Ergebnis
Gültigkeit der RSA-Signatur ✅ Gültig (von Mojang für Jeb_ signiert)
Entspricht die profileId im Payload der UUID des Hosts ? ❌ Nein (Jeb_s UUID ≠ Host-UUID)
Prüft der Client die Übereinstimmung ? ❌ Nein. Nur die RSA-Signatur wird geprüft.

Minecraft vertraut der Signatur statt der Identität dessen, der sie trägt. Solange die Signatur von Mojang kommt, akzeptiert der Client sie. Es ist wie einen gefälschten von der Regierung signierten Pass zu zeigen, das Siegel ist legitim, auch wenn der Pass dir nicht gehört.

Die Sicherheitsimplikationen

Auf LAN begrenzte Reichweite

Der Mod funktioniert nur auf einem integrierten Server (LAN). Der Angreifer muss:

  • Einen installierten Fabric-Mod haben
  • Host einer LAN-Welt sein
  • Seine Freunde verbinden sich ohne Mod (vanilla)

Aber die Möglichkeiten erweitern sich

In der Theorie könnte man mit derselben Technik:

  • Andere signierte Daten reinjizieren: Heads, illegale Enchantments, bösartige Chat-Komponenten
  • Mit einem LAN-Tunnel kombinieren (NGROK, playit.gg, Radmin VPN), um Spieler im Internet zu betreffen
  • Auf andere Eigenschaften des Profils ausweiten, die von Signaturen abhängen

Warum Mojang wahrscheinlich nicht patchen wird

Es geht um etwas anderes als eine "Schwachstelle" im strengen Sinn, die Signatur ist gültig. Das zu patchen würde erfordern, dass Mojang das komplette Authentifizierungsmodell ändert, was komplex ist. Vorerst ist es ein Grenzfall: LAN-Spieler sollen einander vertrauen.

Die philosophische Falle

Cape Mod ist ein exzellenter Proof of Concept einer breiteren Wahrheit: Du musst immer prüfen, wer Daten signiert hat und für welches Subjekt, bevor du ihnen vertraust.

Das ist eine Lektion in Basiskryptografie. RSA signiert eine Nachricht; die Identität des Empfängers bleibt außerhalb der Signatur. Wenn ich dir eine gültige RSA-Signatur von Mojang gebe, weißt du nur, dass Mojang etwas signiert hat, ohne verlässliche Angabe zum Empfänger aus der bloßen Nachricht.

Genau das passierte mit SSL/TLS-Zertifikaten in den 2000ern, als CAs Zertifikate signierten, ohne die Domain korrekt zu prüfen, die Signatur war gültig, galt aber für die falsche Domain.

Fazit

Cape Mod ist etwas anderes als ein Hack im klassischen Sinn, es ist eine elegante Ausnutzung fehlender Logikvalidierung in Minecraft. Es zeigt, dass:

  1. Eine gültige Signatur garantiert nicht die Identität dessen, der sie trägt
  2. In LAN ist das Vertrauen schwächer, als man glaubt
  3. Minecrafts textures-Eigenschaften sind im Wesentlichen injizierter Inhalt, man muss prüfen, dass sie zum Spieler passen, der sie trägt

Wenn du einer LAN-Welt auf einem "unbekannten" Server beitrittst (oder eher, dessen Host einen verdächtigen Mod hat), hast du schon ein Sicherheitsproblem lange vor der Cape. Aber es ist aufschlussreich: Minecraft nimmt an, dass sich alle in einem LAN vertrauen. Das stimmt... bis zum ersten Host, der dieses Vertrauen missbraucht.

El fallo: signature replay

El cliente verifica que la firma RSA sea válida. Omite sistemáticamente comprobar que el profileId contenido en el JSON corresponda al UUID real del jugador.

Dicho de otro modo: una propiedad textures tomada de una cuenta Mojang existente (por ejemplo la de un empleado de Mojang) puede repetirse en cualquier otro jugador. La firma sigue siendo válida: la produjo realmente Mojang, solo que viene de otra cuenta.

El código: cómo funciona el mod

El mod cape-mod es minúsculo: 65 líneas de Java. Aquí el corazón:

public class ServerPlayerMixin {
    private static final String TEXTURES_VALUE =
        "ewogICJ0aW1lc3RhbXAiIDogMTc4MzY2NjMxNjI2OSwKICAicHJvZmlsZUlkIiA6ICJkOTBi...";

    private static final String TEXTURES_SIGNATURE =
        "oxoAfZRLVNSfXYFMNbDKZ9XxrTHmz/k2yxzOxksXY3f6aDhY3gCyFCCtDreEWI7fpG9...";

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;",
            at = @At("RETURN"), cancellable = true)
    private void injectCape(CallbackInfoReturnable<GameProfile> cir) {
        Player self = (Player) (Object) this;
        if (!(self instanceof ServerPlayer serverPlayer)) return;
        MinecraftServer server = ((ServerPlayerAccessor) serverPlayer).getServer();
        if (!(server instanceof IntegratedServer)) return;

        GameProfile host = server.getSingleplayerProfile();
        GameProfile original = cir.getReturnValue();
        if (host == null || !host.name().equals(original.name())) return;

        // Reemplaza la propiedad textures por la de Jeb_
        ImmutableMultimap.Builder<String, Property> b = ImmutableMultimap.builder();
        for (Property p : original.properties().values()) {
            if (!p.name().equals("textures")) {
                b.put(p.name(), p);
            }
        }
        b.put("textures", new Property("textures", TEXTURES_VALUE, TEXTURES_SIGNATURE));
        cir.setReturnValue(new GameProfile(original.id(), original.name(),
                                           new PropertyMap(b.build())));
    }
}

Pasos:

  1. Mixin sobre Player.getGameProfile(): el punto donde se devuelve el perfil del jugador
  2. Comprueba que es un servidor local (Integrated Server)
  3. Comprueba que es el host (mundo LAN)
  4. Reemplaza la propiedad textures por la de Jeb_ (hardcodeada)
  5. Devuelve un nuevo GameProfile con las texturas inyectadas

El GameProfile queda por tanto forjado: es un perfil construido artificialmente, que no corresponde al verdadero jugador. Las propiedades textures están repetidas desde Jeb_: la firma RSA es auténtica pero aplicada al perfil equivocado. El paquete de red, en cambio, es legítimo: el servidor envía normalmente el ClientboundPlayerInfoUpdatePacket con ese perfil modificado. Es el perfil el que está forjado; el paquete sigue siendo legítimo.

  1. Decodifica el payload base64
  2. Verifica la firma RSA → ✅ válida (es realmente la de Jeb_)

  4. Pasa el filtro !isRemote || ps.secure() → ✅ pasa

Por qué es un fallo (y por qué no lo es)

Es irónico: el exploit funciona justamente porque la firma es válida. No se trata de un bypass criptográfico: es peor, un fallo lógico en el modelo de confianza.

Las implicaciones de seguridad

Alcance limitado a LAN

El mod solo funciona en un servidor integrado (LAN). El atacante tiene que:

  • Tener un mod Fabric instalado
  • Ser el host de un mundo LAN
  • Sus amigos se conectan sin mod (vanilla)

Pero las posibilidades se amplían

En teoría, con la misma técnica, se podría:

  • Reinyectar otros datos firmados: heads, encantamientos ilegales, componentes de chat maliciosos
  • Combinar con un túnel LAN (NGROK, playit.gg, Radmin VPN) para afectar a jugadores en internet
  • Extender a otras propiedades del perfil que dependan de firmas

Por qué Mojang probablemente no lo parcheará

No se trata de una "vulnerabilidad" en sentido estricto: la firma es válida. Parchearlo exigiría a Mojang modificar el modelo de autenticación completo, lo cual es complejo. Por ahora, es un caso límite: se supone que los jugadores LAN confían entre sí.

La trampa filosófica

Cape Mod es un excelente proof of concept de una verdad más amplia: siempre tienes que verificar quién firmó un dato y para qué sujeto antes de confiar en él.

Es una lección de criptografía básica. RSA firma un mensaje; la identidad del destinatario queda fuera de la firma. Si te doy una firma RSA válida de Mojang, solo sabes que Mojang firmó algo, sin indicación fiable sobre el destinatario a partir del solo mensaje.

Es exactamente lo que pasó con los certificados SSL/TLS en los años 2000 cuando las CA firmaban certificados sin verificar correctamente el dominio: la firma era válida, pero se aplicaba al dominio equivocado.

Conclusión

Cape Mod no es un hack en sentido clásico: es una explotación elegante de una falta de validación lógica en Minecraft. Muestra que:

  1. Una firma válida no garantiza la identidad de quien la lleva
  2. En LAN, la confianza es más débil de lo que se cree
  3. Las propiedades textures de Minecraft son esencialmente contenido inyectado: hay que verificar que correspondan al jugador que las lleva

Si te unes a un mundo LAN en un servidor "desconocido" (o más bien, cuyo host tiene un mod sospechoso), ya tienes un problema de seguridad mucho antes que la capa. Pero es revelador: Minecraft supone que todo el mundo en una LAN confía entre sí. Es verdad... hasta el primer host que abusa de esa confianza.

Por que é uma falha (e por que não é)

É irônico : o exploit funciona justamente porque a assinatura é válida. Não se trata de um bypass criptográfico, é pior : uma falha lógica no modelo de confiança.

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;",
            at = @At("RETURN"), cancellable = true)
    private void injectCape(CallbackInfoReturnable<GameProfile> cir) {
        Player self = (Player) (Object) this;
        if (!(self instanceof ServerPlayer serverPlayer)) return;
        MinecraftServer server = ((ServerPlayerAccessor) serverPlayer).getServer();
        if (!(server instanceof IntegratedServer)) return;

            }

खामी : हस्ताक्षर replay

क्लाइंट जाँचता है कि RSA हस्ताक्षर वैध है। वह व्यवस्थित रूप से यह जाँचना भूल जाता है कि JSON में समाहित profileId खिलाड़ी के असली UUID से मेल खाता है।

दूसरे शब्दों में : मौजूदा Mojang खाते (उदाहरण के लिए किसी Mojang कर्मचारी का) से ली गई textures गुण किसी भी अन्य खिलाड़ी पर replay की जा सकती है। हस्ताक्षर वैध रहता है, यह सच में Mojang द्वारा बनाया गया था, यह बस दूसरे खाते से आया है।

public class ServerPlayerMixin {

        "ewogICJ0aW1lc3RhbXAiIDogMTc4MzY2NjMxNjI2OSwKICAicHJvZmlsZUlkIiA6ICJkOTBi...";

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;", 
            at = @At("RETURN"), cancellable = true)
    private void injectCape(CallbackInfoReturnable<GameProfile> cir) {
        Player self = (Player) (Object) this;
        if (!(self instanceof ServerPlayer serverPlayer)) return;
        MinecraftServer server = ((ServerPlayerAccessor) serverPlayer).getServer();
        if (!(server instanceof IntegratedServer)) return;

        GameProfile host = server.getSingleplayerProfile();
        GameProfile original = cir.getReturnValue();
        if (host == null || !host.name().equals(original.name())) return;

        // textures गुण को Jeb_ वाले से बदलता है
        ImmutableMultimap.Builder<String, Property> b = ImmutableMultimap.builder();
        for (Property p : original.properties().values()) {
            if (!p.name().equals("textures")) {
                b.put(p.name(), p);
            }
        }
        b.put("textures", new Property("textures", TEXTURES_VALUE, TEXTURES_SIGNATURE));
        cir.setReturnValue(new GameProfile(original.id(), original.name(), 
                                           new PropertyMap(b.build())));

  1. Player.getGameProfile() पर Mixin, वह बिंदु जहाँ खिलाड़ी का प्रोफाइल लौटाया जाता है
  2. जाँचता है कि यह स्थानीय सर्वर है (Integrated Server)
  3. जाँचता है कि यह host है (LAN world)
  4. textures गुण को Jeb_ वाले से बदलता है (hardcoded)

इसलिए GameProfile जाली है : यह कृत्रिम रूप से बनाया गया प्रोफाइल है, जो असली खिलाड़ी से मेल नहीं खाता। textures गुण Jeb_ से replay किए गए हैं, RSA हस्ताक्षर प्रामाणिक है लेकिन गलत प्रोफाइल पर लगाया गया। नेटवर्क पैकेट, अपनी ओर से, वैध है : सर्वर सामान्य रूप से संशोधित प्रोफाइल के साथ ClientboundPlayerInfoUpdatePacket भेजता है। प्रोफाइल जाली है ; पैकेट वैध रहता है।

जब host के दोस्त LAN से जुड़ते हैं, तो उन्हें संशोधित प्रोफाइल के साथ ClientboundPlayerInfoUpdatePacket मिलता है। क्लाइंट :

  1. base64 पेलोड डिकोड करता है
  2. RSA हस्ताक्षर जाँचता है → ✅ वैध (यह सच में Jeb_ वाला है)
  3. स्किन को secure=true चिह्नित करता है (क्योंकि हस्ताक्षर वैध है)
  4. !isRemote || ps.secure() फ़िल्टर पास करता है → ✅ पास
  5. Jeb_ की केप डाउनलोड और प्रदर्शित करता है

Cape Mod : كيف تسرق cape الخاص بـJeb_ بحقن توقيع RSA

وماذا لو قلت لك أنه يكفي توقيع RSA صالح، لكن للحساب الخطأ، لتوهم أصدقاءك أنك تحمل cape الرسمية لـMojang ؟ مرحبا بك في cape-mod، استغلال Fabric يوضح كيف تثق Minecraft بتوقيع بينما تغفل التحقق من أن الملف الذي ينتمي له هو فعلا ملفك.

السياق : كيف تدير Minecraft الـskins والـcapes

في Java Edition، هناك سؤال نادر الطرح : من المسؤول عن عرض skin وcape لاعب، العميل أم الخادم ؟

الجواب دقيق :

المكوّن من يرسله ؟ من ينزّله ؟
قوام skin الخادم يرسل الرابط الموقَّع العميل ينزّل من textures.minecraft.net
قوام cape الخادم يرسل الرابط الموقَّع العميل ينزّل من textures.minecraft.net
خاصية textures الخادم يرسل GameProfile من مصادقة Mojang العميل يتحقق من توقيع RSA

النقطة الأساسية : كل شيء محتوى في خاصية تسمى textures من GameProfile. تحوي هذه الخاصية :

  • حمولة JSON بترميز base64 مع روابط القوام
  • توقيع RSA مصنوع بمفتاح Mojang الخاص

// Property.java (authlib)
public boolean isSignatureValid(PublicKey publicKey) {
    Signature sig = Signature.getInstance("SHA1withRSA");
    sig.initVerify(publicKey);
    sig.update(this.value.getBytes());
    return sig.verify(Base64.decodeBase64(this.signature));
}

PlayerSkin skin = optional

الثغرة : إعادة تشغيل توقيع

يتحقق العميل أن توقيع RSA صالح. ويغفل منهجيا التحقق من أن profileId المحتوى في JSON يطابق UUID الحقيقي للاعب.

            at = @At("RETURN"), cancellable = true)

  • Là host của thế giới LAN
  • Bạn bè kết nối không mod (vanilla)

Nhưng khả năng mở rộng

Về lý thuyết, với cùng kỹ thuật, có thể :

  • Tiêm lại dữ liệu có chữ ký khác : head, enchant bất hợp pháp, thành phần chat độc hại
  • Kết hợp với tunnel LAN (NGROK, playit.gg, Radmin VPN) để ảnh hưởng người chơi trên internet
  • Mở rộng sang thuộc tính khác của hồ sơ phụ thuộc chữ ký

Vì sao Mojang có thể sẽ không vá

Đây không phải "lỗ hổng" theo nghĩa chặt -- chữ ký hợp lệ. Vá nó đòi Mojang sửa toàn bộ mô hình xác thực, việc này phức tạp. Hiện tại, đây là trường hợp biên : người chơi LAN được cho là tin nhau.

Cái bẫy triết học

Cape Mod là một proof of concept xuất sắc cho một sự thật rộng hơn : bạn luôn phải kiểm tra ai đã ký một dữ liệu và cho chủ thể nào trước khi tin nó.

Đó là bài học mật mã cơ bản. RSA ký một thông điệp ; danh tính người nhận vẫn nằm ngoài chữ ký. Nếu tôi đưa bạn một chữ ký RSA hợp lệ của Mojang, bạn chỉ biết Mojang đã ký cái gì đó, mà không có chỉ dẫn đáng tin về người nhận chỉ từ thông điệp.

Đó chính xác là chuyện đã xảy ra với chứng chỉ SSL/TLS những năm 2000 khi các CA ký chứng chỉ mà không kiểm tra đúng tên miền -- chữ ký hợp lệ, nhưng áp sai tên miền.

Kết luận

Cape Mod không phải hack theo nghĩa cổ điển -- đó là khai thác thanh lịch một thiếu sót xác thực logic trong Minecraft. Nó cho thấy :

  1. Chữ ký hợp lệ không đảm bảo danh tính người mang nó
  2. Trong LAN, mức tin cậy thấp hơn ta tưởng
  3. Các thuộc tính textures của Minecraft về cơ bản là nội dung được tiêm -- phải kiểm tra chúng khớp với người chơi mang chúng

Nếu bạn tham gia thế giới LAN trên máy chủ "không quen" (hay đúng hơn, host có mod đáng ngờ), bạn đã có vấn đề bảo mật từ lâu trước cái cape. Nhưng điều này đáng suy ngẫm : Minecraft cho rằng mọi người trên LAN tin nhau. Điều đó đúng... cho tới host đầu tiên lạm dụng niềm tin đó.

// Property.java (authlib)
public boolean isSignatureValid(PublicKey publicKey) {
    Signature sig = Signature.getInstance("SHA1withRSA");
    sig.initVerify(publicKey);
    sig.update(this.value.getBytes());
    return sig.verify(Base64.decodeBase64(this.signature));
}

โค้ด : ม็อดทำงานอย่างไร

ม็อด cape-mod มีขนาดเล็กมาก -- แค่ 65 บรรทัดของ Java นี่คือหัวใจสำคัญ :

@Mixin(Player.class)
public class ServerPlayerMixin {
    private static final String TEXTURES_VALUE =
        "ewogICJ0aW1lc3RhbXAiIDogMTc4MzY2NjMxNjI2OSwKICAicHJvZmlsZUlkIiA6ICJkOTBi...";
    
    private static final String TEXTURES_SIGNATURE =
        "oxoAfZRLVNSfXYFMNbDKZ9XxrTHmz/k2yxzOxksXY3f6aDhY3gCyFCCtDreEWI7fpG9...";

    @Inject(method = "getGameProfile()Lcom/mojang/authlib/GameProfile;", 
            at = @At("RETURN"), cancellable = true)
    private void injectCape(CallbackInfoReturnable<GameProfile> cir) {
        Player self = (Player) (Object) this;
        if (!(self instanceof ServerPlayer serverPlayer)) return;
        MinecraftServer server = ((ServerPlayerAccessor) serverPlayer).getServer();
        if (!(server instanceof IntegratedServer)) return;

        GameProfile host = server.getSingleplayerProfile();
        GameProfile original = cir.getReturnValue();
        if (host == null || !host.name().equals(original.name())) return;

        // แทนที่พร็อพเพอร์ตี้ textures ด้วยของ Jeb_
        ImmutableMultimap.Builder<String, Property> b = ImmutableMultimap.builder();
        for (Property p : original.properties().values()) {
            if (!p.name().equals("textures")) {
                b.put(p.name(), p);
            }
        }
        b.put("textures", new Property("textures", TEXTURES_VALUE, TEXTURES_SIGNATURE));
        cir.setReturnValue(new GameProfile(original.id(), original.name(), 
                                           new PropertyMap(b.build())));
    }
}

ขั้นตอน :

  1. Mixin บน Player.getGameProfile() -- จุดที่โปรไฟล์ของผู้เล่นถูกส่งกลับ
  2. ตรวจสอบว่าเป็นเซิร์ฟเวอร์ภายในเครื่อง (Integrated Server)
  3. ตรวจสอบว่าเป็นโฮสต์ (โลก LAN)
  4. แทนที่ พร็อพเพอร์ตี้ textures ด้วยของ Jeb_ (แบบ hardcode)
  5. ส่งคืน GameProfile ใหม่ที่มี texture ที่ถูกฉีดเข้าไป

GameProfile จึงถูกปลอมแปลงขึ้นมา : เป็นโปรไฟล์ที่สร้างขึ้นโดยไม่ได้ตรงกับผู้เล่นจริง พร็อพเพอร์ตี้ textures ถูกนำมาเล่นซ้ำจาก Jeb_ -- ลายเซ็น RSA เป็นของแท้ แต่ถูกใช้กับโปรไฟล์ผิด แพ็กเก็ตเครือข่ายนั้นถูกต้องตามกฎหมาย : เซิร์ฟเวอร์ส่ง ClientboundPlayerInfoUpdatePacket ตามปกติกับโปรไฟล์ที่ถูกแก้ไขนี้ สิ่งที่ถูกปลอมคือโปรไฟล์ ไม่ใช่แพ็กเก็ต

เมื่อเพื่อนของโฮสต์เข้าร่วมผ่าน LAN พวกเขาจะได้รับ ClientboundPlayerInfoUpdatePacket พร้อมกับโปรไฟล์ที่ถูกแก้ไข ไคลเอ็นต์ :

  1. ถอดรหัส payload base64
  2. ตรวจสอบลายเซ็น RSA → ✅ ถูกต้อง (เป็นของ Jeb_ จริง ๆ)
  3. ทำเครื่องหมายสกินว่า secure=true (เพราะลายเซ็นถูกต้อง)
  4. ผ่านตัวกรอง !isRemote || ps.secure() → ✅ ผ่าน
  5. ดาวน์โหลดและแสดงเคปของ Jeb_

ในทางเทคนิคแล้ว ด้วยเทคนิคเดียวกัน สามารถ :

  • นำข้อมูลที่เซ็นแล้วกลับมาฉีดใหม่ : หัว, เอ็นแชนต์ที่ผิดกฎหมาย, ส่วนประกอบแชทที่เป็นอันตราย
  • รวมกับอุโมงค์ LAN (NGROK, playit.gg, Radmin VPN) เพื่อส่งผลต่อผู้เล่นบนอินเทอร์เน็ต
  • ขยายไปยังพร็อพเพอร์ตี้อื่น ๆ ของโปรไฟล์ที่ขึ้นอยู่กับลายเซ็น

ทำไม Mojang อาจจะไม่แพตช์

ไม่มี "ช่องโหว่" ในความหมายที่เคร่งครัด -- ลายเซ็นถูกต้อง การแพตช์สิ่งนี้จะต้องการให้ Mojang เปลี่ยนโมเดลการยืนยันตัวตนทั้งหมด ซึ่งเป็นเรื่องซับซ้อน ในตอนนี้มันเป็นกรณีขอบ : ผู้เล่น LAN ถูกสันนิษฐานว่าไว้ใจซึ่งกันและกัน

กับดักเชิงปรัชญา

Cape Mod เป็นการพิสูจน์แนวคิดที่ยอดเยี่ยมของความจริงที่กว้างกว่า : คุณไม่ควรเชื่อถือลายเซ็นโดยไม่ตรวจสอบว่าใครเป็นคนเซ็นและเกี่ยวกับอะไร

นี่คือบทเรียนพื้นฐานด้านการเข้ารหัส RSA เซ็นข้อความ ไม่ใช่ตัวตน ถ้าฉันให้ลายเซ็น RSA ที่ถูกต้องของ Mojang แก่คุณ คุณก็รู้ว่า Mojang เซ็นบางอย่าง คุณไม่รู้ว่าสำหรับใคร และคุณไม่สามารถสันนิษฐานได้เพียงแค่มองข้อความ

นี่คือสิ่งที่เกิดขึ้นกับใบรับรอง SSL/TLS ในช่วงปี 2000 เมื่อ CA รับรองอะไรก็ได้ -- ลายเซ็นถูกต้อง แต่มันใช้กับโดเมนผิด

บทสรุป

Cape Mod ไม่ใช่แฮ็กในความหมายคลาสสิก -- มันเป็นการใช้ประโยชน์อย่างสวยงามจากการขาดการตรวจสอบเชิงตรรกะใน Minecraft มันแสดงให้เห็นว่า :

  1. ลายเซ็นที่ถูกต้องไม่ได้รับประกันตัวตนของผู้ถือมัน
  2. ใน LAN ความเชื่อถือนั้นอ่อนแอกว่าที่เราคิด
  3. พร็อพเพอร์ตี้ textures ของ Minecraft โดยเนื้อแท้แล้วคือเนื้อหาที่ถูกฉีด -- จำเป็นต้องตรวจสอบว่ามันตรงกับผู้เล่นที่สวมใส่หรือไม่

ถ้าคุณเข้าร่วมโลก LAN บนเซิร์ฟเวอร์ "ที่ไม่รู้จัก" (หรือโฮสต์ที่มีม็อดน่าสงสัย) คุณมีปัญหาด้านความปลอดภัยตั้งแต่ก่อนเคปอยู่แล้ว แต่มันเป็นอาการ : Minecraft สมมติว่าทุกคนบน LAN ไว้ใจซึ่งกันและกัน ซึ่งเป็นจริง... จนกว่าจะไม่เป็น
