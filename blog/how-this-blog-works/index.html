How Does This Blog Work?

Ever wondered how this blog works under the hood? In this article, I'll walk you through the whole app architecture, from the tech stack to the article-writing process. And yes, I'll even show you how I write my articles from VS Code!

The Tech Stack

This blog is built with modern web technologies:

  • React 19: for the user interface
  • TypeScript: for typed, more reliable code
  • Vite: as an ultra-fast build tool
  • React Router v7: for navigation between pages
  • react-markdown: for turning Markdown into HTML
  • rehype-raw + rehype-sanitize: for allowing raw HTML in Markdown safely

Project Structure

Here's what the project tree looks like:

├── .github/
│   └── workflows/
│       └── deploy.yml              ← CI/CD pipeline
├── public/
│   ├── home.md                     ← Homepage content
│   ├── portfolio.md                ← Portfolio content
│   └── articles/
│       ├── index.json              ← List of all articles
│       ├── hello-world.md          ← An article
│       ├── how-this-blog-works.md  ← This article!
│       └── /articles/assets/                 ← Article images
├── src/
│   ├── main.tsx                    ← React entry point
│   ├── App.tsx                     ← Main router
│   ├── components/
│   │   ├── Header.tsx              ← Navigation bar
│   │   └── Footer.tsx              ← Footer
│   └── pages/
│       ├── Home.tsx                ← Homepage
│       ├── BlogList.tsx            ← Article list

│       ├── Portfolio.tsx           ← Portfolio page
│       └── NotFound.tsx            ← 404 page
└── vite.config.ts                  ← Vite config

The core idea is simple: content is separated from code. Pages are written in Markdown in the public/ folder, and the React code in src/ takes care of displaying them. I care about that separation: it keeps the content easy to reread and the code easy to evolve.

The Routing System

The App.tsx file defines all the app routes with React Router:

Route Page Description
/ Home Homepage, loads home.md
/blog BlogList List of all articles
/blog/:slug Article One article, loads articles/{slug}.md
/portfolio Portfolio Portfolio page, loads portfolio.md
* NotFound 404 page for unknown URLs

Each page has a well-defined role: it fetches a Markdown file, turns it into HTML with react-markdown, and displays it on screen.

How Does an Article Work?

This is my favorite part! Here's an article's lifecycle:

1. The index.json File

All articles are referenced in public/articles/index.json. Each entry holds the article's metadata:

[
  {
    "slug": "hello-world",
    "title": "Hello World",
    "description": "A sample post for Fox's Blog.",
    "date": "2026-03-08"
  }
]
  • slug: the unique identifier, used in the URL (/blog/hello-world)
  • title: the title shown in the list
  • description: a short summary
  • date: the publication date

2. The Markdown File

The article's content is a plain .md file in public/articles/. The filename matches the slug defined in index.json.

You can put anything you want in it: titles, lists, images, tables, and even raw HTML thanks to rehype-raw!

3. React-Side Rendering

When you visit /blog/hello-world, here's what happens:

  1. React Router grabs the slug parameter from the URL
  2. The Article.tsx component loads /articles/hello-world.md
  3. The Markdown is turned into HTML by react-markdown
  4. Links to /articles/assets/ are automatically rewritten to /articles//articles/assets/
  5. In parallel, metadata is loaded from index.json to show the date and description

Simple as that!

The Homepage and Portfolio

The Home and Portfolio pages work exactly the same way: they load a Markdown file (home.md or portfolio.md) and render it as HTML.

The special part is they use a custom sanitization schema that allows class and style attributes on every HTML element. That lets me write styled HTML directly in Markdown, image galleries for example.

The Header and Footer

The Header is pinned at the top of the page with position: fixed. It contains:

  • My GitHub avatar (loaded directly from github.com/fox3000foxy.png)
  • The blog title
  • The nav links: Home, Blog, Portfolio

The Footer is minimalist: just a copyright with the dynamically computed current year.

The Dark Theme

The site stays in dark mode permanently. I made that choice deliberately to keep reading comfortable in the evening: color-scheme: dark is set in the global styles, with a black #000 background and white #fff text. Links are blue (#64b5f6) and turn green on hover (#81c784).

The CI/CD Deploy Pipeline

I set up a complete GitHub Actions pipeline that automates lint, build, and site deploy on every push to main. Let's look at it in detail.

The workflow lives in .github/workflows/deploy.yml and is split into two jobs: build and deploy.

Triggers

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

The pipeline runs on every push to main and every pull request targeting main. PRs are checked (lint + build) before merging, but only pushes to main trigger a deploy.

Job 1: Build

The build job runs on ubuntu-latest and follows these steps:

  1. Checkout: Clones the repo with full history (fetch-depth: 0)
  2. Setup pnpm: Installs the latest pnpm with pnpm/action-setup@v4
  3. Setup Node.js 20: Configures Node with pnpm cache enabled for faster installs
  4. Install dependencies: Runs pnpm install --frozen-lockfile to guarantee reproducible builds (no lockfile changes allowed)
  5. Lint: Runs pnpm run lint (ESLint) to check code quality before the build
  6. Build: Runs pnpm run build, which first type-checks TypeScript (tsc -b) then bundles everything with Vite
  7. Upload artifact: Uploads the dist/ folder as a build artifact for the deploy job

If any step fails (lint, type, or build error), the whole pipeline stops and nothing deploys. That guard protects me from broken code in production and I rely on it on every push.

Job 2: Deploy

The deploy job only runs if:

  • The build job succeeded (needs: build)
  • The event is a push (not a PR)
  • The branch is main
if: github.event_name == 'push' && github.ref == 'refs/heads/main'

It then proceeds:

  1. Download the build artifact: Fetches the dist/ folder produced by the build job
  2. Configure GitHub Pages: Sets up the Pages environment
  3. Upload to Pages: Prepares the dist/ folder for GitHub Pages
  4. Deploy: Publishes the site with actions/deploy-pages@v4

The whole process takes about a minute between push and going live. I publish with a simple git push, everything stays automatic with no FTP or SSH.

The Production Build

Under the hood, the pnpm build command runs:

  1. tsc -b: Checks TypeScript types
  2. vite build: Bundles and optimizes all the code

Vite produces minified, optimized files with automatic code-splitting. The result is an ultra-fast static site.

Why This Architecture?

I could have used a CMS, a static site generator like Hugo or Jekyll, or even Next.js. But here's why I picked this approach:

  • Simplicity: Write in Markdown, push to GitHub, it's live
  • Full control: No dependency on a CMS or database
  • Performance: Vite + React = fast loading
  • Flexibility: I can mix Markdown and HTML however I want
  • Learning: It's a great project for mastering React and TypeScript
  • CI/CD: Quality checks and automated deploys with GitHub Actions

Conclusion

This blog is a simple but well-thought-out project: Markdown for content, React for rendering, Vite for performance, GitHub Actions for CI/CD, and GitHub Pages for hosting. It relies only on static files served efficiently, with an automated pipeline that guarantees quality on every push.

Job 1：Build

  1. Checkout：克隆仓库，带完整历史（fetch-depth: 0）

  4. Install dependencies：跑 pnpm install --frozen-lockfile，保证构建可复现（不允许改 lockfile）
  5. Lint：跑 pnpm run lint（ESLint），构建前先查代码质量
  6. Build：跑 pnpm run build，先做 TypeScript 类型检查（tsc -b），再用 Vite 打包
  7. Upload artifact：把 dist/ 目录作为构建产物上传，供部署 job 用

任何一步失败（lint、类型或构建报错），整条流水线停下，什么都不部署。这道防线让我每次 push 都很安心。

Job 2：Deploy

部署 job 只在满足以下条件时跑：

  • 构建 job 成功（needs: build）
  • 事件是 push（不是 PR）
  • 分支是 main

  4. 部署：用 actions/deploy-pages@v4 发布站点

글은 어떻게 동작하나요?

제가 제일 좋아하는 부분이에요! 글의 생애주기는 이렇습니다.

1. index.json 파일

모든 글은 public/articles/index.json에 참조되어 있어요. 각 항목에 글 메타데이터가 들어 있어요.

[
  {
    "slug": "hello-world",
    "title": "Hello World",
    "description": "A sample post for Fox's Blog.",
    "date": "2026-03-08"
  }
]
  • slug: 고유 식별자, URL에 쓰여요 (/blog/hello-world)
  • title: 목록에 표시되는 제목
  • description: 짧은 요약
  • date: 발행일

2. Markdown 파일

글 내용은 public/articles/의 단순 .md 파일이에요. 파일 이름이 index.json에 정한 slug와 일치해요.

원하는 것을 넣을 수 있어요. 제목, 목록, 이미지, 표, 심지어 rehype-raw 덕분에 날것 HTML까지!

3. React 쪽 렌더링

/blog/hello-world에 들어가면 이런 일이 일어나요.

  1. React Router가 URL에서 slug 매개변수를 가져와요
  2. Article.tsx 컴포넌트가 /articles/hello-world.md를 불러와요
  3. Markdown이 react-markdown으로 HTML로 바뀌어요
  4. /articles/assets/ 링크는 자동으로 /articles//articles/assets/로 다시 써져요
  5. 나란히 메타데이터가 index.json에서 불러와져서 날짜와 설명을 보여줘요

이렇게 단순해요!

홈 페이지와 포트폴리오

홈과 포트폴리오 페이지는 정확히 같은 방식으로 동작해요. Markdown 파일(home.md 또는 portfolio.md)을 불러와서 HTML로 렌더링해요.

특이한 점은 모든 HTML 요소에 class와 style 속성을 허용하는 맞춤형 살균 스키마를 쓴다는 거예요. 그래서 이미지 갤러리처럼 스타일된 HTML을 Markdown에 바로 쓸 수 있어요.

헤더와 푸터

헤더는 position: fixed로 페이지 위에 고정돼 있어요. 들어있는 것은요.

  • 제 GitHub 아바타 (github.com/fox3000foxy.png에서 바로 불러와요)
  • 블로그 제목
  • 탐색 링크: 홈, 블로그, 포트폴리오

푸터는 미니멀해요. 동적으로 계산된 올해 연도가 있는 copyright뿐이에요.

다크 테마

사이트는 항상 다크 모드로 있어요. 저녁에 편하게 읽으려고 일부러 고른 거예요. 전역 스타일에 color-scheme: dark가 정해져 있고, 검은 배경 #000에 흰 글자 #fff예요. 링크는 파랑(#64b5f6)이고 호버하면 초록(#81c784)이 돼요.

5단계: 발행하기

단순한 git push면 충분해요! CI/CD 파이프라인이 나머지를 자동으로 맡아요.

CI/CD 배포 파이프라인

매 main 푸시마다 사이트의 린트와 빌드, 배포를 자동화하는 완전한 GitHub Actions 파이프라인을 두었어요. 자세히 봐요.

워크플로는 .github/workflows/deploy.yml에 있고, build와 deploy 두 작업으로 나뉘어요.

트리거

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

파이프라인은 main으로의 매 push와 main을 향한 매 pull request에 실행돼요. PR은 합치기 전에 검증(린트 + 빌드)받고, main으로의 푸시만이 배포를 일으켜요.

작업 1: 빌드

빌드 작업은 ubuntu-latest에서 돌고 다음 단계를 따라요.

  1. Checkout: 전체 히스토리와 함께 저장소를 복제해요 (fetch-depth: 0)
  2. Setup pnpm: pnpm/action-setup@v4로 최신 pnpm을 설치해요
  3. Setup Node.js 20: 더 빠른 설치를 위해 pnpm 캐시를 켜고 Node를 설정해요
  4. Install dependencies: 재현 가능한 빌드를 보장하려고 pnpm install --frozen-lockfile을 실행해요 (lockfile 수정 허용 안 해요)
  5. Lint: 빌드 전에 코드 품질을 확인하려고 pnpm run lint(ESLint)를 실행해요
  6. Build: 먼저 TypeScript 타입을 확인(tsc -b)한 뒤 Vite로 전부 묶는 pnpm run build를 실행해요
  7. Upload artifact: 배포 작업을 위해 dist/ 폴더를 빌드 산출물로 올려요

한 단계라도 실패하면(린트, 타입, 빌드 오류) 파이프라인 전체가 멈추고 아무것도 배포되지 않아요. 깨진 코드가 프로덕션에 가는 것을 막아주는 장치이고, 매 푸시마다 의지해요.

작업 2: 배포

배포 작업은 다음일 때만 실행돼요.

  • 빌드 작업이 성공했어요 (needs: build)
  • 이벤트가 push예요 (PR이 아니에요)
  • 브랜치가 main이에요
if: github.event_name == 'push' && github.ref == 'refs/heads/main'

그리고 이렇게 진행해요.

  1. 빌드 산출물 내려받기: 빌드 작업이 만든 dist/ 폴더를 가져와요
  2. GitHub Pages 설정: Pages 환경을 세팅해요
  3. Pages로 올리기: dist/ 폴더를 GitHub Pages용으로 준비해요
  4. 배포: actions/deploy-pages@v4로 사이트를 올려요

프로덕션 빌드

후드 아래에서 pnpm build 명령은 이렇게 실행돼요.

  1. tsc -b: TypeScript 타입을 확인해요
  2. vite build: 모든 코드를 묶고 최적화해요

Vite는 자동 코드 스플리팅이 있는 minify되고 최적화된 파일을 만들어요. 결과는 초고속 정적 사이트예요.

CMS나 Hugo, Jekyll 같은 정적 사이트 생성기, 심지어 Next.js를 쓸 수도 있었어요. 하지만 이 접근을 고른 이유는 이렇습니다.

  • 완전한 통제: CMS나 데이터베이스 의존성 없어요
  • 성능: Vite + React = 빠른 불러오기
  • 유연함: Markdown과 HTML을 원하는 대로 섞을 수 있어요
  • 학습: React와 TypeScript를 익히는 훌륭한 프로젝트예요
  • CI/CD: GitHub Actions로 품질 검사와 배포 자동화예요

Bir Makale Nasıl Çalışır?

1. index.json Dosyası

Tüm makaleler public/articles/index.json içinde referanslanır. Her girdi makalenin meta verilerini içerir:

[
  {
    "slug": "hello-world",
    "title": "Hello World",
    "description": "A sample post for Fox's Blog.",
    "date": "2026-03-08"
  }
]
  • slug: URLde kullanılan benzersiz tanımlayıcı (/blog/hello-world)
  • title: listede gösterilen başlık
  • description: kısa bir özet
  • date: yayın tarihi

2. Markdown Dosyası

Makalenin içeriği public/articles/ içinde basit bir .md dosyasıdır. Dosya adı index.json içinde tanımlı slug ile eşleşir.

İstediğini koyabilirsin: başlıklar, listeler, görseller, tablolar ve rehype-raw sayesinde ham HTML bile!

3. React Tarafında Render

/blog/hello-world adresini ziyaret ettiğinde şunlar olur:

  1. React Router URLden slug parametresini alır
  2. Article.tsx bileşeni /articles/hello-world.md dosyasını yükler
  3. Markdown react-markdown tarafından HTMLye dönüştürülür
  4. /articles/assets/ bağlantıları otomatik olarak /articles//articles/assets/ yoluna yeniden yazılır

यह ब्लॉग कैसे काम करता है ?

तुमने कभी सोचा यह ब्लॉग हुड के नीचे कैसे काम करता है ? इस लेख में, मैं application की पूरी आर्किटेक्चर विस्तार से बताऊँगा, तकनीकी स्टैक से लेकर लेख लिखने की प्रक्रिया तक। और हाँ, मैं यह भी दिखाऊँगा कि मैं VS Code से अपने लेख कैसे लिखता हूँ !

तकनीकी स्टैक

यह ब्लॉग आधुनिक वेब तकनीकों से बना है :

  • React 19 : उपयोगकर्ता इंटरफेस के लिए
  • TypeScript : typed और ज्यादा विश्वसनीय कोड के लिए
  • Vite : अति तेज build उपकरण के रूप में
  • React Router v7 : पेजों के बीच नेविगेशन के लिए
  • react-markdown : Markdown को HTML में बदलने के लिए
  • rehype-raw + rehype-sanitize : Markdown में कच्चा HTML सुरक्षित अनुमति देने के लिए

मैंने पूरा GitHub Actions पाइपलाइन लगाया है जो main पर हर push पर साइट का lint, build और परिनियोजन स्वचालित करता है। विस्तार से देखते हैं।

Job 1 : Build

build job ubuntu-latest पर चलता है और इन चरणों का पालन करता है :

  1. Checkout : पूरे इतिहास के साथ रिपॉजिटरी clone करता है (fetch-depth: 0)
  2. Setup pnpm : pnpm/action-setup@v4 से pnpm का नवीनतम संस्करण स्थापित करता है
  3. Setup Node.js 20 : तेज स्थापना के लिए सक्षम pnpm cache के साथ Node कॉन्फ़िगर करता है
  4. Install dependencies : पुनरुत्पादनीय build गारंटी के लिए pnpm install --frozen-lockfile निष्पादित करता है (lockfile का कोई बदलाव अनुमत नहीं)
  5. Lint : build से पहले कोड गुणवत्ता जाँचने के लिए pnpm run lint (ESLint) निष्पादित करता है
  6. Build : pnpm run build निष्पादित करता है, जो पहले TypeScript प्रकार जाँचता है (tsc -b) फिर Vite से सब bundle करता है
  7. Upload artifact : परिनियोजन job के लिए dist/ फोल्डर build कलाकृति के रूप में अपलोड करता है

अगर कोई चरण विफल होता है (lint, प्रकार या build त्रुटि), तो पूरा पाइपलाइन रुकता है और कुछ परिनियोजित नहीं होता। यह सुरक्षा मुझे production में टूटे कोड से बचाती है और मैं हर push पर इस पर भरोसा करता हूँ।

Job 2 : Deploy

परिनियोजन job तभी चलता है अगर :

  • build job सफल हुआ (needs: build)
  • घटना push है (PR नहीं)
  • शाखा main है
if: github.event_name == 'push' && github.ref == 'refs/heads/main'

फिर वह आगे बढ़ता है :

  1. build कलाकृति डाउनलोड : build job द्वारा बनाई dist/ फोल्डर लेता है
  2. GitHub Pages कॉन्फ़िगर : Pages वातावरण स्थापित करता है
  3. Pages की ओर अपलोड : GitHub Pages के लिए dist/ फोल्डर तैयार करता है
  4. परिनियोजन : actions/deploy-pages@v4 से साइट प्रकाशित करता है

Production Build

हुड के नीचे, pnpm build कमांड निष्पादित करता है :

  1. tsc -b : TypeScript प्रकार जाँचता है
  2. vite build : सारा कोड bundle और अनुकूलित करता है

Vite स्वचालित code-splitting के साथ minified और अनुकूलित फाइलें बनाता है। परिणाम अति तेज स्थिर साइट है।

यह आर्किटेक्चर क्यों ?

मैं CMS, Hugo या Jekyll जैसा स्थिर साइट जनरेटर, या Next.js भी इस्तेमाल कर सकता था। लेकिन मैंने यह दृष्टिकोण क्यों चुना :

  • सरलता : Markdown में लिखो, GitHub पर push करो, ऑनलाइन है
  • पूर्ण नियंत्रण : CMS या डेटाबेस पर कोई निर्भरता नहीं
  • प्रदर्शन : Vite + React = तेज लोडिंग
  • लचीलापन : मैं Markdown और HTML जैसे चाहूँ मिला सकता हूँ
  • सीखना : React और TypeScript में महारत का बढ़िया प्रोजेक्ट है
  • CI/CD : GitHub Actions से स्वचालित गुणवत्ता जाँच और परिनियोजन

निष्कर्ष

यह ब्लॉग सरल लेकिन सोच समझा प्रोजेक्ट है : सामग्री के लिए Markdown, रेंडर के लिए React, प्रदर्शन के लिए Vite, CI/CD के लिए GitHub Actions, और होस्टिंग के लिए GitHub Pages। यह सिर्फ कुशलता से परोसी स्थिर फाइलों पर टिका है, स्वचालित पाइपलाइन के साथ जो हर push पर गुणवत्ता गारंटी करती है।

كيف تعمل هذه المدونة ؟

هل تساءلت يوما كيف تعمل هذه المدونة تحت الغطاء ؟ في هذا المقال، سأفصّل لك بنية التطبيق كاملة، من الحزمة التقنية حتى عملية كتابة مقال. ونعم، سأريك حتى كيف أكتب مقالاتي من VS Code !

الحزمة التقنية

هذه المدونة مبنية بتقنيات ويب حديثة :

  • React 19 : لواجهة المستخدم
  • TypeScript : لكود مُنمَّط وأكثر موثوقية
  • Vite : كأداة بناء فائقة السرعة
  • React Router v7 : للتنقل بين الصفحات
  • react-markdown : لتحويل Markdown إلى HTML
  • rehype-raw + rehype-sanitize : للسماح بـHTML خام في Markdown بأمان

بنية المشروع

إليكم كيف تبدو شجرة المشروع :

├── public/
│   ├── home.md                     ← محتوى الصفحة الرئيسية
│   ├── portfolio.md                ← محتوى المحفظة

كيف يعمل مقال ؟

هذا هو الجزء الذي أفضله ! إليكم دورة حياة مقال :

1. ملف index.json

كل المقالات مُشار إليها في public/articles/index.json. يحوي كل مدخل بيانات المقال الوصفية :

[
  {
    "slug": "hello-world",
    "title": "Hello World",
    "description": "A sample post for Fox's Blog.",
    "date": "2026-03-08"
  }
]
  • slug : المعرف الوحيد، المستخدم في الرابط (/blog/hello-world)
  • title : العنوان المعروض في القائمة
  • description : ملخص قصير

2. ملف Markdown

محتوى المقال هو ملف .md بسيط في public/articles/. يطابق اسم الملف slug المعرّف في index.json.

تستطيع وضع ما تريد فيه : عناوين وقوائم وصور وجداول، وحتى HTML خام بفضل rehype-raw !

3. العرض جهة React

عندما تزور /blog/hello-world، يحدث هذا :

  1. يستخرج React Router معامل slug من الرابط
  2. يحمّل المكوّن Article.tsx ملف /articles/hello-world.md
  3. يتحوّل Markdown إلى HTML بواسطة react-markdown
  4. تُعاد كتابة روابط /articles/assets/ تلقائيا نحو /articles//articles/assets/
  5. بالتوازي، تُحمَّل البيانات الوصفية من index.json لعرض التاريخ والوصف

الخطوة 5 : النشر

تكفي git push بسيطة ! يتكفل خط CI/CD بالباقي تلقائيا.

خط النشر CI/CD

وضعت خط GitHub Actions كاملا يؤتمت الفحص والبناء ونشر الموقع مع كل دفع على main. لنرَ ذلك بالتفصيل.

يوجد workflow في .github/workflows/deploy.yml ومنقسم إلى وظيفتين : build وdeploy.

المحفزات

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

يعمل الخط مع كل دفع على main ومع كل pull request تستهدف main. تُفحَص إذن PRs (فحص + بناء) قبل دمجها، لكن الدفعات وحدها على main تحفّز نشرا.

الوظيفة 1 : Build

تعمل وظيفة البناء على ubuntu-latest وتتبع هذه الخطوات :

  1. Checkout : استنساخ المستودع مع السجل كله (fetch-depth: 0)
  2. Setup pnpm : تثبيت أحدث إصدار من pnpm مع pnpm/action-setup@v4
  3. Setup Node.js 20 : إعداد Node مع تفعيل كاش pnpm لتثبيتات أسرع
  4. Install dependencies : تنفيذ pnpm install --frozen-lockfile لضمان بناء قابلة لإعادة الإنتاج (لا تعديل لملف القفل مسموح)
  5. Lint : تنفيذ pnpm run lint (ESLint) لفحص جودة الكود قبل البناء
  6. Build : تنفيذ pnpm run build، الذي يتحقق أولا من أنواع TypeScript (tsc -b) ثم يحزم الكل مع Vite
  7. Upload artifact : رفع مجلد dist/ كمنتج بناء لوظيفة النشر

إذا فشلت خطوة (خطأ فحص أو نوع أو بناء)، يتوقف الخط كله ولا يُنشَر شيء. يحميني هذا الحارس من الكود المكسور في الإنتاج وأعتمد عليه مع كل دفع.

الوظيفة 2 : Deploy

لا تعمل وظيفة النشر إلا إذا :

  • نجحت وظيفة البناء (needs: build)
  • الحدث دفع (لا PR)
  • الفرع main
if: github.event_name == 'push' && github.ref == 'refs/heads/main'

ثم تتابع :

  1. تنزيل منتج البناء : استرجاع مجلد dist/ الذي أنتجته وظيفة البناء
  2. إعداد GitHub Pages : تجهيز بيئة Pages
  3. الرفع نحو Pages : تجهيز مجلد dist/ لـGitHub Pages
  4. النشر : نشر الموقع مع actions/deploy-pages@v4

بناء الإنتاج

تحت الغطاء، ينفذ أمر pnpm build :

  1. tsc -b : يتحقق من أنواع TypeScript

  • تعلم : إنه مشروع رائع لإتقان React وTypeScript

Pipeline chạy mỗi lần đẩy lên main và mỗi pull request nhắm main. Các PR vì vậy được kiểm tra (lint + build) trước khi merge, nhưng chỉ các lần đẩy lên main mới kích hoạt triển khai.

Job 1 : Build

Job build chạy trên ubuntu-latest và theo các bước :

  1. Checkout : Clone repo với toàn bộ lịch sử (fetch-depth: 0)
  2. Setup pnpm : Cài bản pnpm mới nhất bằng pnpm/action-setup@v4
  3. Setup Node.js 20 : Cấu hình Node với cache pnpm bật để cài nhanh hơn
  4. Install dependencies : Chạy pnpm install --frozen-lockfile để đảm bảo build tái tạo được (không cho sửa lockfile)
  5. Lint : Chạy pnpm run lint (ESLint) để kiểm tra chất lượng mã trước build
  6. Build : Chạy pnpm run build, kiểm tra kiểu TypeScript trước (tsc -b) rồi bundle tất cả bằng Vite
  7. Upload artifact : Tải thư mục dist/ lên làm artefact build cho job triển khai

Nếu một bước hỏng (lỗi lint, kiểu hay build), toàn bộ pipeline dừng và không gì được triển khai. Chốt này bảo vệ tôi khỏi mã hỏng trong production và tôi tin nó mỗi lần đẩy.

Job 2 : Deploy

Job triển khai chỉ chạy nếu :

  • Job build thành công (needs: build)
  • Sự kiện là đẩy (không phải PR)
  • Nhánh là main
if: github.event_name == 'push' && github.ref == 'refs/heads/main'

Deployment Pipeline CI/CD

ผมตั้งค่า GitHub Actions pipeline ที่สมบูรณ์ซึ่งจะทำ lint, build และ deploy เว็บไซต์โดยอัตโนมัติทุกครั้งที่มีการ push ไปยัง main มาดูรายละเอียดกัน

Workflow อยู่ใน .github/workflows/deploy.yml และแบ่งออกเป็นสอง jobs: build และ deploy

ตัวกระตุ้น (Triggers)

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

Pipeline จะทำงานทุกครั้งที่มี push ไปยัง main และทุก pull request ที่มีเป้าหมายเป็น main ดังนั้น PRs จะถูกตรวจสอบ (lint + build) ก่อนที่จะถูก merge แต่เฉพาะ push ที่ main เท่านั้นที่จะกระตุ้นให้มีการ deploy

Job 1: Build

Job build ทำงานบน ubuntu-latest และทำตามขั้นตอนเหล่านี้:

  1. Checkout -- โคลน repository พร้อมประวัติทั้งหมด (fetch-depth: 0)
  2. Setup pnpm -- ติดตั้ง pnpm เวอร์ชันล่าสุดด้วย pnpm/action-setup@v4
  3. Setup Node.js 20 -- กำหนดค่า Node พร้อมเปิดใช้งานแคช pnpm เพื่อการติดตั้งที่เร็วขึ้น
  4. Install dependencies -- รัน pnpm install --frozen-lockfile เพื่อรับประกัน build ที่ reproducible (ไม่อนุญาตให้แก้ไข lockfile)
  5. Lint -- รัน pnpm run lint (ESLint) เพื่อตรวจสอบคุณภาพโค้ดก่อน build
  6. Build -- รัน pnpm run build ซึ่งตรวจสอบชนิด TypeScript ก่อน (tsc -b) จากนั้น bundle ทุกอย่างด้วย Vite
  7. Upload artifact -- อัปโหลดโฟลเดอร์ dist/ เป็น build artifact สำหรับ job deploy

หากขั้นตอนใดล้มเหลว -- ไม่ว่าจะเป็น lint error, type error หรือ build error -- ทั้ง pipeline จะหยุดและไม่มีอะไรถูก deploy ซึ่งช่วยปกป้องเว็บไซต์ใน production จากโค้ดที่เสียหาย

Job 2: Deploy

Job deploy จะทำงานก็ต่อเมื่อ:

  • Job build สำเร็จ (needs: build)
  • Event เป็น push (ไม่ใช่ PR)
  • Branch เป็น main
if: github.event_name == 'push' && github.ref == 'refs/heads/main'

จากนั้นดำเนินการ:

  1. ดาวน์โหลด build artifact -- ดึงโฟลเดอร์ dist/ ที่ผลิตโดย job build
  2. กำหนดค่า GitHub Pages -- ตั้งค่าสภาพแวดล้อม Pages
  3. อัปโหลดไปยัง Pages -- เตรียมโฟลเดอร์ dist/ สำหรับ GitHub Pages
  4. Deploy -- เผยแพร่เว็บไซต์ด้วย actions/deploy-pages@v4

กระบวนการทั้งหมดใช้เวลาประมาณหนึ่งนาทีตั้งแต่ push จนถึงออนไลน์ ไม่มีการ deploy ด้วยตนเอง, ไม่มี FTP, ไม่มี SSH -- แค่ git push เท่านั้น

Production Build

ภายใต้ฝาครอบ, คำสั่ง pnpm build จะทำงาน:

  1. tsc -b -- ตรวจสอบชนิด TypeScript
  2. vite build -- Bundle และปรับแต่งโค้ดทั้งหมด

Vite สร้างไฟล์ที่ minified และปรับแต่งแล้วพร้อม code-splitting อัตโนมัติ ผลลัพธ์คือเว็บไซต์แบบ static ที่เร็วเป็นพิเศษ

ทำไมถึงเลือกสถาปัตยกรรมนี้ ?

ผมอาจใช้ CMS, เครื่องมือสร้างเว็บไซต์ static อย่าง Hugo หรือ Jekyll, หรือแม้แต่ Next.js แต่ทำไมผมถึงเลือกแนวทางนี้:

  • ความเรียบง่าย -- เขียนใน Markdown, push ไปยัง GitHub, ก็ออนไลน์
  • ควบคุมได้ทั้งหมด -- ไม่พึ่งพา CMS หรือฐานข้อมูล
  • ประสิทธิภาพ -- Vite + React = โหลดเร็ว
  • ความยืดหยุ่น -- ผมสามารถผสม Markdown และ HTML ได้ตามต้องการ
  • การเรียนรู้ -- มันเป็นโปรเจกต์ที่ยอดเยี่ยมสำหรับการเรียนรู้ React และ TypeScript
  • CI/CD -- การตรวจสอบคุณภาพและการ deploy อัตโนมัติด้วย GitHub Actions

บทสรุป

บล็อกนี้เป็นโปรเจกต์ที่เรียบง่ายแต่ออกแบบมาอย่างดี: Markdown สำหรับเนื้อหา, React สำหรับการเรนเดอร์, Vite เพื่อประสิทธิภาพ, GitHub Actions สำหรับ CI/CD, และ GitHub Pages สำหรับโฮสต์ ไม่มีฐานข้อมูล, ไม่มีเซิร์ฟเวอร์ backend, แค่ไฟล์ static ที่ให้บริการอย่างมีประสิทธิภาพด้วย pipeline อัตโนมัติที่รับประกันคุณภาพทุกครั้งที่มีการ push
