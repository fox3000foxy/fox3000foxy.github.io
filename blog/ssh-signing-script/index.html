SSH commit signing script -- explained

This article breaks down the setup-ssh-signing.sh script I published on Gist. We'll look at what each part does, how it makes repo-local SSH signing completely painless, and, yes, why I even bothered writing it (spoiler: I just wanted my commits to look cool).

Motivation

I've always loved tinkering with my Git workflow, and after seeing people with little "Verified" badges next to their commits, I thought: why not me? The built-in GPG signing is heavyweight and global, so I ended up writing a small helper that:

  • creates a dedicated signing key,
  • configures only the current repo,
  • optionally rewrites history to sign old commits,
  • and lets you carry the key between machines.

Honestly, the need was mostly vanity. My personal projects impose no signing requirements, but seeing a green "Verified" badge on a commit does have an effect, and writing that script in shell was genuinely fun.

Signing your commits is a bit like wearing a leather jacket to a code review -- totally useless, but it makes you feel like a hacker.

What the script does

The script is a single Bash file with set -euo pipefail at the top to abort on the first error. Here's a summary of what it does:

  1. Generate or import a signing key Keys land in .git-signing/ in the directory where you run it.
  2. Configure Git locally It sets gpg.format=ssh, user.signingkey, commit.gpgsign=true, tag.gpgSign=true, and an allowedSignersFile pointing at the public key.
  3. Move keys between machines With --export-keys / --import-keys, you can transfer your private key from one machine to another without touching the global config.
  4. Optional history rewrite (--resign-all) Rewrites all commits on all branches/tags and re-signs them with -S, without touching the other authors.
  5. Utility flags --autostash, --autopush, --commit-date, --yes for non-interactive mode, etc.
  6. Fork detection and safety checks It detects the upstream remote, warns before rewriting history, checks required tools (git, ssh-keygen, zip/unzip), makes sure permissions are right, and even creates a secure copy of the key if the filesystem permissions are too loose.

The script is idempotent: running it twice doesn't regenerate your key or overwrite the existing config.

Step-by-step walkthrough

Here are a few key excerpts from the code with their explanations.

#!/usr/bin/env bash
set -euo pipefail

# Configure SSH commit signing in a controlled, repo-local way.
# - Key files are created in the directory where this script is launched.
# - Git config is written locally to the current repository only.

The header sets the safety ground rules and documents the goal. The next chunk parses CLI options (--name, --email, --repo, etc.) with a while [[ $# -gt 0 ]]; do case … esac done loop. The required identity fields are checked later:

if [[ -z "$NAME" || -z "$EMAIL" ]]; then
  echo "Error: missing identity. Provide --name and --email." >&2
  exit 1
fi

Key generation happens in $LAUNCH_DIR/.git-signing. If a key already exists, the script keeps it as is; --import-keys fills the directory from a ZIP.

mkdir -p "$KEY_DIR"

if [[ -n "$IMPORT_ZIP_PATH" ]]; then
  import_keys_from_zip "$IMPORT_ZIP_PATH"
fi

if [[ ! -f "$KEY_PATH" ]]; then
  ssh-keygen -t ed25519 -N "" -C "$EMAIL signing key" -f "$KEY_PATH" >/dev/null
  echo "Generated signing key: $KEY_PATH"
else
  echo "Signing key already exists: $KEY_PATH"
fi

After verifying the private key is usable (ssh-keygen -Y sign …), the script writes an allowed_signers file containing the public key and sets the local Git config:

git -C "$REPO_DIR" config --local gpg.format ssh
git -C "$REPO_DIR" config --local user.signingkey "$RUNTIME_KEY_PATH"
git -C "$REPO_DIR" config --local gpg.ssh.allowedSignersFile "$ALLOWED_SIGNERS"
git -C "$REPO_DIR" config --local commit.gpgsign true
git -C "$REPO_DIR" config --local tag.gpgSign true

If you ask for a history rewrite with --resign-all, the script builds a git filter-branch command that re-signs eligible commits with -S. It respects fork state by optionally skipping commits already present in upstream.

The final output prints the public key and instructions for adding it in GitHub's Signing Key section, with a test recipe.

Why sign your commits?

This is where I admit I didn't need it. My repos require no provenance for what I publish, and I don't use signed tags for releases. The "why" is:

  • because I could,
  • because it looks good (you saw the badge?),
  • because it gave me an excuse to experiment with git filter-branch and shell,
  • and because it's one more "I built this myself" for the blog.

In short, it was just for showing off, but that's what I love about tinkering with my tools.

Usage examples

chmod +x ./setup-ssh-signing.sh
./setup-ssh-signing.sh --name "Your Name" \
                       --email "you@example.com"

# export keys for another machine
./setup-ssh-signing.sh --export-keys ./my-signing-keys.zip

# import keys on a second machine
./setup-ssh-signing.sh --import-keys ./my-signing-keys.zip --repo ./my-repo \
                       --name "Your Name" --email "you@example.com"

# rewrite history and push
./setup-ssh-signing.sh --repo ./my-repo --name "Your Name" --email "you@example.com" \
                       --resign-all --autostash --autopush --yes

Final thoughts

This script stays a compact utility, but it carries a few principles I stand by:

  • keep cryptographic keys local and per-repo,
  • never touch the global config unless you ask,
  • provide simple import/export and history rewrite,
  • and document the whole process in a blog article to keep a reusable record.

If you feel like adding signatures to your own commits, give it a try! And if you're just here for the style, same. 😎

SSH 提交签名脚本详解

动机

我一直喜欢折腾自己的 Git 工作流，看到别人提交旁边挂着"Verified"小徽章，我就想：凭什么我不行？内置的 GPG 签名又重又全局，于是我写了个小助手，它可以：

  • 创建专用于签名的 SSH 密钥，
  • 只配置当前仓库，
  • 必要时重写历史，给旧提交补签名，
  • 还能在机器之间携带密钥。

说实话，需求基本是虚荣心。我的个人项目没有任何签名要求，但提交上挂个绿色"Verified"徽章确实好看，而用 shell 写这个脚本的过程本身让我玩得很开心。

脚本做了什么

  6. Fork 检测与安全检查 它能识别 upstream 远程，重写历史前先警告，检查所需工具（git、ssh-keygen、zip/unzip），确认权限没问题，如果文件系统权限太宽松还会做一份安全的密钥拷贝。

動機

Gitワークフローいじりが昔から大好きで、コミット横に小さな「Verified」バッジ付けた人たちを見て思ったんだ。なんで自分じゃないのって。内蔵GPG署名は重くてグローバルだ。結局小さなヘルパーを書いて、こうする。

  • 署名専用SSH鍵を作る、
  • 現リポジトリだけを設定する、
  • 履歴書き換えで古いコミットに署名し直せる、
  • マシン間で鍵を運べる。

正直、需要はほぼ見栄だった。個人プロジェクトは署名要件ゼロだ。でも緑「Verified」バッジがコミットに付くのを見るのはちょっとした効果があって、shellでこのスクリプト書くのは本当に楽しかった。

まあ、コミット署名ってコードレビューに革ジャン着てくみたいなものだ。全然無駄だけど、ハッカーな気分になれる。

スクリプトがすること

スクリプトは単一Bashファイルで、頭にset -euo pipefailがあって最初のエラーで中断する。やることの概要はこうだ。

  3. マシン間で鍵を管理する
    --export-keysや--import-keysで、グローバル設定に触らず秘密鍵を別PCへ移せる。
  4. 任意の履歴書き換え（--resign-all）
    全ブランチやタグの全コミット（fork用にupstreamにないものだけも可）を書き換えて-Sで再署名する。他作者には触らない。
  5. 便利フラグ

    upstreamリモートを検出して、履歴書き換え前に警告して、必須道具（git、ssh-keygen、zip/unzip）を確認して、正しい権限を確かめる。ファイルシステム権限が緩すぎれば鍵の安全コピーまで作る。

커밋용 SSH 서명 스크립트 설명

이 글에서는 제가 Gist에 공개한 setup-ssh-signing.sh 스크립트를 뜯어봐요. 각 부분이 무슨 일을 하는지, 로컬 저장소 단위의 SSH 서명을 완전히 수월하게 만드는 방법, 그리고 굳이 이걸 만들었던 이유까지 살펴볼 거예요. 스포일러하자면, 제 커밋을 멋지게 보이게 하고 싶었을 뿐이에요.

동기

저는 Git 워크플로를 만지작거리는 것을 늘 좋아했고, 커밋 옆에 작은 "Verified" 배지를 단 사람들을 보고 저도 모르게 생각했어요. 나도 해보면 어떨까? 내장된 GPG 서명은 무겁고 전역 설정이라서, 결국 이렇게 동작하는 작은 헬퍼를 만들었어요.

  • 서명 전용 SSH 키를 만들고,
  • 현재 저장소에만 설정하고,
  • 필요하다면 예전 커밋까지 다시 서명해서 히스토리를 고치고,
  • 기기 사이에서 키를 옮길 수 있게 해줘요.

솔직히 말하면, 필요라기보다는 허영심에 가까웠어요. 제 개인 프로젝트에는 서명을 요구하는 규칙이 전혀 없지만, 커밋에 초록색 "Verified" 배지가 붙으면 기분이 좋거든요. 게다가 이 스크립트를 셸로 짜는 과정 자체가 정말 즐거웠어요.

커밋에 서명하는 건, 코드 리뷰에 가죽 재킷을 입고 가는 것과 비슷해요. 완전히 쓸모없지만, 해커가 된 기분이 들거든요.

스크립트가 하는 일

이 스크립트는 하나의 Bash 파일이고, 맨 위에 set -euo pipefail을 두어서 첫 오류에서 바로 실행을 멈춰요. 하는 일을 요약하면 이렇습니다.

  1. 서명 키 생성 또는 가져오기 스크립트를 실행한 폴더 안의 .git-signing/에 키가 들어가요.
  2. Git을 로컬로 설정하기 gpg.format=ssh와 user.signingkey, commit.gpgsign=true, tag.gpgSign=true, 그리고 공개 키를 가리키는 allowedSignersFile을 설정해요.
  3. 기기 사이에서 키 관리하기 --export-keys와 --import-keys 덕분에 전역 설정을 건드리지 않고 개인 키를 한 컴퓨터에서 다른 컴퓨터로 옮길 수 있어요.
  4. 선택적인 히스토리 다시 쓰기 (--resign-all) 모든 브랜치와 태그의 커밋(포크에서는 upstream에 없는 것만)을 전부 다시 쓰고 -S로 다시 서명해요. 다른 작성자는 건드리지 않아요.
  5. 유틸리티 플래그 --autostash, --autopush, --commit-date, 비대화형 모드용 --yes 등이 있어요.
  6. 포크 감지와 보안 검사 upstream 리모트를 감지하고, 히스토리를 다시 쓰기 전에 경고하고, 필요한 도구(git, ssh-keygen, zip/unzip)를 확인하고, 올바른 권한을 보장하고, 파일시스템 권한이 너무 너그러우면 키의 안전한 복사본까지 만들어요.

이 스크립트는 멱등적이에요. 두 번 실행해도 키가 다시 만들어지거나 기존 설정이 덮어써지지 않아요.

Motivazione

Ho sempre adorato trafficare col mio workflow Git, e dopo aver visto gente con piccoli badge "Verified" accanto ai loro commit, mi sono detto: perché non io? La firma GPG integrata è pesante e globale, così ho finito per scrivere un piccolo helper che:

  • crea una chiave SSH dedicata alla firma,
  • configura solo il deposito corrente,
  • riscrive eventualmente lo storico per firmare i vecchi commit,
  • e permette di trasportare la chiave tra macchine.

Francamente, il bisogno era soprattutto vanità. I miei progetti personali non impongono alcun requisito di firma, ma vedere un badge verde "Verified" su un commit fa il suo effetto, e scrivere questo script in shell mi ha fatto davvero piacere.

Cosa fa lo script

Lo script è un solo file Bash con set -euo pipefail in cima per interrompere l'esecuzione alla prima erreur. Ecco un riassunto di ciò che fa:

  1. Genera o importa una chiave di firma Le chiavi finiscono in .git-signing/ nella cartella dove lanci lo script.
  2. Configura Git localmente Imposta gpg.format=ssh, user.signingkey, commit.gpgsign=true, tag.gpgSign=true, e un allowedSignersFile che punta alla chiave pubblica.
  3. Gestisci le chiavi tra macchine Grazie a --export-keys / --import-keys, puoi trasferire la tua chiave privata da un computer all'altro senza toccare la config globale.
  4. Riscrittura storico opzionale (--resign-all) Riscrive tutti i commit di tutti i branch/tag (o solo quelli non in upstream per i fork) e li rifirma con -S, senza toccare gli altri autori.
  5. Flag utilitari --autostash, --autopush, --commit-date, --yes per la modalità non interattiva, ecc.
  6. Rilevamento di fork e verifiche di sicurezza Rileva il remote upstream, avvisa prima di riscrivere lo storico, verifica gli strumenti richiesti (git, ssh-keygen, zip/unzip), assicura i buoni permessi, e crea persino una copia sicura della chiave se i permessi del filesystem sono troppo permissivi.

Lo script è idempotente: lanciarlo due volte non rigenera la tua chiave e non schiaccia la config esistente.

  6. Fork-Erkennung und Sicherheitsprüfungen
    Es erkennt das upstream-Remote, warnt vor dem Umschreiben der Historie, prüft die benötigten Tools (git, ssh-keygen, zip/unzip), stellt die richtigen Berechtigungen sicher und erstellt sogar eine sichere Kopie des Schlüssels, falls die Dateisystemberechtigungen zu locker sind.

Das Skript ist idempotent: Es zweimal laufen zu lassen generiert deinen Schlüssel nicht neu und überschreibt die bestehende Config nicht.

Мотивация

Я всегда любил ковырять свой Git-воркфлоу, и после того как увидел людей с маленькими бейджами «Verified» рядом с коммитами, подумал : а чем я хуже? Встроенная подпись GPG тяжёлая и глобальная, так что я в итоге написал маленький хелпер, который :

  • создаёт отдельный SSH-ключ для подписи,
  • настраивает только текущий репозиторий,
  • при желании переписывает историю, чтобы подписать старые коммиты,

Честно, нужда была в основном про тщеславие. Мои личные проекты не требуют никакой подписи, но зелёный бейдж «Verified» на коммите даёт свой маленький эффект, а писать этот скрипт на шелле было прям в кайф.

Скрипт идемпотентный : запуск дважды не пересоздаёт твой ключ и не затирает существующую конфигурацию.

सच कहूँ तो जरूरत ज्यादातर दिखावे की थी। मेरे निजी प्रोजेक्ट कोई हस्ताक्षर आवश्यकता नहीं थोपते, लेकिन किसी कमिट पर हरा "Verified" बैज देखना अपना असर करता है, और इस स्क्रिप्ट को शेल में लिखने में मुझे सच में मजा आया।

खैर, अपने कमिट हस्ताक्षर करना कोड रिव्यू के लिए चमड़े की जैकेट पहनने जैसा है, पूरी तरह बेकार, लेकिन तुम्हें हैकर जैसा महसूस कराता है।

स्क्रिप्ट क्या करती है

स्क्रिप्ट ऊपर set -euo pipefail वाली एक Bash फाइल है ताकि पहली त्रुटि पर निष्पादन रुक जाए। यह इसका सारांश है :

  1. हस्ताक्षर कुंजी बनाना या आयात करना कुंजियाँ उस फोल्डर में .git-signing/ में उतरती हैं जहाँ तुम स्क्रिप्ट चलाते हो।
  2. Git को स्थानीय रूप से कॉन्फ़िगर करना यह gpg.format=ssh, user.signingkey, commit.gpgsign=true, tag.gpgSign=true, और एक allowedSignersFile सेट करता है जो सार्वजनिक कुंजी की ओर इशारा करता है।
  3. मशीनों के बीच कुंजियाँ प्रबंधित करना --export-keys / --import-keys के माध्यम से, तुम वैश्विक कॉन्फ़िग छुए बिना अपनी निजी कुंजी एक कंप्यूटर से दूसरे में स्थानांतरित कर सकते हो।
  4. वैकल्पिक इतिहास पुनर्लेखन (--resign-all) सभी शाखाओं/टैग के सभी कमिट फिर से लिखता है (या फोर्क के लिए सिर्फ वे जो upstream में नहीं हैं) और -S से उन्हें फिर से हस्ताक्षर करता है, अन्य लेखकों को छुए बिना।
  5. उपयोगी ध्वज गैर इंटरैक्टिव मोड के लिए --autostash, --autopush, --commit-date, --yes, आदि।
  6. फोर्क पहचान और सुरक्षा जाँच यह upstream रिमोट पहचानता है, इतिहास फिर से लिखने से पहले चेतावनी देता है, आवश्यक उपकरण जाँचता है (git, ssh-keygen, zip/unzip), सही अनुमतियाँ सुनिश्चित करता है, और अगर फाइलसिस्टम अनुमतियाँ बहुत अनुमतिशील हों तो कुंजी की सुरक्षित प्रति भी बनाता है।

स्क्रिप्ट idempotent है : इसे दो बार चलाने से तुम्हारी कुंजी फिर से नहीं बनती और मौजूदा कॉन्फ़िग नहीं मिटती।

चरण दर चरण ब्योरा

कोड के कुछ मुख्य अंश उनकी व्याख्या के साथ यहाँ हैं।

#!/usr/bin/env bash
set -euo pipefail

# Configure SSH commit signing in a controlled, repo-local way.
# - Key files are created in the directory where this script is launched.
# - Git config is written locally to the current repository only.

हेडर सुरक्षा तय करता है और उद्देश्य प्रलेखित करता है। अगला टुकड़ा while [[ $# -gt 0 ]]; do case … esac done लूप के साथ CLI विकल्प (--name, --email, --repo, आदि) पार्स करता है। अनिवार्य पहचान फ़ील्ड बाद में जाँचे जाते हैं :

if [[ -z "$NAME" || -z "$EMAIL" ]]; then
  echo "Error: missing identity. Provide --name and --email." >&2
  exit 1
fi

कुंजी पीढ़ी $LAUNCH_DIR/.git-signing में होती है। अगर कुंजी पहले से मौजूद है, तो स्क्रिप्ट उसे जैसी है वैसी रखती है ; --import-keys फोल्डर को ZIP से भरने देता है।

mkdir -p "$KEY_DIR"

if [[ -n "$IMPORT_ZIP_PATH" ]]; then
  import_keys_from_zip "$IMPORT_ZIP_PATH"
fi

if [[ ! -f "$KEY_PATH" ]]; then
  ssh-keygen -t ed25519 -N "" -C "$EMAIL signing key" -f "$KEY_PATH" >/dev/null
  echo "Generated signing key: $KEY_PATH"
else
  echo "Signing key already exists: $KEY_PATH"
fi

निजी कुंजी उपयोग योग्य है यह जाँचने के बाद (ssh-keygen -Y sign …), स्क्रिप्ट सार्वजनिक कुंजी वाली allowed_signers फाइल लिखती है और स्थानीय Git कॉन्फ़िग सेट करती है :

git -C "$REPO_DIR" config --local gpg.format ssh
git -C "$REPO_DIR" config --local user.signingkey "$RUNTIME_KEY_PATH"
git -C "$REPO_DIR" config --local gpg.ssh.allowedSignersFile "$ALLOWED_SIGNERS"
git -C "$REPO_DIR" config --local commit.gpgsign true
git -C "$REPO_DIR" config --local tag.gpgSign true

अगर तुम --resign-all से इतिहास पुनर्लेखन माँगते हो, तो स्क्रिप्ट git filter-branch कमांड बनाती है जो योग्य कमिट -S से फिर से हस्ताक्षर करती है। यह फोर्क की स्थिति का सम्मान करती है, upstream में पहले से मौजूद कमिट वैकल्पिक रूप से छोड़कर।

अंतिम परिणाम सार्वजनिक कुंजी और इसे GitHub के Signing Key खंड में जोड़ने के निर्देश दिखाता है, परीक्षण विधि के साथ।

अपने कमिट हस्ताक्षर क्यों करें ?

यह वह पल है जब मैं मानता हूँ कि मुझे इसकी जरूरत नहीं थी। मेरे रिपॉजिटरी मैं जो प्रकाशित करता हूँ उसके लिए कोई उद्गम नहीं माँगते, और मैं रिलीज के लिए हस्ताक्षरित टैग इस्तेमाल नहीं करता। "क्यों" यह है :

  • क्योंकि मैं कर सकता था,
  • क्योंकि यह अच्छा लगता है (बैज देखा ?),
  • क्योंकि इसने मुझे git filter-branch और शेल से प्रयोग करने का बहाना दिया,
  • और क्योंकि यह ब्लॉग के लिए एक और "मैंने यह खुद बनाया" है।

संक्षेप में, यह सिर्फ दिखावे के लिए था, लेकिन अपने उपकरणों से छेड़छाड़ में मुझे यही पसंद है।

उपयोग उदाहरण

# configuration initiale dans le dépôt courant
chmod +x ./setup-ssh-signing.sh
./setup-ssh-signing.sh --name "Your Name" \
                       --email "you@example.com"

# exporter les clés pour une autre machine
./setup-ssh-signing.sh --export-keys ./my-signing-keys.zip

# importer les clés sur une deuxième machine
./setup-ssh-signing.sh --import-keys ./my-signing-keys.zip --repo ./my-repo \
                       --name "Your Name" --email "you@example.com"

# réécrire l'historique et pousser
./setup-ssh-signing.sh --repo ./my-repo --name "Your Name" --email "you@example.com" \
                       --resign-all --autostash --autopush --yes

  • क्रिप्टोग्राफिक कुंजियाँ स्थानीय और प्रति रिपॉजिटरी रखना,

الدافع

لطالما أحببت العبث بسير عمل Git، وبعد رؤية أناس مع شارات «Verified» الصغيرة بجانب commits خاصتهم، قلت : لماذا لا أنا ؟ توقيع GPG المدمج ثقيل وشامل، فانتهيت بكتابة مساعد صغير :

  • ينشئ مفتاح SSH مخصصا للتوقيع،
  • يضبط المستودع الحالي فقط،
  • يعيد كتابة السجل ربما لتوقيع commits القديمة،
  • ويسمح بنقل المفتاح بين الآلات.

بصراحة، كان الاحتياج غرورا أساسا. مشاريعي الشخصية لا تفرض أي شرط توقيع، لكن رؤية شارة خضراء «Verified» على commit لها أثرها الصغير، وكتابة هذا السكربت في shell أسعدتني فعلا.

حسنا، توقيع commits خاصتك يشبه ارتداء سترة جلدية لمراجعة كود، عديم الفائدة تماما، لكنه يعطيك انطباع أنك هاكر.

ماذا يفعل السكربت

السكربت ملف Bash واحد مع set -euo pipefail في الأعلى لقطع التنفيذ من أول خطأ. إليكم ملخص ما يفعله :

  1. توليد أو استيراد مفتاح توقيع تنزل المفاتيح في .git-signing/ في المجلد الذي تشغّل منه السكربت.
  2. ضبط Git محليا يضع gpg.format=ssh وuser.signingkey وcommit.gpgsign=true وtag.gpgSign=true وallowedSignersFile يشير للمفتاح العام.
  3. إدارة المفاتيح بين الآلات بفضل --export-keys / --import-keys، تستطيع نقل مفتاحك الخاص من حاسوب لآخر دون لمس الإعداد العام.
  4. إعادة كتابة سجل اختيارية (--resign-all) تعيد كتابة كل commits لكل الفروع/الوسوم (أو فقط ما ليس في upstream للـforks) وتعيد توقيعها مع -S، دون لمس الكتّاب الآخرين.
  5. أعلام خدماتية --autostash و--autopush و--commit-date و--yes للوضع غير التفاعلي، إلخ.
  6. كشف fork وفحوص أمان يكشف remote الـupstream، ويحذر قبل إعادة كتابة السجل، ويتحقق من الأدوات المطلوبة (git وssh-keygen وzip/unzip)، ويتأكد من الأذونات الصحيحة، وينشئ حتى نسخة آمنة من المفتاح إذا كانت أذونات نظام الملفات متساهلة أكثر من اللازم.

السكربت idempotent : تشغيله مرتين لا يعيد توليد مفتاحك ولا يمحو الإعداد الموجود.

  • لأنه يبدو جيدا (رأيت الشارة ؟)،
  • لأنه أعطاني ذريعة للتجريب مع git filter-branch والـshell،
  • ولأنه "بنيت هذا بنفسي" إضافي للمدونة.

Script ký SSH cho commit -- giải thích

Bài này mổ xẻ script setup-ssh-signing.sh mà tôi đã đăng trên Gist. Ta sẽ xem mỗi phần làm gì, cách nó khiến việc ký SSH cục bộ cho một repo trở nên hoàn toàn dễ dàng, và, đúng vậy, vì sao tôi lại bỏ công viết nó (spoiler : tôi chỉ muốn commit của mình trông thật ngầu).

Động lực

Tôi luôn thích vọc workflow Git của mình, và sau khi thấy mọi người có huy hiệu « Verified » nhỏ bên cạnh commit, tôi tự nhủ : sao mình lại không? Chữ ký GPG tích hợp thì nặng nề và toàn cục, nên cuối cùng tôi viết một helper nhỏ :

  • tạo một khóa SSH chuyên để ký,
  • chỉ cấu hình repo hiện tại,
  • có thể viết lại lịch sử để ký các commit cũ,
  • và cho phép mang khóa theo giữa các máy.

Thật lòng, nhu cầu chủ yếu là phù phiếm. Các dự án cá nhân của tôi không áp đặt yêu cầu ký nào, nhưng thấy huy hiệu xanh « Verified » trên commit cũng có hiệu ứng riêng, và viết script này bằng shell khiến tôi thực sự vui.

Thôi nào, ký commit cũng giống như mặc áo khoác da đi review code -- hoàn toàn vô dụng, nhưng cho bạn cảm giác mình là hacker.

Script làm gì

Script là một tệp Bash duy nhất với set -euo pipefail ở đầu để dừng thực thi ngay lỗi đầu tiên. Đây là tóm tắt những gì nó làm :

  1. Tạo hoặc nhập khóa ký Khóa nằm trong .git-signing/ ở thư mục nơi bạn chạy script.
  2. Cấu hình Git cục bộ Nó đặt gpg.format=ssh, user.signingkey, commit.gpgsign=true, tag.gpgSign=true, và một allowedSignersFile trỏ tới khóa công khai.
  3. Quản lý khóa giữa các máy Nhờ --export-keys / --import-keys, bạn có thể chuyển khóa riêng từ máy này sang máy khác mà không đụng tới config toàn cục.
  4. Viết lại lịch sử tùy chọn (--resign-all) Viết lại mọi commit của mọi nhánh/tag (hoặc chỉ những commit không nằm trong upstream với fork) và ký lại chúng bằng -S, không đụng tới các tác giả khác.
  5. Cờ tiện ích --autostash, --autopush, --commit-date, --yes cho chế độ không tương tác, v.v.
  6. Phát hiện fork và kiểm tra bảo mật Nó phát hiện remote upstream, cảnh báo trước khi viết lại lịch sử, kiểm tra các công cụ cần thiết (git, ssh-keygen, zip/unzip), đảm bảo quyền đúng, và thậm chí tạo bản sao an toàn của khóa nếu quyền filesystem quá thoáng.

Script có tính idempotent : chạy hai lần không tạo lại khóa và không ghi đè config hiện có.

Diễn tiến từng bước

Dưới đây là vài đoạn mã chính kèm giải thích.

#!/usr/bin/env bash
set -euo pipefail

# Configure SSH commit signing in a controlled, repo-local way.
# - Key files are created in the directory where this script is launched.
# - Git config is written locally to the current repository only.

Phần đầu đặt tính bảo mật và ghi lại mục tiêu. Đoạn tiếp theo phân tích tùy chọn CLI (--name, --email, --repo, v.v.) bằng vòng lặp while [[ $# -gt 0 ]]; do case … esac done. Các trường danh tính bắt buộc được kiểm tra sau :

if [[ -z "$NAME" || -z "$EMAIL" ]]; then
  echo "Error: missing identity. Provide --name and --email." >&2
  exit 1
fi

Tạo khóa diễn ra trong $LAUNCH_DIR/.git-signing. Nếu khóa đã tồn tại, script giữ nguyên; --import-keys cho phép đổ đầy thư mục từ một ZIP.

mkdir -p "$KEY_DIR"

if [[ -n "$IMPORT_ZIP_PATH" ]]; then
  import_keys_from_zip "$IMPORT_ZIP_PATH"
fi

if [[ ! -f "$KEY_PATH" ]]; then
  ssh-keygen -t ed25519 -N "" -C "$EMAIL signing key" -f "$KEY_PATH" >/dev/null
  echo "Generated signing key: $KEY_PATH"
else
  echo "Signing key already exists: $KEY_PATH"
fi

Sau khi kiểm tra khóa riêng dùng được (ssh-keygen -Y sign …), script ghi một tệp allowed_signers chứa khóa công khai và đặt config Git cục bộ :

git -C "$REPO_DIR" config --local gpg.format ssh
git -C "$REPO_DIR" config --local user.signingkey "$RUNTIME_KEY_PATH"
git -C "$REPO_DIR" config --local gpg.ssh.allowedSignersFile "$ALLOWED_SIGNERS"
git -C "$REPO_DIR" config --local commit.gpgsign true
git -C "$REPO_DIR" config --local tag.gpgSign true

Nếu bạn yêu cầu viết lại lịch sử với --resign-all, script dựng một lệnh git filter-branch ký lại các commit đủ điều kiện bằng -S. Nó tôn trọng trạng thái fork bằng cách tùy chọn bỏ qua các commit đã có trong upstream.

Kết quả cuối hiển thị khóa công khai và hướng dẫn thêm nó vào mục Signing Key của GitHub, kèm công thức test.

Vì sao ký commit?

Đây là lúc tôi thú nhận mình không cần nó. Các repo của tôi không đòi hỏi xuất xứ nào cho những gì tôi đăng, và tôi không dùng tag ký cho release. Cái « vì sao » là :

  • vì tôi có thể,
  • vì nó đẹp (bạn thấy huy hiệu chưa?),
  • vì nó cho tôi cớ thử nghiệm với git filter-branch và shell,
  • và vì đó là thêm một « tôi tự xây cái này » cho blog.

Tóm lại, chỉ để khoe thôi, nhưng đó là điều tôi thích khi vọc công cụ của mình.

Ví dụ dùng

# thiết lập ban đầu trong repo hiện tại
chmod +x ./setup-ssh-signing.sh
./setup-ssh-signing.sh --name "Your Name" \
                       --email "you@example.com"

# xuất khóa sang máy khác
./setup-ssh-signing.sh --export-keys ./my-signing-keys.zip

# nhập khóa trên máy thứ hai
./setup-ssh-signing.sh --import-keys ./my-signing-keys.zip --repo ./my-repo \
                       --name "Your Name" --email "you@example.com"

# viết lại lịch sử và đẩy
./setup-ssh-signing.sh --repo ./my-repo --name "Your Name" --email "you@example.com" \
                       --resign-all --autostash --autopush --yes

คำสั่งทำลายลายเซ็นต์ SSH สำหรับคอมมิต -- คำอธิบาย

บทความนี้สรุปสคริปต์ setup-ssh-signing.sh ที่ฉันได้เผยแพร่บน Gist ฉันจะแสดงให้เห็นว่าทุกส่วนทำอะไร ทำอย่างไรทำให้การเซ็นต์ต์ SSH ที่มีเฉพาะที่ดาต้าแปซิ่งในโฟลเดอร์เดียวไม่กังวลและ ทำไมฉันถึงเสียเวลามาสร้างนี้ (เปิดโปง: ฉันอยากให้คอมมิตของฉันมี ลุค)

ความกระตือรือร้น

ฉันมักชอบปรับแต่งกระบวนการทำงาน Git ของฉันเสมอและเมื่อได้เห็นคนอื่นมีแบนเนอร์ “Verified” อยู่ข้างคอมมิตของพวกเขา ฉันจึงคิดว่า “ทำให้ฉันกับก็ได้ไหม?” เซ็นต์ต์ GPG ที่มีอยู่แล้วหนักและทั่วโลก ทำให้ฉันจึงเขียนเครื่องมือช่วยเล็ก ๆ ที่ทำให้:

  • สร้างคีย์ SSH เฉพาะสำหรับการเซ็นต์ต์
  • กำหนดค่าเฉพาะสำหรับโฟลเดอร์ปัจจุบัน
  • เขียนใหม่ย้อนหลังเพื่อเซ็นต์ต์คอมมิตเก่า ๆ
  • และทำให้สามารถถ่ายโอนคีย์ระหว่างเครื่องได้

จริง ๆ แล้วความต้องการนี้เป็นเพียงความทะเยอทะยานส่วนตัว โครงการส่วนตัวของฉันไม่จำเป็นต้องมีลายเซ็นต์ แต่เห็นแบนเนอร์สีเขียว “Verified” อยู่บนคอมมิตก็สร้างความรู้สึกดีและการเขียนสคริปต์นี้ใน Shell ก็ทำให้ฉันมีความสุขอย่างแท้จริง

หั่นแหละ, เซ็นต์คอมมิตของฉันก็เหมือนกับใส่เสื้อหนังเมื่อทำรีวิวโค้ด -- เป็นเรื่องไร้ประโยชน์ทั้งหมด แต่ก็ทำให้คุณรู้สึกเหมือนเป็นแฮกเกอร์

สิ่งที่สคริปต์ทำ

สคริปต์เป็นไฟล์ Bash เดียวที่มี set -euo pipefail ด้านบนเพื่อหยุดการทำงานทันทีเมื่อพบข้อผิดพลาดแรก นี่คือสรุปสิ่งที่สคริปต์ทำ:

  1. สร้างหรือดึงคีย์เซ็นต์
    คีย์จะจัดเก็บใน .git-signing/ ที่อยู่ในโฟลเดอร์ที่คุณรันสคริปต์
  2. ตั้งค่า Git บนเครื่อง
    มันตั้งค่า gpg.format=ssh, user.signingkey, commit.gpgsign=true, tag.gpgSign=true และ allowedSignersFile ที่ชี้ไปยังคีย์สาธารณะ
  3. จัดการคีย์ระหว่างเครื่อง
    ด้วย --export-keys / --import-keys คุณสามารถโอนคีย์ลับจากคอมพิวเตอร์หนึ่งไปยังอีกคอมพิวเตอร์หนึ่งโดยไม่กระทบต่อการตั้งค่าทั่วไป
  4. การเขียนประวัติใหม่แบบตัวเลือก (--resign-all)
    เขียนบันทึกของทุกคอมมิตทั้งหมดทุก

นี่คือบางส่วนสำคัญของโค้ดพร้อมคำอธิบายของแต่ละส่วน

#!/usr/bin/env bash
set -euo pipefail

# กำหนดการลงนาม SSH ในรูปแบบที่ควบคุมได้และเฉพาะใน repo
# - ไฟล์คีย์ถูกสร้างในไดเรกทอรีที่สคริปต์นี้ถูกเรียกใช้งาน
# - การตั้งค่า Git จะถูกเขียนใน repository ปัจจุบันเท่านั้น

หัวเรื่องกำหนดความปลอดภัยและบันทึกวัตถุประสงค์. ส่วนต่อไปนี้จะทำงานแยกตัวเลือก CLI (--name, --email, --repo, etc.) ด้วยวงวน while [[ $# -gt 0 ]]; do case … esac done. ฟิลด์ข้อมูลตัวตนที่จำเป็นจะถูกตรวจสอบต่อไป:

if [[ -z "$NAME" || -z "$EMAIL" ]]; then
  echo "Error: missing identity. Provide --name and --email." >&2
  exit 1
fi

การสร้างคีย์ทำใน $LAUNCH_DIR/.git-signing หากมีคีย์อยู่แล้ว สคริปต์จะเก็บไว้ตามเดิม ; --import-keys ช่วยเติมไฟล์ในโฟลเดอร์จาก ZIP.

mkdir -p "$KEY_DIR"

if [[ -n "$IMPORT_ZIP_PATH" ]]; then
  import_keys_from_zip "$IMPORT_ZIP_PATH"
fi

if [[ ! -f "$KEY_PATH" ]]; then
  ssh-keygen -t ed25519 -N "" -C "$EMAIL signing key" -f "$KEY_PATH" >/dev/null
  echo "Generated signing key: $KEY_PATH"
else
  echo "Signing key already exists: $KEY_PATH"
fi

หลังจากตรวจสอบว่าคีย์ส่วนตัวสามารถใช้ได้ (ssh-keygen -Y sign …), สคริปต์เขียนไฟล์ allowed_signers ที่บรรจุคีย์สาธารณะและตั้งค่า Git ภายในเครื่อง :

git -C "$REPO_DIR" config --local gpg.format ssh
git -C "$REPO_DIR" config --local user.signingkey "$RUNTIME_KEY_PATH"
git -C "$REPO_DIR" config --local gpg.ssh.allowedSignersFile "$ALLOWED_SIGNERS"
git -C "$REPO_DIR" config --local commit.gpgsign true
git -C "$REPO_DIR" config --local tag.gpgSign true

ถ้าคุณร้องขอการเขียนประวัติใหม่ด้วย --resign-all สคริปต์จะสร้างคำสั่ง git filter-branch ที่ re‑sign commits ที่มีสิทธิ์ด้วย -S มันจะเคารพสถานะของ fork โดยเลือกข้าม commits ที่มีอยู่แล้วใน upstream

ผลลัพธ์สุดท้ายจะแสดงคีย์สาธารณะและคำแนะนำในการเพิ่มในส่วน Signing Key ของ GitHub พร้อมสูตรทดสอบ

ทำไมถึงต้องเซ็น commit ของตนเอง?

นี่เป็นช่วงเวลาที่ฉันยอมรับว่าฉันไม่จำเป็นต้องทำการเซ็นเลย พื้นที่ของฉันไม่ได้ต้องการแหล่งกำเนิดใด ๆ สำหรับสิ่งที่ฉันเผยแพร่ และฉันไม่ได้ใช้ tags ที่ถูกเซ็นต์เพื่อการปล่อยเวอร์ชั่น “release” แต่อย่างใด จุดที่ผมกำลังจะบอกคือ

  • เพราะฉันทำได้
  • เพราะมันดูดี (คุณเห็น badge ไหม?)
  • เพราะมันให้ฉันมีข้ออ้างทดลองใช้ git filter-branch และ shell
  • และเพราะมันเป็นแค่ “ฉันสร้างสิ่งนี้เอง” อีกหนึ่งครั้งสำหรับบล็อก

สรุปคือมันแค่เป็นการดีใจแค่เล็ก ๆ แต่ก็เป็นสิ่งที่ฉันชอบเมื่อทำงานกับเครื่องมือของฉัน

ตัวอย่างการใช้งาน

# การกำหนดค่าเริ่มต้นในคลังปัจจุบัน
chmod +x ./setup-ssh-signing.sh
./setup-ssh-signing.sh --name "Your Name" \
                       --email "you@example.com"

# ส่งออกคีย์เพื่อใช้กับเครื่องอื่น
./setup-ssh-signing.sh --export-keys ./my-signing-keys.zip

# นำเข้าแคีย์บนเครื่องที่สอง
./setup-ssh-signing.sh --import-keys ./my-signing-keys.zip --repo ./my-repo \
                       --name "Your Name" --email "you@example.com"

# เขียนประวัติใหม่และส่งอัป
./setup-ssh-signing.sh --repo ./my-repo --name "Your Name" --email "you@example.com" \
                       --resign-all --autostash --autopush --yes

สุดท้ายความคิด

สคริปต์นี้ยังคงเป็นเครื่องมือที่กระชับ แต่ฉันถือว่ามันมีหลักการบางอย่างที่ฉันเชื่อถือ :

  • เก็บกุญแจเข้ารหัสบนเครื่องและในแต่ละสำเนา,
  • ไม่ควรแตะขาดการตั้งค่าทั่วไปหากคุณไม่ได้ร้องขอ,
  • ให้การนำเข้า/ส่งออกเรียบง่ายและการเขียนทับประวัติ,
  • และกำหนดเอกสารกระบวนการทั้งหมดในบทความบล็อกเพื่อเก็บขั้นตอนที่ใช้ซ้ำได้

ถ้าอยากเพิ่มลายเซ็นให้กับคอมมิตของคุณเอง ลองทำดู! และถ้าคุณอยู่ที่นั่นเพียงเพราะสไตล์ก็เหมือนกัน 😎
